# Шаблон tasklist

Copyable-шаблон для создания tasklist-файла по скоупу. Скопируй, адаптируй под конкретный проект и скоуп.

---

## Структура файла

```markdown
# Tasklist: <Scope Name>

## Контекст

Одно предложение: суть скоупа. Не перечислять конкретные компоненты — это дрейфует.

**Документы:** ссылки на ключевые технические документы скоупа

**Зависимости:** от каких скоупов зависит (или "нет")

## Легенда

- 📋 Planned
- 🚧 In Progress
- ✅ Done
- ⏸️ Paused
- ❌ Cancelled

## Overview

| Итерация | Статус | Закрывает |
|----------|--------|-----------|
| feat-001 | ✅ Done | v1: пункт X |
| feat-002 | 🚧 In Progress | v1: пункт Y |

## Итерации

### <type>-<NNN>: <Читаемое Название>

**Цель:** что должно быть достигнуто (1-2 предложения)

**Статус:** 📋 Planned
**Blocked by:** — (или ссылка на итерацию-зависимость)
**Закрывает:** ссылка на roadmap / задачи
**Ветка:** `<type>/<NNN>-<slug>`

#### Состав работ
- [ ] Блок работ 1
- [ ] Блок работ 2
- [ ] Блок работ 3

#### Критерии приёмки
- [ ] Конкретное проверяемое утверждение 1
- [ ] Конкретное проверяемое утверждение 2

#### Артефакты
<!-- Заполняется по мере работы -->
- design-brief.md (если есть)
- plan.md
- summary.md
- ADR (если есть)
- Обновлённая документация (если есть)
```

## Соглашения

### Именование итерации

Имя итерации используется в трёх местах:

| Место | Формат | Пример |
|-------|--------|--------|
| Заголовок в tasklist | `### <type>-<NNN>: Читаемое Название` | `### feat-001: API Layer` |
| Директория | `<type>-<NNN>-<slug>/` | `feat-001-api-layer/` |
| Ветка git | `<type>/<NNN>-<slug>` | `feat/001-api-layer` |

Нумерация — отдельная для каждого скоупа (001, 002... в рамках одного tasklist).

### Связь веток с итерациями

Формат: `<type>/<NNN>-<slug>`.

При конфликте имён между скоупами (одинаковый номер и slug) — суффикс скоупа: `feat/001-api-layer-be`, `feat/003-api-layer-fe`. Добавляется только при реальном конфликте.

### Типы итераций

Аналогично Conventional Commits:

| Тип | Назначение |
|-----|-----------|
| `feat` | Новая функциональность |
| `fix` | Исправление |
| `refactor` | Рефакторинг |
| `docs` | Документация |
| `test` | Тесты |
| `chore` | Инфраструктура, зависимости |

## Быстро меняющиеся инструменты

Инструменты с активным развитием (фреймворки, build tools, UI-библиотеки) могут иметь устаревшие паттерны в обучающей выборке LLM. Перед реализацией итерации агент проверяет актуальность API и синтаксиса через доступные источники.

**Возможные источники (по приоритету):**
1. Исходный код установленных пакетов (Python inspect, docstrings, сигнатуры)
2. Скиллы (если есть для данного инструмента)
3. MCP-серверы документации (если подключены)
4. firecrawl → официальная документация, PyPI, GitHub

**Примеры:**

| Инструмент | Источник |
|-----------|----------|
| LangGraph | `inspect` пакета, docs-langchain MCP, firecrawl → PyPI/GitHub |
| uv | скилл uv-package-manager |
| Tailwind v4 | firecrawl → tailwindcss.com/docs |

Таблица адаптируется при копировании: оставить только инструменты, релевантные скоупу. Добавлять строки по мере появления новых быстро меняющихся зависимостей.

## Пояснения по полям

### Контекст

Одно предложение о сути скоупа + ссылки на документы + зависимости. Не перечислять конкретные компоненты/фичи — при появлении новых придётся обновлять, а забудем. Когда итерации заполнены, скоуп и так очевиден из их состава.

### Состав работ

Тезисный уровень — верхнеуровневые блоки, не пошаговый план реализации. Пошаговый план — отдельный файл `plan.md`.

Хорошо:
```
- [ ] SQLAlchemy модели (User, Project, ThreadView, Artifact)
- [ ] Repository Layer (CRUD для каждой сущности)
- [ ] FastAPI роутеры + Pydantic schemas
```

Плохо (это уровень plan.md):
```
- [ ] Создать файл app/models/user.py
- [ ] Добавить поля id, name, created_at
- [ ] Написать миграцию alembic revision --autogenerate
```

### Критерии приёмки

Конкретные проверяемые утверждения. Не "работает корректно", а "`make lint && make test` проходят", "POST /projects возвращает 201".

### Артефакты

Ссылки на файлы, созданные в ходе итерации. Заполняются по мере работы. До старта — шаблон-заглушка. Типичные артефакты:

- **design-brief.md** — контекст реализации: контракты, схемы, точки интеграции (опционально, при развитии существующей системы)
- **reference-\*.md** — опорный материал из другого проекта или внешнего источника (опционально)
- **plan.md** — implementation plan (опционально)
- **summary.md** — post-implementation summary
- **ADR** — архитектурные решения, принятые в ходе итерации
- **Технические документы** — новые или обновлённые документы в `doc/tech/`
