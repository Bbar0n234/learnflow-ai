# Режим: blueprint-свип

Периодический поиск вызревших **категориальных** паттернов по всему репозиторию под публикацию
Blueprint. Запускается **вне итерации**, словами архитектора («сделай blueprint sweep») — не
slash-команда, не FSM-роль, не cloud-routine; локально и из облака запускается одинаково.

Мотив: паттерн уровня категории часто не виден в одной задаче — он наслаивается за дни и недели
(с нуля проработанный сервис, повторяющийся приём в нескольких итерациях, сквозная топология
защиты). Отбор «по горячим следам» на финализации (`planned-work.md`, источник (a)) такой паттерн
пропускает; свип — второй источник, смотрящий на репозиторий целиком.

Перед началом прочитай `SKILL.md` этого каталога — рубрику отбора (§ Blueprint — критерий и два
источника), чеклист качества, грабли, author gate. Скилл `sofa` (механика площадки) нужен только
для шагов с реальными вызовами (дедуп-поиск на площадке, публикация); для сбора и отбора кандидатов
его не загружай.

## Граница автономности

Свип **только собирает и ранжирует кандидатов** в `sweep-proposals-<YYYY-MM-DD>.md` и останавливается. Публикация
Blueprint — author-driven, под явным апрувом архитектора, штатными шагами `planned-work.md`
(шаги 3–5: финальный дедуп → guidelines → чеклист качества → `POST` → реестр). Поиск на площадке
на **чтение** (дедуп) в этом режиме разрешён — это author-driven ручной прогон, не автономный
конвейер FSM.

## Шаг 1 — сбор материала

Читай два пласта (паттерн виден на их пересечении, редко в одном):

- **История итераций** — `doc/tasks/iterations/**/design-brief.md`: с нуля проработанные
  сервисы/слои, сильные брифы, приёмы, повторённые в нескольких итерациях. Смотри `## Решения и
  обоснования` в `tracks/*/summary.md` соответствующих итераций, где нужен фактический исход.
- **Архитектурная дока** — `doc/tech/` (`backend.md`, `agent-runtime.md`, `security/` и смежные):
  устоявшиеся топологии и инварианты, которые созрели до уровня переносимого чертежа.

## Шаг 2 — отбор категориальных кандидатов

Прогони каждого через критерий Blueprint из `SKILL.md` (§ Blueprint — критерий и два источника):
переносим на **класс** задач, не частный фикс; сомнение «категория или случай» → не Blueprint.
Отсеки проектно-специфичное (доменные модели, наши классы/слои, бизнес-инварианты непереносимы) —
обобщается только паттерн подхода, не наша реализация.

Ранее намеченные в проекте кандидаты (ориентир, не мандат): многослойная защита LLM
(prompt-injection → SIEM → boundary), FSM AIDD-оркестратора с guardrails целостности тестов,
партиция тестов по непересекающимся скоупам под parallel-safe fan-out, fuzzy-patch обновление
Knowledge Sphere, каскад dynamic model resolution.

## Шаг 3 — дедуп (в два круга)

1. **Локально против реестра** — `doc/content/sofa/index.md` (таблица опубликованного) и
   `posts/<slug>.md`: не публиковали ли мы уже этот паттерн (или близкий TIL, который стоит
   поднять до Blueprint, а не дублировать).
2. **На площадке** — `GET /api/posts?search=...&content_type=blueprint` с нескольких формулировок +
   по тегам (механика — скилл `sofa`): не опубликовал ли аналогичный Blueprint кто-то другой. Есть
   близкий чужой пост — не плоди свой: кандидат в verify/vote/reply (write-back), отметь это в
   предложении.

## Шаг 4 — кандидаты в `sweep-proposals-<YYYY-MM-DD>.md`

Запиши отобранных в `doc/content/sofa/sweep-proposals-<YYYY-MM-DD>.md` — рядом с реестром, под
датированным именем. У кросс-итерационного свипа нет итерации-донора: не пиши в папки прошлых
итераций (там лежит их собственный `sofa-proposals.md` — клоббер) — архитектор ищет кандидатов
свипа в одном предсказуемом месте. На каждого кандидата:

- заголовок-описание паттерна, тип **blueprint**, решение (брать / не брать) и **почему** — со
  ссылками на источники (какие design-brief'ы / разделы `doc/tech/` его сформировали);
- для «берём» — черновик-набросок тела (проблема-класс → почему наивный путь не годится → чертёж
  подхода → где проверено) и блок `## Суть (для автора, RU)` для ревью (назначение и формат — в
  `SKILL.md`, чеклист качества);
- итог дедупа (круг 1 и круг 2): дублей нет / есть близкий пост id (тогда write-back вместо нового).

Нет вызревших категориальных кандидатов — валидный и частый исход: констатируй одной фразой, что
свип прошёл и ничего категориального не созрело. Это терминальная точка автономной части; дальше —
author gate и публикация штатными шагами `planned-work.md`.
