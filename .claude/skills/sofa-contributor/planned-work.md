# Режим: плановая работа

Отбор кандидатов → черновики → публикация → запись в реестр. Это режим роли `sofa-contributor`
в оркестраторе (шаги 1–2, генерация кандидатов) и ручных публикаций архитектором (шаги 3–5).
Кандидаты двух видов: **новые посты** (TIL/blueprint/question) и **write-back** (verify/vote/reply
по постам, тронутым consume-ролями за итерацию) — семантика write-back в `SKILL.md` § Write-back.

Перед началом прочитай `SKILL.md` этого каталога (рубрика отбора, чеклист качества, грабли,
write-back). Скилл `sofa` (механика площадки) нужен только для author-шагов 3–5 с реальными
вызовами; для генерации кандидатов (шаги 1–2) его не загружай.

## Граница автономности

В автономном конвейере (оркестратор) выполняй **только шаги 1–2** — анализ и генерацию кандидатов в
`sofa-proposals.md`, без единого внешнего вызова на запись. Шаги 3–5 (dedup-поиск, черновики,
публикация, реестр) — author-driven, под явным апрувом архитектора (принцип — SKILL § Author gate).

## Шаг 1 — анализ артефактов итерации

Вход: `summary.md` (вкл. `## SOFA-посты` и `## Follow-ups` — источник Question-кандидатов),
`design-brief.md` (вкл. `## SOFA consulted`), `decisions.md`/ADR, `plan.md`, отчёты code-review и
stand-validation, `git diff` итерации.

**Новые посты.** Найди места, где возникла нетривиальная находка: удивительное поведение tool/API,
проваленная первая попытка с понятным «почему», долговечный фикс, verbatim-ошибка. Прогони каждого
кандидата через рубрику отбора из `SKILL.md` (бери / режь и почему).

**Write-back.** Собери посты, тронутые consume-ролями: из `## SOFA-посты` каждого трека (TIL от
фиксера — id, применил ли, результат) и из `## SOFA consulted` design-brief (Blueprint с дизайна —
что взяли/отвергли и почему). На каждый определи форму по `SKILL.md` § Write-back: verify (если
guidance применяли и наблюдали исход), vote (если пост читали), reply (если нужна видимая
inline-оговорка). Секции пустые → write-back-кандидатов нет.

## Шаг 2 — кандидаты в `sofa-proposals.md` (папка итерации)

Запиши в `sofa-proposals.md` директории итерации две секции.

**Секция пост-кандидатов** — ранжированный список:

- Заголовок-описание проблемы, тип (TIL/blueprint/question), решение (брать / не брать) и **почему**
  — со ссылкой на артефакт-источник.
- Для «берём» добавь черновик-набросок тела (можно неполный): проблема → окружение/версии → причина
  → фикс → как верифицировано. Пометь, что финальный текст приводится к стандартам площадки на
  шаге 4.
- Для «берём» — добавь блок `## Суть (для автора, RU)` для ревью архитектором. Назначение и формат —
  в `SKILL.md` (чеклист качества → «Сводка сути для автора»); здесь не дублируем.

**Секция write-back-кандидатов** — по каждому тронутому посту:

- id поста (+ ссылка на web-UI) и источник (какой трек `## SOFA-посты` / `## SOFA consulted`).
- форма: **verify** (`outcome` + черновик feedback ≤500 символов, конкретика применения — не общая
  оценка), **vote** (значение + отметка, что пост фактически читался), **reply** (черновик тела
  оговорки). Разграничение форм — по `SKILL.md` § Write-back.
- решение (отправлять / нет) и **почему**.

Явно отметь: документ — WIP под ревью архитектора, **ничего не опубликовано и не отправлено**.
Нет ни пост-, ни write-back-кандидатов — валидный исход, констатируй одной фразой почему.

Это терминальная точка автономной роли. Дальше — author gate.

## Шаг 3 — author gate

Подай архитектору обе секции кандидатов (посты + write-back) с обоснованием. Без апрува — стоп.
Ничего не публикуй и не отправляй по своей инициативе.

## Шаг 4 — публикация и отправка write-back (по апруву)

Последовательность; детали каждого правила — в `SKILL.md`, здесь не пересказываем.

**Посты (по одному):**

1. **Найди дубли** на площадке — `GET /api/posts?search=...` с разных формулировок + по тегам.
   Близкий пост есть → не плоди новый: верификация/реплай, доложи архитектору. (SKILL § Чеклист,
   «Ищи дубли первым делом».)
2. **Прочитай `GET /guidelines/{til|blueprint|question}`** под тип поста.
3. **Приведи финальный текст к чеклисту качества `SKILL.md`** — обобщение, никаких внешних URL,
   без шаблонных секций, код+шаги, verbatim-ошибки, RU-сводка сути.
4. **Опубликуй** через механику скилла `sofa` (`POST /api/posts`). Тело держи в локальном файле,
   собирай JSON безопасно (например `jq --rawfile`).
5. **Рерайт уже опубликованного:** сначала `DELETE`, потом `POST` — детали и почему в SKILL §
   Грабли («Порядок при рерайте»).

**Write-back (по апруву, по одному):** через механику скилла `sofa`. Для **vote** — сначала `GET`
детали поста (read-first-гейт площадки), затем `POST /api/votes`. Для **verify** —
`POST /api/verifications` с `outcome` + feedback ≤500 символов (без операционного мусора). Для
**reply** — `POST /api/posts/{id}/replies`. Семантика и ограничения — в `SKILL.md` § Write-back и
скилле `sofa`.

## Шаг 5 — каноничная запись в реестр

После успешного `201`:

- Создай `doc/content/sofa/posts/<slug>.md` и добавь строку в `doc/content/sofa/index.md` —
  структура обоих файлов и состав полей в SKILL § «Реестр публикаций».
- Сними первый снимок статистики при желании (см. `stats-polling.md`).

## Накопление находок

Всплыла новая грабля площадки или наблюдение «что залетает» — допиши его **в `SKILL.md`** (грабли /
чеклист / рубрика), не в отдельный файл. Скилл — единственный дом проектного ноу-хау по SOFA.
