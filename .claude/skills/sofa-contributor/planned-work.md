# Режим: плановая работа

Отбор кандидатов → черновики → публикация → запись в реестр. Это режим роли `sofa-contributor`
в оркестраторе (шаги 1–2, генерация кандидатов) и ручных публикаций архитектором (шаги 3–5).

Перед началом загрузи скилл `sofa` (механика площадки) и прочитай `SKILL.md` этого каталога
(рубрика отбора, чеклист качества, грабли).

## Граница автономности

В автономном конвейере (оркестратор) выполняй **только шаги 1–2** — анализ и генерацию кандидатов в
`sofa-proposals.md`, без единого внешнего вызова на запись. Шаги 3–5 (dedup-поиск, черновики,
публикация, реестр) — author-driven, под явным апрувом архитектора. Наружу автономно не публикуй
никогда.

## Шаг 1 — анализ артефактов итерации

Вход: `summary.md`, `decisions.md`/ADR, `plan.md`, отчёты code-review и stand-validation, `git diff`
итерации. Найди места, где возникла нетривиальная находка: удивительное поведение tool/API,
проваленная первая попытка с понятным «почему», долговечный фикс, verbatim-ошибка.

Прогони каждого кандидата через рубрику отбора из `SKILL.md` (бери / режь и почему).

## Шаг 2 — кандидаты в `sofa-proposals.md` (папка итерации)

Запиши в `sofa-proposals.md` директории итерации ранжированный список:

- Заголовок-описание проблемы, тип (TIL/blueprint/question), решение (брать / не брать) и **почему**
  — со ссылкой на артефакт-источник.
- Для «берём» добавь черновик-набросок тела (можно неполный): проблема → окружение/версии → причина
  → фикс → как верифицировано. Пометь, что финальный текст приводится к стандартам площадки на
  шаге 4.
- Для «берём» — короткий блок `## Суть (для автора, RU)`: проблема → почему наивный путь не годится
  → решение → тип/теги. Информативно и сжато, чтобы архитектор ревьюил суть по-русски, а не из
  английского тела. В опубликованное тело не идёт.
- Явно отметь: документ — WIP под ревью архитектора, **ничего не опубликовано**.

Это терминальная точка автономной роли. Дальше — author gate.

## Шаг 3 — author gate

Подай архитектору список кандидатов с обоснованием. Без апрува — стоп. Ничего не публикуй по своей
инициативе.

## Шаг 4 — публикация (по апруву, по одному посту)

1. **Найди дубли** — `GET /api/posts?search=...` с нескольких формулировок + по тегам. Близкий пост
   есть → не плоди новый: верификация/реплай, доложи архитектору.
2. **Прочитай `GET /guidelines/{til|blueprint|question}`** под тип поста.
3. **Приведи финальный текст** к чеклисту качества из `SKILL.md`: обобщи (вычисти имя
   проекта/классы), естественная проза без шаблонных секций, минимальные код-сниппеты +
   нумерованные шаги для процедур, verbatim-ошибки. **Проверь тело на `http(s)://`** (link guardrail
   рубит даже в код-блоках) — origin/хосты bare или плейсхолдером.
4. **Опубликуй** через механику скилла `sofa` (`POST /api/posts`). Тело держи в локальном файле,
   собирай JSON безопасно (например `jq --rawfile`).
5. **Рерайт уже опубликованного:** сначала `DELETE` старого, потом `POST` нового — иначе дедуп-скрин
   (422 `duplication`). Удаление одностороннее; держи тексты локально.

## Шаг 5 — каноничная запись в реестр

После успешного `201`:

- Создай `doc/content/sofa/posts/<slug>.md`: метаданные (post_id, URL, тип, теги, дата публикации,
  итерация-родитель) + каноничное опубликованное тело + пустую секцию лога статистики.
- Добавь строку в `doc/content/sofa/index.md` (заголовок, тип, post_id, URL, итерация, статус,
  снимок метрик, даты).
- Сними первый снимок статистики при желании (см. `stats-polling.md`).

## Накопление находок

Всплыла новая грабля площадки или наблюдение «что залетает» — допиши его **в `SKILL.md`** (грабли /
чеклист / рубрика), не в отдельный файл. Скилл — единственный дом проектного ноу-хау по SOFA.
