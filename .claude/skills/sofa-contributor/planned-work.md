# Режим: плановая работа

Отбор кандидатов → черновики → публикация → запись в реестр. Это режим роли `sofa-contributor`
в оркестраторе (шаги 1–2, генерация кандидатов) и ручных публикаций архитектором (шаги 3–5).

Предусловие: загружен скилл `sofa` (механика площадки) и прочитан `SKILL.md` этого каталога
(рубрика отбора, чеклист качества, грабли).

## Граница автономности

Автономный конвейер (оркестратор) выполняет **только шаги 1–2** — анализ и генерацию кандидатов в
`sofa-proposals.md`, без единого внешнего вызова на запись. Шаги 3–5 (dedup-поиск, черновики,
публикация, реестр) — author-driven, под явным апрувом архитектора. Публикация наружу автономно
не делается никогда.

## Шаг 1 — анализ артефактов итерации

Вход: `summary.md`, `decisions.md`/ADR, `plan.md`, отчёты code-review и stand-validation, `git diff`
итерации. Цель — найти места, где возникла нетривиальная находка: удивительное поведение tool/API,
проваленная первая попытка с понятным «почему», долговечный фикс, verbatim-ошибка.

Прогнать каждого кандидата через рубрику отбора из `SKILL.md` (берём / режем и почему).

## Шаг 2 — кандидаты в `sofa-proposals.md` (папка итерации)

Записать в `sofa-proposals.md` директории итерации ранжированный список:

- Заголовок-описание проблемы, тип (TIL/blueprint/question), решение (брать / не брать) и **почему**
  — со ссылкой на артефакт-источник.
- Для «берём» — черновик-набросок тела (можно неполный): проблема → окружение/версии → причина →
  фикс → как верифицировано. С пометкой, что финальный текст приводится к стандартам площадки на
  шаге 4.
- Явно отметить: документ — WIP под ревью архитектора, **ничего не опубликовано**.

Это терминальная точка автономной роли. Дальше — author gate.

## Шаг 3 — author gate

Подать архитектору список кандидатов с обоснованием. Архитектор решает, что публиковать. Без
апрува — стоп. Публиковать ничего по своей инициативе.

## Шаг 4 — публикация (по апруву, по одному посту)

1. **Поиск дублей** — `GET /api/posts?search=...` с нескольких формулировок + по тегам. Близкий
   пост есть → не плодить новый: верификация/реплай, доложить архитектору.
2. **Прочитать `GET /guidelines/{til|blueprint|question}`** под тип поста.
3. **Финальный текст** — привести черновик к чеклисту качества из `SKILL.md`: обобщить (вычистить
   имя проекта/классы), естественная проза без шаблонных секций, минимальные код-сниппеты +
   нумерованные шаги для процедур, verbatim-ошибки. **Проверить тело на `http(s)://`** (link
   guardrail рубит даже в код-блоках) — origin/хосты bare или плейсхолдером.
4. **Публикация** через механику скилла `sofa` (`POST /api/posts`). Тело держать в локальном файле,
   собирать JSON безопасно (например `jq --rawfile`).
5. **Рерайт уже опубликованного** (если правим): сначала `DELETE` старого, потом `POST` нового —
   иначе дедуп-скрин (422 `duplication`). Удаление одностороннее; тексты сохранены локально.

## Шаг 5 — каноничная запись в реестр

После успешного `201`:

- Создать `doc/content/sofa/posts/<slug>.md`: метаданные (post_id, URL, тип, теги, дата публикации,
  итерация-родитель) + каноничное опубликованное тело + пустая секция лога статистики.
- Добавить строку в `doc/content/sofa/index.md` (заголовок, тип, post_id, URL, итерация, статус,
  снимок метрик, даты).
- При желании снять первый снимок статистики (см. `stats-polling.md`).

## Накопление находок

Если по ходу публикации всплыла новая грабля площадки или наблюдение «что залетает» — дописать его
**в `SKILL.md`** (грабли / чеклист / рубрика), не в отдельный файл. Скилл — единственный дом
проектного ноу-хау по SOFA.
