# Режим: опрос статистики

Периодический сбор метрик опубликованных постов в реестр. Пока запускается **вручную** (по запросу
архитектора); к расписанию (cron-routine) придём, когда формат устаканится.

Перед началом загрузи скилл `sofa` (сессии/механика). Сетевые вызовы — вне sandbox (escape hatch).

## Что собираем

Источник истины по тому, какие посты опрашивать, — таблица в `doc/content/sofa/index.md` (колонка
post_id). На каждый пост сделай `GET /api/posts/{post_id}` и бери:

- `view_count` — просмотры (слабый сигнал: инкрементится на каждом GET детали, включая наши проверки).
- `reply_count` — реплаи.
- `trust_summary` — `status` (`not_enough_evidence` → scored), `score`, `latest_verified_at`. Это
  главный сигнал качества контента: сдвиг `status` в scored и движение `latest_verified_at` — то,
  ради чего мониторим.

Опционально сними снимок репутации агента (`GET /api/me/agents` → `stats.reputation`) и позиции в
лидерборде, но фиксируй это отдельно: это агентский, а не пост-уровень, не путай с метриками поста.

## Процедура

1. Проверь/создай сессию (скилл `sofa`).
2. Для каждого post_id из `index.md` сделай `GET /api/posts/{post_id}`, извлеки поля выше.
3. В `doc/content/sofa/posts/<slug>.md`, в секцию лога статистики, допиши датированный снимок строкой:
   дата, views, replies, trust_status, trust_score, latest_verified_at.
4. В `index.md` обнови колонку «последний снимок метрик» + дату последнего опроса.
5. Доложи архитектору, что сдвинулось с прошлого раза (особенно переходы trust-статуса и новые
   верификации), без сырого дампа всех чисел.

## Каденс и трактовка

- Раз в неделю достаточно. Не части: просмотры — шумный сигнал, и каждый наш GET сам их накручивает.
- Не делай выводов из абсолютных чисел просмотров. Показателен переход `trust_summary` из
  `not_enough_evidence` в scored и появление верификаций — это и есть ведущий индикатор.
- Наблюдения «такой угол/формат собирает верификации, такой нет» дописывай в `SKILL.md` (рубрика
  отбора / чеклист качества), чтобы влияли на будущие посты.
