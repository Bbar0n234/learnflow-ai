# Backlog

Входящий поток задач из опытной эксплуатации и Langfuse. Элементы приоритизируются и тянутся в tasklist при триаже. После переноса в tasklist элемент удаляется из backlog — tasklist становится его новым домом (секция "Из backlog" в записи итерации).

Приоритеты: **P0** (блокер) / **P1** (важно) / **P2** (желательно) / **P3** (когда-нибудь)

Группировка по scope для параллельной работы. Cross-cutting элементы помечаются *(cross: scope)*.

## Documentation Quality & Architecture

_Работа над качеством существующей арх-документации и создание сводных архитектурных документов._

- **P1** Doc feedback loop — непрерывный цикл улучшения документации на основе реальных взаимодействий агента с ней. Текущее состояние: ручное ревью архитектора — боттлнек качества документации; цель — переместить боттлнек, а не убрать ревью. Состав: **(1) Сбор фидбэка** — workflow-агент при работе фиксирует gaps (полез в код, потому что в доке нет / противоречие / устарело / неоднозначно); формат и место хранения — на этапе реализации (отдельный файл, маркеры в документах, structured log — варианты). Триггер сбора: часть промпта implementer/planner + опционально опрос архитектора в конце сессии. **(2) Периодическая обработка через async/cloud doc-review agent** — раз в день/неделю облачный агент пробегается по накопленному feedback log, поднимает релевантные документы, формирует архитектору **предложения** правок (документы / чек-листы / промпты workflow-агентов). Запускается автономно (Claude Routines / Codex cloud triggers). **(3) Архитектор как финальный ревьюер** — на текущем этапе зрелости системы любые изменения структуры/правил/конвенций утверждает человек; верхнеуровневое идейное ревью остаётся за человеком. Полное делегирование агентам преждевременно: дай агентам строить систему — выйдет херня. Связано с Async / cloud agent workflow (один из первых use case async-агентов), Tech/ full documentation audit (разовый аудит vs continuous loop), AIDD skill actualization (root-cause фикс в источнике), Workflow-agent prompts formalization (точка встраивания триггера сбора), Doc-first execution discipline (парный пункт — генерирует обращения к коду как сигнал о gap'ах) *(cross: Agent Harness, Infra)*

- **P2** Codebase-wide patterns & conventions pass — плановая фаза "взросления" кодовой базы: проход по всем слоям (backend / agent runtime / frontend), изучение текущих паттернов, выявление несоответствий, переход на единые практики, закрытие техдолга, написание недостающих тестов. Результат: (a) обновлённый код, (b) новые/уточнённые конвенции в `conventions.md` (через continuous improvement на реальных примерах), (c) тест-покрытие критичных участков. Связанные пункты, которые естественно поглощаются или стыкуются: REST API cleanup / audit, DB architecture audit, LangGraph audit, Error return types conventions, Logging conventions enforcement, Tech/ full documentation audit. Спаривается с Async / cloud agent workflow в Agent Harness — вторая волна реализации (после установления конвенций) идёт преимущественно через async-агентов по свежим правилам. Дробление на конкретные итерации — на этапе tasklist *(cross: Documentation Quality, Agent, Backend, Frontend)*
- **P3** Frontend stack deep-read — целенаправленное погружение архитектора в фронтенд-код проекта (React/TypeScript) для прокачки компетенции. **Не задача по коду и не рефакторинг** — задача по компетенции архитектора, без которой невозможно выстраивать серьёзную архитектуру фронтенда
- **P3** Linter/formatter stack deep-read — целенаправленное изучение конфигов и правил `ruff` / `mypy` / `eslint` / `prettier` для прокачки компетенции. Аналогично frontend: цель — экспертиза, а не рефакторинг
