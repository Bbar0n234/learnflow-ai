# Backlog

Входящий поток задач из опытной эксплуатации и Langfuse. Элементы приоритизируются и тянутся в tasklist при триаже. После переноса в tasklist элемент удаляется из backlog — tasklist становится его новым домом (секция "Из backlog" в записи итерации).

Приоритеты: **P0** (блокер) / **P1** (важно) / **P2** (желательно) / **P3** (когда-нибудь)

Группировка по scope для параллельной работы. Cross-cutting элементы помечаются *(cross: scope)*.

## Security

- **P1** SIEM `/events` endpoint без `require_admin` — Information Disclosure — `services/siem-service/siem_service/api/routes.py:42-101` объявляет `GET /events` без `Depends(require_admin)`, в отличие от `/alerts` (`:108`) и `/rules` (`:229`). Любой залогиненный пользователь (необязательно admin) получает полный поток security events: попытки prompt injection других пользователей, IP-адреса, user_id, classifier verdicts, canary-leak инциденты, metadata инцидентов. Воспроизведено на production-стенде 2026-05-18 при отладке SIEM UI: токен без `is_admin=true` → `/events` 200 OK, `/alerts` и `/rules` 403 *(Backend, SIEM)*
- **P2** `X-Forwarded-For` доверяется безусловно — спуфинг IP в security-контексте — `backend/app/main.py` (request_id middleware) и `backend/app/api/routes/auth.py` (`_get_client_ip`) берут первый элемент `X-Forwarded-For` без проверки, что запрос пришёл от доверенного прокси. Клиент с прямым доступом (порт 8000 опубликован на 127.0.0.1, но в dev/LAN-сценариях достижим) подменяет свой IP в логах, SIEM-событиях и ключах rate limiter'а (`login:{name}:{ip}`) — обходит лимит и загрязняет корреляцию. Варианты: доверять заголовку только при известном прокси (`ProxyHeadersMiddleware` uvicorn с `--forwarded-allow-ips`), либо конфиг-флаг `TRUST_PROXY_HEADERS`. Выявлено в slice feat-004 *(Backend, Security)*
- **P2** RBAC guard страницы `/security` пропускает не-админов — заявленный в DoD feat-005 «React страница `/security` (lazy chunk + RBAC guard)» по факту даёт зайти на страницу пользователю с устаревшим / не-админским JWT. Пользователь видит частично работающий UI (события — 200 благодаря пункту выше, алерты/правила — 403), без понятной диагностики. Guard должен либо отсекать вход на страницу целиком при отсутствии `is_admin`, либо страница должна показывать explicit message «Требуются права администратора» вместо обычной ошибки загрузки *(Frontend)*
- **P3** JWT claim `is_admin` не освежается после `grant-admin` — claim фиксируется в JWT при логине; `make grant-admin USER=...` обновляет `users.is_admin` в БД, но активные токены остаются со старым значением до relogin / истечения. На UI это выглядит как «выдал админа, но SIEM-вкладки всё ещё 403». Варианты: (a) короткоживущий access token + refresh при изменении прав; (b) явная invalidation токенов по user_id при `grant-admin`; (c) проверка `is_admin` через БД в dependency, не из claim; (d) минимальный UX-фикс — на 403 от SIEM API показывать toast «Перелогиньтесь, чтобы обновить права». Workaround сейчас — logout + login *(Backend, Frontend, Auth)*
- **P2** Async Guard — параллельная проверка guard с main LLM для снижения latency. Tool execution ждёт вердикта *(Agent)*
- **P2** Multi-turn escalation detection — текущий classifier видит history, отдельный механизм not planned; пересматриваем при появлении подтверждённого FN-класса, который history-aware classifier стабильно пропускает *(Agent)*
- **P3** Trust-tier formalization для internal tools — если выйдет class internal tools, чьи outputs регулярно конфликтуют с защитными слоями (по аналогии с tool result + skills corpus), описать tier-механизм для исключений *(Agent)*
- **P3** User MCP attack probe в eval-наборе — добавить attack probe для пункта «User MCP → единая строгость» при возврате eval-инфраструктуры из parked-режима *(Agent)*
- **P3** Глобальный refactor паттерна `get_db_session` commit — активируется при повторном проявлении 404-симптома в других routes (сейчас покрыт точечным фиксом в ChatService, конвенция — в conventions.md) *(Backend)*
- **P3** Guard observations иерархия в Langfuse UI — guards рендерятся как siblings root span, не вложены в позицию между iter'ами agent node. Не блокирует observability; ремедиация требует синхронизации CallbackHandler vs OTel scope, low value *(Agent)*
- **P1** Fundamental red-team eval — объективная метрика защиты — feat-008 дал baseline: инструмент Promptfoo + первый поверхностный прогон (22 кейса, 0 успешных атак, 6/22 errored по timeout / grader edge case). Нужен фундаментальный, более полный прогон: глубже разобраться в Promptfoo (plugins / strategies / frameworks) и/или подключить более жёсткие red-team наборы, выбить измеримую объективную метрику качества защиты. Цель — не быть голословным во флагманской статье о многослойной защите (см. `doc/content/security-article-draft.md`). Фундамент — `doc/security/`. Закрывает Фазу 4 / Трек A1 *(Agent, Security)*

## Meta (Backlog & Workflow Infrastructure)

_Мета-работа над процессом и инструментами разработки, не фичи продукта._

- **P1** Meta Agent Harness — самоулучшающийся слой workflow. Background-агент анализирует артефакты итераций (design-brief, plan, summary, transcripts сессий) и истории сообщений Claude Code → предлагает архитектору улучшения skill'ов / инструкций / чек-листов / промптов workflow-агентов. Цель — root-cause fixing промахов workflow-агентов (агент затупил, ревьюер пропустил, чек-лист не покрыл) через правки в первоисточниках (промпт, документ, чек-лист), не через точечные правки симптомов. Идея на основе статьи https://arxiv.org/abs/2603.28052 — meta agent harness, который сам себя улучшает. Скорее всего реализуется как отдельный skill, в который упакован background-агент; AIDD-skill сам по себе не часть этого пункта. Отдельный домен, не привязан к фазам типа codebase-maturity. Стыкуется с P1 Doc feedback loop (Documentation Quality) — там тот же паттерн background-анализа, но для документации

## Documentation Quality & Architecture

_Работа над качеством существующей арх-документации и создание сводных архитектурных документов._

- **P1** Doc feedback loop — непрерывный цикл улучшения документации на основе реальных взаимодействий агента с ней. Текущее состояние: ручное ревью архитектора — боттлнек качества документации; цель — переместить боттлнек, а не убрать ревью. Состав: **(1) Сбор фидбэка** — workflow-агент при работе фиксирует gaps (полез в код, потому что в доке нет / противоречие / устарело / неоднозначно); формат и место хранения — на этапе реализации (отдельный файл, маркеры в документах, structured log — варианты). Триггер сбора: часть промпта implementer/planner + опционально опрос архитектора в конце сессии. **(2) Периодическая обработка через async/cloud doc-review agent** — раз в день/неделю облачный агент пробегается по накопленному feedback log, поднимает релевантные документы, формирует архитектору **предложения** правок (документы / чек-листы / промпты workflow-агентов). Запускается автономно (Claude Routines / Codex cloud triggers). **(3) Архитектор как финальный ревьюер** — на текущем этапе зрелости системы любые изменения структуры/правил/конвенций утверждает человек; верхнеуровневое идейное ревью остаётся за человеком. Полное делегирование агентам преждевременно: дай агентам строить систему — выйдет херня. Связано с Async / cloud agent workflow (один из первых use case async-агентов), Tech/ full documentation audit (разовый аудит vs continuous loop), Meta Agent Harness (тот же паттерн background-анализа, но для skill'ов/инструкций workflow-агентов), skill `aidd-orchestrator` (точка встраивания триггера сбора в промпты ролей), Doc-first execution discipline (парный пункт — генерирует обращения к коду как сигнал о gap'ах) *(cross: Agent Harness, Infra)*
- **P2** Tech/ full documentation audit — пройтись по всем документам в `tech/` через doc reviewer по принципам, зафиксированным в `conventions.md` (раздел Documentation) и скилле `aidd-methodology`. Выявить проблемные точки, завести точечные итерации на рефакторинг. Зависит от существования doc reviewer как формализованного агента — в текущем `aidd-orchestrator` роли нет, потребуется отдельная формализация
- **P2** REST API contracts summary — сводный документ с REST API контрактами со всех сервисов. **Не дубль** `tech/backend.md` (там живут детали реализации) — обзорная страница "где какой endpoint живёт, какой контракт, какие коды ответа, какая аутентификация". Полезна при cross-service обсуждениях и при планировании работ, затрагивающих несколько API. Роль документа явно обозначена как "summary / overview", не как "source of truth", чтобы избежать дрейфа дубликации
