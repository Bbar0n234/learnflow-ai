Входящий поток задач из опытной эксплуатации и Langfuse. Элементы приоритизируются и тянутся в tasklist при триаже. После переноса в tasklist элемент удаляется из backlog — tasklist становится его новым домом (секция "Из backlog" в записи итерации).

Приоритеты: **P0** (блокер) / **P1** (важно) / **P2** (желательно) / **P3** (когда-нибудь)

Группировка по scope для параллельной работы. Cross-cutting элементы помечаются *(cross: scope)*.

_Findings из feat-002 REST API slice (Codebase Maturity) — отложены архитектором, фиксятся не в slice'е._

- **P3** Feedback resource modeling — убрать протечку Langfuse `trace_id` в REST-контракт. Сейчас feedback адресуется `PUT|DELETE /projects/{id}/chats/{cid}/feedback/{trace_id}` (feat-002): `trace_id` — observability-идентификатор Langfuse, утёкший в публичный контракт, а вложенность depth-3 избыточна (trace_id глобально уникален, project/chat в пути — только ради авторизации). Целевая модель — адресация по доменному `message_id` (`.../chats/{cid}/messages/{message_id}/feedback`), `trace_id` резолвится на бэке для `create_score`. Требует: маппинг message_id↔trace_id (сейчас в Redis только прямой `trace:{thread_id} → {message_id: trace_id}`), правки фронта (`FeedbackButtons` оперирует `trace_id` из SSE `done`), резолв в роуте. Не горит — текущий контракт работает и ownership-безопасен; это чистота доменной модели на вырост. Нужно продумать маппинг детальнее перед реализацией *(cross: Frontend, Langfuse)*

Кандидат на вынос в shared-пакет. Решать вместе с feat-004 Codebase Maturity (там выпиливается дубль `SecurityEvent` в пользу `siem_contracts` — единый принцип «общий контракт → shared»), не плодя shared-пакеты вразнобой. Trade-off: DRY vs независимость сервисов (CLAUDE.md: «services/ — самостоятельные runtime'ы») *(Backend, SIEM)*
- **P2** PDF-экспорт артефактов неработоспособен — `backend/app/api/export.py` использует pdfkit/wkhtmltopdf; wkhtmltopdf archived/deprecated и сегфолтится на MathJax-скрипте (воспроизведено на Fedora 43, wkhtmltopdf 0.12.6: `GET .../artifacts/{id}/download?format=pdf` → 500, обнаружено при прогоне тест-кейсов feat-002). Для образовательной платформы рендер формул критичен → замена нужна с поддержкой математики: headless-Chromium/Playwright (исполняет MathJax, тяжёлый), KaTeX server-side pre-render → HTML → weasyprint, или pandoc+LaTeX (лучшее качество, тяжёлый tex-стек) *(Backend)*
- **P3** MCP `mcp_unreachable` — неточный статус-код — `backend/app/services/mcp_server.py:271` отдаёт `503` при недоступности внешнего MCP на create/update. Сам fail-closed (security-валидация metadata требует доступного сервера) — корректен. Но `503` означает «наш сервис недоступен» (провоцирует ретраи / реакцию балансировщиков); недоступный URL, указанный клиентом, семантически ближе к `422` (не можем обработать данные запроса) или `502` (upstream не ответил). Поправить только код, security-логику не трогать *(Backend)*

## Security

- **P2** RBAC guard страницы `/security` пропускает не-админов — заявленный в DoD feat-005 «React страница `/security` (lazy chunk + RBAC guard)» по факту даёт зайти на страницу пользователю с устаревшим / не-админским JWT. После feat-002 (закрытие `/events` под `require_admin`) все SIEM-эндпоинты не-админу отдают 403 — пользователь видит неработающий UI без понятной диагностики. Guard должен либо отсекать вход на страницу целиком при отсутствии `is_admin`, либо страница должна показывать explicit message «Требуются права администратора» вместо обычной ошибки загрузки *(Frontend)*
- **P2** `X-Forwarded-For` доверяется безусловно — спуфинг IP — `backend/app/main.py` (request_id middleware) и `backend/app/api/routes/auth.py` (`_get_client_ip`) берут первый IP из `X-Forwarded-For` без проверки доверенного прокси. Два следствия: (1) обход per-IP rate-лимитов (register 3/3600с, login, refresh) — подтверждено прогонами тест-кейсов feat-002 и feat-004; (2) подмена IP в логах и SIEM-событиях → загрязнение корреляции. Лечится знанием числа trusted-hops (брать N-й IP справа), `uvicorn --proxy-headers --forwarded-allow-ips`, конфиг-флагом `TRUST_PROXY_HEADERS` или перезаписью XFF на проксе. Зависит от топологии прода *(Backend, Auth, Security, Infra)*
- **P3** JWT claim `is_admin` не освежается после `grant-admin` — claim фиксируется в JWT при логине; `make grant-admin USER=...` обновляет `users.is_admin` в БД, но активные токены остаются со старым значением до relogin / истечения. На UI это выглядит как «выдал админа, но SIEM-вкладки всё ещё 403». Варианты: (a) короткоживущий access token + refresh при изменении прав; (b) явная invalidation токенов по user_id при `grant-admin`; (c) проверка `is_admin` через БД в dependency, не из claim; (d) минимальный UX-фикс — на 403 от SIEM API показывать toast «Перелогиньтесь, чтобы обновить права». Workaround сейчас — logout + login *(Backend, Frontend, Auth)*
- **P2** Async Guard — параллельная проверка guard с main LLM для снижения latency. Tool execution ждёт вердикта *(Agent)*
- **P2** Multi-turn escalation detection — текущий classifier видит history, отдельный механизм not planned; пересматриваем при появлении подтверждённого FN-класса, который history-aware classifier стабильно пропускает *(Agent)*
- **P3** Trust-tier formalization для internal tools — если выйдет class internal tools, чьи outputs регулярно конфликтуют с защитными слоями (по аналогии с tool result + skills corpus), описать tier-механизм для исключений *(Agent)*
- **P3** User MCP attack probe в eval-наборе — добавить attack probe для пункта «User MCP → единая строгость» при возврате eval-инфраструктуры из parked-режима *(Agent)*

- **P1** Fundamental red-team eval — объективная метрика защиты для статьи — feat-008 дал baseline: инструмент Promptfoo + первый поверхностный прогон (22 кейса, 0 успешных атак, 6/22 errored по timeout / grader edge case). Нужен фундаментальный, более полный прогон: глубже разобраться в Promptfoo (plugins / strategies / frameworks) и/или подключить более жёсткие red-team наборы, выбить измеримую объективную метрику качества защиты на сотнях кейсов. Цель — не быть голословным во флагманской статье о многослойной защите (см. `doc/content/security-article-draft.md`). Фундамент — `doc/security/`. **Зависимость флагманской статьи (Трек C), а НЕ гейт Фазы 4:** LLM-защита в проекте — артефакт исследования, не продуктовая потребность; прогон тянется тогда, когда садимся за статью *(Agent, Security, cross: Контент)*
- **P2** Kill-switch LLM-защиты — флаг полного отключения inline LLM-defense (SecurityGuard / LLM-классификатор, unicode-детектор, Universal I/O Guard, boundary enforcement): всё проходит насквозь, защитные слои не запускаются. Мотив — LLM-защита артефакт исследования («Защита нейронных сетей»), не продуктовая потребность; в проде стоит лишних LLM-вызовов и latency без ценности. Per-env тумблер (не выпиливание кода), default off в проде, включается под red-team прогон для статьи (прогон идёт через реальный API). Скоуп строго: только inline LLM-defense — НЕ трогает SIEM-пайплайн, auth, rate limiting, RBAC, биндинг портов (обычная app-security остаётся 100%). Env-гигиена: Settings + .env.example + .env.local.example + docker-compose.yml. Точка реализации — отдельный мелкий chore сразу после agent-слайса codebase maturity (feat-005) *(Agent, Backend)*
- **P3** SIEM → SOC evolution — развить текущий SIEM (сбор / корреляция / алертинг / уведомление) в полноценную SOC-систему с активным реагированием: не только обнаруживать и уведомлять, но и блокировать (напр. брутфорс по IP / аккаунту). Сейчас SIEM реализован из учебной потребности (дисциплина по ИБ, фундамент диплома); как продуктовая фича не требуется, но при выходе на реальный прод (~сотни пользователей, ближе к осени) активное реагирование 100% пригодится — требует допила функционала. Далёкий горизонт: не гейт Фазы 4 и, вероятно, дальше Фазы 5. SIEM асинхронный и дешёвый — под kill-switch LLM-защиты НЕ попадает, работает независимо *(Backend, SIEM, Security)*

## Agent Harness & Workflow

_Формализация multi-agent dev workflow, промпты workflow-агентов, детерминированные проверки, systematic fixes инфраструктуры разработки._

- **P2** Kill-process bug systematic fix — разобраться, почему Claude Code регулярно не убивает процессы с первого раза при работе с `make`-таргетами (повторяющаяся проблема: агент думает, что убил процесс, потом видит занятый порт). - **P3** Browser automation в cloud-сессиях — known limitation: Anthropic proxy не пропускает HTTP CONNECT → headless-браузеры к HTTPS не работают ([issue #11791](https://github.com/anthropics/claude-code/issues/11791), open без ETA). Сейчас покрывается merge-конвенцией: UI-валидация — архитектором локально после pull feature-ветки (см. `conventions.md` § Cloud sessions). Реактивировать при фиксе CONNECT в Anthropic proxy (тогда обычный Playwright заработает) или если merge-конвенция начнёт быть боттлнеком. ## Documentation Quality & Architecture

_Работа над качеством существующей арх-документации и создание сводных архитектурных документов._

- **P1** Doc feedback loop — непрерывный цикл улучшения документации на основе реальных взаимодействий агента с ней. Текущее состояние: ручное ревью архитектора — боттлнек качества документации; цель — переместить боттлнек, а не убрать ревью. Состав: **(1) Сбор фидбэка** — workflow-агент при работе фиксирует gaps (полез в код, потому что в доке нет / противоречие / устарело / неоднозначно); формат и место хранения — на этапе реализации (отдельный файл, маркеры в документах, structured log — варианты). Триггер сбора: часть промпта implementer/planner + опционально опрос архитектора в конце сессии. **(2) Периодическая обработка через async/cloud doc-review agent** — раз в день/неделю облачный агент пробегается по накопленному feedback log, поднимает релевантные документы, формирует архитектору **предложения** правок (документы / чек-листы / промпты workflow-агентов). Запускается автономно (Claude Routines / Codex cloud triggers). **(3) Архитектор как финальный ревьюер** — на текущем этапе зрелости системы любые изменения структуры/правил/конвенций утверждает человек; верхнеуровневое идейное ревью остаётся за человеком. Полное делегирование агентам преждевременно: дай агентам строить систему — выйдет херня. Связано с Async / cloud agent workflow (один из первых use case async-агентов), Tech/ full documentation audit (разовый аудит vs continuous loop), Meta Agent Harness (тот же паттерн background-анализа, но для skill'ов/инструкций workflow-агентов), skill `aidd-orchestrator` (точка встраивания триггера сбора в промпты ролей), Doc-first execution discipline (парный пункт — генерирует обращения к коду как сигнал о gap'ах) *(cross: Agent Harness, Infra)*

## Оптимизация под будущие нагрузки

_Отложенные оптимизации из DB slice (feat-003): на текущих объёмах не окупаются, активируются при росте нагрузки._

- **P3** Корреляционные стратегии SIEM на SQL-агрегаты — сейчас стратегии тянут все события окна в Python и группируют в памяти (sequence — вложенный цикл A×B); перевод на `GROUP BY ... HAVING` / self-join переносит счёт в БД и возвращает только пробившие порог группы. Триггер: рост объёма событий в окне
- **P3** UUIDv7 вместо UUIDv4 для PK — random v4 разбрасывает вставки по случайным страницам B-tree (page splits, холодный кэш); v7 time-ordered, вставки идут в правый край. Генерация client-side (Python-библиотека), смены типа колонок не требует. Триггер: заметный insert-трафик в таблицы main app
- **P3** Индексы на `siem_alerts.first_event_id` / `latest_event_id` — FK с `ON DELETE RESTRICT` без индексов; каждое удаление события проверяет ссылки seq scan'ом. Обязательно перед включением retention-удаления `siem_events` (`SIEM_DELETE_AFTER_DAYS`)
- **P3** Retention для `siem_alerts` — `expired`/`resolved` алерты копятся бессрочно (в отличие от событий, у которых retention есть). Сейчас осознанно: алерты — аудит-след. Триггер: рост объёма таблицы алертов; вводить вместе с retention-индексами выше (FK на события не дадут удалить событие, пока на него ссылается алерт)
- **P3** Политика хранения refresh-токенов неактивных пользователей — оппортунистическая чистка при логине (feat-003) не затрагивает пользователей, которые не возвращаются; глобальная фоновая чистка/политика хранения — при необходимости
