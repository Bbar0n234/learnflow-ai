# Backlog

Входящий поток задач из опытной эксплуатации и Langfuse. Элементы приоритизируются и тянутся в tasklist при триаже. После переноса в tasklist элемент удаляется из backlog — tasklist становится его новым домом (секция "Из backlog" в записи итерации).

Приоритеты: **P0** (блокер) / **P1** (важно) / **P2** (желательно) / **P3** (когда-нибудь)

Группировка по scope для параллельной работы. Cross-cutting элементы помечаются *(cross: scope)*.

- **P1** Live-обратная связь в чате во время работы агента — SSE-стрим не шлёт ни байта до первого события LangGraph: замерено на живом стенде — 13–15 с тишины до первого `text_chunk` на тривиальном ответе (reasoning-модель + guard) и 47 с до первого события (`tool_start` для `load_skill`) при tool-first ходе. Фронтовый first-byte timeout (30 с, `useAgentStream`) срабатывает раньше → пользователь видит «Превышено время ожидания» и пустой чат, хотя бэкенд дорабатывает `status=ok` и ответ появляется после перезагрузки. Состав: (а) ack-событие при открытии стрима + периодический heartbeat в тишине — новый контракт в `streaming.md`; (б) мгновенный индикатор «агент думает…» с момента отправки, состояния по фазам (guard → рассуждает → инструмент → review); (в) пересмотр таймаута — считать от heartbeat, не от первого байта; (г) ранний `tool_start` — эмитить из token-level стрима (`tool_call_chunks` в `stream_mode="messages"`), не дожидаясь завершения узла графа. **Клиентский минимум закрыт в feat-011**: мгновенный индикатор «агент думает» (`ThinkingIndicator`, включая паузы между шагами) + first-byte-таймаут 30с→300с (`VITE_SSE_FIRST_BYTE_TIMEOUT_MS`; ложные «Превышено время ожидания» на легитимных прогонах устранены). Остаётся серверная часть (а, г) и фазовые состояния из (б); варианты отрисовки фаз — мокап `doc/tasks/iterations/post-mvp/feat-011-subagents-v1/mockups/live-feedback-variants.html` (V1 доставлен, V2/V3 требуют (а)/(г)) *(cross: Backend, Agent)*
- **P3** Стриминг reasoning-токенов в UI — отдельный SSE event type для рассуждений модели + сворачиваемая секция «агент рассуждает» в чате; закрывает основную долю воспринимаемой тишины на reasoning-моделях. Продвинутая фича поверх P1 live-обратной связи *(cross: Backend, Agent)*
- **P3** Системная проработка интерактивности вывода агента в чате — обычные текстовые реплики в порядке; всё остальное (трансляция работы агента) сделано примитивно: единственная плашка с сырым именем инструмента (`run_subagent`) на время выполнения — не видно, что это инструмент, не видно тип субагента, после завершения не остаётся следа в истории, результаты инструментов не показываются никак. Точечными итерациями это не лечится — нужен один системный дизайн-заход (design-brief + мокапы): персистентный рендер tool-вызовов в истории сообщений, интерактивный стриминг хода инструментов и (выборочно) их результатов, различимость субагентов, стриминг рассуждений — красиво и динамично, уровнем дизайн-системы. Зонт, поглощающий при реализации: P3 «Стриминг reasoning-токенов» (выше), серверный остаток P1 «Live-обратная связь» (ранний `tool_start`, heartbeat, `agent_type` в payload), варианты V2/V3 мокапа `feat-011/mockups/live-feedback-variants.html` *(Frontend, cross: Backend, Agent, Design-branding)*
- **P1** Voice input — голосовой ввод сообщений агенту (STT). Фича тривиальна; нетривиальное — UX: склоняемся к «транскрипт → редактируемое поле чата» (пользователь правит ошибки STT по терминам/именам), а не «сразу агенту»; финальный UX — на этапе реализации *(cross: Backend)*
- **P3** Rich Artifact UI — специализированные viewer/editor-компоненты для разных типов артефактов (аудио, графики, презентации и др.) вместо универсального markdown-viewer. Это обычный типизированный UI, не Generative UI; конкретные сценарии и приоритет уточняются через dogfooding. **Фронт-заглушки вьюеров (slides/image/audio, диспатч по `type`) доставлены в feat-004 на mock-данных**; остаётся бэкенд (реальные типы артефактов + хранение/отдача) и проводка фронта на реальные данные *(cross: Backend)*

Для текущего продукта подтверждённого сценария нет; вернуться при развитии LearnFlowAI в платформу для студентов, где потребуются адаптивные учебные интерфейсы. Ресерч завершён (`doc/research/generative-ui-research-report.md`) *(cross: Agent, Backend)*
- **P3** Rich Material Export — экспорт rich-артефактов с сохранением визуального качества (не markdown-дамп). Форматы и требования определяются после появления реальных типов rich-артефактов; Generative UI не является обязательной зависимостью *(cross: Backend)*

Триггер актуальности — многоминутные раны субагентов (feat-011): вероятность дисконнекта на длинном ране высокая. Затрагивает стрим-ядро → правка `streaming.md` *(Agent, Backend)*

Разобраться, как чекпойнтер LangGraph держит пул и можно ли включить pre-ping/reconnect *(Agent, Infra)*
- **P3** Редактирование и версии артефактов (на подумать) — у агента единственный инструмент `create_artifact`, и он всегда `repo.create` (`backend/app/agent/tools/artifacts.py`): каждое «пересохранение» рождает новый артефакт с новым id; инструмента update/patch и версионирования артефакта нет. ## Security

- **P3** Fail-open write-роутов при отсутствии security guard — все три write-роута (`user_memory.py`, `skill_context.py`, `mcp_servers.py`) резолвят guard через `getattr(request.app.state, "security_guard", None)`: если guard не сконструирован/не положен на `app.state` (misconfiguration в lifespan), сервисы получают `guard=None` и пропускают security-checkpoint целиком — запись проходит без проверки вместо явного отказа. Риск теоретический (Sec 2.0 всегда строится в lifespan до роутеров), но паттерн воспроизведён по коду во всех трёх файлах. Целевая модель: явный fail-closed (500) при отсутствии guard вместо молчаливого пропуска. Не дубль пункта про деградацию LLM-классификатора (ADR-017 D-ERR-6) — тот про недоступность LLM, этот про отсутствие guard-объекта целиком. Отдельного флага отключения у SIEM **нет** (kill-switch LLM-защиты её явно не трогает). Два пути: **(A)** добавить per-env kill-switch для SIEM по образцу kill-switch LLM-защиты (отключать в проде, где она не нужна и стоит ресурсов), либо **(B)** допилить до реально продакшн-пригодного состояния (валидация правил, рабочий RBAC, активное реагирование — см. ## Agent Harness & Workflow

- **P1** Подход к тестированию/ревью фронтенда — выстроить архитектуру так, чтобы минимизировать ручную нагрузку и когнитивный груз архитектора, оставляя ему только высокоценный вкусовой фидбэк (человеческое ревью без него всё равно не обойтись). Это **запись мыслей под отдельную итерацию проектирования**, не выбор реализации сейчас. Категория реальная: off-the-shelf (BugHerd / Marker.io / Pastel / Vercel Toolbar comments) или лёгкий self-built dev-overlay, пишущий element-anchored комментарии в файл для агента — нужен ресёрч. **(4)** Догфудинг как основной канал полировки: точечную визуальную доводку делать во время реального пользования продуктом, а не «тыкать просто так» (двух зайцев — пользуешься и тестируешь). ## Оптимизация под будущие нагрузки

_Отложенные оптимизации из DB slice (feat-003): на текущих объёмах не окупаются, активируются при росте нагрузки._

Триггер: рост объёма таблицы алертов; вводить вместе с retention-индексами выше (FK на события не дадут удалить событие, пока на него ссылается алерт)
