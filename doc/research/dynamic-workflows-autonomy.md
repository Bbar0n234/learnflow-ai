# Dynamic Workflows и verifier-grounded автономия — ресёрч и направления

Дата: 2026-06-14. Контекст: разбор фичи Anthropic **Claude Code Dynamic Workflows** (инструмент `Workflow`) и оценка, где она применима в LearnFlow AI — в частности, стоит ли переписывать под неё skill `aidd-orchestrator`.

Документ фиксирует **картину и направления**, а не дизайны. Конкретные воркфлоу-скрипты, схемы ролей и enforcement-конфиги проектируются отдельно, когда дойдут руки. Здесь — принципы, к которым пришли, и карта, от которой потом проектировать.

## Что такое Dynamic Workflows (механика)

Dynamic Workflows — это **слой детерминированной оркестрации сабагентов, написанный кодом**. Главная модель (Claude в основной петле) пишет JavaScript-скрипт и передаёт его инструменту `Workflow`. Единственные недетерминированные точки скрипта — вызовы `agent(prompt, opts)` (LLM-сабагенты-листья). Всё остальное — циклы, ветвления, fan-out, синхронизация, голосование — обычный управляющий код, который харнесс исполняет дословно, а не «держит в голове» модель.

Ключевой сдвиг: управляющая логика переезжает **из контекста модели в код**. Это противоположность текущему подходу `aidd-orchestrator`, где FSM итерации описана прозой в SKILL.md, а исполняет её главная модель, перечитывая инструкцию.

Существенные свойства движка:

- **Песочница дирижёра.** Сам JS-скрипт исполняется в урезанной среде: нет fs, нет сети, отключены `Date.now`/`Math.random`/`new Date`. Это сделано **ради детерминизма и резюмируемости** (см. журнал ниже), а не ограничивает агентов. Ограничение касается только тонкого слоя-дирижёра.
- **Агенты полнофункциональны.** Сабагенты, которых порождает `agent()`, — обычные сабагенты Claude Code с полным тулсетом: Bash, Read/Write/Edit, WebFetch, MCP, сеть, локальные файлы. Никакой деградации возможностей против текущих сабагентов оркестратора.
- **`parallel` vs `pipeline`.** `parallel(thunks)` — барьер (ждёт все). `pipeline(items, …stages)` — без барьера между стадиями: элемент A может быть в стадии 3, пока B в стадии 1; wall-clock = самая длинная цепочка одного элемента, не сумма «самых медленных на стадию».
- **Structured output.** Опция `schema` принуждает сабагента вернуть провалидированный JSON (ретрай на уровне tool-call). Данные между стадиями текут типизированными объектами, а не прозой в файле, — ветвление идёт по полям.
- **Изоляция контекста.** Результаты `agent()` живут в JS-переменных, не в контексте чьей-либо LLM. Главная модель видит только финальный `return` всего воркфлоу. Fan-out любой ширины не платится контекстом оркестратора.
- **Журнал и резюме.** Каждый результат `agent()` журналируется по ключу `(prompt, opts)`. Вызов `Workflow` идёт в фоне (возвращает `runId`, шлёт нотификацию по завершении). Перезапуск с `resumeFromRunId` реиграет неизменённый префикс из кэша мгновенно, исполняет вживую с первого изменённого/нового вызова. Отсюда запрет на `random`/`Date` в дирижёре.
- **Прочее.** `budget` (потолок токенов под директиву пользователя), `isolation:'worktree'` (своя копия дерева на агента — для параллельной мутации файлов), `workflow()` (вложенный воркфлоу на один уровень).

**Тарификация.** Воркфлоу наследует биллинг сессии Claude Code. Под подпиской (Pro/Max) токены идут в счёт лимитов подписки, отдельной платы нет — но воркфлоу **прожорлив по токенам** (каждый `agent()` = отдельный полный контекст), и недельный бюджет выжигается быстрее пропорционально числу агентов. Под API-ключом — метрия по токенам, может выйти дорого. Именно из-за прожорливости инструмент требует явного opt-in (инструкция скилла, велящая звать `Workflow`, считается opt-in). Резюме — в пределах сессии.

## Принцип: автономию закрывает только объективный верификатор

Сквозной инвариант, на котором сходятся все источники: **автономию можно отпускать ровно до границы дешёвого объективного верификатора.** Anthropic формулирует прямо: дай агенту проверку, которую он может запустить сам; без неё единственный сигнал остановки — «выглядит готово», и верификатором становишься ты, каждая ошибка ждёт человека.

Здесь и далее **oracle** (test oracle) — термин из тестирования: механизм, который объективно говорит «правильно/неправильно» без участия человека. Тесты, компилятор, mypy, линтер, eval-score — всё это oracle'ы. «Сильный oracle» = есть дешёвый автоматический судья, закрывающий петлю.

**Граница автономии сжимается с длиной рана.** METR (Model Evaluation & Threat Research) меряет *time horizon* — длину задачи (в человеко-времени), которую модель добивает с заданной вероятностью. 80%-горизонт заметно короче 50%-горизонта: чем выше планка надёжности, тем короче задача, которую можно отдать. Вероятность успеха — не бинарна, это кривая, ползущая вниз с длиной.

Практический вывод (ключевой): длинный автономный ран нельзя делать одной петлёй с проверкой только в конце — к финалу ты глубоко в зоне низкой надёжности, ошибки успели накопиться, и при поимке в конце перелопачивать придётся всё. Надо декомпозировать на короткие шаги (в зоне высокой надёжности) и **повесить объективный критерий на каждый шаг** — не только в конце. Акцент именно на «на каждый»: иначе ошибка компаундится между шагами.

**Верификатор сам становится поверхностью атаки.** На заведомо нерешаемых задачах модели массово хакают тесты (ImpossibleBench: правят тест-файлы, перегружают `__eq__`, хардкодят выходы под входы). На нормальных решаемых задачах это редкость, но страховка дешёвая: **исполнитель не должен иметь права писать в верификатор** (контроль доступа бьёт промптинг «не жульничай»). Разводи роли: кто пишет код и кто владеет oracle — разные агенты, oracle для исполнителя read-only.

**Failure modes длинной автономии.** Ошибки копятся на уровне траектории (зацикливание, лишний backtracking, дрейф к нерелевантным подцелям, неумение остановиться). Agentic-рефакторинг надёжен на механических локальных правках (rename, change-type), не на высокоуровневом дизайне. Отсюда — «много автономного кода» без верификатора есть рост площади дрейфа и долга, а не ценности.

**Eval-driven петли для недетерминированного.** Там, где детерминированного oracle нет (качество промптов/агента), его строят через eval-датасеты + калиброванный LLM-judge: максимизируй долю дешёвых детерминированных проверок, judge оставляй на остаток (релевантность, корректность). LLM-judge нестабилен (противоречивость pointwise vs pairwise, нарушения транзитивности) — без калибровки на human-labeled выборке его нельзя ставить гейтом наравне с тестами. Рабочая модель на нашем стеке (Langfuse): offline-эксперимент на датасете как gate перед деплоем промпта/модели + online-evaluators на проде с сэмплингом 5–10%; прод-трейсы конвертируются в regression-датасеты.

## Стратегическая рамка: куда направлять бюджет

Метрика — потраченные токены **при условии, что работа автоматизирована, верифицируема и качественна**. «Не тратишь все токены подписки» — сигнал, что workflow недостаточно автономен, но «больше токенов» ≠ «больше кода»: нетривиальное без человеческого суждения не выйдет, тривиальное в продукт не нужно.

Правильный сток бюджета — две чисто-положительные вещи:

1. **Верификация вширь и вглубь на фиксированном объёме кода** — тот же код, прогнанный через много автономных проходов (adversarial review, тест-генерация, edge-case hunting, security-свипы, поиск дрейфа). Не добавляет продуктовой поверхности, жрёт токены, поднимает качество.
2. **Постройка самих верификаторов там, где их нет.** Мета-ход: тратишь автономные токены, чтобы построить oracle, который разблокирует автономию везде, куда дотянется. Самоусиливающийся цикл.

Текущий потолок «не на что тратить токены» — прямое следствие пустого тест-сьюта: автономии не на что опереться. Поэтому стратегическая последовательность — **сначала строишь oracle'ы (тесты — codebase maturity / feat-009; security evals уже есть), потом автономия компаундится** везде, куда они дотянулись.

## Карта LearnFlow AI по верифицируемости

```
СИЛЬНЫЙ ORACLE (автономия безопасна сейчас)
├─ Security posture     ← eval-sec датасеты + Langfuse scoring + Promptfoo redteam — УЖЕ ПОСТРОЕН
├─ Backend logic        ← mypy strict + ruff (PLC0415) — безопасные рефакторы
├─ DB schema            ← Alembic autogenerate — детерминированно
├─ API contracts        ← Pydantic + mypy
└─ Conventions          ← часть автоматом (PLC0415), часть через grep + judge

СЛАБЫЙ / СТРОЯЩИЙСЯ ORACLE (автономия после постройки верификатора)
├─ Backend behaviour    ← тестов нет (codebase maturity) — построить = разблокировать всё
├─ Frontend logic       ← tsc + eslint есть, семантических тестов нет
└─ Doc alignment        ← grep подтверждает дрейф, но не полностью

НЕТ ORACLE (остаётся за человеком — и правильно)
├─ Agent Runtime quality (общее «хорошо ли рассуждает агент»)
├─ Архитектура, новые контракты (и так architect-gate)
└─ Продуктовое / UX-суждение
```

Важная поправка к «Agent Runtime не измерить»: это верно для *общего* качества рассуждений, но **security-срез Agent Runtime уже объективно измерим** — построен eval-харнесс (`tools/eval-sec/` датасеты attack/benign + Langfuse scoring INJECTION/CLEAN + `tools/security-scan/` Promptfoo). Это редкий случай, когда кусок «недетерминированного» домена переведён в «полуобъективный» через evals. Туда eval-driven автономия заходит уже сегодня.

## Направления к продумыванию (не дизайны)

Перечень областей, отсортированный по тому, что разблокирует остальное. Это кандидаты, не решения; форма воркфлоу и enforcement проектируются позже.

1. **Тест-инфра + автономная тест-генерация** (энейблер codebase maturity). Самый высокий рычаг: построить отсутствующий тест-сьют, который станет oracle для всей будущей автономии. Обязательно mutation-testing/judge, иначе агент насочиняет «change-detector»-тестов. Тест-генератор и исполнитель — разные роли, исполнитель в тесты не пишет.
2. **Security eval-driven hardening loop.** Готовый замкнутый цикл (датасеты + Langfuse scores + Promptfoo). Harvest прод-трейсов → расширение attack-датасета → прогон → scoring → предложения правок детекторов/промптов → повторный прогон → diff архитектору. Самый «токеноёмкий + ценный + с oracle», инфра стоит.
3. **Code-review fan-out** (дешёвый вход / PoC). Ревью по измерениям {корректность, безопасность, конвенции, контракты, тесты} параллельно → adversarial-верификация каждой находки скептиком со свежим контекстом → наружу только подтверждённые. Read-only, инвариант общей ветки не нарушает. Reviewer ограничивать «только то, что влияет на корректность», иначе генерит over-engineering.
4. **Convention-enforcement свип.** Миграционный воркфлоу вширь на машинно-проверяемые конвенции (PLC0415 автоматом, structlog/no-singletons через grep + judge). Oracle — `make check`/`make check-fe`; worktree-изоляция на агента для параллельных правок.
5. **Doc-drift свип.** Read-only fan-out по `doc/` против кода, репортит расхождения. Ложится на ценность из CLAUDE.md («исправляй дрейф на месте»). Горячие точки: `agent-runtime.md` (структура графа), `observability.md` (Redis-ключи, event types), `frontend.md` (роуты/компоненты — наибольший дрейф).
6. **Автономная сборка измеримой периферийной фичи** (условно). Сборка периферии под заранее заданным e2e-харнессом (пример: полная админка CM/SIEM). Работает только после того, как человек задал тест-харнесс (downstream от №1) и только для периферии, не для ядра Agent Runtime, где нужно человеческое суждение.

## Технические предпосылки

**Реальные сабагенты вместо псевдо.** Текущий `aidd-orchestrator` использует *псевдо-сабагентов*: general-purpose агент, которому оркестратор выдаёт роль в нужный момент. Чтобы заработал контроль доступа (развод ролей исполнитель/верификатор), нужны **реальные сабагент-типы** с разным тулсетом, а не одна роль на общем агенте.

Слои enforcement «исполнитель не пишет в верификатор» (нативно у Claude Code):

1. **Ограничение тулсета сабагент-типа.** Тестировщик с тулсетом `Read`/`Bash`/`Grep` и без `Edit`/`Write` физически read-only.
2. **Permission deny по путям** в `settings.json` (`deny: ["Edit(tests/**)", "Write(tests/**)"]`) — харнесс блокирует вызов, что бы модель ни пыталась. Точечнее: исполнителю оставляешь запись в код, закрываешь каталог тестов.
3. **PreToolUse-hook** — детерминированный гейт на уровне харнесса (план Б, самый жёсткий).
4. **В Dynamic Workflows конкретно** — через `agentType` маршрутизируешь роль на ограниченный тип + глобальные permission/hook поверх; для физической гарантии `isolation:'worktree'`. У самого `agent()` параметра «запрети путь X» нет — опора на тулсет-скоупинг типа + hook/permission.

## Связь с текущим aidd-orchestrator

Целиком переписывать оркестратор под один Dynamic Workflow смысла нет: его определяющие черты — строгая последовательность («один сабагент за раз, общая ветка») и частые HITL-гейты (Open Questions, эскалации, pre-commit gate) — ровно две вещи, где воркфлоу слабее всего (воркфлоу бежит до конца и возвращает одно значение, мид-ран человеческого апрува внутри нет). Каждый HITL-гейт становится **границей воркфлоу**, а не точкой внутри.

Где воркфлоу встаёт без нарушения инвариантов:

- **Read-only fan-out фаз** (review, doc-drift, security-свип, анализ тест-кейсов) — эти фазы возвращают находки, а не мутируют файлы, поэтому разворачиваются вширь даже на общей ветке.
- **Автономные сегменты между гейтами** (implement-track → make check → test → ≤2 fix → commit) — ради детерминированных bounded-loops (модель перестаёт «считать» fix-циклы), journal-resume (упавшую итерацию доигрываешь из журнала) и изоляции контекста.

То есть главная петля остаётся дирижёром гейтов, а воркфлоу — движком автономных read-only/между-гейтных сегментов. Это апгрейд по надёжности control flow + резюмируемости + изоляции контекста даже без fan-out; fan-out отдельно усиливает read-only фазы.
