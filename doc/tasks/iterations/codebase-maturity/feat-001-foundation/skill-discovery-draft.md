# Skill Discovery — feat-001 Foundation (hands-off трекер)

> **Назначение документа.** Это рабочий hands-off трекер фазы skill discovery. Он
> самодостаточен: статусы всегда актуальны, любой свежий агент (если у предыдущего кончился
> контекст) подхватывает картину отсюда без потери нити. Финал заходом 2 растекается в три
> постоянных места:
> 1. `CLAUDE.md` — тезисная таблица «Skill — When to use»;
> 2. `.claude/skills/` — сами skill-файлы выбранных скиллов;
> 3. `doc/tech/skill-map.md` — постоянный развёрнутый индекс (что/почему/когда/когда НЕ).

## Статусы

- 🔍 **К изучению** — решили прогнать перед использованием. Рядом чекбокс: `- [ ]` →
  `- [x]`, когда изучили. Это очередь архитектора на разбор. Изучённый и принятый скилл
  помечаем `- [x]` и ставим ✅ в сводной таблице.
- 👤 **Свой скилл архитектора** — авторский скилл, берём как есть, не ревьюим и не правим.
- ⛔ **Не берём** — отклонён, причина указана рядом.

Дополнительно у каждого скилла поле **Источник**: `установлен` (уже в `~/.claude/skills/` или
`.claude/skills/`) либо `поставить` (внешний, ставим в заходе 2 / в своём slice).

> **Правило копирования (стоячее).** Любой скилл из adoption-набора, лежащий на уровне
> пользователя (`~/.claude/skills/`), **сразу копируем в репозиторий** `.claude/skills/`, чтобы
> архитектор изучал его из репо и скилл версионировался вместе с проектом. Отклонённые (⛔) не
> копируем. Уже скопированы: `api-design-principles`, `postgresql`, `fastapi`, `frontend-design`
> (свои `langgraph-patterns`/`schema-guided-reasoning`/`prompt-engineering` были в репо изначально).

## Общие принципы по скиллам (мета — вынести позже)

> Накопительный блок проектных принципов отбора и применения скиллов. Пока живут здесь;
> в заходе 2 переносим в `skill-map.md` (или политику в `CLAUDE.md`). Это переносимые
> инварианты, не привязанные к одному скиллу.

1. **Объём скиллов не страшен при дисциплине скоупа.** Много скиллов в каталоге — не
   проблема сама по себе при двух условиях: (а) каждый скилл узко ограничен своим скоупом;
   (б) грузится лениво и только в релевантном контексте (например, тестовые скиллы
   подтягиваются лишь когда пишем тесты / в контексте тестировщика). Тогда они не раздувают
   контекст и не мешают друг другу. Критерий применения: не боимся 4–5 тестовых скиллов, если
   каждый по делу и подгружается по месту.
2. **Скилл вокруг незрелого / быстроменяющегося инструмента — слабый скилл.** Если скилл по
   сути упакованная документация вокруг инструмента, который быстро меняется (LangGraph) или
   ещё незрелый, его сигнатурам доверять нельзя — он устаревает быстрее, чем приносит пользу.
   Для таких доменов первоисточник (MCP `docs-langchain`, firecrawl по офиц. докам, GitHub
   releases) важнее скилла; скилл держим максимум как концептуальную карту, а конкретику
   сверяем вживую. (Это причина отбраковки `langchain-architecture` и того, почему
   `langgraph-patterns` используем концептуально, сверяя API.)
3. **Воевать с training prior нейронки стоит только за семантику, не за стиль** («can't fight
   gradient descent» — итог разбора скилла `fastapi`). Если правило скилла — чистая косметика,
   заставлять модель писать против привычного ей паттерна = расход инструкционного бюджета ради
   нуля. Но когда старый паттерн из training data — **баг или бомба** (блокирующий код в
   `async def`, утечка полей без response_model, deprecated API), бороться обязательно — и
   скилл-в-файле это оружие, которое работает дёшево: in-context инструкции бьют prior почти
   бесплатно, пока правила локальные и механические («X вместо Y»), а не требующие глобального
   переосмысления. Следствия: (а) оценивая скилл, дели правила на корзины
   *семантика / anti-rot / косметика* — скилл оправдан корзиной семантики, косметика едет
   паровозом; (б) на чистой кодовой базе скилл работает **стабилизатором против регрессии** —
   без него новые правки тянут старый стиль и получается микс, который хуже обоих чистых
   вариантов; (в) правила в файле — это ещё и **артефакт для ревью** (чек-лист reviewer'у),
   а не только инструкция генератору.
4. **Глубина разбора скилла = глубина решения, а не объём содержимого.** Архитектор ныряет в
   скилл там, где решается **политика проекта** (примеры из feat-001: resource-oriented как
   дефолт-vs-догма в `api-design-principles`; «бороться ли с training prior» в `fastapi`), и
   проходит по верхам там, где внутри детали реализации, от которых ни одно решение архитектора
   не зависит (`postgresql`, `feature-sliced-design`) — их исполняет и проверяет агент со скиллом
   и линтерами. Критерий понимания: способность оценить результат и объяснить решение, не знание
   каждого правила. Развёрнутая модель — в Obsidian vault архитектора:
   `knowledge/Understanding_Depth_Boundary.md` (два концепта: понимание как вершина иерархии;
   вайб-кодинг = не владеешь решениями + не способен заметить отклонение; четыре вопроса перед
   погружением; «экспертиза по доверенности» для слабых зон).

> **Смежное (API-конвенция, не skill-политика):** *resource-oriented дизайн REST — дефолт,
> не догма* (где ресурсная модель переусложняет, идём action-эндпоинтами в стиле Google AIP
> custom methods). Это решение проекта → переезжает в `conventions.md` через feat-002, здесь
> только ссылка.

## Скиллы по доменам — детали, статусы, контекст

### REST API design — `api-design-principles`
- **Статус:** ✅ Изучён (принят) — [x] изучён · **Источник:** в репо `.claude/skills/api-design-principles/` · **Slice:** feat-002
- **Решение архитектора:** **берём полноценно.** Resource-oriented дизайн — правильный
  дефолт; где ресурсная модель переусложняет (auth-флоу, запуск/стриминг агента, отдельные
  security/admin-операции) — идём action-эндпоинтами, как делает Google (AIP custom methods).
  Не догматизируем ресурсы на честных действиях.
- **Суть скилла:** полноценный гайд по контрактам API (REST + GraphQL). Ядро —
  resource-oriented: ресурсы-существительные, семантика HTTP-методов, идемпотентность,
  статус-коды. Далее: версионирование, пагинация (offset/cursor), формат ошибок, HATEOAS;
  GraphQL — schema-first, DataLoader против N+1. Есть чеклист (`assets/api-design-checklist.md`)
  и FastAPI-каркас (`assets/rest-api-template.py`).
- **Границы / оговорка:** формат ошибок в скилле самодельный, не RFC 9457 — одна неидеальность
  на фоне годного гайда, ей жертвуем (RFC 9457 кодифицируем сами в feat-002). Не покрывает auth
  вглубь, streaming/SSE, реализацию rate-limit.
- **Привязка:** main app — `backend/app/api/` (`routes/` + `schemas/`), ~12 модулей, ~50
  эндпоинтов. SIEM — `services/siem-service/siem_service/api/routes.py`, 10 эндпоинтов, **уже
  зрелый REST** (плюральные ресурсы, `PaginatedXResponse`, 201/204, PATCH) — эталон для main app.

### PostgreSQL / DB — `postgresql`
- **Статус:** ✅ Изучён (принят) — [x] изучён · **Источник:** в репо `.claude/skills/postgresql/` · **Slice:** feat-003
- **Решение архитектора:** **берём** — хороший реализационный скилл, рефакторим по нему и
  прогоняем будущие правки. Логическое проектирование в скилле буквально одной строкой —
  отдельного скилла под логику охота не дала, **логику/доменную модель проектируем сами**.
- **Суть скилла:** перекос в реализацию под движок (~90%): типы колонок (`BIGINT IDENTITY`/
  `UUID`, `TIMESTAMPTZ`, `NUMERIC` для денег, JSONB, массивы), индексы (B-tree/partial/covering/
  GIN/GiST/BRIN), constraints (PK/FK/UNIQUE/CHECK, ловушка «FK не индексируются автоматически»),
  партиционирование, RLS, PG-грабли (MVCC/dead tuples, NULL в UNIQUE, TOAST). Логика — одно
  правило «3NF + денормализация по измеренному ROI».
- **Границы:** нет ORM-специфики (SQLAlchemy 2.x async, Alembic) — закрываем внешним
  `sqlalchemy-alembic-expert` (см. охоту) и своими паттернами.
- **Привязка:** `backend/app/models/` (~10 файлов, 8 таблиц), `backend/app/repositories/`,
  `backend/alembic/versions/` (~5 ревизий); SIEM `repositories.py`. Масштаб небольшой.

### FastAPI — `fastapi`
- **Статус:** ✅ Изучён (принят) — [x] изучён · **Источник:** в репо `.claude/skills/fastapi/` · **Slice:** feat-004
- **Решение архитектора:** **однозначно берём.** Официальный скилл от авторов FastAPI. Ключевая
  формулировка ценности (итог разбора «can't fight gradient descent»): **ядро скилла — не
  оптимизации, а предохранители**. Правила делятся на три корзины:
  - *Семантика/безопасность* (ради неё скилл и держим): async vs sync (блокирующий вызов в
    `async def` останавливает event loop — при нашем SSE-ядре это вешает стримы всех
    пользователей; нейронки рефлекторно лепят `async def` на всё — здесь training prior ведёт
    в инцидент); return type / `response_model` как фильтр утечки internal-полей; `yield`+`scope`
    для корректного lifecycle ресурсов.
  - *Anti-rot*: запреты deprecated (`ORJSONResponse`, `RootModel`, Ellipsis) — без них код
    ломается при будущих апгрейдах фреймворка.
  - *Косметика* (Annotated-синтаксис, prefix/tags на роутере): прирост минимальный, едет
    паровозом, отдельной цены не имеет.
- **Роль скилла — стабилизатор против регрессии, а не двигатель миграции.** Проверка по коду
  (греп, 2026-06-09): база **уже на новом каноне** — ноль `= Depends(` как дефолт, `deps.py` на
  `Annotated`, ноль `RootModel`/`ORJSONResponse`/`Field(...)`. Без скилла каждая новая фича от
  нейронки тянула бы старый стиль из training data → микс двух стилей, который хуже обоих.
  Найдено одно отличие: **SSE на самодельном `StreamingResponse`** (`api/routes/messages.py`)
  вместо нативного `fastapi.sse.EventSourceResponse` — кандидат на рассмотрение в feat-004, не срочно.
- **Инсайт архитектора:** ценность скилла ещё и в том, что правила лежат **в файле, а не «в
  голове нейронки»** — это отдельный артефакт, по которому потом можно ревьюить код
  (чек-лист для reviewer'а), а не только генерировать.
- **Суть скилла:** уровень хендлеров. Depends (`Annotated[T, Depends]`, `yield`+`scope` для
  cleanup, провайдер-функции), Pydantic v2 (response_model, `Field(gt=0)`, `TypeAdapter` вместо
  `RootModel`, запрет `ORJSONResponse`), async (`async def` vs `def`, threadpool), streaming
  (SSE `EventSourceResponse`), роутинг (`APIRouter(prefix=, tags=)`), тулинг (uv, Ruff, ty).
- **Границы (важно):** **не покрывает инфраструктуру** — `lifespan`, `app.state`,
  `Settings(BaseSettings)`, middleware, exception handlers, тесты. Плюс советует SQLModel
  (у нас raw SQLAlchemy async). Инфраслой кодифицируем сами в feat-004 (см. «Пробелы»).
- **Привязка:** `backend/app/{main.py,config.py,infra/,services/}`; SIEM аналогично. Обе службы
  плотно на `lifespan` + `app.state` + `BaseSettings` — ровно то, чего в скилле нет.

### Frontend архитектура — `feature-sliced-design` + `react-state-management`
- **`feature-sliced-design`** — **Статус:** ✅ Изучён (принят) — [x] изучён · **Источник:** в репо
  `.claude/skills/feature-sliced-design/` (одна папка: SKILL.md 483 строки + 7 conditional references) · **Slice:** feat-006
  - **Решение архитектора:** **берём, вопросов нет.** Закрывает структурную ось фронта.
    Сильнейшая часть — **decision framework** («куда класть код», золотое правило: сомневаешься —
    оставь в pages) и неожиданная анти-оверинжиниринговая тональность: «Start simple, extract when
    needed», запрет пустых слоёв «на вырост», консерватизм по entities (CRUD → `shared/api`,
    auth → `shared/auth`). С этим скиллом + Steiger агент проектирует размещение кода по дереву
    решений, а не по наитию — ожидание «не будет большого комка грязи» обоснованно.
  - **Про объём (3100 строк):** ядро — 483 строки SKILL.md; остальное — conditional references
    (перебор кейсов × фреймворков: Next.js/Nuxt/Vite/Astro-интеграции, миграции, примеры
    Redux/TanStack Query). Эффективная загрузка в задаче — SKILL.md + максимум один reference
    (~700–900 строк); скилл сам запрещает предзагрузку references. Образцовое progressive disclosure.
  - **Steiger** (официальный FSD-линтер, правила `insignificant-slice`/`excessive-slicing`) —
    кандидат на enforcement фронта в **feat-008**.
  - **Findings прогона нашего `frontend/src` против правил скилла (входной материал feat-006, не чиним сейчас):**
    1. Нет слоя `pages/` — `features/` главный. Наша SPA чат-центрична (по сути один экран),
       наши features ближе к «секциям страницы». Главный архитектурный вопрос feat-006: нужен ли
       pages/ или наша адаптация легитимна (скилл разрешает адаптировать строгость).
    2. Публичных API нет совсем: ноль `index.ts` в features/shared; все 16 межслайсовых импортов
       лезут вглубь чужих слайсов.
    3. Кросс-импорты одного слоя: `chat → settings` (2), `chat → projects` (1) — разруливать по
       стратегиям A–D из скилла.
    4. Внеметодные топ-уровни `stores/` (Zustand) и `types/` — по FSD состояние живёт в
       `model/`-сегментах слайсов.
    5. Технические имена файлов: `shared/lib/utils.ts`, `shared/api/types.ts` (нарушение правила 4-4).
    6. Дубль `shared/components` vs `shared/ui` — разобраться, что где.
  - **Фундамент совпадает** — перелопачивать через колено не придётся, доводка мелко-средняя.
- **`react-state-management`** — **Статус:** ⛔ Не берём (изучён) — [x] изучён · **Источник:**
  `wshobson/agents` → `plugins/frontend-mobile-development/skills/react-state-management`
  (в репо НЕ копируем — правило для отклонённых) · **Slice:** feat-006 (cherry-pick идей)
  - **Решение архитектора:** **целиком as is не берём.** Причины: ~40% мёртвого веса
    (Redux Toolkit, Jotai, миграция с легаси-Redux — у нас Zustand 5 + TanStack Query 5, выбор
    сделан навсегда); жанр «выбери инструмент из четырёх» при уже сделанном выборе; небрежное
    качество — quick-start пример нарушает собственные best practices скилла (деструктуризация
    всего стора без селектора, серверный `user` в Zustand). Самый слабый из внешних кандидатов.
  - **Ценное ядро переиспользуем** — допишем в конвенции feat-006 и/или сформулируем в свой
    скилл, когда дойдём:
    1. **Таксономия категорий состояния** и правило не смешивать: серверное → только TanStack
       Query, клиентское UI → Zustand, производное вычисляем, не храним.
    2. **Don'ts как анти-регрессия:** не дублировать серверное состояние в сторе; подписки
       через селекторы (не деструктурировать весь стор); не over-глобализировать.
    3. **TanStack Query паттерны:** фабрика query keys (иерархические ключи под точечную
       инвалидацию), `staleTime`/`gcTime`, `enabled` для условных запросов, optimistic update
       с откатом (`onMutate`/`onError`/`onSettled`).
  - **Чего в скилле всё равно не было** (наши вопросы остаются нашими): стриминговое состояние
    (наш `stream-store` под SSE), стратегия инвалидации между сущностями после мутаций.
  - **Сверка с кодбазой:** мы уже на целевой двухосевой архитектуре — 2 честно клиентских
    Zustand-стора (`stream-store`, `ui-store`) + TanStack Query во всех features. Проверка
    качества query keys / optimistic updates — материал feat-006.
- **Итого по фронту — 1 скилл (`feature-sliced-design`).** Ось состояния закрываем не скиллом,
  а конвенцией feat-006 (ядро из react-state-management выше). Отдельный React/TS-арх-скилл
  не нужен. Глубокий TanStack-Query-скилл — опционально, только если Query станет несущей.
