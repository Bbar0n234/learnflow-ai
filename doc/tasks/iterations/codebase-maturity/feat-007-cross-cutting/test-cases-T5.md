# Тест-кейсы — T5: Frontend error handling (обвязка)

Итерация feat-007 (cross-cutting error handling), трек T5. Ручные тест-кейсы на **целевое** поведение после реализации трека. Источники: `plan-T5.md`, `decisions.md` (D-ERR-8/9/11, OQ-F), `audit-raw-06-frontend.md`, `conventions.md` § Обработка ошибок → Frontend (строка 349) + § Frontend.

**Frontend e2e-инфра ещё нет** (feat-009). Здесь — ручные кейсы; точечный автотест указан там, где он удобнее ручного (чистая функция-парсер). Браузерные кейсы помечены `👤` — их прогоняет независимый агент-тестировщик в реальном UI.

**Слои.**
- **Layer 0** — статический gate: `make check-fe` (ESLint + Prettier --check) проходит.
- **Layer 1** — модульная логика без браузера: парсер problem+json (детерминированная функция, edge-cases) и предикат ретраев QueryClient. Проверяется точечным автотестом или ручным вызовом в dev-консоли.
- **Layer 2 / 👤** — наблюдаемое поведение в браузере: осмысленное RU-сообщение вместо сырья, различение категорий ошибок, честный error-state по таймауту, устойчивость SSE к битому кадру, откат оптимистичного лайка.

**Как симулировать ошибки в Layer 2.** Где не сказано иначе — через DevTools Network (request blocking, throttling «Offline»/искусственная задержка) либо подменой ответа backend (остановить сервис, временно вернуть нужный статус). Точные RU-формулировки сверять с реализацией `api-error.ts` (детали могут отличаться по словам — проверяем смысл и категорию, а не дословность).

## Layer 1 — парсер problem+json и предикат ретраев

Кейсы T5.2–T5.10 проверяют чистую функцию `getApiErrorMessage(error: unknown): string` (и адаптер по телу для fetch-ветки SSE). Удобнее точечным автотестом (vitest) или вызовом в dev-консоли; браузер не нужен.

**{T5.2}** · Layer 1 · _Предусловие:_ парсер реализован. · _Шаги:_ передать `AxiosError` с `response.status = 422` и телом `{ type, title: "Validation failed", detail: "Имя правила уже занято", status: 422 }`. · _Ожидаемо:_ возвращается `detail` («Имя правила уже занято») — `detail` имеет приоритет над `title` и над категорией.

**{T5.3}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ `AxiosError`, `status = 409`, тело `{ title: "Conflict", status: 409 }` (без `detail`). · _Ожидаемо:_ возвращается `title` («Conflict») — fallback на `title`, когда нет `detail`.

**{T5.4}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ `AxiosError`, `status = 500`, тело `{}` или отсутствует `detail`/`title`. · _Ожидаемо:_ категорийное RU-сообщение для 5xx («Ошибка сервера, попробуйте позже»), **не** «HTTP 500», **не** `error.message` («Request failed with status code 500»).

**{T5.5}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ по очереди `AxiosError` со статусами 401, 403, 404, 409, 422 и пустым телом. · _Ожидаемо:_ каждый статус даёт свою категорию на русском: 401/403 → «Недостаточно прав / требуется вход»; 404 → «Не найдено»; 409 → «Конфликт…»; 422 → «Некорректные данные». Категории различимы между собой.

**{T5.6}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ `AxiosError` без `response` (сетевой сбой/CORS), `code` не `ECONNABORTED`. · _Ожидаемо:_ «Сервер недоступен, попробуйте позже» — ветка «нет ответа сервера».

**{T5.7}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ `AxiosError` с `code === "ECONNABORTED"` (таймаут axios), без `response`. · _Ожидаемо:_ «Превышено время ожидания» — таймаут отличается от обычной недоступности сети.

**{T5.8}** · Layer 1 · _Предусловие:_ то же (edge — не-JSON / пустое тело). · _Шаги:_ (а) `AxiosError` со `status = 502` и телом — строкой HTML («Bad Gateway», не problem+json); (б) `status = 503`, тело `null`/пустая строка. · _Ожидаемо:_ парсер не падает, не отдаёт сырой HTML/строку наружу; возвращает категорийное RU-сообщение по статусу (5xx). Type guard на `{ detail?, title? }` корректно отсекает не-объектное тело.

**{T5.9}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ передать (а) обычный `Error("boom")`; (б) строку; (в) `undefined`/`null`. · _Ожидаемо:_ во всех случаях — общий RU-генерик; **никогда** не утекает `error.message` («boom») и не возвращается пустая строка.

**{T5.10}** · Layer 1 · _Предусловие:_ адаптер для fetch-ветки SSE реализован (`getProblemMessageFromBody(status, body)` или эквивалент). · _Шаги:_ вызвать с (а) `status = 422`, body `{ detail: "Сообщение нарушает политику" }` → ожидается `detail`; (б) `status = 500`, body `{}` → категорийное 5xx RU; (в) `status = 503`, body — невалидный JSON/прочитать не удалось → категорийное RU без падения. · _Ожидаемо:_ та же логика приоритетов detail→title→категория, что и `getApiErrorMessage`; общий код переиспользуется, ветки не расходятся.

**{T5.11}** · Layer 1 · _Предусловие:_ дефолты `QueryClient` реализованы (`QueryProvider.tsx`). · _Шаги:_ вычислить предикат `defaultOptions.queries.retry` для: (а) `AxiosError` со `status` 400/403/404/422 → должен вернуть `false` сразу; (б) `AxiosError` со `status = 503` при `failureCount = 0,1` → `true`, при `failureCount = 2` → `false`; (в) сетевая ошибка без `response` → bounded (как 5xx, `failureCount < 2`). · _Ожидаемо:_ 4xx не ретраится ни разу; 5xx/сеть ретраятся ограниченно (≤2, согласовано с backend `max_retries=2`). Проверка через unit-вызов предиката либо наблюдением в T5.16.

**{T5.12}** · Layer 1 · _Предусловие:_ то же. · _Шаги:_ проверить `defaultOptions.mutations.retry`. · _Ожидаемо:_ `false` — мутации не ретраятся (побочные эффекты не повторяем).

## Layer 2 / 👤 — поведение в браузере

**{T5.13}** · Layer 2 · `👤` · _Предусловие:_ приложение запущено, пользователь авторизован, страница `/security` (Security Rules). · _Шаги:_ заставить backend вернуть 5xx на загрузку правил (остановить/замокать сервис), открыть страницу. · _Ожидаемо:_ error-блок показывает осмысленное RU-сообщение (категорийное «Ошибка сервера…» или серверный `detail`), **не** «Request failed with status code 500», **не** «Unknown error», **не** «HTTP 500». То же для SecurityAlerts и SecurityEvents.

**{T5.14}** · Layer 2 · `👤` · _Предусловие:_ форма входа (AuthGate), backend поднят. · _Шаги:_ ввести неверный пароль, отправить. · _Ожидаемо:_ показано серверное RU-`detail` (например «Неверный логин или пароль»), а не «Something went wrong». Ручной семиуровневый разбор `err.response.data.detail` заменён единым парсером — сообщение приходит из него.

**{T5.15}** · Layer 2 · `👤` · _Предусловие:_ модалка «Новый проект» открыта; существует проект с именем X (или backend вернёт 409 на дубликат). · _Шаги:_ создать проект с именем X. · _Ожидаемо:_ внутри модалки появляется инлайн-сообщение об ошибке (RU `detail`/категория «Конфликт…»); модалка **не зависает** и не закрывается молча, нет unhandled rejection в консоли. После исправления имени создание проходит.

**{T5.16}** · Layer 2 · `👤` · _Предусловие:_ открыты DevTools → Network. · _Шаги:_ (а) вызвать запрос, который backend завершит 404/422 (например операция над несуществующим ресурсом); посчитать число попыток в Network. (б) Вызвать запрос, дающий 503; посчитать попытки. · _Ожидаемо:_ (а) 4xx — ровно одна попытка, без 3× ретраев; (б) 5xx — ограниченные ретраи (исходный + до 2 повторов), затем error-state. Подтверждает T5.11 на живом стеке.

**{T5.17}** · Layer 2 · `👤` · _Предусловие:_ диалоги rename и delete проекта (ProjectActions); backend вернёт 409/403 на операцию. · _Шаги:_ переименовать проект в конфликтное имя; затем попытаться удалить проект, на который нет прав (или замокать 403). · _Ожидаемо:_ в соответствующем диалоге появляется инлайн-RU-сообщение (различимы «Конфликт…» для 409 и «Недостаточно прав…» для 403); диалог не остаётся молча открытым без обратной связи. Без тоста — инлайн.

**{T5.18}** · Layer 2 · `👤` · _Предусловие:_ форма MCP-сервера (MCPServerForm); backend вернёт не-security ошибку (дубликат имени → 409, невалидный URL → 422, или 5xx). · _Шаги:_ сохранить сервер, провоцируя такую ошибку. · _Ожидаемо:_ показано RU-сообщение парсера для не-security ошибки (раньше глоталось — рендерился только `isSecurityViolation`). _Контроль регрессии:_ при настоящем security-violation (422 c `type=urn:learnflow:security-policy-violation`) по-прежнему показывается `SECURITY_VIOLATION_MESSAGE`, а не общая категория.

**{T5.19}** · Layer 2 · `👤` · _Предусловие:_ чат; backend вернёт `!ok` (например 500 или 422 с problem+json) **до** первого SSE-байта при отправке сообщения. · _Шаги:_ отправить сообщение, backend отвечает ошибочным статусом с телом problem+json. · _Ожидаемо:_ пользователю показан серверный `detail`/категорийное RU-сообщение, а не «HTTP 500». Стрим корректно завершается (спиннер/состояние стрима снимается).

**{T5.20}** · Layer 2 · `👤` (таймаут apiClient) · _Предусловие:_ `VITE_API_TIMEOUT_MS` задан (умеренное значение для теста), backend искусственно «висит» (не отвечает) на обычный REST-запрос — например через Network throttling или паузу на сервере. · _Шаги:_ инициировать такой запрос (загрузка списка/мутация). · _Ожидаемо:_ по истечении таймаута запрос завершается ошибкой (axios `ECONNABORTED`) → честный error-state с RU «Превышено время ожидания»; **нет вечного спиннера**.

**{T5.21}** · Layer 2 · `👤` (таймаут siemClient) · _Предусловие:_ то же, но для security-страниц, которые ходят через `siemClient` (`shared/api/security.ts`). · _Шаги:_ открыть security-страницу при «висящем» SIEM-backend. · _Ожидаемо:_ тот же честный таймаут-error-state, не вечный спиннер. Подтверждает дрейф-фикс: `siemClient` получил `timeout` из той же `VITE_API_TIMEOUT_MS`, что и `apiClient`.

**{T5.22}** · Layer 2 · `👤` (SSE first-byte timeout) · _Предусловие:_ first-byte timeout для SSE реализован (`VITE_SSE_FIRST_BYTE_TIMEOUT_MS` либо переиспользование `VITE_API_TIMEOUT_MS`); backend принимает POST на стрим, но долго не отдаёт первый чанк. · _Шаги:_ отправить сообщение в чат; backend держит соединение без первого байта дольше таймаута. · _Ожидаемо:_ по истечении таймаута стрим прерывается (`controller.abort()`), показывается RU error-сообщение через парсер; **нет бесконечного ожидания**. _Контроль:_ при нормальном стриме (первый байт приходит вовремя) таймер снимается и текст течёт без прерывания.

**{T5.23}** · Layer 2 · `👤` (битый SSE-кадр) · _Предусловие:_ возможность вставить в SSE-поток один невалидный `data:`-кадр (не-JSON) между валидными `text_chunk` — через тестовый эндпоинт/прокси/мок. · _Шаги:_ запустить стрим, в середине которого приходит битый кадр, после него — ещё валидные кадры и `done`. · _Ожидаемо:_ битый кадр пропускается (логируется `logger.warn`), **весь стрим не падает**: уже полученный текст сохраняется, последующие валидные кадры обрабатываются, `done` доходит. Раньше `JSON.parse` бросал → внешний catch ронял стрим с потерей текста.

**{T5.24}** · Layer 2 · `👤` (откат оптимистичного лайка, фаза 6 — если включена) · _Предусловие:_ сообщение ассистента с кнопками feedback (FeedbackButtons); backend вернёт ошибку на запрос feedback. · _Шаги:_ нажать «лайк», backend отвечает ошибкой. · _Ожидаемо:_ подсветка кнопки **откатывается** к предыдущему значению (UI снова синхронен с сервером), ошибка залогирована. Без отката кнопка осталась бы подсвеченной при несохранённом на сервере состоянии. _Если фаза 6 в backlog — кейс пропускается._

**{T5.25}** · Layer 2 · `👤` (нормализация языка, фаза 7) · _Предусловие:_ приложение запущено. · _Шаги:_ спровоцировать: (а) валидацию пароля в AuthGate (короткий пароль, несовпадение паролей); (б) обрыв SSE-соединения (раньше «Connection lost»/«Connection error»); (в) ErrorBoundary (бросить ошибку рендера), error-states ChatView и ProjectList. · _Ожидаемо:_ во всех перечисленных местах сообщения об ошибке на русском, без вкраплений английского. UI-лейблы вне ошибок (заголовки диалогов, кнопки) — вне скоупа, не проверяем.

## Gate (итог)

Трек T5 считается прошедшим тест-кейсы, когда:
- **{T5.1}** — `make check-fe` зелёный.
- **Layer 1 ({T5.2}–{T5.12})** — парсер даёт верное сообщение/категорию во всех ветках, включая edge (пустое/не-JSON тело, не-Axios ошибка); адаптер fetch-ветки переиспользует ту же логику; предикат ретраев не ретраит 4xx и ограничивает 5xx/сеть; мутации не ретраятся.
- **Layer 2 ({T5.13}–{T5.25})** — в браузере ошибки показываются осмысленным RU-текстом (не «HTTP 500»/«Request failed»/«Something went wrong»); категории 403/409/422/5xx различимы; зависший REST-запрос (apiClient и siemClient) и зависший SSE-first-byte дают честный таймаут-error-state, а не вечный спиннер; битый SSE-кадр не рвёт стрим; оптимистичный лайк откатывается; язык сообщений русский.

Кейсы T5.24 (фаза 6) и частично T5.22 (отдельная vs общая env) зависят от резолюций Open Questions плана — прогонять по фактической реализации.
