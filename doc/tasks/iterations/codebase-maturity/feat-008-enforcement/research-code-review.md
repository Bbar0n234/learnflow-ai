# Research: фундаментальные принципы code review (питание для режима A)

## Назначение и контекст

Документ собирает базу принципов code review из зрелых инструментов и классических
инженерных гайдов, чтобы спроектировать промпт **LLM-ревьюера режима A** — «хорош ли код
сам по себе»: баги, корректность, читаемость, сложность, мёртвый код, нейминг,
безопасность — суждение о коде безотносительно проектных конвенций. Параллельно документ
проводит границу «что отдать детерминированному чекеру (линтеры / import-linter / AST), а
что — LLM-ревьюеру», поскольку всё, что детерминированно ловится, не должно засорять
бюджет внимания и контекст LLM.

Метод: разобраны 13 источников — вендорские AI-ревьюеры (Anthropic Claude Code, OpenAI
Codex, GitHub Copilot, CodeRabbit, Greptile, Cursor BugBot, Qodo), детерминированная
статика (SonarQube, Semgrep, OSS-линтеры), канонический инженерный гайд (Google
eng-practices), стандарт разметки комментариев (Conventional Comments) и community-коллекция
ревью-промптов (Awesome Reviewers). По каждому утверждению ниже помечено, это **консенсус**
(встречается у ≥3 независимых источников) или **частное** решение конкретного вендора.

## 1. Классический инженерный чек-лист — Google eng-practices

Это эталон, на который ссылается почти вся индустрия. «What to look for in a code review»
даёт ровно тот набор смысловых категорий, который нужен режиму A, и явно отделяет их от
стиля (стиль = style guide = детерминированная зона).

Категории Google (в порядке приоритета, как у них):

1. **Design** — самое важное. Имеют ли смысл взаимодействия частей кода; на месте ли
   изменение; хорошо ли интегрируется с системой. *(Это пограничная категория: «архитектурная
   нетривиальность» уходит в режим B, но «локальный дизайн функции/класса» — режим A.)*
2. **Functionality** — делает ли код то, что задумано, и хорошо ли это для пользователей
   (и конечных, и разработчиков-потребителей кода). Явно требуют думать про **edge cases,
   concurrency-проблемы (deadlocks, race conditions)** — их «очень трудно поймать прогоном,
   нужно вычитывать».
3. **Complexity** — сложнее ли код, чем нужно. Определение: *«нельзя быстро понять
   читателю»* либо *«разработчики, скорее всего, внесут баги, когда будут вызывать/менять
   этот код»*. Отдельно выделяют **over-engineering** — обобщённость и функциональность «на
   будущее», которой сейчас не нужно. Ревьюер обязан давить спекулятивную обобщённость.
4. **Tests** — есть ли адекватные unit/integration/e2e; корректны ли тесты; **упадут ли они,
   когда код сломается**; не дают ли ложных срабатываний; просты ли ассерты. Тесты — тоже код,
   сложность в них не оправдана.
5. **Naming** — достаточно ли длинное имя, чтобы полностью передать суть, но не настолько,
   чтобы стать нечитаемым.
6. **Comments** — ясные ли; **объясняют ли «почему», а не «что»**. Если код не самоочевиден —
   упрощать код, а не комментировать. Исключения: regex, сложные алгоритмы.
7. **Style / Consistency** — соответствие style guide. **Явно: чисто стилевое и
   форматирование — зона style guide; нитпики помечать «Nit:» и не блокировать ими.** Это
   формальное признание границы «стиль → автоматика».
8. **Documentation** — обновлены ли README / справочники, если изменился способ сборки/
   использования/релиза.
9. **Every Line / Context** — вычитывать каждую строку (кроме сгенерированного/данных);
   смотреть изменение в контексте файла и системы целиком.

Из «The Standard of Code Review» — два принципа, важных для калибровки промпта:

- **Senior-принцип:** одобрять, как только изменение «определённо улучшает общее здоровье
  кода», даже если не идеально. *«Perfect» кода не бывает, есть только «better».* Ревьюер
  ищет непрерывное улучшение, а не полировку каждой мелочи. → Для LLM это прямая команда **не
  раздувать нитпики** и не блокировать на вкусовщине.
- **Иерархия авторитета:** технические факты > мнения; в вопросах стиля абсолют — style guide;
  аспекты дизайна почти никогда не «чистый вкус», их взвешивают по инженерным принципам. → Для
  режима A: суждение о дизайне допустимо и нужно, но должно опираться на принцип, а не на
  предпочтение.

## 2. AI-ревьюеры вендоров: какие классы проблем и как устроены

### Anthropic Claude Code (`/review`, GitHub Code Review)

Самый релевантный нам ориентир, т.к. это та же модельная архитектура.

- **Архитектура:** «флот специализированных агентов», **каждый агент ищет свой класс
  проблем**, параллельно по диффу и окружающему коду; затем **шаг верификации сверяет
  кандидатов с реальным поведением кода, отсеивая false positives**; результаты дедуплицируются
  и ранжируются по severity. → Прямой паттерн для нашего дизайна: один режим = один
  когнитивный фокус + отдельная верификация против false positives.
- **Что проверяет по умолчанию:** *«фокус на correctness: баги, которые сломают прод, а не
  форматирование и не покрытие тестами»*. Ищет logic errors, security vulnerabilities, broken
  edge cases, subtle regressions. → Дефолт вендора — **correctness-first, стиль/тесты вне
  дефолта** (консенсус с Greptile/BugBot/Codex).
- **Severity (3 уровня):** 🔴 Important (баг, чинить до мержа) / 🟡 Nit (мелочь, не блокирует) /
  🟣 Pre-existing (баг уже был в коде, не внесён этим PR). Машиночитаемый счётчик
  `{"normal": N, "nit": N, "pre_existing": N}` для гейтинга в CI.
- **Калибровка через файлы:** `CLAUDE.md` читается как контекст, **нарушения проектных правил
  флагуются как nit** (не Important). `REVIEW.md` — ревью-онли инструкции наивысшего приоритета,
  ими переопределяют что считать Important, кап на число нитов, skip-правила, **verification
  bar** («claims про поведение требуют `file:line`-цитаты, а не вывода из имени»), правила
  ре-ревью («после первого прохода — только Important»). → Ровно наша граница режим A (дефолтный
  correctness) vs режим B (`CLAUDE.md`-конвенции как nit-слой).
- Локально: `/code-review` с уровнями effort (low → fewer high-confidence findings; high→max →
  шире охват, больше неуверенных). → Бюджет находок управляется явно.

### OpenAI Codex (`@codex review`)

- Позиционируется как «ещё один high-signal проход». **В GitHub флагует только P0 и P1** —
  самые высокоприоритетные риски, чтобы комментарии оставались сфокусированными. → Самая
  узкая severity-модель (2 уровня, priority-семантика).
- Review guidelines живут в `AGENTS.md` (наш аналог — `CLAUDE.md`), применяется ближайший к
  изменённому файлу. Пример правил: «не логировать PII», «проверить, что auth-middleware
  оборачивает каждый роут» — это уже режим B / security.

### GitHub Copilot code review

- «Ревью с нескольких углов»; effort levels **Low** (быстрый, common issues: bugs, security
  vulnerabilities, style inconsistencies) и **Medium** (higher-reasoning модель для сложной
  логики, security-sensitive и cross-service изменений).
- **Excluded files** (показательно для границы): dependency-манифесты (`package.json`,
  `Gemfile.lock`), лог-файлы, SVG — их не ревьюят. → Машинно-генерируемое/данные исключаются из
  LLM-прохода (консенсус с Google «every line кроме сгенерированного» и Claude `REVIEW.md`
  skip-rules).

### CodeRabbit

- **Гибрид:** собственный LLM-ревью + интеграция **40–50+ OSS-линтеров и SAST-сканеров**. То
  есть детерминированную зону вендор сознательно делегирует линтерам, а LLM оставляет
  семантику. (Greptile/Sourcegraph критикуют CodeRabbit за слабость на cross-file багах — он в
  основном видит дифф + узкое окно.)
- **Двухосная модель находок** (полезно как образец):
  - *Типы:* ⚠️ Potential issue (баг/уязвимость/проблемный паттерн) · 🛠️ Refactor suggestion
    (maintainability/perf/best practice) · 🧹 Nitpick (стиль/формат, только в Assertive-режиме).
  - *Severity (5 уровней):* 🔴 Critical · 🟠 Major · 🟡 Minor · 🔵 Trivial · ⚪ Info.

### Greptile (full-codebase context review)

- Чёткая формулировка ценности и границы: *«built to catch real bugs, broken assumptions, and
  production-impacting issues, **not style nits or formatting problems better handled by
  linters**»*. Прямо называет себя **комплементом, а не заменой SAST, secrets-сканеров и
  линтеров**.
- Уникальная ценность LLM — **баги «в швах» между файлами/сервисами/общими зависимостями,
  невидимые из одного диффа** (зависят от вызывающих, shared-модулей, внутренних API,
  допущений вне диффа). → Это и есть то, что нельзя отдать детерминированной статике.
- Метрика №1 — **signal-to-noise**, триаж по severity.

### Cursor BugBot

- Multi-pass review; **по умолчанию отфильтровывает style nits**, держит объём комментариев на
  функциональных проблемах. → Ещё один голос за «correctness-first, стиль глушим».

### Qodo

- Multi-agent: **severity-categorized фидбэк от отдельных агентов под bug detection, security,
  code quality, test coverage** (та же «агент-на-класс» архитектура, что у Claude Code).
  Governance-first: силён после настройки правил (ближе к режиму B).

**Консенсус по AI-ревьюерам:** (1) дефолт — correctness/logic-баги и security, **не**
форматирование; (2) стиль и известные паттерны делегируются линтерам/SAST; (3) главная
ценность LLM — контекстные, cross-file, semantic-находки; (4) ключевая метрика —
signal-to-noise / доля false positives; (5) зрелые системы строятся как **набор
узко-сфокусированных агентов + шаг верификации** (Claude Code, Qodo) — это аргумент за наш
двухрежимный раздельный дизайн.

## 3. Детерминированная зона: что индустрия отдаёт статике

Самая ясная артикуляция — из обзора Sourcegraph «13 Best Automated Code Review Tools (2026)»:

> **Rule-based static analysis** парсит код, строит синтаксическое/семантическое
> представление и матчит против правил, data-flow и policy-паттернов. Силён на
> **детерминированных находках: security issues, duplication, complexity, style violations,
> policy checks**. Здесь живут SonarQube, Semgrep, OSS-линтеры (ESLint, Pylint, RuboCop, PMD).
> Вывод детерминированный — поэтому это правильный субстрат для **compliance-гейтов**.
>
> **AI-powered review** шлёт дифф (+ окружающий контекст) LLM-агенту, который даёт
> **semantic feedback**: *«эта функция молча глотает timeout-ошибку, на которую полагаются два
> вызывающих»*, а не *«missing return type»*. Ловит контекст-зависимое, что простые
> lint-правила пропускают; но более вариативен и хуже годится как жёсткий compliance-гейт.
>
> Большинство команд **комбинируют**: статика для high-confidence гейтов + AI для раннего
> контекстного фидбэка.

Конкретика по детерминированным инструментам:

- **SonarQube** — code smells, vulnerabilities, duplication, **complexity-метрики**, quality
  gates; 40+ языков; жёсткое enforcement в CI. Дефолтные правила «генерируют шум без
  per-team-настройки» — урок: детерминированные метрики тоже надо калибровать.
- **Semgrep / Snyk Code** — кастомные security-правила, SAST/SCA-политики.
- **OSS-линтеры (ESLint, Pylint/Ruff, RuboCop)** — per-language style и bug-rules, бесплатно,
  детерминированно.
- **Reviewdog** — клей, постящий вывод любого линтера как PR-комментарии.

**Вывод для нашей границы.** Детерминированной зоне (линтеры / import-linter / AST / форматтеры)
отдаём всё, что выразимо правилом и проверяемо без понимания намерения:

- форматирование, whitespace, чисто стилевые конвенции (Ruff/Prettier);
- import-правила и слоевые границы (import-linter — наш `PLC0415`, FSD-границы);
- complexity-метрики как **порог** (cyclomatic/cognitive, длина функции) — *число* считает
  статика; *«а оправдана ли эта сложность»* — уже LLM;
- дублирование, мёртвые импорты/переменные (линтер ловит синтаксический dead code);
- известные security-паттерны и хардкод-секреты (SAST / secrets-scan);
- наличие type-аннотаций, базовые typing-нарушения (mypy);
- запрет конкретных API/вызовов (Semgrep-правило).

LLM-ревьюеру (режим A) оставляем то, что требует понимания намерения и поведения:

- логические баги, неверные инварианты, ошибки в edge cases;
- concurrency: race conditions, deadlocks (Google и Claude явно — это вычитка, не прогон);
- **семантический** мёртвый код (недостижимая ветка по смыслу, переменная-результат, который
  игнорируется) — то, что синтаксически живо, но бессмысленно;
- качество нейминга (передаёт ли имя суть — оценка смысла, не паттерна);
- читаемость *намерения*: понятно ли, *зачем* код, а не только *что* он делает;
- оправданность сложности и over-engineering (метрику дал линтер — суждение даёт LLM);
- cross-file/cross-service последствия, нарушенные допущения вызывающих;
- комментарии: объясняют «почему», не врут, не устарели;
- контекстная безопасность (логирование PII, нескоупленные запросы) — поведенческая, не
  чисто паттерновая.

Эвристика-формулировка: **детерминировано всё, для чего достаточно увидеть форму кода; LLM —
всё, для чего нужно понять смысл и поведение кода.**

## 5. Выжимка для режима A — каркас чек-листа фундаментального качества

Готовый скелет для промпта режима A. Порядок = приоритет (correctness вперёд, вкусовщина в
конце), категории взяты из консенсуса Google + Claude + Greptile, очищены от того, что ловит
детерминированный чекер.

**A. Корректность и поведение (ядро, высший приоритет)**
- Делает ли код то, что заявлено? Нет ли логических ошибок, неверных условий, off-by-one?
- Edge cases: пустые/нулевые/предельные входы, ошибки парсинга, неинициализированное состояние.
- Обработка ошибок: не глотаются ли исключения; корректны ли коды/ветки ошибок.
- Concurrency: возможны ли race conditions / deadlocks при параллельном доступе.
- Регрессии: не ломает ли изменение существующее поведение, на которое кто-то полагается.
- Ресурсы: утечки, незакрытые соединения/файлы, неосвобождённые блокировки.

**B. Сложность и дизайн (локальный)**
- Не сложнее ли нужного — на уровне строки, функции, класса?
- Over-engineering: есть ли обобщённость/абстракции «на будущее», не нужные сейчас?
- Дизайн локальной единицы: разумны ли границы функции/класса, нет ли «бога-функции».
- Мёртвый/недостижимый по смыслу код, бессмысленные присваивания.

**C. Читаемость и сопровождаемость**
- Нейминг: точно ли имена передают суть, без избыточной длины.
- Комментарии: объясняют ли «почему», а не «что»; не устарели; не врут.
- Понятность намерения: поймёт ли следующий разработчик, *зачем* это, за разумное время.

**D. Безопасность (поведенческая, не паттерновая)**
- Утечки чувствительных данных (PII/секреты в логах, ошибках, ответах).
- Доверие к вводу: инъекции, нескоупленные/неавторизованные запросы, обход проверок.
- Опасные дефолты, небезопасная обработка внешних данных.

**E. Тесты (если затронуты)**
- Упадёт ли тест, когда код реально сломается; нет ли ложных срабатываний.
- Осмысленны ли ассерты; покрыты ли новые ветки/edge cases.

**Калибровочные директивы (из консенсуса вендоров):**
- *Correctness-first.* Сначала баги, ломающие прод; стиль/формат **не репортить** — их ловит
  линтер (Claude, Greptile, BugBot, Sourcegraph).
- *Verification bar.* Утверждение о поведении подкреплять `file:line`-свидетельством, а не
  выводом из имени (Claude `REVIEW.md`). Отдельный шаг само-верификации против false positives.
- *Signal-to-noise.* Капать число нитов; «perfect не цель, цель — улучшение» (Google,
  Greptile). Не блокировать на вкусовщине.
- *Контекст.* Смотреть изменение в контексте файла/системы, не только дифф (Google, Greptile).
- *Исключения.* Сгенерированный код, lock-файлы, данные — не вычитывать (Google, Copilot
  excluded files, Claude skip-rules).

## 6. Severity-модели: сравнение и рекомендация

| Источник | Уровни | Семантика |
|---|---|---|
| OpenAI Codex | **2:** P0, P1 | priority-риски; только high-priority попадает в PR |
| Anthropic Claude Code | **3:** 🔴 Important / 🟡 Nit / 🟣 Pre-existing | блокирующий баг / мелочь / унаследованный |
| Google eng-practices | **2 де-факто:** (обычный) / «Nit:» | mandatory vs опциональная полировка |
| CodeRabbit | **5:** Critical/Major/Minor/Trivial/Info (+типы) | классическая шкала серьёзности |
| Conventional Comments | label + decoration | praise/nitpick/suggestion/issue/todo/question/thought/note · `(blocking)`/`(non-blocking)` |

**Наблюдения.**
- Консенсус — **блокирующее vs неблокирующее** различие важнее точной грануляции. У всех есть
  явный «Nit/non-blocking» класс, и все призывают его глушить/капать.
- Шкалы расходятся (2–5 уровней) — это **частное** решение под продукт. Узкая (Codex P0/P1)
  даёт высокий signal, широкая (CodeRabbit ×5) — гибкость ценой шума.
- Класс **Pre-existing** у Claude — ценная идея для AIDD: отделять баги, внесённые итерацией,
  от унаследованных (перекликается с правилом проекта «исправляй дрейф на месте», но не
  раздувай scope).
- **Conventional Comments** дают ортогональную ось — *намерение* комментария (issue / suggestion
  / question / nitpick / praise) поверх *серьёзности*. Полезно: «issue» парно с «suggestion»,
  «question» когда ревьюер не уверен (снижает ложную уверенность LLM), машиночитаемый формат
  `label (decorations): subject`.

**Рекомендация для feat-008** (синтез, не цитата одного вендора):

- **Ось серьёзности — 3 уровня** в духе Claude Code: `blocker` (баг/уязвимость, чинить до
  мержа) · `nit` (улучшение, неблокирующее) · `pre-existing` (унаследованное, вне scope
  итерации). Минимально достаточно, машиночитаемо, совместимо с гейтингом по счётчику
  blocker'ов.
- **Ось намерения** (опционально, из Conventional Comments) — `issue` / `suggestion` /
  `question`, чтобы LLM явно отделял «здесь точно баг» от «возможно стоит» и от «не уверен,
  уточни». `question` — встроенный антидот к галлюцинированной уверенности.
- **Жёсткий verification bar** на blocker: только с `file:line`-свидетельством, иначе понижать
  до question/nit. Это прямой рычаг против false positives, которые у всех вендоров — главная
  метрика провала.
