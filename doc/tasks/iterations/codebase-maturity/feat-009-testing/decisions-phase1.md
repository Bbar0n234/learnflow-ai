### Журнал: решено архитектором по ходу разбора

- **A5 — ручные test-cases остаются.** Практика `test-cases.md` (ручной прогон) сохраняется для длинного
  хвоста: многошаговые e2e, тяжело автоматизируемое, exploratory, приёмка UX. Объём кратно меньше прежнего —
  основная масса переезжает в автотесты. Станет пунктом конвенции (граница авто/ручное).
- **A6 — TDD.** Тесты пишем безусловно. Strict TDD (test-first на всё) — не императив, применяем где чёткий
  контракт. Тесты-как-оракул для автономных агентов — да, но с гейтами целостности тестов (имплементер не
  трогает тест-файлы; тесты пишет не тот, кто код; adversarial-ревью; опц. held-out) — вход в Фазу 6 +
  стык с enforcement feat-008. Детали — `theory/06-tdd.md`.
- **C4 — evals вне scope feat-009.** Качество ответов LLM (датасеты + метрики + judge на Langfuse) — отдельный
  контур, не CI-гейт, прогон перед выкаткой. Осмысленно собирать только при понимании агента изнутри (минимум
  dogfooding, в идеале первый прод). → **backlog**, не эта итерация.
- **E1 — внешний testing-skill не берём.** Ведём на своих конвенциях + research. Переиспользуем 3 идеи
  смыслом (Hypothesis для чистых функций, coverage `branch=true`, `with_server.py` при необходимости).
  Свой проектный testing-skill — кандидат в backlog. Разбор — `theory/07-skills-deep-dive.md`.
- **B2 — cloud-контекст.** Целевой workflow — облако Anthropic, где Docker доступен → testcontainers/Docker-
  Postgres работают и в CI; риск «негде поднять БД» снят. Выбор testcontainers vs dev-контейнер остаётся, но
  без блокера.

## A. Стратегия и философия

### A3. Coverage-политика — *решает архитектор*
Консенсус research жёсткий: процент покрытия **как цель** вреден (Goodhart — 100% добиваются
тестом без ассертов, false-green). Полезен **как диагностика**: branch coverage, per-package,
гейт «не понижать», `term-missing` для поиска непокрытых веток.
- **Вариант 1 (реко):** без числовой цели; в CI гейт «не понижать» + диагностика; mutation testing
  (mutmut) точечно на ядре (auth/guard/SIEM-парсинг) как периодический аудит силы тестов.
- **Вариант 2:** прагматичный floor (например 80% per-package) как защита от регресса — проще
  объяснить, но провоцирует охоту за числом.

### A4. Строгость DoD — *решает архитектор*
Норму «каждый функционал обязан иметь тесты» принимаем в трактовке «**каждое поведение/контракт
покрыто на адекватном уровне**», не «каждая строка имеет unit». Минимум новой фичи: unit на
нетривиальную логику сервиса + integration на критпуть + проходит static. Развилка — насколько
жёстко гейтить: жёстко для services/repositories, мягко (с явной пометкой-исключением) для
glue/конфига/прототипов/UI-полировки. **Реко:** именно так. Это позже встроится в reviewer-чек-лист
и FSM оркестратора (Фаза 6 → правка после A4).

## B. Python-инфраструктура

### B2. Откуда берём Postgres для тестов — *решает архитектор*
Наш sandbox изолирует сеть (`--unshare-net`) — БД-тесты в любом случае гоняются вне sandbox через
цели Makefile (как и сейчас весь сетевой доступ).
- **testcontainers** (session-scoped контейнер): самодостаточно, чистый старт/гашение, не зависит от
  поднятого окружения; цена — Docker в CI + управление жизненным циклом контейнера.
- **Переиспользовать `make docker-up-db`**: контейнер уже живёт → быстрее старт; минус — тесты
  зависят от внешнего состояния, нужна аккуратная чистка между прогонами.
- **Реко:** testcontainers для герметичности; но если хотим минимум новых зависимостей и опора на
  уже существующий dev-контейнер ценнее — второй вариант рабочий. Влияет на CI-конфиг.

### B3. Подготовка схемы в тестах — *решает архитектор (касается hard-rule)*
У нас hard-rule: изменения схемы только через `alembic revision --autogenerate`. Вопрос — как
поднимать схему в тестовой БД.
- **Миграции (`alembic upgrade head`):** честно, тестовая БД поднимается тем же путём, что прод;
  ловит факт, что миграции применяются. Дороже по времени.
- **`Base.metadata.create_all()`:** быстро, но тестирует модель, а не реальную БД — расхождения
  миграций с моделью остаются незаметными.
- **Гибрид (реко):** `create_all` для скорости основной массы тестов + отдельный быстрый тест-страж
  «autogenerate против тестовой БД пуст» (ловит дрейф модель↔миграции) + CI-шаг «миграции
  применяются от нуля до head». Завязано на то, насколько медленны наши миграции сейчас.

### B5. Общие тест-утилиты — *решает архитектор*
Фабрики/фикстуры/билдеры — в отдельном пакете `packages/testing` (dev-зависимость сервисов, DRY,
единый источник) или дублировать в каждом пакете. **Реко:** отдельный пакет. Цена — +1 пакет в
workspace и его поддержка. Архивные наборы feat-005 прямо показали долг дублирующихся ручных
фейков (`_FakeGuard`/`_FakeGraph`/`_FakeCheckpointer`) — этот пакет его закрывает.

### B7. Фикстура аутентифицированного клиента — *решает архитектор*
Auth первый в списке критпутей (F1), но защита стоит на каждом приватном endpoint — integration-тестам
нужен способ ходить «как залогиненный пользователь». Развилка:
- **(а) Override `Depends`-зависимости текущего пользователя (реко):** фикстура подменяет провайдер
  `current_user` на тест-юзера через `app.dependency_overrides` — быстро, без минта реальных JWT,
  обходит крипто. Минус — не покрывает сам auth-флоу (его тестируем отдельной группой явно).
- **(б) Реальный логин-флоу:** фикстура дёргает `/auth/login`, кладёт refresh/access-токены, ходит с
  ними — честнее, заодно проверяет auth, но медленнее и связывает каждый тест с auth-подсистемой.
- **Реко:** обе — (а) как дефолтная фикстура для тестов, не про auth; (б) узкой группой именно на
  auth-критпуть (логин, refresh-ротация, отзыв). Surface: `services/auth.py`, `api/routes/auth.py`,
  `repositories/refresh_token.py`.

### B8. Контрактные тесты main app ↔ siem-service — *решает архитектор*
Два сервиса связаны общим пакетом `packages/siem-contracts` (`vocabulary.py` — словарь событий, плюс
зеркала `problem.py` / иерархии `AppError`, за консистентностью которых уже следит arch-checker).
Это классический contract-surface, но в research он не разобран. Развилка — как ловим дрейф контракта:
- **(а) Тесты-стражи на сам `siem-contracts`** (значения словаря, сериализация событий) + проверка,
  что обе стороны (эмиттер в main app, консьюмер в siem) используют один словарь. Лёгкий путь.
- **(б) Полноценный consumer-driven contract** (pact-стиль) — тяжелее, вероятно избыточно для двух
  внутренних сервисов в монорепо.
- **Реко:** (а). Где живут эти тесты (в `packages/siem-contracts/tests` как библиотека, см. B5) —
  решаем вместе.

## C. LLM / агент — ядро итерации

### C1. Шов инъекции модели — *решает архитектор*
Уточнение по коду (сверено): шов **частично уже есть**, картина мягче, чем казалось из feat-006.
- `build_graph(model: BaseChatModel, ...)` (`graph.py:193`) и `LLMClassifier(llm: BaseChatModel, ...)`
  (`classifier.py:34`) **уже принимают модель параметром** и программированы против `BaseChatModel`.
  Guard-модель создаётся в composition root (`main.py:342` `create_guard_llm` → `:365` `LLMClassifier(llm=...)`)
  и прокидывается внутрь. Значит тесты логики графа и guard можно писать с фейком **без правок прода** —
  вызывая `build_graph(model=fake, ...)` и `LLMClassifier(llm=fake, ...)` напрямую.
- Единственная точка без шва — `GraphFactory.build()` (`graph_factory.py:52`): agent-LLM создаётся
  внутри через `create_llm_from_config(...)`. Плюс сам composition root в lifespan. То есть недоступен
  только путь «через фабрику / полное приложение».

Поэтому решение — **не «переписать архитектуру», а дотянуть шов в одной точке**:
- **(а) Параметр/фабрика модели в `GraphFactory` (реко):** `GraphFactory` принимает model-factory
  (callable), переопределяемую в тестах; прод передаёт текущую `create_llm_from_config`. Локальная
  правка, без глобального состояния — в духе hard-rule «никаких module-level синглтонов».
- **(б) Dependency-override на уровне приложения:** подменять провайдер модели через `app.state` /
  `app.dependency_overrides` в тест-фикстуре. Меньше трогает `GraphFactory`, но завязывает тест на
  устройство composition root.
- **(в) Тестировать преимущественно на уровне `build_graph`/`LLMClassifier`** (где шов уже есть), а
  через фабрику гонять лишь тонкий integration. Минимум продакшн-правок ценой меньшего охвата
  «полного» пути.

Закрытые ревью экшен-айтемы (были помечены как открытые — сняты чтением кода):
- **Форма фейка guard.** Guard НЕ использует structured output: `classifier.py:100` делает обычный
  `ainvoke` и парсит `str(response.content).strip().upper()` против `{CLEAN, SUSPICIOUS, INJECTION}`
  (`:28`). Фейк = `AIMessage(content="INJECTION")` (простой текст), без tool_calls и JSON.
- **Словарь вердиктов.** `Verdict = CLEAN/SUSPICIOUS/INJECTION` (`types.py:48`). `block/warning/redact` —
  **отдельный слой действий** (маппинг `INJECTION→ERROR` и т.д.), его ветвление тестируется отдельно
  от вердикта. Деградация в CLEAN при сбое модели живёт в `guard.py:149` (не в classifier).

### C4. Граница unit vs eval и попадает ли eval в feat-009 — *решает архитектор (scope)*
Линия: детерминированная обвязка (ноды, рёбра, роутинг, парсинг, ветвление guard на фиксированных
вердиктах CLEAN/SUSPICIOUS/INJECTION + отдельный слой действий block/warning/redact, трансформация
SSE) → **unit/CI, без ключа**. Качество ответов и точность
guard на реальных атаках → **eval** (Langfuse datasets + LLM-judge), недетерминично, отдельный
пайплайн по расписанию, не CI-гейт.
- **Вариант 1 (реко):** в feat-009 закрываем детерминированный контур (он и есть «покрытие
  критичных путей»); eval-харнесс на Langfuse выносим отдельной итерацией (требует датасетов +
  живого ключа).
- **Вариант 2:** заводим минимальный eval-контур уже в feat-009. Дороже и расширяет scope.

## F. Процесс и scope

### F1. Глубина покрытия feat-009 — *решает архитектор (scope)*
DoD итерации говорит «критичные участки» (auth, security guard, SIEM pipeline + business invariants
из slice-аудитов + привести архивные тесты к общей рамке). Твой исходный запрос — «покрыть всю
кодовую базу».
- **Вариант 1 (реко):** feat-009 = инфраструктура + философия + критпути + вливание архивных тестов;
  широкое покрытие набирается дальше по норме DoD «новый функционал → тесты». Держит итерацию
  завершаемой.
- **Вариант 2:** замахнуться на широкое покрытие всех слоёв в рамках feat-009. Сильно раздувает
  Фазу 3 (фан-аут), дольше, риск незавершаемости.
- Это прямо определяет размер Фазы 3 и число тестировщиков (F2).

### F2. Размер фан-аута Фазы 3 — *решает архитектор*
Партиционирование по доменам (зеркально slice-аудитам), непересекающиеся директории → безопасная
параллельность после заморозки инфры. Предложение слайсов: auth+security · REST-хендлеры (main) ·
services/бизнес-логика · repositories/DB · agent-runtime (на фейк-LLM) · SIEM-pipeline · frontend.
6–7 агентов. Финальный список и приоритет зависят от F1.

### F3. Гейтинг CI — *решает архитектор*
Пока `make test` стоит с `continue-on-error: true` (`ci.yml:60`) и собирает 0 тестов — вся итерация
не имеет рычага: тесты ничего не гейтят. Решение процессное, без него Фаза 5 не «закрывается»:
- снять `continue-on-error` и ввести `make test` в обязательный гейт (после того как набор зелёный);
- включить frontend-тесты (`make test-fe`) в `check-fe`;
- где крутится Docker-Postgres для БД-тестов в CI (связано с B2);
- проводка coverage-гейта (связано с A3).
**Реко:** включаем гейт в конце Фазы 5, когда набор стабильно зелёный (раньше — заблокируем мержи).
