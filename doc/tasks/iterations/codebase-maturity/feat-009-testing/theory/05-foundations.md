# feat-009 · Фундамент тестирования + ответы на вопросы

Этот документ — отдельный «слой фундамента» под `01-philosophy.md`. Он не заменяет философию, а
закрывает базу, без которой философия читается как набор терминов: что такое unit/integration/e2e
по сути, что такое статанализ, дубли, solitary vs sociable, «test behavior not implementation»,
почему mock-heavy хрупок, чем smoke отличается от Google-размеров, что такое регрессионный тест. Везде
— примеры на реальном коде LearnFlow AI. Читается сверху вниз; каждый раздел самодостаточен.

В конце — раздел «Твои позиции, которые фиксирую» (ручные test-cases, evals в backlog, «не следуем
одной модели на 100%», cloud-контекст).

## 1. Три уровня тестов: unit / integration / e2e — по сути

Это **ось охвата (scope)**: сколько системы участвует в одном тесте. Твоё понимание было верным, уточняю
формулировки и приземляю.

**Unit-тест** — проверяет один «юнит» (функцию, метод, класс) в изоляции от инфраструктуры. Быстрый
(миллисекунды), детерминированный, без сети/диска/БД. Минус, который ты верно назвал: зелёные unit'ы
не гарантируют, что собранная система работает — они проверяют детали по отдельности.

Пример нашего чистого unit'а — `backend/app/agent/security/detectors/normalize.py:11`:
```python
def normalize(text: str) -> str:        # lowercase + схлопывание -/_/пробелов
    ...
```
Тест: таблица `вход → ожидаемый выход`. Ни БД, ни сети, ни моков. Запускается тысячами в секунду.

**Integration-тест** — проверяет несколько компонентов вместе, включая реальную инфраструктуру там, где
она существенна (например, настоящий Postgres). Не «полный прогон», а узел системы: «сервис + репозиторий
+ БД» или «хендлер + сервис + БД через HTTP». Медленнее unit'а (нужна БД), но ловит то, что unit пропускает:
неправильный JOIN, не та сериализация, рассинхрон контракта между слоями.

Пример участка под integration — `backend/app/repositories/thread_view.py:46` (`list_recent`): реальный
SQL с JOIN, eager-загрузкой и пагинацией. Правильность запроса проверяема **только** против настоящего
Postgres — unit тут бессмысленен (мокать SQLAlchemy = тестировать заглушку, а не запрос).

**E2E (end-to-end)** — полный прогон близко к реальному пользовательскому сценарию: HTTP-запрос проходит
через всё приложение, как в проде. Самый дорогой, медленный, хрупкий. Берём только на критичные journey
(логин → создание проекта → чат). Зелёные unit и integration не гарантируют зелёный e2e: на стыке всего
может вылезти то, что по кускам работало.

> **Smoke-тест — это НЕ четвёртый уровень.** Smoke — это про *цель*, а не про охват: мелкая широкая проверка
> «оно вообще поднимается и базовый happy-path не падает». У нас канонический smoke — инстанцировать
> `create_app()` обоих сервисов и дёрнуть `/health`. Подробнее про оси — §7.

**Вывод для нас:** unit на чистую логику, integration как основная масса (наш слоистый бэкенд именно
здесь даёт ценность), тонкий e2e на 2–3 journey. Это и есть «гибрид trophy/diamond» из философии.

## 2. Статический анализ (статанализ) — «тесты, которые ты не пишешь»

Статанализ — проверка кода **без его запуска**: инструмент читает исходник и ловит класс ошибок ещё до
тестов. У нас это уже стоит и работает как CI-гейт (`make check` / `make check-fe`):
- **mypy** — проверка типов: поймает «передал `str`, где ждали `UUID`», «функция вернёт `None`, а ты
  обращаешься к атрибуту» — без единого теста.
- **ruff** — линтер + форматтер: неиспользуемые импорты, антипаттерны, в т.ч. наши arch-правила.
- **tsc / eslint** (фронт) — то же для TypeScript.

Почему это «фундамент пирамиды/трофи»: целый пласт ошибок, который в динамических языках (особенно JS)
приходилось бы покрывать тестами, статанализ закрывает бесплатно и мгновенно. Поэтому в «трофи» он —
нижний, самый широкий слой: дешевле всего, ловит больше всего на единицу усилий. Фраза из философии
«static нужен, потому что в JS его нет по умолчанию» означает ровно это: Kent Dodds добавил статанализ
в модель, потому что в JavaScript типов нет из коробки (в отличие от нашего Python с mypy и TS с tsc).

**Связь с тестами:** чем сильнее статанализ, тем меньше нужно тестов на «глупые» ошибки — тесты освобождаются
для проверки *поведения*, а не того, что типы сходятся.

## 3. Дубли (test doubles) — что это и зачем

«Дубль» — перевод *test double* (по аналогии с «дублёром» в кино). Это подставной объект, которым в тесте
заменяют настоящего коллаборатора, чтобы тест был быстрым, детерминированным и сфокусированным. Не
«дубликат» в смысле копии — а **управляемый заменитель** на время теста. Таксономия (Meszaros/Fowler),
от простого к «умному»:

| Дубль | Что делает | Пример у нас |
|-------|------------|--------------|
| **Dummy** | Заполняет обязательный параметр, не используется | Пустой `observation=None` там, где он не важен тесту |
| **Stub** | Отдаёт заранее заданный ответ на вызов | Фейковый `ThreadViewRepository.get_by_id()`, возвращающий готовый объект |
| **Spy** | Stub + записывает, как его вызвали | Тот же фейк, но ещё помнит, с каким `thread_id` дёрнули |
| **Mock** | Заранее запрограммирован *ожиданиями* вызовов, сам проверяет | «Ожидаю ровно один вызов `create_score` с таким payload» |
| **Fake** | Рабочая упрощённая реализация | In-memory подмена репозитория (хранит в dict вместо БД) |

**Правило:** предпочитать **fake и stub**, mock — только когда сам *факт/форма вызова и есть проверяемое
поведение*.

Конкретно у нас mock уместен в `backend/app/api/routes/feedback.py:69`:
```python
langfuse.create_score(trace_id=..., name=SCORE_NAME, value=..., ...)
await anyio.to_thread.run_sync(langfuse.flush)
```
Здесь *смысл фичи* — «мы отправили оценку во внешнюю систему с правильным payload». Проверять нечего, кроме
самого факта вызова → mock на `langfuse.create_score`, ассерт «вызван с такими аргументами» — это честная
проверка поведения, потому что вызов **и есть** поведение.

А вот сервис `chat.py:73` (`get_chat`) с тремя коллабораторами тестируем **fake'ами**, а не моками: подменяем
`ThreadViewRepository`/`AgentRunner`/`TraceStore` на in-memory заглушки, отдающие данные, и проверяем
**результат** (`ChatDetail`, ветку 404, деградацию при сбое Redis) — а не «какие методы дёрнулись внутри».

**Как дубли выглядят в Python (на практике).** Твоя картинка «наследуемся от `ThreadViewRepository`,
переопределяем `get_by_id`» — рабочая, но не единственная и не самая частая. Благодаря duck-typing (и нашим
`Protocol`-интерфейсам) дубль не обязан наследовать реальный класс — достаточно объекта с теми же методами.
Три типичные формы: **stub/fake** — маленький свой класс с тем же интерфейсом (fake-репозиторий с `dict`
внутри); **mock/spy** — `unittest.mock.AsyncMock`/`MagicMock`, который сам записывает вызовы и умеет
`assert_called_once_with(...)`; **dummy** — обычно просто `None` или голый объект, лишь бы пройти сигнатуру
(твоё понимание точное: «пустышка для параметра», логики в ней нет принципиально).

**Граница, которую ты сам нащупал, — верная.** Для unit-теста сервиса с коллабораторами поднимать реальную БД
(testcontainers/Docker) — overkill: коллабораторы подменяются fake'ами в памяти. Реальный Postgres нужен
**только** repository-integration-тестам, где проверяется сам SQL (§1, `thread_view.py:46`). «Тяжёлую» инфру
поднимаем точечно под тот слой, ради которого она и существует, а не под каждый тест.

## 4. Solitary vs sociable unit — на нашем коде

Fowler разводит два смысла слова «unit-тест» по тому, **что делать с коллабораторами**:

- **Solitary (одиночный):** все соседи заменены дублями, юнит варится в полной изоляции.
- **Sociable (общительный):** настоящие соседи участвуют, дублями подменяем только болезненные границы
  (внешний мир, недетерминизм, медленное I/O).

**Solitary у нас** — `normalize()` (§1): зависимостей нет вообще, дублировать нечего. Естественно одиночный.

**Sociable у нас** — `chat.py:73` `get_chat`. Если внутри он зовёт чистую функцию-форматтер или другой
ин-процесс компонент — пусть зовёт настоящий (sociable). Дублируем только то, что лезет наружу/в инфру:
`TraceStore` (Redis), `AgentRunner`. Почему так лучше: solitary-стиль на каждый сервис заставляет мокать
*всех* соседей → тест знает слишком много про внутреннее устройство → ломается от любого рефакторинга
(см. §5, §6). Sociable проверяет реальное поведение связки, дублируя минимум.

**Семантический спор, который снимает философия:** то, что Honeycomb/Diamond называют «integration-тест»,
часто = ровно fowler-овский «sociable unit». Поэтому драка «пирамида vs honeycomb» во многом про слова.
Практический вывод: **sociable по умолчанию, solitary точечно** на чистой логике и болезненных границах.

## 5. «Test behavior, not implementation» — ты понял верно

Твоя формулировка про чёрный ящик — точная. Тестируем **наблюдаемый контракт**: вход → выход / побочный
эффект, через публичный интерфейс. Не лезем в приватные методы, внутренние вызовы, структуру.

Пример: у `normalize()` внутри есть `while`-цикл, схлопывающий разделители. Тест проверяет
`normalize("a-b  c") == "a_b_c"` — **результат**. Если кто-то перепишет цикл на регулярку с тем же
результатом — тест зелёный, потому что поведение не изменилось. Это правильно.

**Диагностический признак нарушения:** тест падает при рефакторинге, который **не менял поведение**. Значит
он прибит к реализации (привязан к тому, *как* сделано, а не *что* получается) — это «change-detector test»,
он тормозит рефакторинг и врёт о регрессии. Твой пример — «реализация поменялась, тест покраснел, хотя стало
не хуже, а просто по-другому» — ровно об этом.

## 6. Почему mock-heavy → хрупкость (кристально)

Ты ловил это на практике — вот механика. Каждый mock с ожиданием («метод X вызван с аргументом Y») — это
**фиксация того, КАК код работает внутри**, а не что он выдаёт. Чем больше моков, тем больше тест знает про
внутреннюю реализацию связки.

Что происходит дальше:
1. Ты делаешь невинный рефакторинг — например, сервис стал звать репозиторий одним батч-запросом вместо
   трёх вызовов в цикле. Поведение (результат) то же.
2. Но mock'и ожидали «три вызова `get_by_id`», а стало «один вызов `get_batch`» → **тесты краснеют**, хотя
   ничего не сломалось.
3. Ты идёшь чинить *тесты*, а не код. Тесты из страховки превращаются в налог на рефакторинг.

Хуже того — mock-heavy тест часто проверяет **поведение моков, а не твоего кода**: ты сам запрограммировал,
что заглушка вернёт, и сам же это сассертил. Зелёный тест, нулевая ценность (близко к false-green).

**Лечение** (оно же — наш выбор стиля): sociable + fakes. Подменяй реализацией (fake-репозиторий хранит в
dict), а не ожиданиями вызовов; проверяй результат, а не внутренние дёрганья. Mock оставляй там, где вызов
наружу **и есть** контракт (§3, кейс Langfuse). Google после злоупотребления моками дошёл до лозунга «no
more mocks» — это не «моки запрещены», а «моки — последнее средство, не первое».

## 7. Три независимых оси (тут была путаница со smoke / Google-размерами)

Терминов много, потому что они меряют **разные вещи**. Это три ортогональные оси — один тест имеет позицию
на каждой:

1. **Охват (scope):** unit → integration → e2e. *Сколько системы* в тесте (§1).
2. **Размер/изоляция (Google sizes):** small → medium → large. *Какие ресурсы* разрешены.
   - **small** — один процесс, без I/O/сети/диска/сна (всё внешнее — дублями);
   - **medium** — одна машина, можно localhost и реальную БД;
   - **large** — несколько машин / внешние системы.
   Google ввёл эту ось, потому что для CI важны **скорость и детерминизм**, а они определяются ресурсами,
   а не «уровнем». «Coverage мерить только на small» = мерить покрытие там, где оно достоверно и быстро.
3. **Цель (purpose):** smoke (поднялось ли вообще), regression (закрепить пофикшенный баг), happy-path,
   edge-case, contract и т.д. Это *зачем* тест написан.

Поэтому **smoke ≠ unit ≠ small** — это позиции на разных осях. Наш smoke на `create_app()` — это цель
«проверить старт», по охвату он почти e2e (всё приложение), по размеру medium (поднимает приложение). Твоя
догадка «smoke ≈ unit» — единственная неточность; в остальном размеры ты сопоставил с уровнями верно (small
тяготеет к unit, large — к e2e, но это **корреляция, не равенство**).

## 8. Регрессионный тест — ты понял верно

Регрессионный тест — это **цель**, а не отдельный уровень (может быть unit, integration или e2e). Сценарий
ровно твой: баг нашёлся эмпирически/руками в проде (тесты его не поймали → значит покрытие было неполным);
ты пишешь тест, который этот баг **воспроизводит и закрепляет**, чтобы он никогда не вернулся незамеченным.
Формула: «сначала тест, который краснеет на баге → фикс → тест зеленеет → он навсегда сторожит этот случай».
Это и есть «дополнить тесты тем, что они пропустили». Прямой пример в репо — `test_cors_on_500.py` из feat-007:
заведён после того, как 500-ответы эмпирически уходили без CORS-заголовков.

## 9. Модели тестов — с нуля и зачем каждая

В `01-philosophy.md` имена шли до определения — вот они от нуля. Все модели отвечают на один вопрос:
**сколько усилий на каждый уровень при ограниченном времени** (это «форма» распределения тестов).

- **Пирамида** (Cohn): широкое основание из unit, узкая верхушка e2e. Придумана под богатую доменную логику,
  изолируемую от I/O. Слабость: переоценивает unit, провоцирует mock-heavy (чтобы изолировать) и хрупкость;
  молчит про статанализ.
- **Trophy** (Dodds): static → unit → **integration (основная масса)** → e2e. Придумана под фронтенд и
  монолит «в одних руках». Главный принцип, который берём: *чем ближе тест к реальному использованию, тем
  больше уверенности*; центр тяжести — integration.
- **Honeycomb** (Spotify): мало «integrated» (тестов наружу, к чужим системам) → много integration → немного
  на детали реализации. Под микросервисы: сложность не внутри сервиса, а **во взаимодействии** сервисов.
- **Diamond**: unit прорежен до критичного, центр тяжести — integration. Реакция на то, что 100% unit
  эродируют при рефакторинге (их массово переписывают и хочется пропустить).
- **Ice-cone** (перевёрнутая пирамида): всё руками/e2e. **Признанный антипаттерн** — дорого, медленно и,
  как ты верно сказал, флаки (невоспроизводимо).

**«Мы микросервисы?» — уточнение.** Нет, не в honeycomb-смысле. LearnFlow — это **слоистый монолит**
(`backend/`, main app) **плюс один вспомогательный сервис** (`services/siem-service`) и общие пакеты. Значит:
- для main app работает монолитная логика trophy/diamond (наш основной выбор);
- идею honeycomb «тестируй контракт между сервисами» берём **узко** — на границу main↔siem через общий
  пакет `siem-contracts` (это наша развилка B8 про контрактные тесты, не полноценный микросервисный веер).

**Главное, что ты сам сформулировал и что верно:** не следуем ни одной модели на 100%. Берём лучшее —
trophy/diamond-скелет для бэкенда и фронта, honeycomb-идею контракта для одной границы, статанализ как
фундамент. Первичен не *силуэт*, а **стиль**: выразительные тесты, sociable по умолчанию, быстрые и
надёжные, падающие только по полезной причине.

## 10. Coverage — коротко (ты понял верно)

Покрытие = доля кода, исполнённого тестами. **Как цель — вредно** (100% добиваются тестом без ассертов →
false-green; это закон Гудхарта: метрика-цель перестаёт быть хорошей метрикой). **Как диагностика —
полезно:** искать непокрытые ветки, держать гейт «не понижать», смотреть тренд. Что меряют вместо числа:
mutation testing (убивает ли тест внесённую мутацию — проверка *качества ассертов*), флейкость, скорость
suite, defect escape rate. Меряем branch coverage и per-package (см. `02-python-engineering.md`).

## 11. Твои позиции, которые фиксирую

- **Ручные test-cases остаются — но узко.** Практика прошлых итераций (`test-cases.md` как документ ручного
  прогона) сохраняется для **длинного хвоста**: многошаговые e2e, тяжело автоматизируемое, exploratory,
  приёмка UX. Объём — кратно меньше прежнего, потому что основная масса переезжает в автотесты. Это станет
  явным пунктом конвенции (граница «что автотестим / что остаётся ручным кейсом»).
- **Evals — в backlog, вне scope feat-009.** Качество ответов LLM (датасеты + метрики + judge на Langfuse) —
  отдельный контур, не CI-гейт; гоняется перед выкаткой. Собирать метрики/датасеты осмысленно только когда
  есть понимание агента изнутри — **минимум фаза dogfooding, в идеале первый прод**. Сейчас не придумываем,
  фиксируем в backlog. (Развилка C4 закрыта в этом смысле.)
- **Не следуем одной модели на 100%** — берём лучшее из миров (§9).
- **Cloud-контекст.** Целевой workflow — облако Anthropic, где Docker доступен. Значит тестовая БД в облаке
  реальна (testcontainers/Docker-Postgres работают и там) — это снимает риск с развилки B2 и позволяет CI с
  реальным Postgres. Учитываем при выборе инфраструктуры Фазы 2.
