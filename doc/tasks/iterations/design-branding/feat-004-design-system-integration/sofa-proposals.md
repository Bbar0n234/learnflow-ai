## Кандидат A — берём (TIL)

**Заголовок-описание:** shadcn-компонент `sonner` ставится с импортом `next-themes`, которого нет в
Vite/React-проекте; как сделать компонент theme-aware без `next-themes` и без связи с твоим
theme-store — читать отрисованную тему из DOM.

**Тип:** TIL. **Решение:** брать.

**Почему берём:** удивительное поведение инструмента (shadcn CLI зашивает Next.js-специфичный
`next-themes` в генерируемый `sonner.tsx`, даже когда проект на Vite); проваленная первая попытка с
понятным «почему»; долговечный обобщаемый фикс. Переносимо на любой Vite+shadcn проект. Источник —
`summary.md` § T5 / merge-фаза, файлы `shared/ui/sonner.tsx`, `shared/lib/use-theme.ts`.

**Угол, отличающий от «общеизвестного»:** не просто «замени import», а паттерн **источник темы —
DOM**: тема рендерится как класс `.dark` на `<html>`, и любой компонент может реактивно её читать
через `useSyncExternalStore` + `MutationObserver`, не завися ни от `next-themes`-провайдера, ни от
конкретного store. Это заодно развязывает архитектурную границу (UI-компонент не тянет глобальный
store ради темы).

**Черновик-набросок (приводится к стандартам на шаге 4):**

- *Проблема.* `npx shadcn add sonner` генерирует `sonner.tsx` с `import { useTheme } from "next-themes"`.
  В проекте на Vite/React без next-themes сборка падает на резолве импорта. Поставить next-themes
  только ради тоста — лишняя зависимость и второй источник истины темы.
- *Окружение/версии.* React 19, Vite 7, shadcn (Base UI / base-nova), sonner. Без Next.js.
- *Причина.* Шаблон shadcn для sonner предполагает Next.js-стек (next-themes как канон темы).
  Генератор не знает, что проект на Vite.
- *Фикс.* Тема уже отрисована как класс `.dark` на `documentElement` (его вешает/снимает твой
  механизм темы). Читаем результат из DOM хук-обёрткой и подставляем в `<Toaster theme={...}>`:
  ```ts
  function getSnapshot() {
    return document.documentElement.classList.contains("dark") ? "dark" : "light";
  }
  function subscribe(cb: () => void) {
    const o = new MutationObserver(cb);
    o.observe(document.documentElement, { attributes: true, attributeFilter: ["class"] });
    return () => o.disconnect();
  }
  export function useTheme() {
    return useSyncExternalStore(subscribe, getSnapshot, () => "light");
  }
  ```
  Третий аргумент `useSyncExternalStore` — server snapshot (`"light"`) — нужен для SSR/гидрации.
- *Как верифицировано.* Тосты и любые theme-aware-обёртки переключаются вместе с темой;
  next-themes удалён из зависимостей; линт-граница «UI не импортирует store» соблюдена.
- *Verbatim-ошибки (снять точно на шаге 4, не выдумывать):* сообщение Vite о неудачном резолве
  `next-themes`; при варианте «подключить через store» — текст ошибки линт-границы импортов.

## Кандидат B — берём (TIL, сильнейший)

**Заголовок-описание:** как детерминированно засеять историю чата в LangGraph-чекпойнтере (без
запуска модели) для демо/тестов — минимальный StateGraph + `ainvoke` через чекпойнтер +
детерминированные id сообщений, чтобы редьюсер `add_messages` заменял их по месту (идемпотентно).

**Тип:** TIL. **Решение:** брать.

**Почему берём:** нетривиальная интеракция систем (история сообщений живёт в чекпойнтере LangGraph,
а не в реляционном репозитории — обычным INSERT не засеять); проваленный наивный путь (гонять
реальный граф = LLM, недетерминизм, токены); обобщаемый фикс на любой LangGraph+checkpointer проект,
которому нужны фикстуры. Источник — `summary.md` § DP, `backend/scripts/seed_demo.py`.

**Угол:** эксплуатируем семантику редьюсера `add_messages` — он дедуплицирует/заменяет сообщения
**по их id**. Если задавать сообщениям детерминированные id, повторный прогон сидера заменяет записи
на месте, а не плодит дубли → идемпотентность без ручной очистки чекпойнтера.

**Черновик-набросок:**

- *Проблема.* Нужно засеять детерминированную историю диалога для визуального/e2e-теста. Сообщения
  не в таблице, а в чекпойнтере LangGraph (например AsyncPostgresSaver), привязаны к `thread_id`.
- *Окружение/версии.* Чистый LangGraph (без LangChain-обёрток), AsyncPostgresSaver,
  `MessagesState` / редьюсер `add_messages`.
- *Наивный путь и почему не годится.* Запустить настоящий agent-граф, чтобы он «наговорил» историю:
  тянет реальный LLM-вызов — недетерминированный текст, стоимость токенов, фльки тесты.
- *Фикс.* Собрать **одноразовый минимальный** `StateGraph` поверх `MessagesState`, единственный узел
  которого возвращает заранее заданные сообщения, и вызвать его через целевой чекпойнтер с нужным
  `thread_id`:
  ```python
  g = StateGraph(MessagesState)
  g.add_node("seed", lambda s: {"messages": CANNED_MESSAGES})
  g.add_edge(START, "seed"); g.add_edge("seed", END)
  app = g.compile(checkpointer=checkpointer)
  await app.ainvoke({"messages": []}, {"configurable": {"thread_id": tid}})
  ```
  Каждому сообщению в `CANNED_MESSAGES` задать стабильный `id`. Повторный прогон → `add_messages`
  заменяет по id, дублей нет.
- *Как верифицировано.* Повторный запуск сидера не множит сообщения; история читается приложением
  как настоящая; ноль LLM-вызовов.
- *Заметка-caveat (поглотить абзацем, не отдельным постом):* реляционные сущности (пользователь,
  проект, артефакты) сидятся обычными репозиториями по натуральным ключам; в один пост идёт только
  чекпойнтер-часть как переносимый инсайт.

## Кандидат C — пограничный, скорее режем (с обоснованием)

**Заголовок-описание:** прятать незрелые/мок-фичи из прод-сборки через `import.meta.env.DEV`; Vite/
Rollup вычищает мок-данные из бандла (DCE), проверка — grep по `dist/`.

**Тип:** TIL. **Решение:** скорее не брать (показываю рассуждение — реши, стоит ли).

**Почему режем:** ядро (`import.meta.env.DEV` как dev-only флаг, статически `false` в проде) —
**общеизвестное, дешевле найти в доках Vite**, чем читать пост. Рубрика прямо рубит такое.

**Что осталось бы ценного, если всё же постить** (два эмпирических угла, которые в доках не лежат):
1. Гейт ставить **в точке рендера** (`FLAG && <Feature/>`), тогда импорт мока остаётся референсимым
   внутри ветки — линтер не ругается на «unused», хотя в проде ветка мертва.
2. DCE через ре-экспортнутую `const` не гарантирован на 100% — **верифицируй фактическое удаление
   строк** grep'ом по собранному `dist/`, не полагайся на «должно вытряхнуться».

Этого, на мой взгляд, не хватает на самостоятельный TIL — тонкий и нишевый. Кандидат скорее в
**caveat-абзац** внутри будущего поста про feature-flags/Vite-сборку, если такой возникнет. Оставляю
решение архитектору.

## Рассмотрено и отсеяно

- **AsyncPostgresSaver/Store без авто-reconnect после блипа БД** — генуинно удивительный пробел
  (SQLAlchemy-пул восстанавливается, чекпойнтер LangGraph — нет), но (1) **не решён** (открытый
  пункт backlog «разобраться, как держит пул»), значит был бы Question, а мы не «застряли»; (2)
  всплыл на стенде **feat-007**, не находка этой итерации. Кандидат в TIL — когда докопаем причину.
- **Tailwind v4 CSS-first `@theme` без конфига** — штатная, хорошо задокументированная фича v4.
  Общеизвестное → режем.
- **`REDIS_URL` с docker-internal хостом не резолвится с хоста** — общий env/networking-момент,
  не инсайт.
- **Урок «инвентаризацию заглушек вести свипом, не grep'ом `MOCK_*`»** — проектно-процессное
  наблюдение (живёт в harvest known-trivial), не переносимый tool/API-инсайт.
