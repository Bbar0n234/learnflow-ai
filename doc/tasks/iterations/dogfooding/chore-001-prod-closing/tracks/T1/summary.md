# Summary: T1 — клиентский IP

## TL;DR

Трек чинит доверие proxy-заголовкам: middleware и auth-роуты брали левый элемент `X-Forwarded-For` (подконтролен клиенту) и обходили per-IP rate-лимиты. Решение — явный источник IP (`CLIENT_IP_SOURCE`: `socket` / `x-real-ip` / `x-forwarded-for`) и единая точка чтения `app.infra.client_ip.get_client_ip`, с grep-абельным запретом читать proxy-заголовки где-либо ещё. Фаза T1.1 завела env-поверхность: две переменные во всех четырёх местах (`Settings`, `.env.example`, `.env.local.example`, `docker-compose.yml`). Фаза T1.2 добавила сам хелпер и врезала его в обе точки чтения — `auth.py` (три rate-limit ключа) и `main.py` (`request_id_middleware`); наивный `xff.split(",")[0]` из кода удалён полностью, grep подтверждает единственную точку чтения proxy-заголовков. Фаза T1.3 закрепила это в документации: grep-абельное правило в `conventions.md`, актуальная строка про `ip` в `security-events.md`, и попутно — приведение § Dockerfile к целевым флагам `--no-dev`/`--package` из брифа § 4 (T2 их применит к самим Dockerfile'ам). Фаза T1.4 вынесла контракт периметра в `doc/tech/setup/production.md`: инвариант «до приложения нельзя дойти мимо nginx», санитизированный референс боевого nginx-конфига (снят оркестратором с прод-VM read-only, апрувнут архитектором), режимы `CLIENT_IP_SOURCE` в эксплуатации и runbook ручных шагов на прод-VM перед merge в `main`.

## Что реализовано (T1.1)

- `backend/app/config.py` — секция «Client IP» рядом с Auth: `client_ip_source: Literal["socket", "x-real-ip", "x-forwarded-for"] = "socket"`, `client_ip_xff_hops: int = Field(1, ge=1)`. Импорт `Literal` из `typing`, `Field` из `pydantic`.
- `.env.example` — блок `CLIENT_IP_SOURCE=socket` / `CLIENT_IP_XFF_HOPS=1` рядом с Auth, с комментарием про прод (`x-real-ip`) и про то, что hops значим только при `x-forwarded-for`.
- `.env.local.example` — закомментированная строка `# CLIENT_IP_SOURCE=socket` с пояснением, что дефолт для local dev совпадает с системным и переопределение не требуется (по уточнению № 3 PLAN_REVIEW). `CLIENT_IP_XFF_HOPS` в файл не добавлялся — уточнение адресует только `CLIENT_IP_SOURCE`, а сам параметр бессмыслен при дефолтном `socket`.
- `docker-compose.yml` — в `environment:` сервиса `app` две строки: `CLIENT_IP_SOURCE: ${CLIENT_IP_SOURCE:-socket}`, `CLIENT_IP_XFF_HOPS: ${CLIENT_IP_XFF_HOPS:-1}`.

## Что реализовано (T1.2)

- `backend/app/infra/client_ip.py` (новый) — публичная `get_client_ip(request, settings) -> str` и публичный предикат `is_health_path(path: str) -> bool` (константа `_HEALTH_PATH = "/health"` — единственное место, где путь записан). Три режима по `settings.client_ip_source`: `socket` — `request.client.host` либо `"unknown"`; `x-real-ip` — заголовок целиком (strip), при отсутствии/пустом значении — fallback на socket + WARNING; `x-forwarded-for` — `hops`-й элемент справа (`hops=1` → последний), при недостаточной длине списка или отсутствии заголовка — тот же fallback. Fallback-WARNING подавляется на health-пути через `is_health_path`. Логгер — `structlog.get_logger()`, keyword-стиль; в WARNING только `client_ip_source`, `reason`, `path` — без содержимого заголовков. Настройки и request — параметры, модуль не хранит состояния и не читает `Settings()` сам.
- `backend/app/api/routes/auth.py` — `_get_client_ip` удалена; три вызова (`register`, `login`, `refresh`) переведены на `get_client_ip(request, settings)`, `settings` уже был в сигнатурах через `SettingsDep`.
- `backend/app/main.py` — блок ручного разбора `X-Forwarded-For` в `request_id_middleware` заменён вызовом хелпера. `settings` уже в closure `create_app()` (создаётся строкой выше). На health-пути `ip` в contextvars не биндится вовсе (`request_id`/`user_agent_hash` биндятся всегда первым вызовом `bind_contextvars`, `ip` — вторым, условным).

## Что реализовано (T1.3)

- `doc/tech/conventions.md` § Logging Conventions → Security Event Logging — новый абзац «Источник `ip`» сразу после предложения про автоматическое вытягивание identifiers из contextvars, перед примером кода: клиентский IP читается только через `app.infra.client_ip.get_client_ip`, `X-Real-IP`/`X-Forwarded-For` больше нигде в кодовой базе напрямую не читаются, источник задаёт `CLIENT_IP_SOURCE`, а не код на месте вызова.
- `doc/tech/conventions.md` § Dockerfile — строка про установку зависимостей приведена к целевому состоянию брифа § 4: `uv sync --locked --no-dev --package <имя пакета workspace>` вместо `--all-packages`, с пояснением, что это даёт (без dev-группы, без стека остальных членов workspace). Cache-mount и запрет `uv pip install -e` — сохранены из исходной формулировки.
- `doc/tech/security-events.md:89` — строка поля `ip`: источник переписан на `get_client_ip` + `CLIENT_IP_SOURCE` вместо `HTTP middleware (X-Forwarded-For or socket)`; колонка `Optional` дополнена пометкой, что на health-пути `ip` не биндится вовсе (а не просто «опционально»).

## Что реализовано (T1.4)

- `doc/tech/setup/production.md` (новый) — четыре блока: (1) топология и инвариант доверия «до приложения нельзя дойти мимо nginx» с диаграммой и перечнем того, что инвариант ломает; (2) санитизированный референс `/etc/nginx/sites-enabled/learnflow` as-is, с построчными комментариями контракта (`X-Real-IP` — замена, `X-Forwarded-For` — дописывание и не читается кодом, `location = /health` без proxy-заголовков, `location /siem/` срезает префикс и отдаёт 502 при выключенном SIEM) и отдельным предупреждением про повторный дрейф `sites-available`/`sites-enabled`; (3) режимы `CLIENT_IP_SOURCE` в эксплуатации — прод `x-real-ip`, обоснование дефолта `socket`, ограничение `x-forwarded-for` при смешанных точках входа; (4) runbook ручных шагов на прод-VM до merge в `main`, с подзаголовком по подсистеме («Клиентский IP»), под который T4 добавит «SIEM» без переструктурирования раздела.
- `doc/index.md` — строка `tech/setup/production.md` в блок «Setup manuals», рядом с `tech/setup/codex-cloud.md`.

## Решения и обоснования

- **Место переменных в config.py** — секция «Client IP» вставлена сразу после `secure_cookies` (конец блока Auth), до Langfuse. План прямо требовал «рядом с auth-настройками»; выбор точки вставки (после, а не до Auth) не влияет на поведение и не является архитектурным решением.
- **`CLIENT_IP_XFF_HOPS` не попал в `.env.local.example`** — отклонение от буквального текста плана («переменные попадают туда закомментированными», множественное число в описании фазы), но соответствует явному уточнению № 3 PLAN_REVIEW, которое говорит только про `CLIENT_IP_SOURCE`, и принципу файла «только отличия от `.env`»: local dev использует дефолт `socket`, при котором `CLIENT_IP_XFF_HOPS` не читается вовсе — комментировать его там нечего объяснять.
- **Валидация через тип, а не через `field_validator`** — `Literal` даёт pydantic отвергнуть мусорное значение источника на старте (fail-fast), `Field(ge=1)` — то же для отступа; отдельный `field_validator` не нужен, он уже используется в файле только для `cors_origins` (CSV-парсинг), что не наш случай.
- **Никаких изменений в `client_ip.py`, `auth.py`, `main.py`** — вне scope фазы T1.1 (это T1.2), несмотря на то что переменные пока нигде не читаются.
- **`is_health_path` как публичный предикат, а не хардкод в `main.py`** — по уточнению № 2 PLAN_REVIEW: путь `/health` записан один раз, в модуле хелпера; middleware спрашивает предикат, не сравнивает строку сам. Убирает риск, что `client_ip.py` и `main.py` разъедутся по списку «путей без proxy-заголовков».
- **`bind_contextvars` вызывается дважды (безусловно для `request_id`/`user_agent_hash`, условно для `ip`)** вместо сборки одного dict и одного вызова — отклонение от буквального прочтения плана («ip не биндится вовсе»), выбранное ради типовой чистоты: dict пришлось бы типизировать как `dict[str, str]` и это не яснее двух вызовов. Поведение то же: на health-пути ключ `ip` в contextvars отсутствует.
- **`x-forwarded-for`: fallback на socket, а не отказ запроса**, при недостаточной длине списка или отсутствии заголовка — согласовано планом (fallback + WARNING для обоих режимов заголовков); альтернатива «вернуть 400» не рассматривалась, план её не предполагает и это не в скоупе T1.2.
- **WARNING-текст без имени заголовка в значении** — сообщение содержит `client_ip_source` (какой режим настроен) и `reason` (машинно-читаемая причина fallback: `"x-real-ip header missing"` / `"x-forwarded-for header insufficient"`), но не `X-Real-IP`/`X-Forwarded-For` как ключи-значения заголовков — план требует не класть в WARNING содержимое заголовка целиком; имя заголовка в тексте reason не является содержимым заголовка и не противоречит требованию.
- **Куда легло правило чтения IP** — в ядро `conventions.md`, § Logging Conventions → Security Event Logging, а не в `conventions/api.md` и не в § Секреты и fail-fast. Резолюция брифа/плана (Open Question № 3): правило кросс-доменное — затрагивает и auth-роуты, и HTTP middleware, и любых будущих потребителей `ip`, а не специфику REST-контрактов одного домена. Секция Security Event Logging уже объясняла, что `ip` как identifier вытягивается из contextvars автоматически — соседний абзац отвечает на следующий естественный вопрос читателя, «а откуда берётся само значение», не разрывая изложение на два места.
- **§ Dockerfile правится в T1, а не в T2** — намеренное решение партиции (бриф § «Партиция треков»): T1 и T2 иначе пересеклись бы правкой одного файла (`conventions.md`) параллельно. Строка в конвенции — целевое состояние ещё до того, как T2 приведёт к нему сами `backend/Dockerfile` и `services/siem-service/Dockerfile`; расхождение между строкой конвенции и текущими Dockerfile'ами до мержа T2 — следствие партиции, а не дефект T1.3. Метапометку об этом в сам документ не вносил (правило «без временных метапометок»): расхождение — факт состояния веток, а не то, что должно быть написано в конвенции.
- **Источник текста nginx-референса — реальный конфиг с прод-VM, а не реконструкция по брифу.** Оркестратор снял `/etc/nginx/sites-enabled/learnflow` с прод-VM (timeweb) read-only с апрувом архитектора и передал санитизированную копию (плейсхолдеры вместо `server_name` и путей к TLS) вместе с фактами прямо в задание фазы — implementer T1.4 копию не запрашивал и не реконструировал самостоятельно. Контракт брифа подтверждён построчно по снятому файлу: `X-Real-IP` — замена, `X-Forwarded-For` — дописывание, `location = /health` без proxy-заголовков, `location /siem/` срезает префикс. В `production.md` вставлена ровно эта копия, без добавления TLS-параметров или деталей, не выведенных из снятого текста.
- **Дрейф `sites-available`/`sites-enabled` — повторный, не первичная находка.** Та же пара файлов уже расходилась и была синхронизирована вручную в `production/chore-001-ci-cd` (находка 5): `sites-enabled/learnflow` уже тогда оказался обычным файлом, не симлинком. Симлинк восстановлен не был, поэтому конфиги снова разошлись — на этот раз `sites-available` содержит топологию с фронтом на `:3000` и префиксом `/api/`. Зафиксировано в `production.md` как факт с явной ссылкой на прошлую находку, а не как новое открытие; ручной шаг runbook'а в этот раз предлагает на выбор либо ресинхронизацию, либо переход на симлинк, чтобы дрейф не повторился в третий раз — это релевантный контекст для ревьюеров и harvester'а: причина дрейфа (обычный файл вместо симлинка) не устранена предыдущей итерацией, только симптом.

- **Фикс runbook'а после `{T1.7}`: шаг синхронизации nginx-конфигов уничтожал боевой конфиг.** Кейс `{T1.7}` (desk-check runbook'а на исполнимость) вскрыл два дефекта в шаге 3 «Клиентский IP». Первый: формулировка «удалить `sites-available/learnflow` и `sites-enabled/learnflow` и пересоздать `sites-enabled/learnflow` как симлинк на актуальный `sites-available/learnflow`» при буквальном исполнении не работает и разрушает прод — `sites-enabled/learnflow` на VM обычный файл и единственная копия боевого конфига (в репозитории его нет, в `sites-available` лежит устаревшая версия), после удаления обоих файлов цель симлинка не существует и восстанавливать нечего. Первопричина — шаг писался как намерение («хотим симлинк»), а не как последовательность операций над файлами, и в нём потерялось, какой из двух файлов является источником истины. Починено переписыванием шага в четыре команды с явным направлением копирования: резервная копия в `/root/learnflow.nginx.bak`, затем `sites-enabled` → `sites-available` (перезапись устаревшего боевым — это и есть синхронизация), затем удаление файла в `sites-enabled`, затем `ln -s ../sites-available/learnflow`. Второй дефект: после правки конфига периметра в runbook'е не было ни `nginx -t`, ни перезагрузки — правка оставалась непроверенной и неприменённой. Добавлен обязательный завершающий шаг `nginx -t && systemctl reload nginx` (нумерация сдвинула проверку переменной в контейнере на шаг 5) с двумя оговорками: `&&` не даёт применить сломанный конфиг, а `reload` вместо `restart` не рвёт живые соединения, включая открытые SSE-стримы. Правка документа, кода трека не касается.

## Решения и обоснования (фиксы code review B)

- **[review-b nit 1, правило четырёх мест] `.env.local.example` — добавлена закомментированная строка `# CLIENT_IP_XFF_HOPS=1 — значим только при CLIENT_IP_SOURCE=x-forwarded-for`, рядом с `# CLIENT_IP_SOURCE=socket`.** Прежнее решение фазы T1.1 (не заводить переменную в `.env.local.example`, см. выше) закрывало только `CLIENT_IP_SOURCE`, per уточнение № 3 PLAN_REVIEW; `CLIENT_IP_XFF_HOPS` оставался в трёх местах из четырёх, что ревью справедливо отметило как асимметрию без объяснения для следующего читателя файла. Симметрия важнее буквального прочтения принципа «только отличия от `.env`»: обе переменные из одной секции конфигурации, и присутствие одной без другой читается как недосмотр, а не как решение.
- **[review-b nit 3, потерянный инвариант] `doc/tech/conventions.md` § Dockerfile — дописано предложение о дублировании флагов `uv sync` во всех вызовах внутри файла.** Норма задавала целевую форму одного вызова (`uv sync --locked --no-dev --package <пакет>`), но не несла инвариант «кэш-слой и финальный sync обязаны нести одинаковые флаги, потому что кэш-слой физически остаётся в образе» — это знание жило только в комментариях `backend/Dockerfile:22-27`. Дописана одна фраза сразу после описания флагов, без создания нового подпункта — норма остаётся grep-абельной одной строкой.
- **[review-b nit 2, метапометка] `doc/tech/setup/production.md` — убрана фраза «зафиксировать здесь же при следующей правке этого документа».** Формулировка была отложенной документационной задачей внутри архитектурного документа — запрещённый по CLAUDE.md § Документация паттерн («планы живут в тасклистах»). Дисциплина синхронизации `sites-available`/`sites-enabled`, которую фраза откладывала, на самом деле уже полностью выведена из текста шага 3 runbook'а (резервная копия → перенос содержимого в `sites-available` → замена `sites-enabled` на симлинк): переписано прямой констатацией факта («канонический конфиг живёт в `sites-available`, `sites-enabled` — симлинк на него; последующие правки вносятся в `sites-available`») вместо обещания зафиксировать это в будущем.
- Фиксы 3–5 — только правки трёх файлов конфигурации/документации, кода нет; `make check` прогнан оркестратором в рамках общей ре-верификации фикс-раунда (зелёный).
