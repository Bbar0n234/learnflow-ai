# Test Cases: chore-001 (B) — Prod-closing / трек T4 (SIEM kill-switch)

Трек гасит SIEM в проде тремя независимыми тумблерами, ничего не удаляя из кода: python-процесс
перестаёт эмитить security-события в Redis Stream (`SIEM_ENABLED`), compose перестаёт поднимать и
собирать `siem-service`/`siem-db` (`COMPOSE_PROFILES` + `profiles:`), а сборка фронта выбрасывает роут
`/security` и кнопку «Безопасность» (build-time `VITE_SIEM_ENABLED`, выводится из `SIEM_ENABLED` через
`build.args`). Дефолты у всех трёх — «включено», поэтому dev ведёт себя как раньше.

Кейсы страхуют три вещи. Первая — что каждый слой гасится **сам по себе** и проверяется отдельным
наблюдаемым признаком: строкой в логе старта, списком `docker compose config --services`, поведением
собранного фронта. Вторая — что «выключено флагом» и «Redis недоступен» остаются **различимыми**
состояниями: до трека оба давали одинаково пустой холдер и одинаковую тишину, и именно молчаливая
деградация запрещена брифом (§ 1 «Принятые следствия»). Третья — что выключение ничего не ломает
рядом: Redis остаётся живым (на нём висит `TraceStore` фидбека), structlog-процессор остаётся в
цепочке и молча дропает события, продьюсеры в `auth.py`/`guard.py` не знают, что подсистема выключена,
а `siem_pgdata` не теряется, так что обратное включение стоит двух строк в `.env` плюс пересборки
образа.

Единственное изменение dev-поведения по умолчанию — профили compose: «профиль включён по умолчанию»
выразить нельзя, поэтому в уже существующий локальный `.env` строку `COMPOSE_PROFILES=siem` нужно
дописать руками, иначе `make docker-up` перестанет поднимать SIEM-контейнеры. Это осознанная цена
решения и **предусловие половины кейсов ниже** — см. первый кейс Layer 2.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер, прод-VM); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости (структура БД, метрики, Redis state, Langfuse); `🔴` — проверка реальных инъекций / атак / security-событий; `[auto]` — кейс закрыт автотестом (живёт в `tests/<scope>/`); `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check`/`make check-fe`/`make test`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты: structlog (JSON stdout), состояние Redis Streams (`XLEN security.events`, `XINFO STREAM`), `docker compose ps` / `config`, БД siem-service. Код читать только там, где поведение иначе не наблюдаемо (явно отмечать). Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста), не сам тестировщик.

**Скоуп по трекам.** Кейсы с префиксом трека (`{T4.1}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST (`{track_id}=final`). Не пропускать кейсы молча — неприменимый помечать причиной.

**Отдельно про docker.** Кейсы, требующие живого `docker build` / `docker compose up`, писались как
deferred до INTEGRATION_TEST: на момент написания docker-сеть на машине архитектора была сломана.
Сеть починена, и все девять прогнаны на живом стеке (условия — в преамбуле Layer 1); без живого
docker остался только `{T4.9}` — ему нужен nginx-контур прод-VM, которого в этом репозитории нет.
Кейсы на `docker compose config` сети и демона не требуют и проходятся сразу (Layer 0).

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура: полный стек `make docker-up` — трек проверяется именно на собранном образе, потому что build-time флаг фронта вшивается на `docker compose build`, а не читается процессом. Для быстрых проверок слоя 1 годится `make docker-up-db` + `make dev`, но UI-половину так не проверить.
2. Кейсы требуют **трёх** прогонов стека: dev-профиль (`COMPOSE_PROFILES=siem`, `SIEM_ENABLED` не задан), прод-профиль (`COMPOSE_PROFILES=` пусто, `SIEM_ENABLED=false`) и один рассинхрон (`COMPOSE_PROFILES=siem` + `SIEM_ENABLED=false`). Флаг читается один раз в lifespan, UI-флаг — на сборке: между режимами нужен `docker compose build && up -d`, не рестарт.
3. Акторы: обычный **user-a** и **admin** (`make grant-admin USER=<name>`) — кнопка «Безопасность» admin-only, без админа UI-половину кейсов не увидеть.
4. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.
5. После прогона — сводка (pass / failed / **deferred**). Deferred — кейсы 👤 и заблокированные (сломанная docker-сеть, нет доступа к прод-VM): отдельным счётчиком + причина по каждому.

## Дизайн автотестов

**Покрываем автотестом:**

### `test_settings_contract.py` — env-поверхность тумблера `SIEM_ENABLED`

1. **Файл**: `backend/tests/siem_toggle/test_settings_contract.py` — solitary-unit над `Settings`; швов нет, инфры нет.
2. **Тестирует**: `app.config :: Settings.siem_enabled`.
3. **Суть**: суита фиксирует контракт той стороны тумблера, которую администратор набирает руками в боевом `.env`. Она гарантирует безопасный дефолт (машина, ничего не знающая о переменной, ведёт себя как до трека), закрепляет **канонический** off — литеральное `false`, которое предписывает runbook, — и отдельным кейсом проговаривает асимметрию стыка: прочие falsy-написания (`0`, `False`, `no`, `off`) pydantic принимает и эмиссию гасит, но до слоя 3 они не доезжают, потому что compose отдаёт строку во фронт **как есть** (`VITE_SIEM_ENABLED: ${SIEM_ENABLED:-true}`, нормализации нигде на пути нет), а фронтовое правило — `!== "false"`. То есть `SIEM_ENABLED=0` в боевом `.env` даёт половинчатое выключение: событий нет, а кнопка и роут остались. Это контракт стыка, а не баг, и суита предъявляет его в одном месте, а не разносит по двум суитам как два независимо «правильных» ответа. Плюс главное свойство: опечатка роняет старт с `ValidationError` **по полю `siem_enabled`**, а не читается молча как «включено». Отдельным кейсом закреплена независимость двух тумблеров итерации: одна опечатка в имени поля `Settings` связала бы `SIEM_ENABLED` с `LLM_DEFENSE_ENABLED` невидимо.
4. **Кейсы**:
   - пустое окружение → `siem_enabled is True`;
   - канонический `false` → `False`;
   - `0` / `False` / `FALSE` / `no` / `off` → `False`, но значение не равно литеральному `false`, то есть UI остаётся включённым (parametrize, с комментарием-предупреждением про стык);
   - `true` / `1` / `True` → `True` (parametrize);
   - `off-please` → `ValidationError` с `match="siem_enabled"` — без привязки к полю тест зеленел бы от ошибки по `jwt_secret`, который приходит из корневого conftest, а не из теста;
   - `SIEM_ENABLED=false` при неустановленном `LLM_DEFENSE_ENABLED` → `siem_enabled is False`, `llm_defense_enabled is True`.
   - Каждый кейс сначала снимает переменную из окружения: Makefile сорсит `.env`/`.env.local` в шелл перед pytest, и без этого исход решала бы машина разработчика.

### `test_emission_startup.py` — слой 1: что `lifespan` строит под флагом и что при этом говорит

1. **Файл**: `backend/tests/siem_toggle/test_emission_startup.py` — integration-по-стилю unit над composition root; швы — подменённые в неймспейсе `app.main` `create_engine` (фейковый движок вместо Postgres), `create_redis` (стаб-клиент или `None`), `init_langfuse` (всегда `False`) и `setup_logging` (перехватывает процессор, который приложение реально собрало, вместо глобальной переконфигурации логирования). Сети нет, БД нет.
2. **Тестирует**: `app.main :: lifespan` — блок создания `RedisEventTransport` + `publisher_loop`; заодно `app.security_pipeline.processor :: make_security_event_processor` в связке с холдером, который приложение опубликовало в `app.state`.
3. **Суть**: суита проверяет ровно то, ради чего написан `if/elif` в композиционном корне: при выключенном флаге transport не создаётся и publisher-петля не стартует даже при живом Redis, а «выключено флагом» и «Redis лежит» остаются двумя различимыми состояниями — первое даёт ровно одну INFO-строку, второе не даёт ни одной. Она же страхует границы тумблера: сам Redis остаётся в `app.state` (на нём висит `TraceStore` фидбека), холдер публикуется в обоих режимах, а structlog-процессор остаётся в цепочке и при выключенном флаге молча пропускает security-событие, не роняя лог-путь. Позитивный двойник — при включённом флаге то же самое событие проходит холдер → transport → publisher-петлю и доезжает до `xadd` в стрим `security.events`.
4. **Кейсы**:
   - флаг off при **доступном** Redis: холдер пуст, `security_publisher_task` не выставлен (гасит именно флаг, а не отсутствие брокера);
   - флаг off: `siem event emission disabled by flag` ровно один раз, `security event publisher started` — ни разу;
   - флаг off: `app.state.redis` — тот же самый клиент (выключение SIEM не выключает Redis);
   - флаг off: реальный процессор приложения пропускает security-событие, возвращает `event_dict` неизменным, в Redis ничего не уходит;
   - флаг on + Redis: холдер непуст, задача создана, `security event publisher started` ровно один раз, строки про флаг нет;
   - флаг on + Redis: событие лога доезжает до `xadd` в стрим `security.events` с правильным `event_type` — конец контраста с «молча дропает»; без него transport, созданный, но не привязанный к холдеру, оставил бы всю суиту зелёной;
   - флаг on + Redis недоступен (`create_redis` вернул `None`): холдера нет, задачи нет, **и** строки про флаг нет — ветки различимы;
   - в обоих режимах `app.state.security_transport_holder` — `EventTransportHolder`, процессор собран (parametrize).
   - **Почему lifespan обрывается.** Шва вокруг блока нет, а всё, что идёт после него, требует Postgres (LangGraph store/checkpointer), сети (валидация built-in MCP) и LLM. Поэтому подменены пограничные ресурсы, которые блок реально потребляет, а `create_store` — следующий по ходу кусок настоящей инфраструктуры — заменён сентинелом, который бросает исключение. Старт отрабатывает по-настоящему до конца тестируемого блока и там останавливается. Точка обрыва выбрана на инфраструктурном вызове намеренно: обычный рефакторинг внутри блока её не сдвинет.

### `feature-flags.test.ts` — семантика build-time флага фронта

1. **Файл**: `frontend/src/shared/config/feature-flags.test.ts` — unit над модулем-константой; шов — `vi.stubEnv` + `vi.resetModules()` и динамический импорт.
2. **Тестирует**: `frontend/src/shared/config/feature-flags.ts :: SIEM_ENABLED`.
3. **Суть**: флаг вычисляется один раз при импорте модуля, и тест воспроизводит ровно эту форму — переимпорт с подменённым `import.meta.env`, как в реальном бандле, где Vite вшивает значение на сборке и потом его никто не меняет. Проверяемое правило — opt-out, а не opt-in: любой путь сборки, не передающий build-arg (`make dev-fe`, голый `npm run build`, `vite dev`), обязан оставить Security-UI доступным, и только литеральная строка `"false"`, которую compose выводит из бэкендового `SIEM_ENABLED`, его убирает.
4. **Кейсы**: переменная не определена → `true`; `"false"` → `false`; `"true"`, `"1"`, `"0"`, `"no"`, `"False"`, `"FALSE"`, `""` → `true` (перечислены поимённо: это та половина, где оператор ошибается — `0` и `False` доезжают сюда неизменёнными и Security-страницу **не** прячут, хотя бэкенд по ним эмиссию уже погасил; вторая половина того же стыка закреплена в `test_settings_contract.py`).

### `Sidebar.test.tsx` — точка входа в Security-UI из сайдбара

1. **Файл**: `frontend/src/app/components/Sidebar.test.tsx` — integration (компонент + хуки + сеть); швы — MSW на `/api/auth/me`, `/api/projects`, `/api/chats/recent` и мок модуля `@/shared/config/feature-flags` через геттер (`vi.hoisted`), позволяющий отрендерить в одном файле оба бандла.
2. **Тестирует**: `frontend/src/app/components/Sidebar.tsx` — условие кнопки «Безопасность».
3. **Суть**: кнопку гейтят два независимых условия, и суита держит их независимыми — build-time флаг решает, существует ли фича в этом бандле, а admin-claim решает, можно ли её видеть этому пользователю. Флаг **сужает** RBAC, а не заменяет: не-админ не должен получить кнопку только потому, что флаг включён. Отдельным кейсом закреплено, что kill-switch убирает одну кнопку, а не навигацию вокруг неё. Флаг мокается на границе модуля, а не через `import.meta.env`: правила разбора строки закреплены в суите выше, и повторять их здесь значило бы завязать каждый кейс на парсинг вместо гейтинга.
4. **Кейсы**: флаг on + admin → кнопка есть; флаг on + не-admin → кнопки нет; флаг off + admin → кнопки нет; флаг off + admin → «Новый чат», «Новый проект» и секция «Проекты» на месте. Все кейсы ждут появления футера с именем пользователя — то есть профиль уже приехал; иначе «кнопки нет» проходило бы тривиально, просто по слишком раннему ассерту.

### `router.test.tsx` — роут `/security` под флагом

1. **Файл**: `frontend/src/app/router.test.tsx` — integration над деревом маршрутов; швы — те же MSW-хендлеры (профиль отдаётся с задержкой) и тот же мок модуля флагов.
2. **Тестирует**: `frontend/src/app/router.tsx :: AppRoutes`.
3. **Суть**: суита проверяет вторую половину UI-выключателя — в SIEM-off бандле роута `/security` не существует вовсе, а в SIEM-on он на месте и по-прежнему за RBAC-guard'ом. Наблюдаемость здесь бесплатная: роут вложен в бесшовный layout, поэтому «роута нет» видно прямо — не рендерится ни страница, ни обвязка вокруг неё, дерево выходит пустым. SIEM-on кейс удерживается на loading-состоянии guard'а (запрос профиля задержан) — этого достаточно, чтобы доказать совпадение роута, и это оставляет ленивую Security-страницу с её собственной сетью за рамками теста про роутинг.
4. **Кейсы**: флаг on, `/security` → рендерится guard (его «Загрузка...»); флаг off, `/security` → контейнер пуст, guard'а нет; флаг off, `/` → приложение работает как обычно (welcome-страница на месте).

**Инфраструктура тестов.** Добавлен один локальный хелпер — `frontend/src/test/match-media-polyfill.ts`
(в форме уже существующего `pointer-event-polyfill.ts`, вне замороженного харнеса): jsdom не реализует
`window.matchMedia`, а theme-store зовёт его на загрузке модуля, поэтому без полифилла не рендерится
никакое дерево с обвязкой приложения. `packages/testing` не трогался.

**Осознанно не покрываем автотестом** (*что — почему — куда уехало*):

- Слой 2 целиком (профили compose: `siem-service`/`siem-db` не поднимаются и не собираются при пустом `COMPOSE_PROFILES`) — это конфигурация внешнего инструмента, а не код приложения; pytest тут ничего не добавит к самому `docker compose config` → Layer 0 (`config --services`, сети не требует) + ручные `{T4.2}`, `{T4.5}`.
- Проводка build-time флага (`ARG`/`ENV` в стадии `frontend-build`, `build.args: VITE_SIEM_ENABLED: ${SIEM_ENABLED:-true}`) — проверяется рендером compose и реальной сборкой образа, а не тестом в jsdom: смысл фазы в том, что значение доезжает **до `vite build` внутри образа** → Layer 0 (`docker compose config`) + ручной `{T4.4}`.
- Отсутствие коллизии `SIEM_ENABLED` с `siem_service.config.Settings` (`env_prefix="SIEM_"`) — пакет `siem_service` не установлен в окружение backend'а (`uv run --package learnflow-backend python -c "import siem_service"` падает), а кросс-пакетную проверку в чужой тест-скоуп (`services/siem-service/tests/`) я не вношу — это чужая партиция → ручной `{T4.6}`, где рассинхрон `COMPOSE_PROFILES=siem` + `SIEM_ENABLED=false` поднимает оба процесса разом и коллизия проявилась бы падением старта siem-service.

**Замеченные прод-баги (для fixer'а, сам не чиню):** не найдено. Три наблюдения, ни одно не дефект —
фиксирую, чтобы их не приняли за находки на ревью диффа:

- В SIEM-off бандле прямой переход на `/security` даёт **пустую страницу**: роута нет, catch-all
  `404`-роута в `AppRoutes` тоже нет, поэтому не рендерится даже обвязка приложения. Это ровно то
  поведение, которое зафиксировал план T4.4 («роут не рендерится»), и путь недостижим из UI (кнопки
  нет). Заводить 404-роут — отдельное продуктовое решение, не задача kill-switch'а.
- Асимметрия пустых значений: `VITE_SIEM_ENABLED=` (пустая строка) означает «включено» (`""` не
  nullish, `?? "true"` не срабатывает, `"" !== "false"`), а `SIEM_ENABLED=` роняет старт бэкенда с
  `ValidationError`. Через docker-путь недостижимо: `${SIEM_ENABLED:-true}` рендерит пустое значение

  а пустым остаётся **лишь** `COMPOSE_PROFILES=`.
- Та же асимметрия у **непустых** falsy-написаний (находка R1): `SIEM_ENABLED=0` или `=False` гасят
  эмиссию (pydantic читает их как `False`), но во фронт compose отдаёт строку без нормализации, а
  правило флага — `!== "false"`, поэтому кнопка «Безопасность» и роут остаются в бандле. Резолюция

  буквально, канон выключения — литеральное строчное `false`. Закреплено с обеих сторон стыка
  (`test_settings_contract.py` + `feature-flags.test.ts`), предупреждение — в runbook и в Layer 0.
- `EncryptionService` при пустом `MCP_ENCRYPTION_KEY` пишет WARNING на каждом старте, попадающий в
  логи рядом с проверяемой INFO-строкой. К треку отношения не имеет, в кейсах не используется как
  сигнал — упоминаю, чтобы тестировщик не принял его за шум от выключения SIEM.
