# Test Cases: feat-001 — Видимость работы агента / трек T1

Трек T1 сделал серверную половину «видимости работы агента»: контракт SSE v2 (новый словарь
событий, heartbeat, терминальный `cancelled`, generic `security_block`), семантический
custom-канал, вложенность субагента через `parent_call_id`, typed parts в истории и попутные
фиксы аудита. Это **новая фича с изменением контракта**, а не поведение-сохраняющий рефактор:
события `tool_start`/`tool_end` исчезли, `error {"Request was cancelled."}` заменён на
`cancelled {}`, `security_block` потерял payload, `MessageOut` получил `parts`, один ход агента
теперь отдаётся одним сообщением истории вместо нескольких.

Кейсы страхуют ровно то, что в этом контракте ломается тихо. Половина трека — про события,
отсутствие которых ничего не роняет: пропавший `agent_event`, потерянный шаг субагента, не
закрытая строка срезанного guard'ом вызова, утёкшие в чат токены суммаризатора. Ни одна из этих
поломок не даёт исключения — поток просто становится беднее или грязнее, — поэтому каждая
покрыта отдельно и, где это имеет смысл, сквозным прогоном через настоящий `astream`.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости (структура БД, метрики, Redis state, Langfuse); `🔴` — проверка реальных инъекций / атак / security-событий; `[auto]` — кейс закрыт автотестом (живёт в `tests/<scope>/`); *(регресс)* — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check`/`make test`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты: structlog (JSON stdout), Langfuse traces, состояние БД (`checkpoint_blobs`), DevTools → Network (SSE-кадры). Код читать только там, где поведение иначе не наблюдаемо (явно отмечать). Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста).

**Скоуп по трекам.** Кейсы с префиксом трека (`{T1.1}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST. Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура: `make docker-up-db` (Postgres + Redis), `make migrate`, backend `make dev`. Фронт для кейсов этого трека не обязателен — SSE смотрится через DevTools или `curl -N`; для кейсов «как это выглядит в ленте» нужен `make dev-fe` (уже на готовом T2).
2. Актор: один обычный пользователь через UI register / `/api/auth/register`, с проектом и чатом.
3. Ключи: для {T1.1}/{T1.3}/{T1.4} нужны живой ключ reasoning-модели и рабочий MCP-сервер (firecrawl) — без них кейсы уходят в deferred с указанием причины.
4. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.

## Дизайн автотестов

Покрытие разложено по трём уровням. Мапперы (`TokenChunkMapper`, `StreamEventMapper`,
`emit_agent_event`, `HeartbeatPacer`, `CheckpointHistory`) закрыты solitary-юнитами — это чистые
трансляции, где дублей не нужно вовсе. Раннер закрыт двумя способами: скриптованным графом (когда
надо подать в канал ровно тот payload, который живая модель выдаёт редко) и **настоящим прогоном
через `astream`** (когда важно, что механизм вообще работает — writer резолвится, guard срезает
вызов, субагент дотягивается до родительского потока). Провод (`data: {json}`) и API-история
закрыты HTTP-интеграцией через ASGI-клиент с фейковым раннером.

**Покрываем автотестом** — по одной записи на суиту:

### `test_token_chunk_mapper.py` — маппер token-канала

1. **Файл**: `backend/tests/agent/test_token_chunk_mapper.py` — solitary-unit, без дублей (чистая функция над `AIMessageChunk`)
2. **Тестирует**: `app.agent.stream_events :: TokenChunkMapper.map_chunk`
3. **Суть**: Суита фиксирует, как поток токенов провайдера превращается в события ленты: вызов инструмента объявляется на первом же фрагменте (когда имя и id уже известны, а аргументы ещё нет), аргументы отдаются ровно один раз — в момент, когда накопленная строка впервые парсится как JSON, — и всё это правильно раскладывается по вызовам, когда их несколько или когда фрагмент несёт только `index`. Страхует от двух тихих поломок: «строка действия появляется поздно, уже после исполнения» и «аргументы приписаны не тому вызову».
4. **Кейсы**: text → `text_chunk`; reasoning-дельта → `reasoning_chunk`; чанк с обоими; пустой чанк молчит; ранний `tool_call_started` при незавершённом JSON; `tool_call_args` по завершении JSON; повторные фрагменты не дублируют ни то, ни другое; фрагмент без id коррелируется по `index`; два параллельных вызова ведутся независимо; **оборванная генерация (args так и не стали валидным JSON) не даёт `tool_call_args` вовсе**; args > 2 000 усечены с флагом; свежий инстанс не наследует состояние прошлого рана

### `test_stream_events.py` (дополнено) — маппер updates-канала

1. **Файл**: `backend/tests/agent/test_stream_events.py` — solitary-unit, payload узла как отдаёт LangGraph
2. **Тестирует**: `app.agent.stream_events :: StreamEventMapper.updates` / `note_call_announced`
3. **Суть**: Суита фиксирует, что результат исполнения отличим от ошибки, что артефакт объявляется по факту его наличия (а не по имени инструмента из белого списка), и что вызов, срезанный guard'ом после генерации, закрывается событием `tool_call_cancelled`. Последнее — самое хрупкое место словаря: срез узнаётся по форме сообщения, поэтому суита отдельно проверяет, что обычный текстовый ответ и независимая редакция `ToolMessage` за срез **не** принимаются.
4. **Кейсы**: (существующие) старт вызова в updates больше не эмитится, `tool_result` из `ToolMessage`, `artifact_created` с ремапом `type`, отсутствие артефакта; (новые) `status="error"` у упавшего инструмента; усечение `content` с флагом; артефакт у инструмента вне бывшего whitelist; срез guard'ом отменяет все анонсированные вызовы в порядке анонса; разрешённый вызов не отменяется; отмена ровно один раз; обычный ответ не считается срезом; редактированный `ToolMessage` не считается срезом

### `test_agent_events.py` — хелпер эмиссии доменных событий

1. **Файл**: `backend/tests/agent/test_agent_events.py` — solitary-unit, contextvar-скоуп как его выставляет обёртка субагента
2. **Тестирует**: `app.agent.agent_events :: emit_agent_event`
3. **Суть**: Суита проверяет, что инструмент может звать хелпер откуда угодно, ничего не зная про стрим: вне графа это молчаливый no-op (иначе десятки существующих тестов, зовущих `tool.ainvoke` напрямую, падали бы с `KeyError`), при явно переданном writer'е событие уходит именно в него, а привязка к родительскому вызову берётся из контекста, а не из аргументов. Заодно фиксирует, что словарь доменных kind'ов закрыт — опечатка в имени падает на месте эмиссии, а не утекает на провод отдельным типом события.
4. **Кейсы**: вне графового рантайма — no-op; явный writer получает событие; `parent_call_id` появляется под субагентом и отсутствует вне его; все четыре документированных kind'а принимаются; недокументированный отвергается; строковые значения payload усекаются; нестроковые проходят как есть

### `test_heartbeat.py` — пейсер тишины и отмены

1. **Файл**: `backend/tests/agent/test_heartbeat.py` — solitary-unit, источник событий под управлением теста (`asyncio.Event`, без сна по часам)
2. **Тестирует**: `app.agent.heartbeat :: HeartbeatPacer.pace`
3. **Суть**: Суита проверяет две гарантии, которые пейсер держит на одном таймере: клиент не сидит в необъяснённой тишине, и отмена замечается, даже когда граф завис внутри одной итерации. Отдельно фиксирует, что пейсер ничего не глотает — исключение источника пролетает наружу, а закрытие потребителем закрывает и сам ран, а не оставляет его тянуть события в фоне.
4. **Кейсы**: дефолтный интервал — документированные 5 с; тишина даёт `heartbeat`, затем событие источника; при непрерывном потоке heartbeat не появляется; отмена во время блокировки даёт терминальный `cancelled` и закрывает источник; исчерпание источника завершает поток; исключение источника не проглатывается; ранний `aclose` потребителя закрывает источник

### `test_runner_stream_contract.py` — раннер на скриптованном графе

1. **Файл**: `backend/tests/agent/test_runner_stream_contract.py` — sociable-unit, фейковый граф (реальные коллабораторы: enforcer с выключенным guard'ом, `CheckpointHistory` над `InMemorySaver`, отключённый трейсер)
2. **Тестирует**: `app.agent.runner :: LangGraphAgentRunner.stream`
3. **Суть**: Суита фиксирует собственную работу раннера — то, как он переводит три канала графа в контракт и как ведёт жизненный цикл потока. Скриптованный граф нужен там, где надо подать в канал именно тот payload, который живая модель выдаёт редко или недетерминированно: доменный конверт custom-канала, lifecycle-конверт субагента, срезанный guard'ом ход. Отдельно страхует границу «reasoning идёт живьём мимо guard'а, текст — через guard» с обеих сторон, чтобы ни одна половина не проходила по случайности, и изоляцию состояния мапперов между ранами: двух последовательных `stream()` на одном инстансе раннера достаточно, чтобы поймать возврат к общим (не per-run) мапперам — той самой поломке, которую фаза T1.4 чинила в `main.py`.
4. **Кейсы**: `stream_started` — первое событие и уходит до setup-фазы; доменный kind заворачивается в `agent_event`; он же сохраняет `parent_call_id`; lifecycle-конверт субагента пробрасывается своим типом; конверт без `type` игнорируется; анонсированный вызов, срезанный guard'ом, даёт `tool_call_cancelled` после `tool_call_started`; **второй ран того же раннера снова анонсирует повторившийся `call_id`**; **срез в позднем ране не отменяет вызов раннего**; ход только из reasoning не запускает финальное ревью; reasoning не доходит до guard'а, текст — доходит; отмена во время застрявшего графа завершает поток; отмена между итерациями завершает поток; завершившийся ран не оставляет состояния отмены (и после нормального конца, и после раннего блока на USER_INPUT)

### `test_runner.py` (дополнено) — раннер на настоящем графе

1. **Файл**: `backend/tests/agent/test_runner.py` — integration (sociable), реальный `GraphFactory` + реальный `astream`, фейковая модель в шве
2. **Тестирует**: `app.agent.runner :: LangGraphAgentRunner.stream` в связке с `graph.py`, `tools/subagents.py`, `subagents/runner.py`
3. **Суть**: Здесь проверяется, что механизмы вообще работают на живом пути, а не только в разложенном на части виде. Настоящий инструмент зовёт `emit_agent_event` — и событие доезжает до провода; настоящий guard срезает сгенерированный вызов — и раннер узнаёт срез по форме сообщения, которую guard реально производит (а не по той, которую предположил тест); настоящий субагент исполняет свой инструмент — и его шаги выходят в **родительский** поток с `parent_call_id`, пока его собственные токены остаются за бортом. Каждый из этих трёх кейсов страхует поломку, которая иначе не краснеет нигде.
4. **Кейсы**: (новые) доменное событие инструмента доезжает до потока и стоит между стартом вызова и его результатом; шаги субагента приходят в родительский поток с `parent_call_id`, внешний вызов — без него, токены субагента не в чате; срезанный настоящим guard'ом вызов даёт `tool_call_cancelled` и не даёт `tool_result`; reasoning доезжает до потока через настоящий граф и не смешивается с текстом

### `test_compaction_stream.py` — компакция глазами пользователя

1. **Файл**: `backend/tests/agent/test_compaction_stream.py` — integration, настоящий граф с настоящим `_reduce_context`, фейковые основная и суммаризующая модели
2. **Тестирует**: `app.agent.graph :: _reduce_context` через `LangGraphAgentRunner.stream`
3. **Суть**: Суита страхует попутный фикс №1 аудита ровно так, как он ломается: если изоляция суммаризатора отвалится, текст сводки просто окажется вклеен в ответ ассистента, и ни одно исключение об этом не сообщит. Компакция провоцируется честно — крошечным бюджетом контекста, на котором второй ход треда переходит порог, — а не вызовом приватного хелпера. Заодно фиксируется вторая половина контракта: сам факт компакции виден как `agent_event`, и только когда она действительно случилась.
4. **Кейсы**: компакция объявлена событием и текст сводки не попал в ответ; ход в пределах бюджета не сообщает о компакции. **Проверено мутацией**: снятие `"callbacks": []` в `graph.py` красит первый кейс (сводка приходит в `text_chunk`)

### `test_graph.py` (дополнено) — цена проверки и писатель под обёрнутым узлом

1. **Файл**: `backend/tests/agent/test_graph.py` — unit на настоящем графе с фейковой моделью, стаб-guard считает свои вызовы
2. **Тестирует**: `app.agent.graph :: build_graph` (узлы `agent`/`tools`) в связке с `app.agent.tool_guards :: execute_tools_guarded`
3. **Суть**: Проверка результата инструмента переехала внутрь узла `tools`, и добавленные кейсы сторожат две вещи, которые от этого переезда стали хрупкими. Первая — цена: каждый чекпоинт стоит вызова LLM, поэтому «результат проверен» — половина контракта, вторая половина «проверен один раз». Кейсы считают не факт проверки, а точную последовательность чекпоинтов, которую тратит ход: возврат предпроверки в узел `agent` удваивает трафик классификатора и дублирует security-warning, но не меняет ни одного сообщения на выходе — увидеть это можно только счётом. Вторая — писатель: тело инструмента резолвит stream writer на уровень глубже, из конфига, который обёртка передаёт `ToolNode`, и подмена этого конфига на любой другой тихо уносит из ленты доменные события всех инструментов. Отдельный кейс держит тот же инвариант на включённом guard'е: в этом коде уже есть прецедент «отвязать вложенный вызов от рана, передав ему `callbacks: []`» (`_reduce_context`), и повторение приёма вокруг `ToolNode` не задело бы ни один guard-ассерт.
4. **Кейсы**: (новые) ход с одним вызовом тратит ровно `[TOOL_CALL_ARG, TOOL_RESULT]`; вторая итерация ReAct не переклассифицирует батч первой (`[ARG, RESULT, ARG, RESULT]` на два результата); доменное событие инструмента доходит до custom-канала при включённом guard'е, который редактирует этот же батч

### `test_tool_guards.py` — деградация проверки результата

1. **Файл**: `backend/tests/agent/test_tool_guards.py` — solitary-unit, стаб-узел инструментов и состояние, собранное руками; вызов делается изнутри `RunnableLambda`, потому что обёртка читает конфиг из ambient-контекста
2. **Тестирует**: `app.agent.tool_guards :: execute_tools_guarded`
3. **Суть**: Здесь единственное место, где результат инструмента проверяется до того, как попадёт на провод и в чекпоинт, поэтому две дороги, на которых проверка может выродиться, важнее их достижимости: выход узла, в котором нет батча `ToolMessage` (так `ToolNode` отвечает, как только инструмент вернул `Command`), и состояние, из которого не читается беседа (Pydantic- или dataclass-схема вместо `MessagesState`). Штатным путём сегодня недостижимы ни та, ни другая — оба графа на `MessagesState`, `Command` не возвращает ни один инструмент, — и делать их достижимыми правкой прода нельзя, поэтому суита ведёт обёртку напрямую. Ассерты идут парами: что стало с батчем и что осталось об этом в логе. Смысл пары в том, что fail-safe разрешает пропустить ход, когда проверка не может отработать в полную силу, но не разрешает сделать это молча — а тихая деградация как раз и превращает латентную ветку в инцидент, который потом не к чему привязать.

   `tool_calls` и молча возвращает `[]`, то есть не проверяет ничего. Сегодня недостижимо: оба

Обе ветки открываются молча — при появлении первого же `Command`-инструмента или смены схемы
состояния дыра вернётся без единого красного теста. Решение (громкий лог/исключение на
неожиданную форму против явной поддержки `Command`-ветки) — за архитектором; тест на выбранное
поведение — за test-author после решения.

### R4. Дрейф-гейт заголовка держится, но через тестовую константу и три просканированных модуля — minor `[test]`, информационная

Проверено мутацией в две ступени. Ступень 1: в прод добавлен новый тип события
(`StreamEvent(type="brand_new_type")` в `app/agent/runner.py`) — краснеет только
`test_runner_emits_only_the_agreed_wire_vocabulary`, а `test_title_trigger_classifies_every_runner_event_type`
остаётся зелёным, потому что сверяется с тестовой константой `RUNNER_FORWARDED_TYPES`
(`backend/tests/chat/conftest.py:118`), а не с продом. Ступень 2: тип добавлен в константу —
краснеет и гейт заголовка, и `test_chat_service_forwards_each_runner_type_and_consumes_trace_id`.
Цепочка замыкается: «новый тип нельзя протащить, не приняв решение о заголовке» выполняется.

Остаточная щель: AST-скан видит только `StreamEvent(type="<литерал>")` в трёх модулях
(`runner` / `stream_events` / `heartbeat`) плюс dict-литералы `subagents/runner.py` (F3 первого
раунда). Тип, рождённый в другом модуле или через нелитеральный `type=`, минует оба гейта. Цена
промаха теперь на безопасной стороне (неклассифицированный тип не попадает в
`_TITLE_GUARD_CLEARED_TYPES` → чат теряет имя, утечки нет) — это и есть выигрыш от переворота
предиката, поэтому находка информационная.

Там же ремарка: гейт читает модуль-приватную `_TITLE_GUARD_CLEARED_TYPES`, то есть прибит к имени
константы (мутация «вернуть старую схему» красит его через `AttributeError`, а не через ассерт).
Для стража дрейфа это осознанная цена, как и у соседних AST-сканов; поведенческий оракул стоит
отдельно (кейсы отмены), так что дубля контракта нет.
