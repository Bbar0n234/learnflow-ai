# Test Cases: feat-001 — Видимость работы агента / трек T1

Трек T1 сделал серверную половину «видимости работы агента»: контракт SSE v2 (новый словарь
событий, heartbeat, терминальный `cancelled`, generic `security_block`), семантический
custom-канал, вложенность субагента через `parent_call_id`, typed parts в истории и попутные
фиксы аудита. Это **новая фича с изменением контракта**, а не поведение-сохраняющий рефактор:
события `tool_start`/`tool_end` исчезли, `error {"Request was cancelled."}` заменён на
`cancelled {}`, `security_block` потерял payload, `MessageOut` получил `parts`, один ход агента
теперь отдаётся одним сообщением истории вместо нескольких.

Кейсы страхуют ровно то, что в этом контракте ломается тихо. Половина трека — про события,
отсутствие которых ничего не роняет: пропавший `agent_event`, потерянный шаг субагента, не
закрытая строка срезанного guard'ом вызова, утёкшие в чат токены суммаризатора. Ни одна из этих
поломок не даёт исключения — поток просто становится беднее или грязнее, — поэтому каждая
покрыта отдельно и, где это имеет смысл, сквозным прогоном через настоящий `astream`.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости (структура БД, метрики, Redis state, Langfuse); `🔴` — проверка реальных инъекций / атак / security-событий; `[auto]` — кейс закрыт автотестом (живёт в `tests/<scope>/`); *(регресс)* — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check`/`make test`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты: structlog (JSON stdout), Langfuse traces, состояние БД (`checkpoint_blobs`), DevTools → Network (SSE-кадры). Код читать только там, где поведение иначе не наблюдаемо (явно отмечать). Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста).

**Скоуп по трекам.** Кейсы с префиксом трека (`{T1.1}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST. Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура: `make docker-up-db` (Postgres + Redis), `make migrate`, backend `make dev`. Фронт для кейсов этого трека не обязателен — SSE смотрится через DevTools или `curl -N`; для кейсов «как это выглядит в ленте» нужен `make dev-fe` (уже на готовом T2).
2. Актор: один обычный пользователь через UI register / `/api/auth/register`, с проектом и чатом.
3. Ключи: для {T1.1}/{T1.3}/{T1.4} нужны живой ключ reasoning-модели и рабочий MCP-сервер (firecrawl) — без них кейсы уходят в deferred с указанием причины.
4. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.

## Дизайн автотестов

Покрытие разложено по трём уровням. Мапперы (`TokenChunkMapper`, `StreamEventMapper`,
`emit_agent_event`, `HeartbeatPacer`, `CheckpointHistory`) закрыты solitary-юнитами — это чистые
трансляции, где дублей не нужно вовсе. Раннер закрыт двумя способами: скриптованным графом (когда
надо подать в канал ровно тот payload, который живая модель выдаёт редко) и **настоящим прогоном
через `astream`** (когда важно, что механизм вообще работает — writer резолвится, guard срезает
вызов, субагент дотягивается до родительского потока). Провод (`data: {json}`) и API-история
закрыты HTTP-интеграцией через ASGI-клиент с фейковым раннером.

**Покрываем автотестом** — по одной записи на суиту:

### `test_token_chunk_mapper.py` — маппер token-канала

1. **Файл**: `backend/tests/agent/test_token_chunk_mapper.py` — solitary-unit, без дублей (чистая функция над `AIMessageChunk`)
2. **Тестирует**: `app.agent.stream_events :: TokenChunkMapper.map_chunk`
3. **Суть**: Суита фиксирует, как поток токенов провайдера превращается в события ленты: вызов инструмента объявляется на первом же фрагменте (когда имя и id уже известны, а аргументы ещё нет), аргументы отдаются ровно один раз — в момент, когда накопленная строка впервые парсится как JSON, — и всё это правильно раскладывается по вызовам, когда их несколько или когда фрагмент несёт только `index`. Страхует от двух тихих поломок: «строка действия появляется поздно, уже после исполнения» и «аргументы приписаны не тому вызову».
4. **Кейсы**: text → `text_chunk`; reasoning-дельта → `reasoning_chunk`; чанк с обоими; пустой чанк молчит; ранний `tool_call_started` при незавершённом JSON; `tool_call_args` по завершении JSON; повторные фрагменты не дублируют ни то, ни другое; фрагмент без id коррелируется по `index`; два параллельных вызова ведутся независимо; args > 2 000 усечены с флагом; свежий инстанс не наследует состояние прошлого рана

### `test_stream_events.py` (дополнено) — маппер updates-канала

1. **Файл**: `backend/tests/agent/test_stream_events.py` — solitary-unit, payload узла как отдаёт LangGraph
2. **Тестирует**: `app.agent.stream_events :: StreamEventMapper.updates` / `note_call_announced`
3. **Суть**: Суита фиксирует, что результат исполнения отличим от ошибки, что артефакт объявляется по факту его наличия (а не по имени инструмента из белого списка), и что вызов, срезанный guard'ом после генерации, закрывается событием `tool_call_cancelled`. Последнее — самое хрупкое место словаря: срез узнаётся по форме сообщения, поэтому суита отдельно проверяет, что обычный текстовый ответ и независимая редакция `ToolMessage` за срез **не** принимаются.
4. **Кейсы**: (существующие) старт вызова в updates больше не эмитится, `tool_result` из `ToolMessage`, `artifact_created` с ремапом `type`, отсутствие артефакта; (новые) `status="error"` у упавшего инструмента; усечение `content` с флагом; артефакт у инструмента вне бывшего whitelist; срез guard'ом отменяет все анонсированные вызовы в порядке анонса; разрешённый вызов не отменяется; отмена ровно один раз; обычный ответ не считается срезом; редактированный `ToolMessage` не считается срезом

### `test_agent_events.py` — хелпер эмиссии доменных событий

1. **Файл**: `backend/tests/agent/test_agent_events.py` — solitary-unit, contextvar-скоуп как его выставляет обёртка субагента
2. **Тестирует**: `app.agent.agent_events :: emit_agent_event`
3. **Суть**: Суита проверяет, что инструмент может звать хелпер откуда угодно, ничего не зная про стрим: вне графа это молчаливый no-op (иначе десятки существующих тестов, зовущих `tool.ainvoke` напрямую, падали бы с `KeyError`), при явно переданном writer'е событие уходит именно в него, а привязка к родительскому вызову берётся из контекста, а не из аргументов. Заодно фиксирует, что словарь доменных kind'ов закрыт — опечатка в имени падает на месте эмиссии, а не утекает на провод отдельным типом события.
4. **Кейсы**: вне графового рантайма — no-op; явный writer получает событие; `parent_call_id` появляется под субагентом и отсутствует вне его; все четыре документированных kind'а принимаются; недокументированный отвергается; строковые значения payload усекаются; нестроковые проходят как есть

### `test_heartbeat.py` — пейсер тишины и отмены

1. **Файл**: `backend/tests/agent/test_heartbeat.py` — solitary-unit, источник событий под управлением теста (`asyncio.Event`, без сна по часам)
2. **Тестирует**: `app.agent.heartbeat :: HeartbeatPacer.pace`
3. **Суть**: Суита проверяет две гарантии, которые пейсер держит на одном таймере: клиент не сидит в необъяснённой тишине, и отмена замечается, даже когда граф завис внутри одной итерации. Отдельно фиксирует, что пейсер ничего не глотает — исключение источника пролетает наружу, а закрытие потребителем закрывает и сам ран, а не оставляет его тянуть события в фоне.
4. **Кейсы**: дефолтный интервал — документированные 5 с; тишина даёт `heartbeat`, затем событие источника; при непрерывном потоке heartbeat не появляется; отмена во время блокировки даёт терминальный `cancelled` и закрывает источник; исчерпание источника завершает поток; исключение источника не проглатывается; ранний `aclose` потребителя закрывает источник

### `test_runner_stream_contract.py` — раннер на скриптованном графе

1. **Файл**: `backend/tests/agent/test_runner_stream_contract.py` — sociable-unit, фейковый граф (реальные коллабораторы: enforcer с выключенным guard'ом, `CheckpointHistory` над `InMemorySaver`, отключённый трейсер)
2. **Тестирует**: `app.agent.runner :: LangGraphAgentRunner.stream`
3. **Суть**: Суита фиксирует собственную работу раннера — то, как он переводит три канала графа в контракт и как ведёт жизненный цикл потока. Скриптованный граф нужен там, где надо подать в канал именно тот payload, который живая модель выдаёт редко или недетерминированно: доменный конверт custom-канала, lifecycle-конверт субагента, срезанный guard'ом ход. Отдельно страхует границу «reasoning идёт живьём мимо guard'а, текст — через guard» с обеих сторон, чтобы ни одна половина не проходила по случайности.
4. **Кейсы**: `stream_started` — первое событие и уходит до setup-фазы; доменный kind заворачивается в `agent_event`; он же сохраняет `parent_call_id`; lifecycle-конверт субагента пробрасывается своим типом; конверт без `type` игнорируется; анонсированный вызов, срезанный guard'ом, даёт `tool_call_cancelled` после `tool_call_started`; ход только из reasoning не запускает финальное ревью; reasoning не доходит до guard'а, текст — доходит; отмена во время застрявшего графа завершает поток; отмена между итерациями завершает поток; завершившийся ран не оставляет состояния отмены (и после нормального конца, и после раннего блока на USER_INPUT)

### `test_runner.py` (дополнено) — раннер на настоящем графе

1. **Файл**: `backend/tests/agent/test_runner.py` — integration (sociable), реальный `GraphFactory` + реальный `astream`, фейковая модель в шве
2. **Тестирует**: `app.agent.runner :: LangGraphAgentRunner.stream` в связке с `graph.py`, `tools/subagents.py`, `subagents/runner.py`
3. **Суть**: Здесь проверяется, что механизмы вообще работают на живом пути, а не только в разложенном на части виде. Настоящий инструмент зовёт `emit_agent_event` — и событие доезжает до провода; настоящий guard срезает сгенерированный вызов — и раннер узнаёт срез по форме сообщения, которую guard реально производит (а не по той, которую предположил тест); настоящий субагент исполняет свой инструмент — и его шаги выходят в **родительский** поток с `parent_call_id`, пока его собственные токены остаются за бортом. Каждый из этих трёх кейсов страхует поломку, которая иначе не краснеет нигде.
4. **Кейсы**: (новые) доменное событие инструмента доезжает до потока и стоит между стартом вызова и его результатом; шаги субагента приходят в родительский поток с `parent_call_id`, внешний вызов — без него, токены субагента не в чате; срезанный настоящим guard'ом вызов даёт `tool_call_cancelled` и не даёт `tool_result`; reasoning доезжает до потока через настоящий граф и не смешивается с текстом

### `test_compaction_stream.py` — компакция глазами пользователя

1. **Файл**: `backend/tests/agent/test_compaction_stream.py` — integration, настоящий граф с настоящим `_reduce_context`, фейковые основная и суммаризующая модели
2. **Тестирует**: `app.agent.graph :: _reduce_context` через `LangGraphAgentRunner.stream`
3. **Суть**: Суита страхует попутный фикс №1 аудита ровно так, как он ломается: если изоляция суммаризатора отвалится, текст сводки просто окажется вклеен в ответ ассистента, и ни одно исключение об этом не сообщит. Компакция провоцируется честно — крошечным бюджетом контекста, на котором второй ход треда переходит порог, — а не вызовом приватного хелпера. Заодно фиксируется вторая половина контракта: сам факт компакции виден как `agent_event`, и только когда она действительно случилась.
4. **Кейсы**: компакция объявлена событием и текст сводки не попал в ответ; ход в пределах бюджета не сообщает о компакции. **Проверено мутацией**: снятие `"callbacks": []` в `graph.py` красит первый кейс (сводка приходит в `text_chunk`)

### `test_checkpoint_history.py` (дополнено) — сборка typed parts

1. **Файл**: `backend/tests/agent/test_checkpoint_history.py` — solitary-unit, стаб чекпоинтера (болезненная граница)
2. **Тестирует**: `app.agent.checkpoint_history :: CheckpointHistory.history`
3. **Суть**: Суита фиксирует правило «один ход агента = одно сообщение ассистента с упорядоченными parts» и все состояния, в которых ход может застать чекпоинт: вызов упал, вызов не успел разрешиться, аргументы и результат слишком велики, сообщение отредактировано, перед первым ходом лежит служебная сводка компакции. Ошибка в любом из них ломает историю молча — сообщения расползаются или теряется якорь `id`, по которому резолвятся `trace_id`, оценка и артефакты.
4. **Кейсы**: (существующие) ход с вызовом схлопывается в одно сообщение, редакция подменяет и `content`, и parts, парсинг `created_at`; (новые) несколько вызовов одного хода идут одним сообщением в порядке появления; упавший инструмент даёт `status="error"`; неразрешённый вызов даёт `pending` с пустым превью и якорем на последнем `AIMessage`; усечение `args` и `result_preview` с общим флагом; сводка компакции перед первым `HumanMessage` отбрасывается; тред без человеческого сообщения даёт пустую историю; два хода подряд не слипаются; пользовательские сообщения без parts; редактированный ход не показывает свой reasoning

### `test_stream_wire_contract.py` — SSE v2 на проводе

1. **Файл**: `backend/tests/chat/test_stream_wire_contract.py` — HTTP integration, async ASGI-клиент через `.stream()`, реальные репозитории, фейковый раннер
2. **Тестирует**: `app.api.routes.messages :: _event_generator` + `app.services.chat :: ChatService.send_message`
3. **Суть**: Суита фиксирует именно те JSON-кадры, на которые фронт диспетчерит по `event.type`, — это входной контракт трека T2, поэтому переименование поля здесь должно краснеть на бэкенде, а не всплывать в браузере. Отдельно проверяются три свойства контракта: вложенность выражается одним лишь `parent_call_id`, отмена — самостоятельное терминальное событие (а не `error`, который фронт раньше отличал по тексту), и транспорт остаётся passthrough — незнакомый тип события доезжает до клиента, иначе forward-compat не работал бы вовсе.
4. **Кейсы**: полный ход v2 (`stream_started` → `heartbeat` → `reasoning_chunk` → `tool_call_started`/`args`/`tool_result` → `agent_event` → `text_chunk` → `done`) с точными payload'ами; вложенные шаги несут `parent_call_id`, внешний вызов — нет; срезанный вызов закрывается и ход доходит до `done`; `cancelled` терминален без `done`; неизвестный тип события доезжает как есть

### `test_chat_routes.py` (дополнено) — typed parts в API

1. **Файл**: `backend/tests/chat/test_chat_routes.py` — HTTP integration, реальные репозитории на транзакционной сессии, фейковый раннер
2. **Тестирует**: `app.api.routes.chats :: get_chat` + `app.api.schemas.chats :: MessageOut`
3. **Суть**: Суита фиксирует форму, в которой след работы агента пересекает HTTP-границу: дискриминированные по `type` части, все поля `tool_call`-части, и сохранённая обратная совместимость — плоский `content` на месте, а сообщение без parts сериализуется пустым списком, а не падает.
4. **Кейсы**: ход с reasoning + вызовом + текстом отдаётся тремя частями с полными полями и прежним `content`; сообщение без parts отдаёт `[]`

### `test_subagent_lifecycle_events.py` — обёртка инструментов субагента

1. **Файл**: `backend/tests/subagents/test_subagent_lifecycle_events.py` — sociable-unit, настоящий граф субагента и его `ToolNode`, фейковая модель в шве `create_llm_from_config`
2. **Тестирует**: `app.agent.subagents.runner :: SubagentRunner.run` (обёртка исполнения) + `app.agent.tools.subagents :: run_subagent`
3. **Суть**: Суита закрывает механизм, который целиком держится на явной передаче writer'а: внутри субагентского графа `get_stream_writer()` работает, но пишет в никуда, поэтому доменное событие инструмента выживает только за счёт приоритета переданного writer'а — и суита проверяет именно это, вызывая настоящий инструмент из-под настоящего `ToolNode`. 4. **Кейсы**: вызов инструмента субагента даёт четыре события с `parent_call_id` и точными payload'ами; доменное событие изнутри доходит до родительского writer'а; упавший инструмент даёт `status="error"` с текстом ошибки, а сам субагент продолжает цикл; без writer'а обёртка не применяется и ран работает как раньше; после вызова (успешного и упавшего) контекст снят — последующее доменное событие в этот writer не попадает; `run_subagent` передаёт вниз собственный writer и `call_id`

- **Параллельные пользовательские стримы не смешивают состояние мапперов** — «свежий инстанс на ран» проверен на уровне маппера; поднимать два конкурентных стрима в одном тесте мешает один-соединение-на-тест транзакционный харнесс (`testing.md` § HTTP-тесты) → не покрываем, риск закрыт конструкцией (фабрики вместо общих инстансов).

**Замеченные прод-баги (для fixer'а, сам не чиню):** прод-багов не найдено — весь контракт, который удалось выразить автотестом, ведёт себя по документации. Три наблюдения ниже — не баги, но их стоит увидеть архитектору:

1. **Расхождение доки с реализацией по `truncated` у `agent_event`** `[doc]`. `streaming.md` § «Лимиты» говорит: «`args` / `content` / `payload`-строки `agent_event` — единый лимит 2 000 символов **+ флаг `truncated`**», а таблица событий у `agent_event` поля `truncated` не имеет, и `emit_agent_event` усекает строки молча. Тест закрепил поведение по таблице событий (усечение без флага) как более конкретное. Расхождение — в формулировке § «Лимиты»: либо оговорить, что флаг относится только к событиям, которые его несут, либо завести флаг и у `agent_event`.
2. **Custom-канал пробрасывает наружу любой `type`, не только lifecycle-типы субагента** `[prod, minor]`. Ветка «не доменный kind → отдать как есть» не ограничена списком `tool_call_started`/`tool_call_args`/`tool_result`: любой код, написавший в writer конверт с произвольным `type`, получит одноимённое событие верхнего уровня на проводе. Сегодня писателей ровно два (домен-тулы и обёртка субагента), forward-compat это и не запрещает, но защиты от опечатки в имени типа нет — в отличие от доменных kind'ов, где опечатка падает в `emit_agent_event`.
3. **`UserWarning` от pydantic в сквозном субагентном ране** `[prod, minor]`. Прогон `test_subagent_steps_reach_the_parent_stream_with_parent_call_id` даёт `PydanticSerializationUnexpectedValue ... field_name='context'` при исполнении `run_subagent` через настоящий `ToolNode`. На поведение не влияет (все ассерты зелёные), похоже на сериализацию `ToolRuntime` с типизированным контекстом; шум в логах прогона.

## Ручные кейсы + статусы

### Layer 1: Трек T1 — контракт SSE v2 и след работы агента

- [ ] `{T1.1}` 👤 📊 **Reasoning живой модели доезжает до чекпоинта.** Предусловие: в настройках выбрана настоящая reasoning-модель (ключ есть, `make dev` поднят). Действие: задать вопрос, требующий рассуждения; дождаться конца хода; посмотреть SSE-кадры в DevTools, затем перезагрузить чат и заглянуть в `checkpoint_blobs` соответствующего треда. Ожидаемо: `reasoning_chunk` идут в потоке живьём; после хода в сохранённом `AIMessage` присутствует непустой `additional_kwargs["reasoning"]`; тот же текст возвращается в `GET /chats/{id}` как `parts[type=reasoning]`. Фаза T1.1 закрыла это только на фейковой модели — поведение конкретного провайдера не проверялось, а проприетарные модели часто отдают суммированные рассуждения вместо сырых или не отдают их в стриме вовсе. Если reasoning не доезжает — это не баг трека, а вход для решения архитектора о точечном дособоре в узле графа.
- [ ] `{T1.2}` 👤 **Heartbeat в живой тишине и таймаут от него.** Предусловие: чат открыт, DevTools → Network → EventStream. Действие: отправить запрос, который заставит агента долго молчать (тяжёлый инструмент или медленный setup MCP). Ожидаемо: `stream_started` приходит сразу, до первых токенов; в любой паузе идут `heartbeat {}` с интервалом ~5 с; между обычными событиями heartbeat не появляется.
- [ ] `{T1.3}` 👤 **Ранний старт вызова на настоящем провайдере.** Действие: попросить агента что-нибудь найти (реальный MCP-инструмент, например `firecrawl_search`). Ожидаемо: `tool_call_started` с именем инструмента приходит **раньше**, чем `tool_call_args` (то есть до того, как модель дописала аргументы), а `tool_call_args` — до `tool_result`; аргументы в событии — валидный JSON вызова.
- [ ] `{T1.4}` 👤 **Шаги субагента в живом потоке и отзывчивая отмена.** Действие: попросить агента делегировать задачу субагенту (`run_subagent`) так, чтобы субагент сам сходил в инструмент; в середине исполнения нажать «отмена». Ожидаемо: в потоке видны события инструментов субагента с `parent_call_id`, равным `call_id` вызова `run_subagent`; `POST /cancel` завершает поток событием `cancelled {}` в пределах ~5 с, не дожидаясь конца инструмента; `done` не приходит; в логе `agent completed` статус `cancelled`, а не `client_disconnected`.
- [ ] `{T1.5}` 📊 **Компакция на длинном живом треде.** Предусловие: тред, накопивший контекст выше порога компакции. Действие: отправить ещё одно сообщение, следить за потоком. Ожидаемо: приходит `agent_event {kind: "compaction"}`; текст сводки **не** появляется в ответе ассистента; в Langfuse видна отдельная генерация с тегом `context_summarization`, не вложенная в пользовательский ход.
- [ ] `{T1.6}` 🔴 📊 **Срез вызова guard'ом на настоящей инъекции.** Предусловие: guard включён. Действие: спровоцировать инъекцию в аргументах вызова инструмента (сценарий из security-набора). Ожидаемо: анонсированный `tool_call_started` закрывается событием `tool_call_cancelled` с тем же `call_id`; `tool_result` по нему не приходит; ход завершается терминальным `security_block {}` без деталей (`reason`/`checkpoint`/`detection_layer` на проводе отсутствуют, но видны в Langfuse/SIEM); повторная отправка в этот тред отбивается `403`.
- [ ] `{T1.7}` **Фикстур имён соответствует живому старту.** Действие: поднять `make dev` с полным набором MCP-серверов, сверить лог собранных инструментов с `backend/contracts/agent-tool-names.json`. Ожидаемо: все internal- и built-in-MCP-имена из лога присутствуют в фикстуре; пользовательские MCP-инструменты в неё не попали.
