# Test Cases: feat-001 — Видимость работы агента / трек T2

Трек T2 сделал экранную половину «видимости работы агента»: ленту активности, которая рисует
работу агента одними и теми же строками в live и в истории, реестр человекочитаемых подписей
инструментов, переработанный stream-store и диспетчер SSE v2 со сторожем тишины от heartbeat.
Это **новая фича с изменением контракта**, а не поведение-сохраняющий рефактор: `ThinkingIndicator`
и `ToolIndicator` исчезли, `streamingText`/`activeTool`/`pendingImages` в сторе заменены лентой,
сообщение ассистента рендерится по `parts`, а `VITE_SSE_FIRST_BYTE_TIMEOUT_MS` ушла вместе с
first-byte-таймаутом.

Кейсы страхуют то, что в этой картине ломается тихо. Почти всё покрытие трека — про вещи, чья
поломка не даёт ни исключения, ни красного экрана: лента после перезагрузки показывает не то, что
пользователь видел живым; строка вызова теряет подпись; обрезанные сервером аргументы уезжают на
экран сырым обломком JSON; сторож тишины гасит живой поток или, наоборот, не срабатывает вовсе;
заблокированный ход оставляет на экране свои рассуждения. Ни одна из этих поломок не роняет
приложение — она просто врёт пользователю о том, что делал агент, — поэтому каждая покрыта
отдельным кейсом.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости (структура БД, метрики, Redis state, Langfuse); `🔴` — проверка реальных инъекций / атак / security-событий; `[auto]` — кейс закрыт автотестом (живёт рядом со слайсом, `frontend/src/**/*.test.tsx`); *(регресс)* — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe` / `make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты: DevTools → Network → EventStream (кадры SSE), DevTools → Console (логи через `@/shared/lib/logger`, там же предупреждение о неизвестном типе события), React DevTools для состояния стора, structlog бэкенда. Код читать только там, где поведение иначе не наблюдаемо (явно отмечать). Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста).

**Скоуп по трекам.** Кейсы с префиксом трека (`{T2.1}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST. Не пропускать кейсы молча — неприменимый помечать причиной.

## Дизайн автотестов

Покрытие разложено по трём уровням, ровно как советует `testing.md` § Frontend. Чистая модель ленты
и реестр подписей закрыты solitary-юнитами — это трансляции без зависимостей, где дублей не нужно
вовсе. Экран (`MessageItem`, `MessageList`) закрыт integration-тестами через RTL: запросы идут по
роли и тексту, то есть проверяется то, что видит пользователь, а не разметка. Диспетчер стрима
закрыт integration-тестом поверх настоящего `fetch` с MSW-стримом: события подаются кадрами
`data: {json}`, как их шлёт сервер, а таймеры сторожа тишины двигаются фейковыми часами.

Смоук-наборы, оставленные реализаторами фаз T2.1–T2.6, разобраны поимённо: кейсы, проверяющие
контракт, сохранены на месте, остальное дополнено или переписано. Помечено в записях суит ниже.

**Проверено мутацией** (прод-код правился временно, рабочее дерево после каждой проверки чистое):
(1) перенос перезавода сторожа тишины **за** проверку известности типа события — краснеет кейс
«перезаводит сторож тишины и на событии неизвестного типа», и только он; (2) возврат к
консервативному флагу усечения в адаптере истории (`result_truncated || args_truncated` — та самая
эвристика, которую T2.2 выбросила) — краснеют три кейса сразу: независимость флагов в модели,
эквивалентность live/история на ходе с усечением и маркер зоны на экране. То есть оба механизма
сторожатся не по чтению, а по факту.

**Покрываем автотестом** — по одной записи на суиту:

### `agent-tools.test.ts` — реестр подписей инструментов

1. **Файл**: `frontend/src/shared/config/agent-tools.test.ts` — solitary-unit, без дублей; фикстур имён бэкенда читается с диска в рантайме
2. **Тестирует**: `shared/config/agent-tools :: AGENT_TOOL_SIGNATURES` / `resolveToolSignature` / `describeToolCall` / `parseToolArgs`
3. **Суть**: Суита держит границу между машинным именем вызова и тем, что читает пользователь. Первая её половина — сторож полноты: имена берутся из фикстура, сгенерированного реестром бэкенда, поэтому инструмент, добавленный агенту без подписи, красит CI, а не тихо появляется в ленте сырым идентификатором. Вторая половина проверяет, что подпись действительно собирается из аргументов вызова — с теми формулировками, которые зафиксировал утверждённый мокап, — и что ни одна нештатная форма аргументов её не роняет: обрезанная сервером строка не парсится вовсе, битый JSON, массив и скаляр отвергаются, а пустое значение не даёт пустого «· ».
4. **Кейсы**: фикстур прочитан и непуст; каждое имя фикстура имеет запись реестра с непустой подписью; имя вне реестра даёт сырое имя плюс пометку «инструмент MCP»; `run_subagent` присутствует в фикстуре (вложенность узнаётся по имени); шесть представительных инструментов читаются как «действие · дополнение»; три типа субагента получают своё читаемое имя, неизвестный — базовое; вызов без аргументов подписан без дополнения; усечённые аргументы не разбираются; битый JSON не роняет подпись; пустое значение не даёт дополнения; `parseToolArgs` возвращает объект на целой строке и `null` на усечении, обрыве, массиве, скаляре, `null` и пустой строке; целая строка при поднятом флаге усечения всё равно не разбирается

### `agent-feed.test.ts` — чистая модель ленты

1. **Файл**: `frontend/src/shared/lib/agent-feed.test.ts` — solitary-unit, момент времени подаётся аргументом (без подмены системных часов)

3. **Суть**: Здесь живёт главное требование итерации — «живая лента совпадает с историей». Суита подаёт один и тот же ход двумя путями (последовательностью событий SSE и списком `parts`) и требует эквивалентной структуры: не только на happy-path, но и на ходе с двумя вызовами, ошибкой инструмента и раздельно поднятыми флагами усечения, где расхождение стоит дороже всего. Дальше суита фиксирует жизненный цикл вызова по `call_id` (включая параллельные, повторный анонс, результат без анонса и срез guard'ом), вложенность субагента по `parent_call_id` на произвольной глубине, редакцию хода и то, что события вне ленты — служебные, терминальные и неизвестного типа — не оставляют на ней следа. Отдельно проверяется, что редьюсер не переписывает состояние на месте: мутация не разбудила бы подписчиков стора и оставила бы на экране предыдущий кадр.
4. **Кейсы**: накопление чанков одного типа; рассуждения и ответ раздельными элементами; новый элемент после строки действия; старт вызова с моментом старта; аргументы и закрытие результатом с длительностью; срез в `cancelled`; параллельные вызовы закрываются независимо; повторный анонс не задваивает строку; результат без анонса даёт строку; аргументы и отмена неизвестного вызова игнорируются; редьюсер не мутирует прежнее состояние; вложенность по `parent_call_id`; неизвестный родитель оставляет элемент в корне; адресация вложенного вызова на второй глубине; порядок шагов субагента; неизвестный тип события следа не оставляет; десять служебных и терминальных событий ленту не трогают; `agent_event` даёт строку только на компакцию; остальные kind'ы и неизвестный поглощаются; редакция заменяет ленту заглушкой и глушит пять последующих мутирующих событий; адаптер истории переносит `pending`, три статуса и оба флага усечения раздельно; порядок частей; пустые `parts`; эквивалентность live/история на простом ходе, на ходе с ошибкой и усечением и на ходе, оборванном отменой; блоки ленты, пустая лента, ход из одного текста

### `useAgentStream.test.ts` — диспетчер SSE v2

1. **Файл**: `frontend/src/pages/chat/model/useAgentStream.test.ts` — integration, MSW со стриминговым телом `text/event-stream`, фейковые таймеры под сторож тишины
2. **Тестирует**: `pages/chat/model/useAgentStream :: useAgentStream`
3. **Суть**: Суита закрывает единственное место, где словарь контракта превращается в содержимое экрана, и проверяет его с трёх сторон. Первая — маршрутизация: полный ход v2 подаётся кадрами, и суита требует, чтобы в ленте оказались все семь событий ленты в правильном порядке и с правильными статусами, включая срезанный guard'ом вызов; пропущенная ветка диспетчера ничего не роняет, она просто стирает часть работы агента из виду. Вторая — сторож тишины: он обязан взводиться до запроса (иначе сервер, не вернувший даже заголовков, оставляет пользователя в бесконечном ожидании), перезаводиться любым пришедшим кадром — включая `heartbeat` и событие типа, которого фронт ещё не знает, — и сниматься на терминальном событии, чтобы сервер, придержавший соединение открытым после `done`, не превратил успешный ход в ошибку. Третья — терминальные события и кэши: списки чатов рефетчатся на `done`, `cancelled` и `error`, потому что автозаголовок пишется в БД независимо от исхода хода, и не рефетчатся на блокировке, где генерация заголовка не запускается вовсе.
4. **Кейсы**: `done` отдаёт message/trace id; блокировка заменяет ленту одной заглушкой; блокировка оптимистично помечает чат заблокированным; блокировка закрывает стрим; `error` доносит detail; не-ok ответ отдаёт problem-сообщение; битый кадр пропускается, поток продолжается; отмена не даёт ошибки; unmount рвёт поток и сбрасывает стор; хвостовая ошибка после отмены подавлена; полное молчание сервера даёт таймаут ровно за порогом; heartbeat держит молчаливый поток живым; неизвестный тип не рвёт поток; он же перезаводит сторож тишины; сторож снимается на терминальном событии; `cancelled` закрывает поток без ошибки и рефетчит detail и оба списка; повтор POST после 401; `artifact_created` инвалидирует артефакты; обрыв без терминального события; сетевая ошибка; полный ход v2 доезжает до ленты; списки рефетчатся на терминальной ошибке; списки чатов проекта не рефетчатся на блокировке, detail и recents — рефетчатся; feat-002: патч заголовка в три кэша, отсутствие рефетча на `title_updated`, отсутствие кэшей не роняет ход, fallback-инвалидация на `done` ровно по своему ключу

### `MessageItem.test.tsx` — сохранённый ход на экране

1. **Файл**: `frontend/src/pages/chat/ui/MessageItem.test.tsx` — integration (RTL), запросы по роли и тексту
2. **Тестирует**: `pages/chat/ui/MessageItem` в связке с `ActivityFeed` / `ActivityRow` / `ActivityDetails`
3. **Суть**: Суита проверяет, что сохранённый ход читается как работа агента, а не как дамп: строка действия несёт подпись из реестра вместо машинного имени, разворот показывает зоны «Вызов» и «Результат» с сырым именем инструмента, а статус вызова выражен словом, а не одним цветом — все три состояния истории, включая `pending` у хода, оборванного отменой. Отдельная её половина — про большие и обрезанные данные: обрезанные сервером аргументы на экран сырой строкой не идут вовсе (оборванный посреди JSON текст читать нечем), маркер обрезки стоит ровно у той зоны, которую обрезали, а кнопка раскрытия не обещает того, чего сервер не прислал. ### `MessageList.test.tsx` — живой ход на экране

1. **Файл**: `frontend/src/pages/chat/ui/MessageList.test.tsx` — integration (RTL), лента собирается тем же редьюсером, что работает в сторе
2. **Тестирует**: `pages/chat/ui/MessageList` в связке с `ActivityFeed` / `ActivityPauseRow` / `StreamEndNotice` / `GeneratingArtifactCard`
3. **Суть**: Суита страхует второй столп брифа — «молчаливого UX не существует»: до первого события живёт строка-паузы, идущее действие светится точками и, если идёт дольше порога, счётчиком времени, а хвостовое рассуждение подписано процессом и развёрнуто без клика. Отдельным блоком суита сверяет живую ленту с историей: один и тот же ход рендерится обоими путями, и подписи строк обязаны совпасть — иначе перезагрузка страницы меняет пользователю картину работы агента на глазах. Третий блок — автопрокрутка: она обязана следовать за ростом ленты, а не за одним текстом, потому что ход из одних tool-событий уезжал бы за нижнюю границу экрана. Замыкают суиту вложенная лента субагента (шаги видны в live без клика, синтетической первой строки нет) и терминальные состояния, которые намеренно не красные и отличимы друг от друга.
4. **Кейсы**: карточка генерации на каждый незакрытый вызов `generate_image`, её снятие результатом, отсутствие у не-картиночного вызова и на пустой ленте; строка-пауза до первого события и её снятие; строка-пауза уступает индикатору проверки ответа; хвостовое рассуждение подписано процессом и развёрнуто; завершённое подписано следом; счётчик времени после порога; те же строки на событиях и на `parts`; тот же текст ответа обоими путями; автопрокрутка догоняет новую строку действия, растущий текст и терминальное уведомление; шаги субагента видны внутри его вызова; синтетической первой строки нет; завершённый субагент сворачивается с вердиктом; «Генерация остановлена» на отмене; generic-карточка блокировки; терминальное уведомление не показывается, пока ход идёт

**Осознанно не покрываем автотестом:**

- **Как лента выглядит** — соответствие мокапу `live-timeline-v3.html` на светлой и тёмной теме: цвета, отступы, лавандовый тон субагента, соединительная нить, fade у clamp'а. Автотест на классы был бы прибит к реализации и покраснел бы от любой правки вёрстки, ничего не сказав о том, как это смотрится → ручные кейсы `{T2.1}` / `{T2.7}` 👤.
- **Анимации живости** — бегущие точки, пульс review-строки, шиммер карточки генерации и их выключение под `prefers-reduced-motion`. jsdom не исполняет CSS-анимаций вовсе (`css: false` в конфиге раннера), проверять нечем → ручной кейс `{T2.8}` 👤.
- **Реальный ранний старт вызова и живость на настоящем провайдере** — что подпись строки появляется до того, как модель дописала аргументы, — свойство провайдера, а не фронта; на фейковом потоке это уже доказано в T1 → ручной кейс `{T2.2}` 👤.
- **Прокрутка как физический эффект** — `scrollIntoView` в jsdom заглушка без layout: автотест доказывает, что сигнал прокрутки взводится в нужные моменты, но не что экран действительно доезжает до низа при длинной ленте → ручной кейс `{T2.6}` 👤.
- **Счётчик времени в реальных секундах** — автотест двигает фейковые часы; что счётчик тикает раз в секунду на живом ходе и не дёргает ширину строки, видно только глазами → покрыто ручным кейсом `{T2.3}`.
- **Поведение при `security_block` на живом стеке** (заблокированный ввод, заглушка в истории, 403 на повторную отправку) — половина сценария живёт на бэкенде и уже покрыта его тестами и кейсом `{T1.6}`; фронтовую половину автотест закрывает на уровне диспетчера → ручной кейс `{T2.5}` как сквозная сверка.
- **Форма `parts`, приезжающая с сервера** — что бэкенд действительно отдаёт те поля, которые фронт читает, сторожат тесты T1 (`test_chat_routes.py`) плюс общий фикстур имён инструментов; дублировать контракт схемой на фронте значило бы завести второе место, которое надо синхронизировать → другая суита (T1).
- **`ActivityRow` / `ActivityDetails` / `LiveDots` / `ActivityPauseRow` собственными юнит-тестами** — это презентационные части одной ленты, у них нет контракта отдельно от неё; тест на каждый компонент повторил бы разметку и стал бы налогом на рефакторинг (`testing.md` § Антипаттерны) → покрыты через `MessageItem` / `MessageList`, где проверяется видимое поведение.

**Замеченные прод-баги (для fixer'а, сам не чиню):**

**П1. Автопрокрутка не следует за ростом вложенной ленты субагента — major `[prod]`.**
`frontend/src/pages/chat/ui/MessageList.tsx:79-88`. Сигнал прокрутки считается только по корню ленты
(`feed.length` плюс длина хвостового текстового элемента), а шаги субагента приезжают в `children`
строки его вызова: массив верхнего уровня при этом не меняется, хвостовой элемент остаётся
`tool_call` с нулевой «длиной текста». Наблюдаемо так: пока субагент работает, его лента растёт на
экране (идущий вызов развёрнут автоматически, шаги видны без клика), а окно за ней не едет — новые
шаги оказываются ниже нижней границы, и пользователь смотрит в неподвижный кусок. Это ровно та
поломка, против которой T2.4 перепривязывала прокрутку с `streamingText` на ленту, просто оставшаяся
в её вложенной половине. Проверено на месте: кейс, который дорисовывает шаг с `parent_call_id` к уже
отрисованной строке субагента и требует нового вызова `scrollIntoView`, красный (`expected 21 to be
greater than 21`); в набор он не заведён намеренно — зелёный вариант закрепил бы дефект. После фикса
кейс добавляется в `MessageList.test.tsx` § «автопрокрутка за ростом ленты» третьим соседом
(шаблон — соседние кейсы про новую строку и растущий текст). Правка по существу — считать сигнал
рекурсивно по всей ленте, включая `children`.
**✅ Закрыто (fixer, попытка 1):** сигнал считается рекурсивно, закрывающий кейс заведён; разбор — summary трека § Решения и обоснования → GREEN.

**П2. Инструмент, чьё имя совпадает с ключом `Object.prototype`, роняет рендер всего сообщения — major `[prod]`.**
`frontend/src/shared/config/agent-tools.ts:203-213`. `AGENT_TOOL_SIGNATURES[name]` ищет по обычному
объектному литералу, поэтому имена `constructor`, `toString`, `valueOf`, `hasOwnProperty` резолвятся
в унаследованные члены прототипа: они истинны, ветка fallback'а не срабатывает, и
`resolveToolSignature` возвращает `{known: true}` с `label === undefined` и `icon === undefined`.
Дальше `ActivityRow` рендерит `<view.icon />` с `undefined` и React бросает `Element type is invalid`
— падает не строка, а всё сообщение ассистента. Поверхность реальная: имена инструментов приходят с
провода, а пользовательские MCP-серверы фронт по контракту обязан переживать fallback'ом — это
прямое требование design-brief § Frontend, нарушенное ровно на том входе, ради которого fallback и
заведён. Проверено на месте: `describeToolCall("constructor", {args: "{}"})` даёт
`{known: true, icon: undefined}`, а рендер `MessageItem` с таким `tool` падает с указанной ошибкой.
Кейс в набор не заведён намеренно (он красный до фикса); после фикса добавляется в
`agent-tools.test.ts` § «реестр подписей» параметризованным списком имён прототипа рядом с кейсом
про имя вне реестра. Правка по существу — `Object.hasOwn(AGENT_TOOL_SIGNATURES, name)` перед
обращением либо реестр на `Object.create(null)`.
**✅ Закрыто (fixer, попытка 1):** реестр опрашивается по собственным ключам, закрывающие кейсы заведены; разбор — summary трека § Решения и обоснования → GREEN.

**Наблюдение (не баг, к сведению ревьюера):** незавершённый вызов в live несёт `result: null`, а
приехавший из истории — `result: ""` (сервер отдаёт пустой `result_preview`). На экране разницы нет
— обе ветки дают «Вызов не завершён — результата нет», — поэтому в структурной сверке
«live = история» этот вызов сравнивается по полям идентичности, а не целиком. Если модель когда-нибудь
начнёт различать «результата не было» и «результат пуст», расхождение придётся закрывать нормализацией
в `fromMessageParts`.

## Ручные кейсы + статусы

### Layer 1: Трек T2 — лента активности на живом стеке

> Все кейсы этого слоя требуют поднятого стека с живым ключом reasoning-модели и включённым
> MCP-сервером: трек показывает работу агента, и на фейковых данных проверять здесь нечего.
> Кейсы `{T2.1}`, `{T2.7}`, `{T2.8}` — визуальная приёмка, финальное слово по ним за архитектором.

- [ ] `{T2.1}` 👤 **Лента соответствует мокапу на обеих темах.** Предусловие: стек поднят, открыт чат с ходом, где есть рассуждение, поиск и обновление памяти проекта. Действие: сверить экран с `mockups/live-timeline-v3.html` (оси «Точки» и «Метки») на светлой и тёмной теме. Ожидаемо: строки действий на единой соединительной нити с иконками в кружках; подпись действия и её дополнение различаются насыщенностью; развёрнутые детали — зоны «ВЫЗОВ» / «РЕЗУЛЬТАТ» микро-заголовками с тонким разделителем; clamp больших данных в три строки с fade; ничего не сливается с фоном и не теряет контраст ни на одной теме. Расхождение с мокапом фиксируется отдельно от дефекта: часть отступлений принята осознанно (см. summary трека § Решения).
- [ ] `{T2.2}` 👤 **Молчаливого UX не существует ни в одной точке хода.** Действие: задать вопрос, требующий рассуждения и поиска, и смотреть на экран от нажатия «отправить» до ответа, не отводя глаз. Ожидаемо: сразу после отправки живёт строка-пауза с бегущими точками; она сменяется строкой рассуждения раньше, чем приходит первый токен ответа; строка поиска появляется **до** того, как модель дописала аргументы (подпись сначала без дополнения, дополнение доезжает следом); ни в одной паузе экран не остаётся статичным.
- [ ] `{T2.3}` 👤 **Счётчик времени у долгого действия.** Действие: спровоцировать вызов, который идёт дольше 3 секунд (тяжёлый скрейп или субагент). Ожидаемо: у идущей строки появляется счётчик `m:ss` моноширинным, тикает раз в секунду, ширину строки при тике не дёргает; по завершении сменяется итоговой длительностью («4,2 с»), а точки исчезают.
- [ ] `{T2.4}` 👤 **Субагент разворачивается сам и живёт вложенной лентой.** Действие: попросить делегировать задачу субагенту так, чтобы он сам сходил в инструмент. Ожидаемо: строка `run_subagent` подписана читаемым именем субагента с типом в дополнении, идёт в лавандовом тоне и **развёрнута без клика**; внутри — задание прозой, под ним лента шагов субагента, ниже — «Ответ субагента» с вердиктом; по завершении строка сворачивается сама, вердикт открывается кликом; синтетической строки «получил задание» нет.
- [ ] `{T2.5}` 🔴 **Заблокированный ход схлопывается в одну заглушку.** Предусловие: guard включён. Действие: спровоцировать блокировку (сценарий из security-набора, тот же, что `{T1.6}`). Ожидаемо: в момент события лента хода заменяется единственной заглушкой — ни рассуждений, ни строк вызовов заблокированного хода на экране не остаётся; ниже стоит нейтральная карточка «Ход остановлен системой безопасности» без деталей; ввод заблокирован с подсказкой «Чат заблокирован системой безопасности»; красной плашки ошибки нет; **после `F5` картина ровно та же** — заглушка одна, а не две.
- [ ] `{T2.6}` 👤 **Экран следует за растущей лентой.** Действие: задать вопрос, на который агент отвечает несколькими вызовами инструментов подряд и длинным текстом; не трогать колесо мыши. Ожидаемо: каждая новая строка действия и растущий текст держатся у нижней границы окна, ничего не приходится доскроливать; **шаги работающего субагента — тоже** (прод-баг П1 закрыт, этот пункт — его сквозная проверка на живом стеке).
- [ ] `{T2.7}` 👤 **Терминальные состояния отличимы друг от друга.** Действие: последовательно получить три исхода в одном чате — отмену по кнопке, блокировку и ошибку (например, оборвав backend). Ожидаемо: отмена — нейтральная строка со стоп-квадратом «Генерация остановлена»; блокировка — карточка на приглушённой подложке; ошибка — единственная красная плашка; после отмены композер снова принимает ввод и следующее сообщение уходит нормально, error-toast не показывается.
- [ ] `{T2.8}` 👤 **Уважение к `prefers-reduced-motion`.** Действие: включить в системе или в DevTools → Rendering → Emulate CSS `prefers-reduced-motion: reduce`, повторить кейс `{T2.2}`. Ожидаемо: бегущие точки, пульс review-строки и шиммер карточки генерации перестают анимироваться, но остаются видимыми; живость по-прежнему читается подписью и статусом строки, экран не становится немым.
- [ ] `{T2.9}` **Незнакомый инструмент и незнакомое событие не ломают ленту.** Действие: подключить пользовательский MCP-сервер с инструментом, которого нет в реестре подписей, и попросить агента им воспользоваться. Ожидаемо: строка ленты показывает сырое имя инструмента с пометкой «инструмент MCP», разворот работает как у остальных; в консоли фронта — предупреждение только на неизвестные типы событий (если такие придут), поток при этом не рвётся и ход доходит до ответа.
