# Summary: T2 — Frontend: вход через первое сообщение + `title_updated` + ChatActions

## TL;DR

Трек T2 завершён (T2.1–T2.7). Финальное состояние: оба пути входа в чат (поле первого сообщения на странице проекта, композер `/projects/:id/chats/new`, кнопка «+ Новый чат» в сайдбаре через модалку выбора проекта) сходятся в одну механику `POST /chats` без тела → `navigate(..., { state: { initialMessage } })` → однократная авто-отправка; нигде в продукте пользователь не вводит имя чата. Title приезжает событием `title_updated` (только `setQueryData`, без рефетча открытого чата), рендерится с посимвольной печатью (`TypedTitle`) во всех трёх хостах. Rename/delete чата доступны из списка проекта и recents через `features/chat-actions`, включая заблокированные `security_blocked` чаты. Все инвалидации по `queryKeys.projects.chats(id)` — с `exact: true`. `make check-fe`/`make test-fe` зелёные на всех семи фазах, существующий набор (29 файлов / 163 теста) не сломан ни разу, тесты трека не потребовали правок ни на одной фазе.

По итогам ручного прогона трека закрыты два прод-бага (фаза фикса, детали — в `## Решения и обоснования`): авто-отправка первого сообщения в dev не доезжала до сети (Strict Mode обрывал её собственным cleanup'ом — теперь отправка планируется задачей и снимается в cleanup, так что уходит ровно один `POST …/messages`), и подсветка печати title терялась в шапке чата и в списке чатов проекта (`text-primary` вырезался `twMerge` цветом хоста — теперь он собирается после `className` хоста и виден во всех трёх местах). Живая верификация на dev-сборке пройдена на обоих путях входа, `make check-fe` и `make test-fe` (38 файлов / 227 тестов) зелёные, ни один тест не потребовал правок.

Добавлены `DEFAULT_CHAT_TITLE = "Новый чат"` и `CHAT_TITLE_MAX_LENGTH = 100` рядом с типами. `ChatList.tsx`/`Sidebar.tsx` механически адаптированы под новую сигнатуру `useCreateChat` (без изменения текста/поведения — это работа T2.5/T2.7). Отступление сверх буквы фазы: заодно проставил `exact: true` и в уже существующей инвалидации `useCreateChat` (её код правился в этой же фазе) — того требует Cross-cutting-инвариант трека «все инвалидации по `projects.chats(id)` — с `exact: true`», иначе он не выполнялся бы уже на этой фазе. ## Реализовано в фазе T2.4

- Новый `frontend/src/shared/ui/TypedTitle.tsx` — презентационный компонент, домен-нейтральный: пропы `text` (актуальное значение из кэша), `animateFrom` (значение, с которого запускается печать — хосты передают `DEFAULT_CHAT_TITLE`), `className`, `as` (`"span" | "p"`). Печать (посимвольный `setInterval`, 38 мс/символ) запускается только на переходе `prev === animateFrom → text`; любой другой переход (rename, обычный рендер уже готового названия, загрузочный fallback) — мгновенная подстановка без анимации. Реагирует на `prefers-reduced-motion: reduce` (проверка `window.matchMedia` в момент запуска перехода) — показывает текст сразу целиком. `useEffect` возвращает cleanup, чистящий и `setInterval` печати, и `setTimeout` снятия подсветки — таймеры не текут при размонтировании хоста посреди анимации.
- `frontend/src/index.css` — блок `TypedTitle: каретка посимвольной печати auto-title`: `@keyframes typed-title-caret-blink` (мигание через `opacity`) + `.typed-title-caret::after` (`::after`-псевдоэлемент 2px шириной, `background: var(--primary)`, `animation: ... .7s step-end infinite`) + `@media (prefers-reduced-motion: reduce)` отключает `animation` каретки. Размещён рядом с существующими кастомными keyframes (`gen-progress-indeterminate`, `thinking-dot-pulse`) по тому же паттерну. Цвет текста и `transition-colors` не потребовали кастомного CSS — задаются Tailwind-утилитами прямо в компоненте (`text-primary`, `transition-colors duration-[400ms]`).
- Подключение во все три хоста мокапа: `pages/chat/ui/ChatHeader.tsx` (название открытого чата, `as="span"`), `pages/project-chats/ui/ChatList.tsx` (заголовок строки в списке чатов проекта, `as="p"`), `app/components/Sidebar.tsx` (строка recents, `as="p"`) — во всех трёх `animateFrom={DEFAULT_CHAT_TITLE}`, стилевой `className` перенесён с прежнего статичного `<span>`/`<p>` без изменений (визуально ничего не меняется вне периода анимации).
- **Ревизия унаследованного от прерванной фазы:** `TypedTitle.tsx`, блок keyframes в `index.css` и частичное подключение в `ChatHeader.tsx` (сделаны предыдущим агентом до инцидента) сверены построчно с планом T2.4 и мокапом (`applyTitle`/`typeInto`/`.type-caret` в `mockups/chat-ux.html`) — тайминги (38 мс, 700 мс подсветки, `.7s step-end`), правило запуска печати только на `animateFrom → text`, `prefers-reduced-motion` в CSS и JS, cleanup таймеров — всё совпадает один в один, правок не потребовалось. Недостающим было только подключение в `ChatList.tsx`/`Sidebar.tsx`, дописанное в этой сессии.

Текст сообщения из поля не теряется: `newChatText` очищается только по успешной навигации (де-факто никогда явно не обнуляется, так как страница меняется).

  - Новый `useEffect` (после `handleSend`, до JSX): читает `location.state.initialMessage` (локальный интерфейс `ChatEntryState`, не экспортируется — `pages/chat` не делится типами с `pages/project-chats` через прямой импорт, крос-слайсовый импорт между `pages/*` запрещён FSD-границами трека); при непустом сообщении и незанятом `initialMessageRef.current !== cid` — сразу помечает `initialMessageRef.current = cid` (ref-guard от double-invoke эффектов React 18 Strict Mode в dev: оба синхронных вызова читают один и тот же захваченный `location.state` до того, как первый успевает вызвать `navigate` — без ref-флага сообщение ушло бы дважды), вызывает `handleSend(initialMessage)`, затем `navigate(location.pathname, { replace: true, state: null })`. Эффект не блокируется `isLoading` — вызовы хуков идут до ранних `return` по `isLoading`/`isError`, поэтому отправка не ждёт загрузки `useChat` (чат только что создан и пуст), как требовал план.
  - Дальнейшие срабатывания эффекта (например, из-за смены `location.state` на `null` после `navigate`, или пересчёта зависимостей на ре-рендерах во время стрима) — no-op благодаря и ref-guard'у, и уже пустому `initialMessage`; повторной отправки не происходит.

Не вызывает `useChat`/`useAgentStream`/`useStudio` — только `useCreateChat`. `handleSend(content)`: `createChat.mutate(projectId, { onSuccess, onError })` → на успехе `navigate(`/projects/${projectId}/chats/${created.thread_id}`, { replace: true, state: { initialMessage: content } })` (тот же хендофф, что и в T2.5 — приземляется на `ChatThread`, который и делает авто-отправку); на ошибке — `logger.error` + `getApiErrorMessage`, текст показывается инлайн под пояснением (тот же паттерн, что `ChatList`/`CreateProjectModal`).
- `frontend/src/pages/chat/ui/ChatHeader.tsx`: новый опциональный проп `draft` (по умолчанию `false`), `studioOpen`/`onToggleStudio` стали опциональными (не нужны в draft). В draft: `title = DEFAULT_CHAT_TITLE` (вместо fallback `"Чат"`, который дал бы `chat?.title ?? "Чат"` при пустом кэше); весь блок `<div className="ml-auto ...">` с чипами (Модель, Инструменты, stub «Студия» под `SHOW_GROUP_B_STUBS`) обёрнут в `{!draft && (...)}` — не рендерится вовсе. `useChat(projectId, threadId)` вызывается всегда (единообразно для обеих веток), но на draft-маршруте `threadId` (`cid` из `useParams()`) — `undefined` естественным образом (в маршруте `chats/new` нет `:cid`), так что встроенный `enabled: !!chatId` уже гасит запрос — сетевого `GET /projects/{id}/chats/new` не происходит без специального кейса под "cid === 'new'".
- `frontend/src/pages/chat/ui/ChatInput.tsx`: добавлена опциональная контролируемая пара `value`/`onValueChange`. Без них поведение не меняется (внутренний `useState`, очистка поля сразу после `onSend` — как было для `ChatThread`). С ними (использует только `ChatDraft`) — очистку поля решает родитель: `ChatDraft` никогда явно не очищает текст, значит при ошибке `POST /chats` сообщение остаётся в поле, а при успехе компонент размонтируется навигацией (симметрично тому, как `newChatText` не обнуляется в T2.5).

## Решения и обоснования

- **Ошибка создания чата (T2.5) — инлайн-параграф под карточкой поля, не диалог.** В проекте уже есть ровно такой паттерн для non-dialog форм (`CreateProjectModal.tsx`, `WelcomePage.tsx`: `<p className="text-sm text-destructive">{createError}</p>` сразу под полем/карточкой) — использован без изменений, других инлайн-паттернов ошибок (не в `Dialog`) в кодовой базе нет.
- **`newChatText` не обнуляется явно после успешного создания (T2.5).** Раньше `setNewChatText("")` вызывался в `onSuccess`; теперь `onSuccess` сразу уводит со страницы навигацией (`ChatList` размонтируется), так что явный сброс не нужен — а на ошибке текст должен и так остаться, что уже обеспечено отсутствием сброса на этом пути.
- **`handleSend` в `ChatView` переведён в `useCallback` (T2.5), а не оставлен обычной функцией.** Эффект автоотправки должен зависеть от него по правилам `exhaustive-deps` (ESLint `react-hooks/recommended-latest` в проекте это требует, слепых `eslint-disable` в кодовой базе нет прецедента и CLAUDE.md их запрещает); без мемоизации identity `handleSend` менялась бы на каждый рендер `ChatView` (в т.ч. на каждый чанк стрима через zustand-подписки), из-за чего эффект пересчитывался бы без необходимости. С `useCallback([send])` identity стабильна, пока не меняется `chatId`/`projectId` — эффект перевычисляется ровно тогда, когда это осмысленно.
- **Ref-guard (`initialMessageRef`), а не только «затирание router state», защищает от повторной отправки (T2.5).** React 18 Strict Mode в dev вызывает эффект дважды подряд синхронно (mount → cleanup → mount) до того, как любой из вызовов успевает применить `navigate` — оба invoke видят одинаковый `location.state` с сообщением. Одного затирания state недостаточно для этого конкретного случая; бриф прямо требует «guard от двойного срабатывания эффекта — ref-флаг» отдельно от затирания state, оба применены.
- **Локальный интерфейс `ChatEntryState` не экспортируется и не переиспользуется между `ChatList.tsx` и `ChatView.tsx` (T2.5).** Оба файла независимо описывают форму `{ initialMessage?: string }` (structural typing, не общий символ) — вынос в общий модуль означал бы либо кросс-слайсовый импорт `pages/project-chats → pages/chat` (запрещён FSD-границами трека, Cross-cutting плана: «кросс-импортов между слайсами `pages/` нет»), либо новый файл в `shared/`, которого план не просил ради одного узкого поля роутинг-state.
- **`exact: true` добавлен и в `useCreateChat`, хотя фаза явно требовала его только для rename/delete.** Формулировка фазы буквально говорит про `useUpdateChat`/`useDeleteChat`, но раздел «Cross-cutting» плана требует: «Все инвалидации по `queryKeys.projects.chats(id)` — с `exact: true`» — без исключений, и это единственная фаза трека, которая трогает `useCreateChat`. Оставить его без `exact: true` означало бы гарантированно провалить cross-cutting проверку после всех фаз без шанса поправить это позже. Решение — не архитектурное, а прямое следствие уже зафиксированного в плане инварианта; применил на этой же правке.
- **Патч `title` в detail-кэше через `setQueryData` в `useUpdateChat`, а не отдельно в `ChatActions` (T2.3).** План прямо предписывает делать это в T2.1 «симметрично T2.2»: логика инвалидации/патча — ответственность data-хука, а не потребителя. `ChatActions` (следующая фаза) будет просто вызывать `useUpdateChat().mutate(...)`.
- **`updated.title` берётся из ответа мутации** (`Chat`, возвращаемый `PUT`), а не из переданного в мутацию `data.title` — сервер является источником истины по итоговому значению (например, если бы он делал trim/нормализацию); паттерна расхождения в проекте нет, но это дешевле и безопаснее, чем полагаться на эхо клиентского ввода.
- **`ChatList.tsx`/`Sidebar.tsx` тронуты только точечно.** Плейсхолдер «Название нового чата...», чипы «Прикрепить»/«Модель», подпись пустого списка и вся логика входа через первое сообщение — предмет T2.5/T2.7, не эта фаза; менять их сейчас значило бы выйти за scope и задвоить работу.
- **`deleteChat` не удаляет detail-запись из кэша явно** (не `removeQueries`/`setQueryData(undefined)`) — план об этом не просит; переход со страницы удалённого открытого чата (навигация на страницу проекта) — ответственность `ChatActions` в T2.3, а не data-слоя.
- **Не заводил новых query keys** — rename/delete работают на существующих `queryKeys.projects.chats`, `queryKeys.projects.chat`, `queryKeys.chats.recent`, как и требовала verification-секция фазы.
- **`title_updated` патчит все три кэша через один и тот же `chatId` из замыкания хука**, а не из тела события: контракт события в брифе — `{ title: string }` без `thread_id`, `useAgentStream` уже параметризован `projectId`/`chatId` для конкретного открытого чата, так что дополнительный идентификатор в событии не нужен и не вводился.
- **Fallback-инвалидация в `done` — только `projects.chats`, не `projects.chat` (detail) отдельным вызовом сверх уже существующего.** `done` и до этой фазы инвалидировал `projects.chat(projectId, chatId)`; для списка чатов проекта аналогичной инвалидации не было вовсе — её и добавил, ровно как просил план. `chats.recent` инвалидировался уже раньше — дублирующий вызов не вставлял.
- **«Открыт ли этот чат сейчас» — `useLocation().pathname`, не `useParams()`.** Оба хоста `ChatActions` (`ChatList`, `Sidebar`) рендерятся вне поддерева маршрута `chats/:cid`: `ChatList` — элемент индекс-маршрута `/projects/:id`, а не `chats/:cid`; `Sidebar` — часть `AppLayout`, соседствующая с `<Outlet/>`, а не его потомок. В обоих случаях `useParams()` в точке рендера `ChatActions` не получил бы `cid` глубже совпавшего для этого узла дерева маршрутов сегмента (react-router строит `RouteContext.matches` префиксом до текущего уровня, не включая более глубокие матчи) — тот же факт уже эксплуатирует существующий код: `Sidebar` берёт `projectId` через `useMatch("/projects/:id/*")`, а не `useParams()`. Точное сравнение `pathname` с собранным вручную путём — рабочий и более простой инвариант, использован по образцу `ProjectActions.handleDelete`.
- **Действия не гейтятся по `security_blocked`.** Проп в `ChatActions` не заводился и не читается — бриф явно требует, чтобы rename/delete были доступны для заблокированных чатов без исключений; отсутствие проверки — самый прямой способ гарантировать это, а не «добавить и всегда пропускать».
- **Позиционирование слота действий — `top-3` в `ChatList`, без `top` в `Sidebar`.** `ChatList`-строка выравнена `items-start` (многострочный контент — заголовок/превью/дата), поэтому слот действий фиксируется по высоте первой строки текста (`top-3` совпадает с `py-3` контейнера); `Sidebar`-строка recents — `items-center` (однострочная), там достаточно `right-1` без вертикального смещения, как в `ProjectCard`.
- **`prefers-reduced-motion` проверяется в момент запуска перехода (`window.matchMedia(...).matches` внутри эффекта), не через `useState`/`matchMedia`-listener.** Плану достаточно «при включённой настройке текст показывается сразу целиком» — печать чата запускается ровно один раз за весь жизненный цикл компонента (при первой замене плейсхолдера на сгенерированное название), так что реагировать на изменение системной настройки посреди уже идущей печати незачем; более простая точечная проверка на старте перехода покрывает весь описанный в плане случай.
- **`TypedTitle` не читает `DEFAULT_CHAT_TITLE` сам, а получает его пропом `animateFrom` от каждого хоста.** Того требует план явно («компонент домен-нейтрален... плейсхолдер приходит пропом из хостов, не импортируется внутрь») — компонент лежит в `shared/ui`, `DEFAULT_CHAT_TITLE` — доменная константа из `shared/api/chats.ts`, замыкать `shared/ui` на конкретный домен было бы нарушением слоя.
- **Ревизия унаследованного кода (T2.4) правок не потребовала.** Прерванная фаза оставила `TypedTitle.tsx`, keyframes в `index.css` и частичное подключение в `ChatHeader.tsx` в состоянии, полностью совпадающем с планом и мокапом построчно (тайминги, правило запуска, reduced-motion, cleanup) — решил не переписывать код, который уже верен, только проверить и дополнить недостающее (`ChatList.tsx`, `Sidebar.tsx`).

- **Ветвление `ChatView` — по факту наличия `cid` (`useParams().cid`), не по сравнению строки `"new"` (T2.6).** Маршрут `chats/new` объявлен без сегмента `:cid`, так что на нём `cid` строго `undefined` — react-router уже гарантирует это через ранжирование маршрутов (статический `chats/new` побеждает динамический `chats/:cid` при совпадении обоих). Сравнение `cid === "new"` было бы избыточным и хрупким (пришлось бы поддерживать инвариант «id чата никогда не равен литералу `new`» отдельно), а `cid ? <ChatThread/> : <ChatDraft/>` следует прямо из формы маршрута.
- **`ChatHeader` не продублирован в draft-специфичный компонент, а получил проп `draft` (T2.6).** Компонент и так вызывает свои хуки (`useProject`, `useChat`, `useState` для диалогов) безусловно в обеих ветках — Rules of Hooks тут не нарушаются, различие только в рендере (заголовок/чипы). Дублирование `ChatHeader`/`DraftChatHeader` означало бы синхронизировать два файла при любой правке шапки (позиция кнопки назад, стили заголовка) без выигрыша — план и просит именно «draft-осведомлённость» одного компонента, а не отдельный.
- **`useChat` в draft не получил явного `enabled: false` или условного вызова — использована уже существующая гвардия `enabled: !!chatId` в самом хуке (T2.6).** «`useChat` не вызывается с `cid = "new"`» из брифа читается как «не бьёт по сети с таким id»: на маршруте `chats/new` `threadId` — не строка `"new"`, а `undefined` (сегмента `:cid` в этом маршруте нет), так что `useChat(projectId, undefined)` и без спецкейса не делает запроса — специальный код здесь добавил бы дублирующую защиту без нового эффекта.
- **`ChatInput` расширен контролируемой парой `value`/`onValueChange`, а не переиспользован кастомный композер-инпут из `ChatList.tsx` (T2.6).** План прямо требует «снизу обычный `ChatInput`» (мокап `tplComposer` использует тот же `tplInput`, что и обычный чат) — но исходный `ChatInput` безусловно чистит поле сразу после `onSend`, из-за чего текст терялся бы при асинхронной ошибке `POST /chats`. Раз план требует и переиспользование компонента, и сохранение текста при ошибке (`«как в T2.5»`), единственный вариант без дублирования вёрстки — сделать `value`/`onValueChange` опциональными: неконтролируемый режим (без пропов) не меняет поведение существующего вызова в `ChatThread`, контролируемый (только в `ChatDraft`) отдаёт решение об очистке родителю.
- **`ChatDraft` не рендерит `StudioPanel`/`SphereLens` и не вызывает `useStudio` (T2.6).** У черновика нет `thread_id`, а значит нет и артефактов/студии, к которым эти компоненты привязаны; план требует пустой блок чипов в шапке (включая stub «Студия»), но не упоминает сам Studio-дock — раз чипа-триггера нет, открыть панель всё равно неоткуда, так что она безопасно опущена целиком, а не рендерится в заведомо недостижимом закрытом состоянии.
- **`onCreated` в `CreateProjectModal` перекрывает дефолтный `navigate`, а не дополняет его (T2.7).** План формулирует расширение именно так: «необязательный колбэк, перекрывающий текущий безусловный `navigate`». Дополнение (`navigate` + затем `onCreated`) увело бы пользователя на страницу проекта и тут же — в композер, дав лишний прыжок в истории и на экране; `if (onCreated) else navigate(...)` — единственная трактовка, совместимая и с текстом плана, и с флоу мокапа (`createProjectDialog` в мокапе не заходит на страницу проекта вовсе, а сразу `go({name:"composer"})`).
- **`NewChatModal` — новый файл в `app/components/`, а не расширение `CreateProjectModal` или новый слайс в `features/`.** Бриф и план прямо фиксируют раскладку («Модалка выбора проекта | `app/components/` | единственный хост — Sidebar»): в отличие от `ChatActions` (2+ хоста → `features/chat-actions`), у этой модалки ровно один хост, так что критерий заведения `features/` из `conventions/frontend.md` не выполняется.
- **Список проектов в модалке — обычные `Button variant="ghost"`, не `DropdownMenu`/`Command`-палитра.** В проекте уже есть готовый паттерн «кликабельный список сущностей» — `ProjectList`/`ProjectCard` (обычные строки с truncate и hover), а не поисковая палитра; количество проектов у пользователя мало (аналог recents в сайдбаре), так что вводить новый примитив (`command.tsx` в `shared/ui` не установлен) не оправдано — самый простой вариант, согласованный с остальным UI.
- **`goToComposer` — общая функция для клика по проекту и для колбэка после создания нового.** Оба пути (мокап: `.proj-pick button` и `createProjectDialog` → `go({name:"composer"})`) в итоге делают ровно один и тот же переход `navigate('/projects/{id}/chats/new')` с закрытием модалки выбора; общая функция убирает риск, что кто-то поправит один путь и забудет про второй.
- **`projectMatch`/`projectId` в `Sidebar.tsx` удалены вместе с кнопкой, а не оставлены «на будущее».** После снятия зависимости кнопки «+ Новый чат» от текущего проекта эти две переменные не имеют больше ни одного потребителя в файле (проверено grep по `Sidebar.tsx`) — оставлять неиспользуемый `useMatch` держало бы в файле мёртвый код и упало бы на ESLint `no-unused-vars`.

### Фикс прод-багов ручного прогона

- **F2 — первое сообщение не уходило в dev: отправку планируем задачей, а не зовём синхронно в эффекте (`ChatThread.tsx`).** Первопричину подтвердил на живой dev-сборке своим замером (перехват `window.fetch` + `AbortController.prototype.abort`): abort приходит из cleanup-хука `useAgentStream` в `t = 20304 мс`, `POST …/messages` уходит в `t = 20305 мс` с `signal.aborted === true` — запрос не покидает браузер. Механика ровно как в диагностике tester'а: Strict Mode гоняет эффекты как mount → cleanup → mount; синхронный `send()` первого mount успевает завести `AbortController`, но уходит в `await ensureFreshToken()` и до `fetch` не доходит, а cleanup тут же его аннулирует; на втором mount ref-гвард уже не даёт переотправить. Фикс: эффект больше не вызывает `handleSend` в своём теле, а планирует его `setTimeout(..., 0)` и снимает таймер в cleanup. Таймер первого mount снимается собственным cleanup'ом (ничего не отправлено — нечего и обрывать), отправку делает единственный таймер второго mount, когда фаза размонтирования уже позади. Обе гарантии целы: unmount-abort в `useAgentStream` не тронут вовсе (уход со страницы во время стрима по-прежнему рвёт соединение — там повторного mount нет, таймер снимается и сообщение просто не уходит в заведомо покинутый чат), а однократность держат прежний `initialMessageRef` и затирание router state. Замер после фикса: по одному `POST …/messages` (`aborted: false`) на каждом пути входа, ответ агента приходит, F5 и back/forward — ноль `POST`.
- **Отвергнутые альтернативы по F2.** (1) *Отложить сам abort в `useAgentStream`* (`setTimeout` в cleanup + отмена на повторном mount): чинит симптом, но переносит риск в разделяемое состояние — отложенный `endStream()` уже размонтированного чата мог бы погасить стрим соседнего чата, смонтированного в том же тике, и требовал бы дополнительной привязки к `chatId`. Правка в точке, где проблема возникает (одноразовая авто-отправка), дешевле и не меняет семантику отмены. (2) *Сбрасывать `initialMessageRef` в cleanup, чтобы второй mount переотправил*: тогда в dev в сеть уходят два вызова `send()` (первый — аннулированный), задваивается оптимистичная копия сообщения в `localMessages` (Strict Mode не сбрасывает состояние) и ломается сам критерий «ровно один `POST`». (3) *Снести unmount-abort целиком* — прямо запрещено постановкой и убило бы разрыв стрима при уходе со страницы.
- **F3 — `text-primary` собирается после `className` хоста (`TypedTitle.tsx`).** `cn()` = `twMerge(clsx(...))`, а `twMerge` из конфликтующих утилит одной группы (цвет текста) оставляет последнюю; хосты передают собственный цвет (`text-foreground` в `ChatHeader` и `ChatList`), поэтому подсветка, стоявшая до `className`, вырезалась ещё до DOM — она была видна только в recents, где хост цвета не задаёт. Фикс — переставить `highlighted && "text-primary"` в конец списка классов; ни один тайминг и ни один хост не тронуты. Альтернативы: убрать `text-foreground` из хостов (сломало бы обычный, неанимированный вид названий и размазало бы ответственность за цвет по трём файлам) или задать цвет подсветки в CSS с `!important` (лишний спецэффект в обход системы утилит) — обе хуже одной перестановки. Класс каретки `typed-title-caret` оставлен на прежнем месте: её цвет задан в CSS, конфликта с утилитами хоста у неё нет.
- **Живая верификация фикса (dev, React Strict Mode, Playwright).** *Путь «поле на странице проекта»:* один `POST …/messages`, ответ агента пришёл, чат получил auto-title «Предел последовательности», висячего пустого чата не осталось; F5 и back → forward — ноль `POST …/messages`. *Путь «композер `chats/new`»:* один `POST …/messages`, ответ пришёл. *Подсветка:* семплер (12 мс, `textContent` + классы + `getComputedStyle`) в шапке чата и в recents показал синхронную печать 25 символов за ~930 мс (≈37 мс/символ) с `text-primary` и цветом, доехавшим ровно до `--primary` (`rgb(138, 92, 246)` в тёмной теме); в списке чатов проекта (probe-переименование «Новый чат» → «Проверка подсветки печати») — то же самое: пик `rgb(138, 92, 246)` через ~390 мс после старта, снятие подсветки через ~744 мс после последнего символа, возврат к `rgb(237, 232, 226)` за ~400 мс.
- **Наблюдение вне фикс-листа (не баг):** на коротком ране агента (ответ за ~9 с) title сгенерировался на 13 с позже `done`, поэтому `title_updated` в стрим не попал и `done`-инвалидация подхватила ещё старое значение — название доехало только следующим штатным рефетчем. Это ровно тот случай, который design-brief § Доставка title называет принятым («задача независимо дописывает title в БД, UI подхватит его следующим штатным рефетчем; принимаем»), поэтому прод не правил.
