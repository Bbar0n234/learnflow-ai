# Test Cases: feat-002 — Chat UX / трек T2 (Frontend)

Трек T2 переворачивает вход в чат на фронте: пользователь пишет **первое сообщение**, а не
название, чат создаётся вместе с этим сообщением, название приезжает из стрима событием
`title_updated`, а у чатов появляются rename и delete. Тесты страхуют **новую фичу** и её
контракт с бэкендом (трек T1): `POST /chats` без тела, `PUT`/`DELETE` чатов, не-терминальное
SSE-событие `title_updated`.

Ожидаемые изменения поведения (по сравнению с тем, что было):

- Поле на странице проекта — это поле **сообщения** («Спросите о чём угодно — начнётся новый
  чат...»), а не названия; карточка «Название нового чата...» и стаб-чипы под ней удалены.
  Нигде в продукте пользователь больше не вводит имя чата.
- Кнопка «+ Новый чат» в сайдбаре работает **с любого экрана** и не создаёт чат сама: она
  открывает модалку выбора проекта (всегда, в том числе внутри проекта), а та ведёт в композер
  `/projects/:id/chats/new`, где записи в БД ещё нет.
- Оба пути входа сходятся в одну механику: `POST /chats` → `navigate(..., { replace: true,
  state: { initialMessage } })` → однократная авто-отправка в открывшемся чате с затиранием
  router state.
- `title_updated` меняет название **только** через `setQueryData` в трёх кэшах (список чатов
  проекта, recents, detail открытого чата) — без `invalidateQueries`; на `done` добавлена
  fallback-инвалидация списка чатов с `exact: true`.
- Название рисуется `TypedTitle`: печать посимвольно только на переходе «Новый чат» →
  сгенерированное; rename печать не запускает, `prefers-reduced-motion` показывает сразу.
- У строк чата (список проекта и recents) появилось меню `⋯` с rename/delete; удаление
  открытого чата уводит на страницу проекта.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости (DevTools Network, логи фронта, состояние кэша); `[auto]` — кейс закрыт автотестом (colocated Vitest в `frontend/src/**`); `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe`/`make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты: DevTools → Network (SSE-кадры `text/event-stream`, отсутствие лишних запросов), DevTools → Console (`@/shared/lib/logger`), React Query Devtools при необходимости. Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer**.

**Скоуп по трекам.** Кейсы с префиксом `{T2.N}` гоняются на треке T2 + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST, после барьера с T1.

1. Инфраструктура: `make docker-up-db` + `make migrate` + backend `make dev` (нужен трек T1: `POST /chats` без тела, `PUT`/`DELETE` чатов, событие `title_updated`), фронт — `make dev-fe`. Либо `make docker-up` целиком.

## Дизайн автотестов

Все автотесты трека — colocated Vitest в `frontend/src/**` (стек: Vitest + jsdom + RTL + MSW,
свежий `QueryClient` с `retry: false`, авто-сброс Zustand). **66 новых кейсов** в 9 новых файлах
плюс 4 добавленных кейса в существующий `useAgentStream.test.ts`; набор трека вырос со 163/29
до 229 тестов в 38 файлах. Последние два кейса — регрессии багов ручного прогона `{T2.5}` (F2)
и `{T2.1}` (F3): оба бага прошли мимо набора, и обе дыры описаны в своих суитах ниже.

Два сквозных приёма стоит знать при чтении: (1) MSW поднят с `onUnhandledRequest: "error"`, поэтому
утверждения вида «здесь сети быть не должно» (draft-режим, выбор проекта в модалке) проверяются
самим фактом отсутствия handler'а — лишний запрос красит тест; (2) `exact: true` у инвалидаций
наблюдаем через соседний ключ: `queryKeys.projects.chats(id)` — префикс detail-ключей, поэтому
тест кладёт в кэш detail открытого (и соседнего) чата и проверяет, что тот **не** помечен
инвалидированным.

**Покрываем автотестом** — по записи на суиту:

### `chats.test.ts` — слой данных чатов

1. **Файл**: `frontend/src/shared/api/chats.test.ts` — integration (MSW + `renderHook` на мутациях), кэш пред-заполняется вручную
2. **Тестирует**: `shared/api/chats.ts :: createChat/useCreateChat, updateChat/useUpdateChat, deleteChat/useDeleteChat`, доменные константы
3. **Суть**: суита фиксирует, что создание чата уходит на сервер **без единого байта тела** — пользователь нигде не задаёт имя, — и что rename/delete обновляют ровно то, что должны: список чатов проекта и recents рефетчатся, а detail открытого чата только патчится значением, которое вернул сервер. Она же страхует главный риск инвалидации: список чатов — префикс ключа открытого чата, и без `exact: true` любая из этих мутаций дёрнула бы рефетч чата посреди активного стрима. Ошибочные ответы не должны оставлять кэш в наполовину обновлённом виде.
4. **Кейсы**:
   - `DEFAULT_CHAT_TITLE` = «Новый чат», `CHAT_TITLE_MAX_LENGTH` = 100 (согласовано с сервером)
   - `useCreateChat`: `POST` с пустым телом, возвращает новый `thread_id`
   - `useCreateChat`: инвалидирует список (`exact`) + recents, detail открытого чата — нет
   - `useCreateChat`: ошибка 403 — инвалидаций нет
   - `useUpdateChat`: `PUT { title }`, detail патчится на месте
   - `useUpdateChat`: инвалидирует список (`exact`) + recents, detail — никогда
   - `useUpdateChat`: в кэш идёт title из ответа сервера, а не эхо клиентского ввода
   - `useUpdateChat`: ошибка 422 — кэш не тронут, инвалидаций нет
   - `useDeleteChat`: `DELETE` → 204, инвалидирует список (`exact`) + recents
   - `useDeleteChat`: ошибка 500 — инвалидаций нет

### `useAgentStream.test.ts` — обработка `title_updated` (дополнение)

1. **Файл**: `frontend/src/pages/chat/model/useAgentStream.test.ts` — integration, живой SSE через MSW, дополнение к существующему файлу (чистые добавления, существующие кейсы не тронуты)
2. **Тестирует**: `pages/chat/model/useAgentStream.ts :: case "title_updated"`, `case "done"`
3. **Суть**: суита проверяет, что сгенерированное название доезжает до всех трёх мест, где пользователь видит имя чата, и что оно доезжает **тихо** — без единого рефетча, потому что рефетч открытого чата посреди стрима задвоил бы оптимистичную копию сообщения пользователя. Отдельно страхует, что событие не терминальное (поток живёт дальше), что отсутствие кэшей не ломает стрим, и что на `done` срабатывает fallback-инвалидация ровно по своему ключу, не задевая соседние чаты.

   - после события поток продолжается (приходит текст, стрим активен), ни один из трёх ключей (список, recents, detail) не инвалидирован
   - события хватает и без смонтированных кэшей: стрим доходит до `done`, ошибок нет
   - `done` без `title_updated`: список чатов и recents инвалидированы, detail **соседнего** чата — нет (доказательство `exact: true`)

### `TypedTitle.test.tsx` — печать auto-title

1. **Файл**: `frontend/src/shared/ui/TypedTitle.test.tsx` — unit (RTL + фейковые таймеры; `matchMedia` подменяется — в jsdom его нет; стаб отвечает `matches` только на `(prefers-reduced-motion: reduce)`, на прочие запросы — «нет»)
2. **Тестирует**: `shared/ui/TypedTitle.tsx`

Плюс две вещи, которые ломаются молча: уважение к `prefers-reduced-motion` и отсутствие висящих таймеров, если хост размонтировали посреди печати. После бага F3 суита проверяет ещё и то, что подсветка печати переживает встречу с реальным хостом: компонент рендерится с `className` хоста, несущим собственный цвет текста, — раньше кейсы гоняли его без `className` вовсе, поэтому `twMerge`, вырезавший `text-primary` из-за `text-foreground`, оставался невидимым для набора.
4. **Кейсы**:

   - переход «Новый чат» → имя печатается по символу (проверяется частичный и полный текст)
   - *(регресс F3)* с `className` хоста (`text-foreground` рядом с прочими утилитами) на время печати на элементе есть `text-primary` и нет `text-foreground`, остальные утилиты хоста целы; после снятия подсветки — наоборот. Проверка по DOM-классам, а не по цвету: `css: false`, в jsdom утилиты Tailwind ни во что не превращаются

   - `prefers-reduced-motion: reduce` — имя появляется целиком сразу
   - тег обёртки берётся из пропа `as` (хосты держат свою семантику)
   - размонтирование посреди печати не оставляет активных таймеров (перед unmount проверено, что печать реально идёт)
   - размонтирование сразу после конца печати не оставляет активных таймеров (второй таймер — удержание подсветки)

### `ChatThread.test.tsx` — однократная авто-отправка первого сообщения

1. **Файл**: `frontend/src/pages/chat/ui/ChatThread.test.tsx` — integration (MSW: detail чата, проект, SSE-стрим; `MemoryRouter` со стартовым router state)
2. **Тестирует**: `pages/chat/ui/ChatThread.tsx` (эффект передачи `state.initialMessage`)
3. **Суть**: это критпуть гонок. Суита проверяет, что переданное с предыдущего экрана сообщение уходит на сервер **ровно один раз** и один раз же показывается в ленте (ни оптимистичная копия, ни рефетч после `done` его не задваивают), а router state сразу затирается — именно это делает refresh и шаги назад/вперёд безопасными. Плюс две границы: открытие чата без переданного сообщения не шлёт ничего вовсе, а медленная загрузка истории отправку не задерживает (чат только что создан и заведомо пуст). После бага F2 тот же критпуть прогоняется ещё раз под `<StrictMode>` — в dev приложение живёт именно так, и раньше набор монтировал экран без него, поэтому «отправка не доехала до сети» ловилось только руками.
4. **Кейсы**:
   - переданное сообщение уходит одним `POST /messages` и в ленте показано один раз — счёт копий сделан **после** того, как на экране появился текст ответа из рефетча истории (сервер отдаёт ответ агента иной строкой, чем стрим, поэтому его видимость и есть доказательство прихода рефетча)
   - *(регресс F2)* под `<StrictMode>` (mount → cleanup → mount) до MSW-handler'а доезжает **ровно один** `POST …/messages`, и он не аборчен: стрим дочитан до `done`, рефетч принёс ответ сервера на экран; router state после этого пуст. Двойной прогон эффектов подтверждается в самом кейсе зондом (`mount → cleanup → mount`) — иначе он молча выродился бы в дубль соседнего. Тонкость окружения: React прогоняет эффекты дважды, только когда `StrictMode` — **корень** отрисованного дерева (как в `main.tsx`), поэтому провайдеры в этом кейсе уезжают внутрь `StrictMode`, а не приходят обёрткой снаружи из `renderWithProviders`
   - после отправки router state очищен (нечего переотправлять при refresh/back)
   - открытие чата без переданного сообщения не шлёт ни одного запроса сообщений
   - отправка не ждёт загрузки истории чата: history-handler удерживается тестом, факт «история ещё не отдана» ассертится со стороны handler'а, а не по видимому `Loading chat...`
