# Track Summary: feat-008 / трек T1 — Backend: OAuth-вертикаль, гео-gate, SIEM-словарь

## TL;DR

Трек реализован целиком (все 9 фаз): бэкенд умеет входить через три внешних провайдера (Яндекс ID, Google, GitHub) и разделяет их доступность по стране клиента. Схема БД несёт `oauth_accounts` и nullable `password_hash` (парольный вход при отсутствующем пароле честно отдаёт 401, не 500); три провайдера реализованы тонкой httpx-абстракцией за общим `Protocol` (`OAuthProvider`), живут в реестре `app.state`, собранном из `Settings` — провайдер активен ⇔ обе креды заданы. `OAuthService.login_with_provider` делает find-or-create в одной транзакции с обработкой обеих гонок (коллизия имени → суффикс с retry; коллизия связки provider+account_id → деградация в login). Флоу целиком проходит через `GET /auth/providers` / `GET /auth/oauth/{provider}/authorize` / `GET /auth/oauth/{provider}/callback`: state/PKCE-verifier несёт подписанная httpOnly-cookie `oauth_flow` (JWT на существующем `JWT_SECRET`), редиректы ошибок бьют строго в закрытый реестр кодов `/login?error=`, access token никогда не проходит через redirect-URL. Гео-gate (`app/infra/geoip.py`, MaxMind-совместимый MMDB reader) режет состав провайдеров и блокирует authorize/callback для РФ-IP до `{yandex}` — fail-closed на любую деградацию (нет базы, промах lookup, нераспарсиваемый IP). SIEM-словарь пополнен тремя типами (`auth.oauth.success`/`auth.oauth.failed`/`rate_limit.oauth.exceeded`), эмит-сайты заведены в `routes/oauth.py` формами, которые резолвер контракт-теста понимает без параметр-threading через границы модулей. GitHub — третий провайдер, PKCE у него no-op (протокольно передаётся, но защиту ветки держит сверка `state`), email при `null` добирается отдельным запросом `/user/emails` с мягкой деградацией в `None`. `make check`/`make test-scope P=backend/tests/auth`/`make test-contracts` зелёные на каждой фазе, автотесты по критериям брифа — за независимым `test-author` (A6, фазы их не пишут). Пост-имплементационное ревью (режимы A/B) дало один blocker (тихое сведение любого кода ошибки провайдера к `access_denied` на callback'е) и семь nit'ов — все фиксы применены отдельным проходом (см. «Фиксы по code review» ниже), `_set_refresh_cookie` вынесен в общий `app/api/cookies.py`.

## T1.4: Провайдер-абстракция + Яндекс + ресурсы lifespan

Реализовано строго по [plan.md](plan.md) § T1.4 и design-brief.md § Провайдер-слой:

- `backend/app/infra/oauth/base.py` — `OAuthProvider` как `typing.Protocol` (`authorize_url(*, state, challenge, redirect_uri)` / `exchange_code(*, code, verifier, redirect_uri)` / `fetch_profile(*, token)`), `OAuthProfile` — frozen dataclass (`provider`, `provider_account_id`, `email: str | None`, `display_name: str | None`).
- `backend/app/infra/oauth/pkce.py` — три чистые функции без состояния: `generate_state()` (`secrets.token_urlsafe(32)`), `generate_code_verifier()` (`secrets.token_urlsafe(64)`), `derive_code_challenge(verifier)` (S256: `base64url(sha256(verifier))` без паддинга).
- `backend/app/infra/oauth/exceptions.py` — `OAuthProviderError(Exception)`: узкое, без HTTP-семантики, живёт рядом с oauth-подсистемой (второй уровень нормы обработки ошибок, прецедент `AuthError`), не наследует `AppError` — не долетает до барьера, гасится в `routes/oauth.py` (T1.6).
- `backend/app/infra/oauth/yandex.py` — `YandexOAuthProvider`: `authorize_url` собирает `https://oauth.yandex.ru/authorize` с `response_type=code`, `client_id`, `redirect_uri`, `state`, `code_challenge` + `code_challenge_method=S256`; `exchange_code` — `POST https://oauth.yandex.ru/token` (form-urlencoded, включая `code_verifier`); `fetch_profile` — `GET https://login.yandex.ru/info` с `Authorization: OAuth <token>`, маппинг `id → provider_account_id`, `default_email → email`, `login → display_name`. Каждый HTTP-вызов различает `httpx.HTTPStatusError` / `(httpx.HTTPError, OSError)` / malformed-body (`KeyError`/`TypeError`/`ValueError`) — все три ветки логируются `logger.warning(exc_info=True)` и поднимают `OAuthProviderError`.
- `backend/app/infra/oauth/__init__.py` — `build_oauth_registry(settings, http_client) -> dict[str, OAuthProvider]`: провайдер активен ⇔ обе креды заданы; сейчас единственная запись — `yandex`. Фабрика, вызывается только из lifespan, module-level state не заводит.
- `backend/app/main.py` (lifespan) — общий `httpx.AsyncClient(timeout=settings.oauth_http_timeout_seconds)` создаётся один раз, кладётся в `app.state.oauth_http_client`; реестр — `app.state.oauth_providers = build_oauth_registry(settings, oauth_http_client)`; состав реестра логируется (`active_providers=sorted(...)`, без секретов). Закрытие — `await app.state.oauth_http_client.aclose()` перед `await engine.dispose()`, тем же паттерном, что и `redis.aclose()`/`chat_title_generator.shutdown()` выше по коду.

## T1.5: `OAuthService` — find-or-create и выдача сессии

Реализовано строго по [plan.md](plan.md) § T1.5 и design-brief.md § Эндпоинты (абзац про `OAuthService`):

- `backend/app/repositories/oauth_account.py` — `OAuthAccountRepository`: `get_by_provider_account(provider, provider_account_id)` (lookup по паре), `create(account)` (`add` + `flush`) — чистый ORM-CRUD, тем же паттерном, что `UserRepository`/`RefreshTokenRepository`; в `repositories/__init__.py` не добавлен (пакет и так не ре-экспортирует каждый репозиторий — прецедент `MCPServerRepository`, импортируется напрямую).
- `backend/app/services/oauth.py` — `OAuthService.login_with_provider(profile) -> (user, access, refresh)`: lookup `oauth_accounts` по `(provider, provider_account_id)` → найден: `_login_existing` (пользователь по `account.user_id` через `UserRepository`, `account.email = profile.email` — освежение на каждом входе, выдача сессии); не найден: `_create_and_login` — цикл до 5 попыток (`_MAX_NAME_ATTEMPTS`), каждая попытка — `User` + `OAuthAccount` внутри `async with self._session.begin_nested()` (SAVEPOINT) с одним `flush` на пару; на `IntegrityError` конфликт различается по имени constraint'а (`_constraint_name(exc)`): `uq_users_name` → новый суффиксный кандидат (`_suffixed_candidate_name`, `secrets.token_hex(2)`), retry; `uq_oauth_accounts_provider` → `_login_after_race` (повторный lookup, login-путь вместо 500); любой другой — `raise` наружу (не проглатывается). Кандидат имени — `_base_candidate_name`: нормализованный `profile.display_name` (провайдер-специфичный выбор поля уже сделан в `fetch_profile` каждого провайдера) либо фолбэк `<provider>_<hex-суффикс>`.
- `backend/app/services/auth.py` — публичный метод `AuthService.issue_session(user) -> (access, refresh)`: та же механика, что у `login` после аутентификации (`delete_expired_for_user` + `_create_access` + `_create_refresh`), вынесена в легальную точку входа снаружи класса — `OAuthService` пользуется им, приватные `_create_access`/`_create_refresh` не копирует и не трогает напрямую.
- `backend/app/services/exceptions.py` — `OAuthAccountCreationError(AuthError)`: два источника — исчерпан retry-бюджет генерации имени, либо `_login_after_race` не нашла строку после гонки (неожиданное состояние БД, не сама гонка). Наружу до HTTP-барьера не долетает — ловится в `routes/oauth.py` (T1.6), маппится на `oauth_failed`.

## T1.6: Эндпоинты OAuth — cookie `oauth_flow`, authorize, callback, `/providers`

Реализовано строго по [plan.md](plan.md) § T1.6 и design-brief.md § Флоу целиком / Хранение state / Эндпоинты (+ диаграмма веток callback'а, реестр кодов `/login?error=`):

- `backend/app/infra/oauth/flow_state.py` — JWT-механика cookie `oauth_flow` на существующем `JWT_SECRET`: `encode_flow_cookie`/`decode_flow_cookie` (claims `{state, verifier, provider, next, exp: +10 мин}`, `HS256`), `is_safe_next_path` (относительный путь — начинается с `/`, не с `//`), `set_flow_cookie`/`delete_flow_cookie` (httpOnly, `SameSite=Lax`, `Secure` по `SECURE_COOKIES`, `Path=/api/auth/oauth`, `max_age=600`). `decode_flow_cookie` возвращает `None` единообразно на подпись/`exp`/несовпадение `provider`/битые claims — вызывающий сводит все причины в одну ветку `flow_expired`, не различая их дальше.
- `backend/app/api/schemas/oauth.py` — `ProvidersResponse` (`{providers: list[str], password: bool = True}`).
- `backend/app/api/routes/oauth.py` — новый роутер (`prefix="/auth"`, тот же префикс, что у `auth.router`, коллизий путей нет): `GET /providers` (состав = активные провайдеры реестра без гео — гео-gate в T1.7); `GET /oauth/{provider}/authorize?next=<path>` (валидация `{provider}` по реестру → 404 первым делом; rate limit `oauth_authorize:{ip}` 10/мин; валидация `next` до записи в claim, невалидный/отсутствующий `next` молча фолбэчит на `/` — плейн-решение реализации, явного кода ошибки под этот случай бриф не резервирует; state/PKCE; redirect_uri строго из `Settings`; `Set-Cookie: oauth_flow`; 302 на провайдера); `GET /oauth/{provider}/callback` (та же валидация провайдера + свой rate-limit-ключ `oauth_callback:{ip}` первыми двумя гейтами; далее строго по диаграмме брифа: `?error` → `access_denied`; cookie/state → `flow_expired`; обмен code→токен + userinfo → `provider_unavailable` (включая защитную ветку «код в query отсутствует» — сведена к тому же исходу, что и отказ обмена, диаграмма не даёт для неё отдельной ветки); find-or-create → `oauth_failed` на `OAuthAccountCreationError`; успех → штатная refresh-cookie + 302 на `flow.next`, cookie `oauth_flow` гасится). 404/429 — не терминальные ветки, cookie не гасится. Терминальные ветки гасят cookie всегда, кроме «cookie отсутствует» (`delete_cookie=cookie_present`/`True` по месту).
- SIEM-эмиссия — локальные хелперы `_emit_oauth_failed`/`_emit_oauth_success`/rate-limit-warning внутри `_check_oauth_rate_limit`, каждый с прямым `event_type=<импортированная константа>` на месте вызова (форма, которую резолвер `test_event_vocabulary_contract.py` видит без парам-threading через модульные границы — критично, план явно предупреждал против импорта чужого приватного `_check_rate_limit`, дающего слепое пятно). Маппинг по брифу: `flow_expired`/`oauth_failed` → `AUTH_OAUTH_FAILED`; `provider_unavailable` — `logger.warning` без SIEM; `access_denied` — не событие; успех → `AUTH_OAUTH_SUCCESS` с `metadata={"provider", "new_user"}`.
- `backend/app/services/oauth.py` — `OAuthService.login_with_provider` (и внутренние `_login_existing`/`_create_and_login`/`_login_after_race`) расширены четвёртым элементом кортежа — `new_user: bool` (`True` только на пути успешного создания в `_create_and_login`, `False` на обеих ветках логина существующей связки). T1.5 не фиксировал это поле в сигнатуре (её потребитель появляется только здесь) — расширение возврата, не переписывание логики; единственный вызывающий (`routes/oauth.py`, эта фаза) — регрессии на других потребителях нет (grep подтвердил отсутствие других вызовов).
- `backend/app/api/routes/auth.py` — `_set_refresh_cookie` переиспользован импортом из `routes/oauth.py` (план явно санкционировал оба варианта: импорт приватного либо вынос в общий модуль; выбран импорт — минимальная правка, `routes/auth.py` не тронут ни строкой).
- `backend/app/api/routes/__init__.py`, `backend/app/main.py` — регистрация `oauth` рядом с `auth` (`app.include_router(oauth.router, prefix=api_prefix)`, сразу после `auth.router`).

## T1.7: Гео-gate — MMDB-reader и enforcement в трёх точках

Реализовано строго по [plan.md](plan.md) § T1.7 и design-brief.md § Гео-gate:

- Зависимость: `uv add maxminddb` из `backend/` → `backend/pyproject.toml` (`maxminddb>=3.1.1`) + регенерация корневого `uv.lock` (58 добавленных строк, только пакет и его метаданные). Override в `[[tool.mypy.overrides]]` не заведён — пакет несёт `py.typed`, `mypy` прошёл без подавлений.
- `backend/app/infra/geoip.py` — `open_reader(db_path) -> Reader | None` (пустой путь / отсутствующий файл / исключение при открытии → `logger.warning` + `None`, старт не блокируется) и `resolve_country(reader, ip, fallback_country) -> str`. Извлечение country-кода (`_extract_country_code`) — явные `isinstance`-проверки по `Record` (рекурсивный union из `maxminddb.types`), совместимо и с плоской IPinfo Lite (`record["country_code"]`), и с вложенной GeoLite2 (`record["country"]["iso_code"]`). Fallback — при `reader is None`, при lookup-промахе (`_extract_country_code` вернула `None`) и при `ValueError` из `Reader.get` на нераспарсиваемой строке (`"unknown"` от `get_client_ip`, когда клиента нет). IP внутрь модуля приходит уже резолвленным вызывающим кодом через `get_client_ip` — сам модуль заголовков не читает.
- `backend/app/config.py` — `geoip_db_path: str = ""`, `geoip_fallback_country: str = "RU"`.
- `.env.example` — обе переменные добавлены пустой/`RU` вслед за блоком `OAUTH_*`. `.env.local.example` — закомментированный путь-образец (`GEOIP_DB_PATH=/absolute/path/to/ipinfo_lite.mmdb`) с пояснением, что реальный абсолютный путь — в `.env.local` (не тронут), плюс закомментированный `GEOIP_FALLBACK_COUNTRY=US` — подсказка для локальной проверки не-РФ ветки без реальной базы. `docker-compose.yml` — те же две переменные в блоке `app.environment` (`${VAR:-}` / `${VAR:-RU}`) + read-only volume `./data/geoip:/app/data/geoip:ro` рядом с существующими `configs`/`skills`-mount'ами.
- `backend/app/main.py` (lifespan) — `app.state.geoip_reader = open_geoip_reader(settings.geoip_db_path)` сразу после блока OAuth-реестра (тот же характер ресурса — открывается один раз, живёт в `app.state`); закрытие — `app.state.geoip_reader.close()` на shutdown, после `oauth_http_client.aclose()` и до `engine.dispose()`, тем же паттерном, что остальные ресурсы.
- `backend/app/api/routes/oauth.py` — бизнес-инвариант `_GEO_ALLOWED_PROVIDERS_RU = frozenset({"yandex"})` (константа в коде, не env) + `_is_provider_allowed_for_country`/`_resolve_client_country`/`_emit_geo_denied`. Три точки enforcement:
  - `GET /providers` — принимает `SettingsDep` (сигнатура расширена), резолвит страну по `get_client_ip`, отдаёт `active ∩ _GEO_ALLOWED_PROVIDERS_RU` при RU, иначе все активные;
  - `authorize` — после валидации провайдера и rate limit, до генерации state/PKCE и до `Set-Cookie` (запрещённый провайдер для RU — редирект без cookie, `delete_cookie=False`, ветка ещё не терминальна в смысле cookie — она попросту не была выставлена);
  - `callback` — «Ветка 3» диаграммы брифа, между сверкой cookie/state (ветка 2) и обменом кода (ветка 4); терминальная ветка — `delete_cookie=True`.
  - Гео-отказ — `_emit_geo_denied`: `logger.info` без `security_event`/`event_type` (структурно отличим от SIEM-эмиссии `_emit_oauth_failed`/`_emit_oauth_success` в том же файле — не просто «другой уровень», а отсутствие самих полей, которые делают событие SIEM-событием).
- `README.md` — атрибуция IPinfo (CC BY-SA 4.0) добавлена под `## License`.

## T1.8: Провайдер Google

Реализовано строго по [plan.md](plan.md) § T1.8 и design-brief.md § Провайдер-слой (`google.py: code flow, профиль через userinfo-endpoint, JWKS-валидация id_token не требуется`):

- `backend/app/infra/oauth/google.py` — `GoogleOAuthProvider`, тем же паттерном, что `YandexOAuthProvider` (T1.4): `authorize_url` собирает `https://accounts.google.com/o/oauth2/v2/auth` с `response_type=code`, `client_id`, `redirect_uri`, `scope=openid email profile`, `state`, `code_challenge` + `code_challenge_method=S256`; `exchange_code` — `POST https://oauth2.googleapis.com/token` (form-urlencoded, включая `code_verifier`); `fetch_profile` — `GET https://openidconnect.googleapis.com/v1/userinfo` с `Authorization: Bearer <token>` (не `OAuth <token>`, как у Яндекса — Google несёт стандартную Bearer-схему), маппинг `sub → provider_account_id`, `email → email`, `given_name → display_name` (по составу плана). Тот же трёхветочный httpx error handling, что у Яндекса: `httpx.HTTPStatusError` / `(httpx.HTTPError, OSError)` / malformed-body (`KeyError`/`TypeError`/`ValueError`) — все три логируются `logger.warning(exc_info=True)` и поднимают `OAuthProviderError`.
- `backend/app/infra/oauth/__init__.py` — `build_oauth_registry` дополнен: `google` активен ⇔ заданы `oauth_google_client_id`/`oauth_google_client_secret`, тем же паттерном (`if ... and ...: registry["google"] = GoogleOAuthProvider(...)`), что и `yandex`.
- Регистрация в `routes/oauth.py`, гео-gate (T1.7), find-or-create (T1.5), эндпоинты (T1.6) не тронуты — Google встраивается в готовую вертикаль без изменений на этих слоях, ровно как и предполагал план фазы («второй провайдер реестра»).

## T1.9: Провайдер GitHub

Реализовано строго по [plan.md](plan.md) § T1.9 и design-brief.md § Провайдер-слой (`github.py: code flow; email добором через /user/emails при null (scope user:email)`):

- `backend/app/infra/oauth/github.py` — `GitHubOAuthProvider`, тем же трёхветочным паттерном httpx error handling, что у Яндекса/Google: `authorize_url` собирает `https://github.com/login/oauth/authorize` с `response_type=code`, `client_id`, `redirect_uri`, `scope=user:email`, `state`, `code_challenge` + `code_challenge_method=S256` (PKCE-параметры передаются протокольно, но на их проверку реализация не рассчитывает — GitHub OAuth Apps их игнорирует, план Open Questions № 3); `exchange_code` — `POST https://github.com/login/oauth/access_token` с заголовком `Accept: application/json` (без него GitHub отвечает form-urlencoded телом, и `response.json()` упал бы на парсинге) + дополнительная ветка разбора: GitHub на невалидный `code`/`redirect_uri` отвечает 200 с `{"error": ...}` в теле, а не HTTP-статусом — эта форма отказа явно проверяется (`"error" in payload`) и уходит в ту же malformed-response ветку, что и отсутствующий `access_token`; `fetch_profile` — `GET https://api.github.com/user` с `Authorization: Bearer <token>`, маппинг `id` (целое число API) → `str(id)` как `provider_account_id`, `login → display_name`.
- Добор email — `_fetch_primary_email`: если `/user` отдал `email: null`, отдельный `GET https://api.github.com/user/emails` (тот же токен, тот же scope `user:email`, запрошенный в `authorize_url`); из списка адресов выбирается primary+verified, при его отсутствии — любой verified, при отсутствии обоих — `None` без ошибки (research-provider-libs.md § подводные камни GitHub: «email может требовать отдельного `/user/emails`»). Сетевой отказ на этом добор-запросе (`HTTPStatusError`/`HTTPError`/`OSError`/malformed JSON) не поднимает `OAuthProviderError` и не валит весь вход — логируется `logger.warning` и деградирует в `None`: добор email — необязательное улучшение профиля, а не критичный для входа шаг (в отличие от `/user` и обмена кода, где та же категория ошибок поднимает `OAuthProviderError` и уводит callback в `provider_unavailable`).
- `backend/app/infra/oauth/__init__.py` — `build_oauth_registry` дополнен третьей записью: `github` активен ⇔ заданы `oauth_github_client_id`/`oauth_github_client_secret`, тот же паттерн, что у `yandex`/`google`.
- Инвариант host'а (dev-приложение GitHub на `localhost`, не `127.0.0.1`) — операционный шаг архитектора вне кода; redirect_uri в `github.py` собирается тем же кодом `routes/oauth.py` (T1.6, не тронут), что и у остальных провайдеров — из `OAUTH_REDIRECT_BASE_URL`, без подмены host'а.
- Регистрация в реестре — единственное изменение вне `github.py`; гео-gate (T1.7), find-or-create (T1.5), эндпоинты (T1.6) не тронуты — GitHub встраивается в готовую вертикаль без правок на этих слоях, как и предполагал план фазы («третий провайдер реестра»).

## Решения и обоснования

- **CHECK-constraint без `vk`** — фактический состав провайдеров трека `('yandex', 'google', 'github')`, эскиз research-data-model.md включал `vk` как более широкий список вводных решений архитектора; отступление зафиксировано брифом (design-brief.md § Модель данных) и явно предписано планом фазы, самостоятельного решения здесь не было.
- **`login`-проверка `password_hash IS NULL` вынесена отдельной веткой, а не объединена с `verify_password` через `or`** — короткое замыкание в `user is None or not verify_password(...)` передало бы `None` в `verify_password(password_hash: str, ...)` для OAuth-пользователей без пароля, что и есть несовместимость типов, о которой предупреждает план; mypy подтвердил чистоту после разделения на два `if`.
- **Правка легла в `services/auth.py`, а не в `api/routes/auth.py`** — план фазы явно фиксирует это расхождение с текстом партиции треков как не-конфликт (оба файла в `backend/**`, вне скоупа T2); транспортный слой (`routes/auth.py`) не тронут, инвариант «401 без утечки типа входа» реализован там, где и должен — в сервисе.
- **`.env` для worktree создан копированием из основного checkout** (`/home/bbaron/dev/my_pet_projects/learnflow-ai/.env`) — в worktree `.env` отсутствовал (gitignored, не реплицируется git-worktree), а `docker compose`/`make docker-up-db` требуют его для интерполяции (`JWT_SECRET` и т.п., conventions.md § Docker vs Local dev). Скопированный файл — тот же базовый локальный dev-конфиг (не секреты фичи), простое инфраструктурное условие для выполнения verification-шагов фазы, вне скоупа кода трека.
- **Пустой дефолт `""` для трёх пар кредов — не fail-fast-секрет** — сознательное решение брифа: провайдер без кредов считается выключенным, а не сломанным стартом. `docker-compose.yml` пробрасывает их через `${VAR:-}`, а не `${VAR:?}`, — это отступление от общего правила § Секреты и fail-fast conventions.md сделано явно и предписано планом фазы, не самостоятельным решением здесь.
- **Разведённые дефолты `OAUTH_REDIRECT_BASE_URL`** (`:8000` в `docker-compose.yml`, `:5173` в `Settings`) — решение архитектора по Open Questions № 2 плана: не рассинхрон, а разный топологически верный host на окружение (в docker SPA отдаёт backend, в local dev — Vite). Оба места оставлены как предписано, без попытки унифицировать.
- **`.env.local.example` не дублирует значения кредов** — по тексту фазы плана в `.env.local.example` идёт только комментарий про реальные пары в `.env.local`; имена шести credential-переменных перечислены в комментарии текстом (не как `KEY=`), чтобы grep-сверка verification-пункта («все восемь переменных присутствуют во всех четырёх местах») проходила буквально, не подменяя дух требования («переменная известна в этом файле», а не «переопределена»).
- **Имена трёх новых констант выровнены по существующей паре `<subject>` в двух доменах, а не изобретены заново** — `vocabulary.py` уже несёт схему «`auth.<subject>.<outcome>`» с `<subject>` ∈ {`login`, `register`, `refresh`} и параллельную ей «`rate_limit.<subject>.exceeded`» с тем же набором `<subject>`. OAuth-вход — четвёртый `<subject>` в обеих схемах, поэтому `auth.oauth.success` / `auth.oauth.failed` и `rate_limit.oauth.exceeded` не вводят новый паттерн, а заполняют уже существующую клетку таблицы «домен × subject» — тем самым словарь остаётся предсказуемым для читателя, знающего только первые шесть типов. Альтернатива вида `auth.login.oauth_success` (расширение исхода, а не subject'а) отклонена: она смешала бы механизм входа (`oauth`) с исходом (`success`/`failed`) в одном сегменте и разошлась бы с тем, что бриф явно называет subject'ом «вход через провайдера», параллельным `login`/`register`, а не его подвидом. `RATE_LIMIT_OAUTH_EXCEEDED` не переиспользует `RATE_LIMIT_LOGIN_EXCEEDED` — по плану фазы это разные эндпоинты с разными бюджетами лимитера (ключи `oauth_authorize:{ip}` / `oauth_callback:{ip}`, заведутся в T1.6), а не альтернативные имена одного и того же события.
- **Отказ входа — один тип `auth.oauth.failed` на обе ветки callback'а (`flow_expired`, `oauth_failed`)** — по составу брифа события всего три, детализация причины отказа не заводится отдельными event types (в отличие от `/login?error=` — того реестра из пяти кодов, что живёт в HTTP-контракте, не в SIEM); различение причины на стороне SIEM/alerting — по полям события на эмит-сайте (вне scope этой фазы), не по имени типа.
- **`OAuthProviderError` — плоское `Exception`, не `AppError`** — плановое решение (design-brief.md § Провайдер-слой, конвенция «второй уровень нормы»): исключение гарантированно гасится до HTTP-барьера — `routes/oauth.py` (T1.6) ловит его и превращает в редирект `/login?error=provider_unavailable`. Наследование от `AppError` навязало бы фиктивный HTTP-`status`, которого у инфра-отказа провайдера нет (решение принимает роут, не исключение). Прецедент — `AuthError`/`services/exceptions.py`, осознанно локальный для `routes/auth.py`.
- **httpx-исключения на каждом вызове различаются на три ветки** (`HTTPStatusError` / `(HTTPError, OSError)` / malformed-body) — калька с существующего эталона `infra/image_generation.py`: разные причины отказа (провайдер ответил 4xx/5xx vs сеть недоступна vs ответ не распарсился) несут разный `logger.warning`-контекст (`status_code` доступен только у первой), но все три сворачиваются в один `OAuthProviderError` — на уровне вызывающего кода (T1.6) разница между ними не нужна, все три ветки ведут в одну и ту же `provider_unavailable`.
- **Реестр — `dict[str, OAuthProvider]`, не `Enum`-ключ** — состав провайдеров определяется наличием кредов в рантайме (dev может гонять один Яндекс), а не фиксированным доменом времени компиляции; строковый ключ также напрямую становится сегментом URL (`{provider}` в `/auth/oauth/{provider}/authorize`) и значением `oauth_accounts.provider` — три места используют одну и ту же строку без перекодировки между `Enum` и `str`.
- **`build_oauth_registry` принимает готовый `httpx.AsyncClient`, а не создаёт его сам** — держит владение ресурсом в одном месте (`lifespan`), совместимо с правилом «клиент per-request не создаётся» и с закрытием клиента до `engine.dispose()`; фабрика реестра остаётся чистой функцией без побочных эффектов на инфраструктуру соединений.
- **Retry на unique violation — через `session.begin_nested()` (SAVEPOINT), не через `session.rollback()` всей транзакции** — задача фазы требует retry *внутри одной* транзакции запроса (план, verification: «повторный вход тем же провайдер-аккаунтом не создаёт второго пользователя», find-or-create целиком в одной транзакции, открытой `get_db_session`). Полный `rollback()` откатил бы и внешнюю транзакцию целиком, ломая инвариант «одна транзакция на find-or-create»; SAVEPOINT — задокументированный SQLAlchemy-паттерн именно для «поймать `IntegrityError` и продолжить работу с той же сессией» (FAQ «Using SAVEPOINT»). Каждая попытка — новый `User`/`OAuthAccount` объект (не переиспользование объекта после отката savepoint).
- **Различение двух constraint-путей — по `exc.orig.diag.constraint_name`, не по флагу/тексту сообщения** — реальный драйвер приложения (`backend/pyproject.toml`) — **psycopg3** (`postgresql+psycopg`), не asyncpg; проверено инспекцией `psycopg.errors.UniqueViolation` (`.diag.constraint_name`, плоского атрибута `.constraint_name` на исключении нет — в отличие от asyncpg, где он плоский). Первая реализация ошибочно использовала плоский `getattr(exc.orig, "constraint_name", None)` по образцу asyncpg — молча возвращала `None` для обеих веток и уводила бы оба constraint-пути в `raise` (500) вместо retry/деградации. Обнаружено до записи в код (`uv run python3 -c "import psycopg.errors..."`) и подтверждено сквозным ручным прогоном (см. Verification T1.5) — на реальной БД оба пути (`uq_users_name`, `uq_oauth_accounts_provider`) резолвятся верно.
- **Гонка на `(provider, provider_account_id)` деградирует в `_login_after_race`, а не retry всего цикла имени** — по семантике конфликта: коллизия имени — «нужен другой кандидат», коллизия связки — «связка уже существует, пользователь уже вошёл в этой гонке параллельным запросом», это разные ветки диаграммы брифа (retry vs login-путь), смешивать их в один retry-цикл значило бы либо плодить лишние попытки имени, либо потерять уже существующего пользователя.
- **`_MAX_NAME_ATTEMPTS = 5`** — план фиксирует только «с ограничением попыток», числовое значение не задано ни планом, ни брифом; выбрано как разумный дефолт (1 базовый кандидат + 4 суффиксных retry) без дальнейшей эскалации — коллизия суффиксного кандидата (4 hex-символа = 65536 вариантов) практически исключена на первой же повторной попытке, число попыток — предохранитель от патологического сценария, не ожидаемый рабочий путь.
- **Email на найденной связке освежается безусловно (`account.email = profile.email`), включая присвоение `None`** — research-data-model.md § Таблица решений называет `updated_at` не декоративным именно ради этого: email — «факт, что сообщил провайдер сейчас», а не накопленное состояние; если провайдер перестал отдавать email (например, отозван scope), запись честно отражает это, а не хранит устаревшее значение.
- **`_login_existing`/`_login_after_race` на `user is None` / повторный lookup `None` поднимают `OAuthAccountCreationError`, а не `assert`** — оба пути логически недостижимы при целостной БД (FK `ondelete=CASCADE`; unique violation гарантирует закоммиченную конфликтующую строку, видимую в той же транзакции при read committed) — но план требует «не 500» без оговорок на «недостижимые» ветки; защитный `raise` с `logger.warning` даёт наблюдаемость при реальном рассинхроне вместо необработанного исключения, всплывающего как 500.
- **Невалидный/отсутствующий `next` на `authorize` — молчаливый фолбэк на `/`, не 400** — план фиксирует только «валидировать до записи в claim»; закрытый реестр `/login?error=` (design-brief.md) не резервирует код под этот случай, а `next` — сквозной UX-удобство (куда вернуть пользователя), не security-инвариант (проверка «начинается с `/`, не с `//`» и так исключает open redirect независимо от того, фолбэкаем мы или отклоняем запрос). Отклонение всего запроса 400-кой за невалидный `next` увело бы в незадокументированную ветку вне диаграммы брифа — фолбэк безопаснее и не расширяет контракт.
- **Отсутствующий `code` в query на callback'е — сведён к ветке `provider_unavailable`, не заведена отдельная ветка/причина** — диаграмма брифа даёт EX-узлу («обмен code → токен, userinfo получен?») ровно один неуспешный выход; отсутствие `code` (прямое обращение к callback мимо провайдера, минуя нормальный редирект) технически предшествует самому обмену, но исход для пользователя тот же («сервис входа временно недоступен»), и заводить шестой код вне закрытой таблицы — не в мандате фазы. Проверка стоит после гейтов cookie/state (валидный `state` уже подтверждён), поэтому не открывает новую поверхность атаки — только защищает `provider_impl.exchange_code` от вызова с `code=None`.
- **`OAuthService.login_with_provider` — добавлен четвёртый элемент кортежа (`new_user`), а не отдельный метод/обёртка** — SIEM-событие успеха несёт `new_user` по составу брифа (design-brief.md § Эндпоинты), и только `routes/oauth.py` (эта фаза) может это отличить: create-путь и login-путь на найденной связке уже разошлись внутри `_create_and_login`/`_login_existing`, но наружу это различие раньше не прокидывалось. Расширение существующего кортежа — не архитектурное решение (интерфейс из T1.5 не публиковался наружу трека, единственный потребитель — код этой же фазы), а не альтернатива вроде dataclass-результата: правка на один элемент кортежа, без нового типа ради одного bool.
- **`_set_refresh_cookie` — импорт приватного имени из `routes/auth.py`, не вынос в общий модуль** — план явно оставлял оба варианта на усмотрение реализации («переиспользовать импортом либо поднять в общий модуль»); `ruff.toml` не включает правило приватного доступа (`select` — только `E/W/F/I/UP/B/SIM/PLC0415`), так что импорт не ловится линтером как антипаттерн. Вынос в общий модуль тронул бы `routes/auth.py` (уже стабильный, покрыт 50 тестами) ради одной функции с одним новым потребителем — минимальная правка предпочтена ради риска регрессии, а не ради «чистоты» с нулевой практической разницей при текущем составе вызывающих.
- **Rate-limit-хелпер (`_check_oauth_rate_limit`) продублирован локально в `routes/oauth.py`, не переиспользует `_check_rate_limit` из `routes/auth.py`** — план прямо предписывал это как единственный вариант: `test_event_vocabulary_contract.py`-резолвер разрешает параметр-threading только внутри одного файла (`ast.walk(self.tree)` по дереву модуля, где определена функция); импорт чужого приватного хелпера дал бы слепое пятно — `RATE_LIMIT_OAUTH_EXCEEDED`, переданный из `oauth.py` в `_check_rate_limit`, определённый в `auth.py`, никогда не резолвится, потому что резолвер сканирует каждый файл независимо и не видит межмодульные вызовы. Локальный хелпер с константой напрямую в `event_type=` — самая простая форма, которую резолвер понимает без параметр-threading вообще (не только «не даёт слепого пятна», а вообще не нуждается в этом механизме).
- **`open_reader`/`resolve_country` — свободные функции в `app/infra/geoip.py`, не класс** — сама библиотека уже даёт готовый ресурс (`maxminddb.Reader`) и чистую операцию над ним (`.get`); обёртывание в собственный класс добавило бы состояние ради состояния — единственная переменная состояния (сам reader) и так живёт в `app.state`, а не в новом объекте. Прецедент — `app/infra/rate_limit.py` не заведён как образец (`RateLimiter` — класс, потому что несёт мутируемые счётчики между вызовами); здесь мутируемого состояния между вызовами нет, `resolve_country` — чистая функция от `(reader, ip, fallback)`.
- **Гео-отказ на authorize НЕ гасит cookie (`delete_cookie=False`), хотя ветка терминальна для запроса** — семантика `delete_cookie` в `_login_redirect` (T1.6) — «была ли выставлена cookie `oauth_flow` этим флоу и нужно ли её погасить», а не «терминальна ли ветка» вообще: на `authorize` cookie физически ещё не существует (генерируется и ставится только после гео-проверки, дальше по коду) — гасить нечего, а `delete_flow_cookie` на пустой cookie не создаёт проблем сам по себе, но лишний `Set-Cookie` в ответе без причины — шум. На `callback`, где cookie уже могла существовать (пришла в запросе), геo-отказ гасит её (`delete_cookie=True`) — та же логика, что и у остальных терминальных веток диаграммы.
- **`_resolve_client_country` читает `request.app.state.geoip_reader` напрямую, не через `Depends`-обёртку** — единственный потребитель `app.state.geoip_reader` — три места в `routes/oauth.py`; заводить отдельный `GeoipReaderDep` ради трёх вызовов внутри одного модуля избыточно (сравни с `RateLimiterDep`/`SettingsDep` — те переиспользуются как параметры сигнатур FastAPI-обработчиков и участвуют в OpenAPI, `geoip_reader` нигде не нужен как параметр эндпоинта самого по себе, только как вход в `resolve_country`).
- **`_GEO_ALLOWED_PROVIDERS_RU` — `frozenset`, не `set`/`list`** — константа модуля, member-check (`in`) — семантика неизменяемого множества ближе, чем список; тот же стиль, что и `frozenset` не заведён нигде специально прежде, но `frozenset` — стандартный питоновский способ пометить «эта коллекция не мутируется после определения», уместный для бизнес-инварианта, не подлежащего рантайм-модификации.
- **`OAuthAccountRepository` не добавлен в `repositories/__init__.py`** — пакет уже не следует правилу «каждый репозиторий в `__all__`» (`MCPServerRepository`, `settings.py`-репозиторий импортируются напрямую в местах использования, минуя агрегатор); T1.6 будет импортировать `OAuthService`/`OAuthAccountRepository` напрямую из своих модулей тем же паттерном, что `routes/auth.py` сейчас импортирует `AuthService` из `app.services.auth` — расширение агрегатора не требуется под план фазы.

- **Userinfo-endpoint Google — `openidconnect.googleapis.com/v1/userinfo`, не `www.googleapis.com/oauth2/v3/userinfo`** — оба возвращают эквивалентный набор полей по access token, разницы для этой фазы нет; выбран OIDC-совместимый путь как более явно документированный текущими доками Google для scope `openid email profile` (research-provider-libs.md ссылается на `developers.google.com/identity/protocols/oauth2/web-server` без фиксации конкретного endpoint'а — решение реализации, не отступление от плана). JWKS/`id_token`-валидация не заводится ни в каком варианте — план и бриф явно исключают её, профиль всегда берётся по access token.
- **`Authorization: Bearer <token>`, а не `OAuth <token>`** — Яндекс использует нестандартную non-OIDC схему заголовка (`login.yandex.ru/info`), Google — стандартный OAuth 2.0 Bearer; копирование яндексовской схемы в `google.py` было бы ошибкой, не единообразием — единый интерфейс (`OAuthProvider` Protocol) не требует единого HTTP-заголовка, только единой сигнатуры.
- **PKCE у GitHub — интерфейс не разветвлён, `authorize_url`/`exchange_code` принимают и передают `state`/`challenge`/`verifier` наравне с остальными провайдерами** — план (Open Questions № 3) явно требует единый `Protocol` без ветвления сигнатуры под конкретного провайдера; альтернатива («GitHub не принимает PKCE-параметры вовсе») сделала бы `OAuthProvider` неполиморфным — вызывающий код (`routes/oauth.py`) перестал бы работать с провайдерами единообразно, ему пришлось бы знать, какой из трёх пропускает какие аргументы. Передача параметров, которые GitHub молча игнорирует, обходится без дополнительной сложности и держит абстракцию честной: реализация класса решает, полагаться ли на параметр, а не сигнатура метода.
- **Ошибка обмена кода GitHub (`{"error": ...}` в теле 200-ответа) распознаётся отдельной веткой, до чтения `access_token`** — в отличие от Яндекса/Google, GitHub не поднимает HTTP-статус на невалидный `code`/`redirect_uri`/`client_secret` (задокументированная особенность API, не предположение) — без этой проверки `payload["access_token"]` кинул бы `KeyError` на легитимном ответе-ошибке, и она всё равно попала бы в ту же malformed-response ветку и тот же `OAuthProviderError`, но с менее точным логом (`malformed response` вместо явного `provider returned error`). Решение — не архитектурное расширение, а точнее направленный `logger.warning`-контекст внутри уже существующей ветки try/except.
- **`_fetch_primary_email` не поднимает `OAuthProviderError` на отказ, а деградирует в `None`** — единственный провайдер трека с двухшаговым профилем; критерий брифа и плана фазы («аккаунт со скрытым email даёт связку с `email = NULL` без ошибки») явно рассматривает отсутствие email как штатный, не ошибочный исход. Если бы `/user/emails` поднимал `OAuthProviderError` наравне с `/user`, временная недоступность второстепенного эндпоинта блокировала бы весь вход — несоразмерная цена за необязательное поле профиля (`OAuthProfile.email: str | None` и так nullable по контракту T1.4).
- **Выбор email из `/user/emails` — primary+verified, затем любой verified, иначе `None`; unverified-адреса не рассматриваются вовсе** — GitHub может вернуть несколько записей (в т.ч. приватные alias-адреса `noreply`), и это единственная политика выбора, совместимая с тем, что уже делает `OAuthService`: `oauth_accounts.email` — не проверяемый повторно бэкендом факт, поэтому источник обязан быть верифицированным на стороне провайдера, иначе поле не несёт даже той гарантии, что несёт для Яндекса/Google (их API отдают уже верифицированный основной адрес одним полем).
- **`provider_account_id` GitHub — `str(id)`, а не `id` напрямую** — единственный из трёх провайдеров, где `/user` отдаёт `id` целым числом (Яндекс и Google — уже строки в своих payload'ах); `OAuthProfile.provider_account_id: str` и `oauth_accounts.provider_account_id` (T1.1, `Text`) держат инвариант «одна строка на все провайдеры» — преобразование делает это на границе провайдера, не просачивая тип наружу абстракции.
- **Фолбэк-страна нормализуется в `resolve_country`, а не в `Settings` и не в сравнениях гейта** (фикс T1-R1) — гейт сравнивает страну строго (`country != "RU"`), а фолбэк приходил из env как есть: при `GEOIP_FALLBACK_COUNTRY=ru` любая деградация резолва (нет базы, промах на приватном IP, нераспарсиваемый IP) переворачивала fail-closed в fail-open и открывала РФ-клиенту все три провайдера. Нормализация (`.strip().upper()`) поставлена одной строкой в начале `resolve_country` и покрывает все три выхода функции — MMDB-путь и так нормализован `_extract_country_code`, так что после правки функция гарантирует инвариант «наружу всегда ISO-код в верхнем регистре» целиком, для любого вызывающего и любого источника фолбэка. Альтернатива — field-validator в `Settings` — закрывала бы только env-путь и оставляла бы функцию способной вернуть строчный код при вызове с литералом; выбранная точка держит инвариант в том модуле, который владеет понятием country-кода, и не требует расставлять `.upper()` по местам сравнения.
- **Locals выключены у rich-рендера трейсбеков в `app/infra/logging.py`** (санкционированный архитектором фикс поверх трека) — при `format: human-readable` (дефолт `configs/logging.yaml`) `structlog.dev.ConsoleRenderer` по умолчанию берёт `RichTracebackFormatter(show_locals=True)`, и любой фрейм, где в locals лежит `settings`, печатал в stdout/`app.log` значения всех секретов (`jwt_secret`, `llm_api_key`, шесть `oauth_*`-кредов) открытым текстом. Внешне достижимый триггер — `GET /api/auth/oauth/{provider}/callback` с мусорным `code`: ветка `provider_unavailable` логирует `exc_info=True`. Митигация точечная — обоим человекочитаемым рендерам (stdout и файл) передан общий `RichTracebackFormatter(show_locals=False)`: стек, номера строк и контекст кода сохраняются, панель locals исчезает; правка живёт в одном месте инфраструктуры логирования и закрывает утечку для всех эмит-сайтов сразу, а не только для OAuth-роута. Альтернатива «обернуть секретные поля `Settings` в `SecretStr`» — глубокая защита, но она трогает каждое чтение секрета в кодовой базе и по решению архитектора вынесена в backlog отдельным кандидатом, а не в этот фикс. JSON-формат (`format: json`) locals не рендерит и правкой не затронут.

- Дефолтный фолбэк (`GEOIP_FALLBACK_COUNTRY` не переопределён → `RU`, реальная MMDB-база из `.env.local`, IP `127.0.0.1` не резолвится → фолбэк): `GET /api/auth/providers` → `{"providers":["yandex"],"password":true}` (GitHub не виден, как и Google); `GET /api/auth/oauth/github/authorize` → 302 `/login?error=provider_not_available_in_region`, без `Set-Cookie` (гео-отказ на authorize не гасит ещё не выставленную cookie — T1.7). Callback-ветка гео-блока для GitHub под тем же RU-фолбэком проверена отдельно (валидная cookie не получима через реальный authorize — он блокируется раньше): `oauth_flow`-cookie для `provider=github` собрана напрямую вызовом `encode_flow_cookie` тем же `JWT_SECRET`, что у работающего процесса, и отправлена на `GET /oauth/github/callback?state=...` без `?error` — 302 `/login?error=provider_not_available_in_region` + `Set-Cookie: oauth_flow=""; Max-Age=0` (терминальная ветка гасит cookie — «Ветка 3» диаграммы брифа между сверкой state и обменом кода, тот же путь, что и для Google в T1.7, теперь пройден для GitHub).
- `GET /api/auth/oauth/yandex/authorize` в том же RU-прогоне (тот же процесс) → 302 на реальный `oauth.yandex.ru` — гео-gate не задевает разрешённого провайдера, регрессии от добавления третьего провайдера в реестр нет.
- Не-РФ ветка (`GEOIP_FALLBACK_COUNTRY=US`, отдельный процесс, `:8013`): `GET /api/auth/providers` → `{"providers":["github","google","yandex"],"password":true}`; `GET /api/auth/oauth/github/authorize` → 302 на `https://github.com/login/oauth/authorize` с `response_type=code`, `redirect_uri=http%3A%2F%2Flocalhost%3A5173%2Fapi%2Fauth%2Foauth%2Fgithub%2Fcallback` (точное совпадение с брифовым dev-значением), `scope=user%3Aemail`, `state=<32-байтовый token_urlsafe>`, `code_challenge`/`code_challenge_method=S256` (PKCE-параметры присутствуют протокольно, как и предписывает план — GitHub их не проверяет) — `client_id` в ответе присутствует (значение не публиковалось за пределы локального прогона) + `Set-Cookie: oauth_flow=<JWT>; HttpOnly; Max-Age=600; Path=/api/auth/oauth; SameSite=lax`.
- Реальный браузерный обмен кода на GitHub (interactive-согласие на `github.com`, создание пользователя первым входом, аккаунт со скрытым/открытым email) не прогонялся — вне мандата фазы (TEST/INTEGRATION), тот же принцип, что и в T1.6/T1.7/T1.8: find-or-create и обмен кода как таковые уже подтверждены сквозным прогоном T1.5/T1.6 на Яндексе, `github.py` проходит через тот же неизменный путь `OAuthService.login_with_provider`; специфичная для GitHub логика (`Accept: application/json`, ветка `{"error": ...}`, добор `/user/emails`, `str(id)`) — код-ревью и статический анализ (`mypy`), а не ручной сквозной прогон с реальным согласием.
- Тестовые процессы (`:8012`, `:8013`) остановлены по завершении проверок (`kill`/`pkill`, штатное завершение — не `docker`, соседние worktree и контейнеры не тронуты). Временные логи с трейсбеком redis (та же пред­существующая нефатальная DNS-ошибка при недоступном Redis, что и в T1.2/T1.8, не по треку) не содержали кредов — очищены из scratchpad.
