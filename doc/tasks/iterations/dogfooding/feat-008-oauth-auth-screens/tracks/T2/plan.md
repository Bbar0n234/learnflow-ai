# Implementation Plan: feat-008 / трек T2 — Frontend: каркас `/login`, guard, бутстрап

## Контекст

Трек перестраивает вход в SPA: блокирующая модалка `AuthGate` над роутером умирает, её место занимает публичная страница `/login` под роутером, а решение «пускать или на логин» принимает guard `RequireAuth` — после того, как единый app-уровневый бутстрап аутентификации отработал (есть access в localStorage → готово; нет → один тихий `POST /api/auth/refresh`, который в том числе подхватывает refresh-cookie, только что поставленную OAuth-callback'ом). Сама страница — **каркас, не дизайн**: состав и порядок блоков берутся из утверждённого мокапа feat-013, но собираются локальными компонентами внутри `pages/login/`, чтобы брендовая презентация feat-013 после merge легла подменой, а не перестройкой DOM.

Бэкенд трека T1 нам не нужен: работаем против контракта из брифа (`GET /api/auth/providers` → `{providers: string[], password: bool}`, закрытый реестр кодов `/login?error=`) и MSW-моков.

## Фазы

### T2.1: Контракт провайдеров в `shared/api` + query key + MSW-фабрика

**Цель:** появляется типизированный доступ к `GET /api/auth/providers` через TanStack Query и мок для тестов — до того, как его начнёт потреблять UI.

**Изменения:**

- `frontend/src/shared/api/auth.ts` — DTO ответа (`providers: string[]`, `password: boolean`), функция запроса через `apiClient` и data-хук над ней (конвенция: data-хуки живут рядом с API-функциями в `shared/api/<domain>.ts`). Отдельный модуль `shared/api/auth-providers.ts` допустим, если файл распухнет; домен тот же, поэтому по умолчанию — `auth.ts`.
- `frontend/src/shared/api/query-keys.ts` — ключ `auth.providers` в существующей ветке `auth` (инлайн-литералов ключей в хуках не заводим).
- `frontend/src/test/msw/` — фабрика хендлеров для `/api/auth/providers` (RU-вариант, не-РФ-вариант, отказ), экспортируемая отдельным модулем. В дефолтный `handlers.ts` не кладём: по конвенции дефолтные хендлеры пусты, сеть каждый тест объявляет сам через `server.use(...)`.

**Направление, не построчный код:**

- `providers` — массив строк с сервера, состав неподконтролен фронту. Отображение в кнопки идёт **позитивным предикатом**: известные id (`yandex`, `google`, `github`) получают подпись, неизвестный id молча не рендерится (conventions § Позитивный предикат над неподконтрольным множеством). Реестр подписей — один объект в слайсе `pages/login`, не в `shared`; порядок записей в реестре и есть порядок рендера (механизм — T2.4).
- Запрос анонимный; правку `shared/api/client.ts` он не требует — текущий response-интерцептор и так исключает `/auth/`-URL из refresh-retry, а семантическое правило feat-013 классифицирует его так же (бриф § Контракты).

**Verification:**

- `make check-fe` проходит (tsc + eslint + prettier)
- `make test-fe` остаётся зелёным (новых сетевых вызовов в существующих тестах не появилось)
- Тип ответа буквально соответствует контракту брифа `{providers: string[], password: bool}`

### T2.3: Перестройка входа — `BrowserRouter` наверх, бутстрап, `RequireAuth`, смерть `AuthGate`

**Цель:** неаутентифицированный пользователь на любом маршруте попадает на `/login` с запоминанием исходного пути и возвращается после входа; возврат из OAuth-callback'а поднимает сессию без мигания `/login` и без редирект-лупа.

**Изменения:**

- `frontend/src/App.tsx` — `ErrorBoundary` → `BrowserRouter` → бутстрап-гейт → `AppRoutes`. `AuthGate` из дерева убирается.
- `frontend/src/app/model/useAuthBootstrap.ts` (новый сегмент `model/` в слое `app`, см. Open Questions #3) — однократный бутстрап: есть access в localStorage → сразу готов; нет → **тихий** `POST /api/auth/refresh` **мимо `apiClient`** (прямой axios/fetch на `${import.meta.env.VITE_API_URL ?? "/api"}/auth/refresh`, передача cookie: `withCredentials` / `credentials: "include"`), 200 → `setAccessToken`, 401 → обычный путь анонима. Существующий `refresh()` из `auth.ts` для бутстрапа **не используется** (он ходит через `apiClient`, чей интерцептор безусловно пишет `logger.error` на 401, а `client.ts` заморожен).
- Пока бутстрап не завершён — рендерится существующий паттерн загрузки (`«Загрузка...»`, как в `router.tsx`/`SecurityRouteGuard`), не редирект.
- `frontend/src/app/components/RequireAuth.tsx` — guard на layout-маршруте: вердикт нереактивный, по наличию access token (как сегодня у `AuthGate`); нет токена → `<Navigate to="/login" replace state={{ from: <строка пути> }} />` (форма `from` — ниже, в «Направлении»).
- `frontend/src/app/router.tsx` — публичный маршрут `login`; существующая группа маршрутов оборачивается в `RequireAuth`. Catch-all `path="*"` **не добавляем** — он принадлежит feat-013.
- `frontend/src/app/components/AuthGate.tsx` — удаляется; проверить, что ссылок на него не осталось.
- `frontend/src/app/components/Sidebar.tsx` — логаут-путь **проверяется, не переписывается**: после `logout()` + `clearAccessToken()` + `window.location.reload()` бутстрап на новой загрузке получает 401 (refresh отозван) и guard уводит на `/login`. Правка нужна, только если фактическое поведение расходится с этим.
- `frontend/src/app/router.test.tsx` — минимальная подгонка, если перестройка входа сломала существующие проверки (тесты монтируют `AppRoutes` в `MemoryRouter` с выставленным токеном). Расширение покрытия — работа `test-author`, не этой фазы.

**Направление:**

- **Форма `from` — строка пути, не объект `location`.** Guard кладёт в `state` результат `location.pathname + location.search + location.hash`; объект `location` в `state` не попадает. Причина: значение уходит в query-параметр `next` (T2.4), где объект дал бы `next=%5Bobject%20Object%5D`, и backend-валидация «относительный путь, начинается с `/`» его отбракует. Оба потребителя работают с этой строкой: `navigate(from)` после успешного парольного входа и `next=<from>` в URL `/authorize`. Значение отсутствует (прямой заход на `/login`) → дефолт `/`.
- **Бутстрап гейтит маршруты целиком**, а не сообщает свой статус guard'у: пока он не завершён, роуты не смонтированы, поэтому `RequireAuth` по построению «принимает вердикт только после бутстрапа» (бриф § Frontend) и ему не нужен ни новый стор, ни проп-дриллинг. Новый auth-стор не заводится (бриф; упрёмся — эскалация, не молчаливый стор).
- Однократность в `StrictMode` (двойной вызов эффектов в dev) обеспечивается дедупликацией на уровне TanStack Query (одноразовый query-ключ, `retry: false`, `staleTime`/`gcTime: Infinity`) либо ref-гвардом. При варианте с Query: `queryFn` **не должна реджектиться на 401** — глобальный `QueryCache.onError` пишет `logger.error`, а тихий путь анонима ошибкой не является; ключ бутстрапа — через фабрику `query-keys.ts`.

**Verification:**

- `make check-fe` и `make test-fe` проходят
- Аноним на защищённом URL получает `/login`, исходный путь сохранён и после успешного парольного входа пользователь возвращается на него (`from`, `replace`)
- `/login` доступен без токена и находится вне guard'а
- Загрузка SPA с валидной refresh-cookie и пустым localStorage заканчивается аутентифицированным состоянием без промежуточного показа `/login`; 401 в этом же сценарии не порождает `logger.error` и не зацикливает редиректы
- В дереве и в исходниках не осталось `AuthGate`; `shared/api/client.ts` в диффе отсутствует

### T2.4: Блок провайдеров, транспорт `next`, реестр кодов ошибок

**Цель:** на `/login` появляются кнопки провайдеров по составу с бэкенда, клик уводит браузер в OAuth-флоу с сохранённым `next`, а возврат с `?error=<код>` показывает человекочитаемое сообщение вместо белого экрана.

**Изменения:**

- `frontend/src/pages/login/ui/` — локальный компонент блока кнопок провайдеров (список из хука T2.1) + локальный реестр подписей: `yandex` → «Войти с Яндекс ID», `google` → «Войти через Google», `github` → «Войти через GitHub» (тексты мокапа).
- **Механизм порядка кнопок:** рендер итерирует **локальный реестр** в фиксированном порядке `yandex` → `google` → `github` и фильтрует его по серверному списку `providers` (а не итерирует ответ сервера). Один приём закрывает три требования: порядок мокапа воспроизводится независимо от порядка в ответе бэкенда (и от чужого трека, который этот ответ формирует), позитивный предикат T2.1 выполняется по построению (неизвестный серверный id просто не встречается в реестре и не рендерится), а состав остаётся серверным (провайдер из реестра без записи в `providers` не рендерится).
- `LoginPage.tsx` — переход по клику: **полная навигация** `window.location.assign('/api/auth/oauth/{provider}/authorize?next=<from>')`, не fetch (флоу редиректный); `from` — **строка пути**, сохранённая guard'ом в `location.state` (форма зафиксирована в T2.3), при отсутствии — `/`; значение проходит `encodeURIComponent`.
- `LoginPage.tsx` — чтение `?error=` из query и маппинг по **закрытому** реестру брифа (§ Эндпоинты, таблица кодов): `access_denied`, `flow_expired`, `provider_not_available_in_region`, `provider_unavailable`, `oauth_failed` — тексты берутся из таблицы дословно; неизвестный код → generic-текст `oauth_failed`. Сообщение рендерится тем же блоком ошибки карточки, что и ошибки парольной формы.

**Краевые состояния (каркас обязан их держать):**

- Список провайдеров грузится — парольная форма доступна, блок кнопок не блокирует экран.
- Запрос провайдеров упал — блок кнопок отсутствует, парольный вход работает (деградация, не белый экран).
- `providers: []` (RU без заполненных кредов Яндекса) — виден только пароль, разделитель «или» без кнопок не висит.

**Verification:**

- `make check-fe`, `make test-fe` проходят
- MSW-вариант `{providers:["yandex"], password:true}` даёт ровно одну кнопку; `{providers:["yandex","google","github"]}` — три, в порядке Яндекс → Google → GitHub (порядок мокапа)
- Клик по кнопке провайдера инициирует полный переход на `/api/auth/oauth/{provider}/authorize?next=<исходный путь>`; XHR-запроса на authorize не происходит
- Каждый из пяти кодов `?error=` даёт свой текст из таблицы брифа; неизвестный код не роняет экран
- Все три краевых состояния списка провайдеров не ломают парольный вход

## Handoff тестовым ролям

Автотесты трека пишет `test-author`; фазы дают ему поверхности, а не готовые тесты. Перечень того, что обязано быть покрыто (кейсы названы брифом § Frontend, «`router.test.tsx` расширяется» и «исключает редирект-луп и мигание `/login`»):

**(а) `frontend/src/app/router.test.tsx` — два кейса**, монтирование `AppRoutes` в `MemoryRouter`, как сегодня:

- неаутентифицированный (пустой localStorage) на защищённом маршруте редиректится на `/login`, исходный путь сохранён в `location.state.from` строкой;
- `/login` открывается без токена — маршрут публичный, вне `RequireAuth`.

**(б) Отдельная тестовая поверхность на `App` / `useAuthBootstrap`.** Через `router.test.tsx` недостижима: хук живёт над `AppRoutes` (в `App.tsx`), а роутерные тесты монтируют именно `AppRoutes` — значит нужен свой файл, монтирующий `App` (или хук напрямую). Сценарии:

- валидная refresh-cookie + пустой localStorage → access получен, аутентифицированное состояние без промежуточного показа `/login` (нет мигания);
- 401 без cookie → тихий путь анонима: `/login`, без `logger.error` (проверяется спаем на логгер — глобальный `QueryCache.onError` не должен сработать).

Сеть для (б) — MSW-хендлер `POST /api/auth/refresh` в двух вариантах: 200 с access и 401.
