# Track Summary: feat-008 / трек T2 — Frontend: каркас `/login`, guard, бутстрап

## TL;DR

**Трек T2 сделан целиком (T2.1–T2.4).** T2.1: типизированный доступ к `GET /api/auth/providers` (DTO `AuthProvidersResponse`, `getAuthProviders`, `useAuthProviders` — в `shared/api/auth.ts`; ключ `auth.providers` в `query-keys.ts`; MSW-фабрика `test/msw/auth-providers.ts`). T2.2: слайс `pages/login` — `LoginPage` (контейнер: режим вход/регистрация, валидация, `login`/`register`, `setAccessToken`) + локальный презентационный `LoginScreenView` (каркас по мокапу feat-013: wordmark+tagline → карточка формы → разделитель «или» → слот провайдеров → ссылка переключения режима), русский копирайт, ошибка через `getApiErrorMessage`. T2.3: вход в SPA перестроен — `App.tsx` теперь `ErrorBoundary` → `BrowserRouter` → бутстрап-гейт (`AppBootstrapGate`) → `AppRoutes`; `AuthGate` удалён; `app/model/useAuthBootstrap.ts` — однократный тихий бутстрап (access есть → готово; иначе один `POST /api/auth/refresh` напрямую через `fetch`, мимо `apiClient`) поверх TanStack Query (queryFn не реджектится на 401 — `QueryCache.onError` не срабатывает); `app/components/RequireAuth.tsx` — нереактивный guard на layout-роуте, кладёт `from` (`pathname+search+hash`) в `location.state` и уводит на `/login`; `/login` — публичный маршрут вне guard'а; `LoginPage` читает `location.state.from` и делает `navigate(from, { replace: true })` после успешного входа. `Sidebar.tsx` — логаут-путь проверен, совпадает с планом буквально, не менялся.

**T2.4** наполнила слот провайдеров и закрыла краевые состояния. `pages/login/ui/provider-registry.ts` — локальный реестр трёх провайдеров в фиксированном порядке (Яндекс → Google → GitHub) и функция `getActiveProviders(providers)` — пересечение реестра с серверным списком; `pages/login/ui/ProviderButtons.tsx` — чисто презентационный блок кнопок (`variant="outline"`, `size="lg"`, как `.prov-btn` мокапа), клик передаётся наружу `onSelect`. `LoginPage.tsx` считает `activeProviders = getActiveProviders(providersData?.providers ?? [])` и либо передаёт `providersSlot` с блоком кнопок, либо `undefined`; клик по кнопке — `window.location.assign('/api/auth/oauth/{provider}/authorize?next=<encodeURIComponent(from)>')`, полная навигация, без fetch. `LoginPage.tsx` также читает `?error=` из `location.search` при монтировании и мапит по закрытому реестру пяти кодов брифа (`OAUTH_ERROR_MESSAGES`, тексты дословно) в тот же `error`-стейт, что и у парольной формы; неизвестный код → текст `oauth_failed`. `LoginScreenView.tsx` — разделитель «или» теперь рендерится только вместе с `providersSlot` (было: безусловно), одним и тем же приёмом закрывающим все три краевых состояния плана: загрузка списка, отказ запроса и `providers: []` — во всех трёх `activeProviders` пуст, слот `undefined`, разделитель не висит, парольная форма не блокируется.

Отклонений от плана нет ни в одной из четырёх фаз (в T2.2 — два мелких копирайт-дополнения сверх буквального списка плана, см. «Решения»). `make check-fe`, `make test-fe` (395/395; без правок `router.test.tsx` — существующая сьюта осталась зелёной как есть) и `make build-fe` — все три зелёные по итогам всего трека. Пост-имплементационное ревью дало три nit'а на этот трек (голый `fetch` бутстрапа без таймаута, хардкод `/api` в кнопке провайдера, две фазовые пометки в докстрингах) — все фиксы применены отдельным проходом (см. «Фиксы по code review» ниже), `make test-fe` остался зелёным (431/431 по всему фронтенду).

## Решения и обоснования

- **Один файл `shared/api/auth.ts`, не отдельный `auth-providers.ts`.** План допускал оба варианта («отдельный модуль допустим, если файл распухнет»). После добавления DTO + функции + хука файл — 90 строк, обозримый; домен тот же (auth), выносить не за что.
- **MSW-фабрика — объект трёх функций (`authProvidersHandlers.ru()` / `.nonRu()` / `.failure()`), не три отдельных экспорта.** В проекте нет прецедента модуля-фабрики хендлеров (только `handlers.ts`/`server.ts`), поэтому форма — решение фазы: один именованный экспорт объединяет вариант-геттеры, каждый возвращает `RequestHandler` под `server.use(...)`, ошибочный вариант даёт `{ detail: ... }` + 500 — по существующему в тестах паттерну (`NewChatModal.test.tsx` и др.), не problem+json (parser `getApiErrorMessage` эту фазу не касается — блок кнопок провайдеров в T2.4 просто не рендерится при отказе, текст ошибки не показывается).
- **`getAuthProviders` без правки `client.ts`.** Подтверждено чтением файла: интерцептор уже исключает `/auth/`-URL из refresh-retry (`!originalRequest.url?.includes("/auth/")`), так что анонимный `GET /auth/providers` уже не попадает в retry-петлю — созвучно с семантическим правилом feat-013 (design-brief.md § Контракты). Правка не потребовалась.
- Полный прогон `make test-fe` (с изменениями трека и без них, дважды) дал один и тот же `Uncaught Exception: window is not defined` из `SecurityRules.test.tsx` (таймер `setTimeout` в `SecurityRules.tsx:84`, стреляющий после teardown jsdom) — воспроизводится идентично на чистом дереве без диффа трека; изолированный прогон файла зелёный. Флейк тестовой инфраструктуры вне скоупа фазы, не блокирует T2.1 (пройденные тесты — 395/395 в обоих прогонах).

**T2.2:**

- **Подзаголовок карточки для режима регистрации — «Создайте аккаунт, чтобы начать работу.», сверх буквального списка плана.** Мокап feat-013 рисует только состояние «Вход» (`.as` = «Продолжите работу со своими проектами.»); экран регистрации в HTML-разметке не представлен, а копирайт-список плана перечисляет заголовки обоих режимов, но не подзаголовок. Структура каркаса («заголовок → подзаголовок → поля») требует DOM-узел подзаголовка в обоих режимах, поэтому текст для «Регистрация» — по аналогии с тоном мокапа, не из явного источника. Низкий риск (чистый копирайт, не архитектурное решение), но отмечаю как отступление от буквы плана.
- **Обратная ссылка переключения режима — «Уже есть аккаунт? Войти», тоже сверх списка плана.** Тот же случай: план даёт только направление логин→регистрация («Нет аккаунта? Зарегистрироваться»), обратное направление нужно функционально (тумблер двусторонний, логика перенесена из `AuthGate`, где было симметричное `Already have an account? Sign in`). Взят русский аналог того же смысла.
- **`providersSlot?: ReactNode` в `LoginScreenView`, не жёстко зашитый провайдерский блок.** Разделитель «или» — статический DOM-узел каркаса (мокап показывает его всегда для РФ, где минимум одна кнопка Яндекса). Сам слот в T2.2 не заполняется (граница трека — блок провайдеров наполняется в T2.4); `LoginPage` пропускает `providersSlot` не заданным, рендерится `undefined` — валидный React-узел, элемент разметки отсутствует. Условное скрытие разделителя при пустом списке провайдеров (`providers: []`) — тоже T2.4, там уже есть реальные данные, по которым решать.
- **`navigate("/", { replace: true })` после успешного входа, без чтения `location.state.from`.** Механизм «вернуться на исходный путь» описан в T2.3 (guard `RequireAuth` кладёт `from` в `location.state`) — в T2.2 такого состояния ещё нет и роутинг не подключён (страница вне `AppRoutes`), поэтому контейнер не читает `location.state` заранее. `navigate("/")` — эквивалент того, что делал `AuthGate` (просто пропускал `children` после успеха); T2.3 заменит его на `navigate(from)`.
- **Стиль ошибки формы — `rounded-lg border border-destructive/30 bg-destructive/10 px-3.5 py-2.5 text-destructive`, не голый `<p className="text-destructive">` из `AuthGate`.** В `AuthGate` ошибка — простая строка без рамки; мокап рисует карточную плашку (`.err-card`, паттерн блока 4). Взят класс существующего в кодовой базе паттерна карточки ошибки (`SecurityAlerts.tsx`, `SecurityEvents.tsx`, `MessageList.tsx` — везде один и тот же набор классов `border-destructive/30 bg-destructive/10 ... text-destructive`), не hex/rgba и не новый примитив.
- **`boxShadow: "var(--shadow-input)"` инлайн-стилем, не Tailwind arbitrary-класс.** В проекте нет прецедента `shadow-[var(--...)]`; существующий паттерн для этого токена — инлайн `style` (`ChatInput.tsx`, `ChatList.tsx`). Повторено буквально, не изобретён новый способ подключения токена.
- **Карточка и разделитель — `rounded-xl` (не `rounded-2xl`).** `--radius-xl` в `index.css` = `calc(var(--radius) * 1.4)` — то же значение, что `.auth-frame`/`.auth-card` в мокапе (`border-radius: calc(var(--radius) * 1.4)`); `rounded-2xl` дал бы другой множитель (`1.8`) и разошёлся бы со структурным референсом.

**T2.3:**

- **Бутстрап — через TanStack Query с не-реджектящим `queryFn`, не ref-гвард.** План допускал оба варианта дедупликации под `StrictMode`. Взят вариант Query: `bootstrapAuth()` в `app/model/useAuthBootstrap.ts` перехватывает и явный 401 (`!response.ok`), и сетевой сбой (`try/catch` вокруг `fetch`) внутри самой функции и всегда резолвится значением `{ authenticated: boolean }` — никогда не реджектится. Это ровно требование плана («queryFn не должна реджектиться на 401» — глобальный `QueryCache.onError` иначе пишет `logger.error` даже на ожидаемый путь анонима) и попутно даёт дедупликацию бесплатно: один query-ключ (`queryKeys.auth.bootstrap`), `retry: false`, `staleTime`/`gcTime: Infinity` — повторный вызов эффекта в `StrictMode` (dev) не порождает второй сетевой запрос, React Query сам делит один in-flight promise.
- **Сетевой сбой (`fetch` бросает, а не резолвится с `!ok`) тоже сводится к `{ authenticated: false }`, без отдельного лога.** План явно требует тишины только для 401 («ожидаемый путь анонима»); про офлайн/DNS-сбой явного указания нет. Решено не заводить асимметрию: оба случая ведут к одному и тому же наблюдаемому поведению (аноним, `RequireAuth` уводит на `/login`), а разный уровень шума на них без явного требования — самостоятельное архитектурное решение, которого фаза не просила. Если понадобится диагностика сетевых сбоев бутстрапа отдельно от 401 — это к архитектору.
- **`useAuthBootstrap` возвращает только `{ ready: boolean }`, не статус аутентификации.** Прямое следствие направления плана «бутстрап гейтит маршруты целиком, а не сообщает свой статус guard'у»: `App.tsx` не рендерит `AppRoutes`, пока `ready` не `true`, а `RequireAuth` внутри дерева маршрутов принимает вердикт синхронным чтением `getAccessToken()` — тем же приёмом, что раньше использовал `AuthGate`. Прокидывать булev флаг «аутентифицирован» через хук было бы лишней осью состояния ровно там, где план прямо просит её не заводить (упомянутый в плане «новый auth-стор»).
- **`LoginPage.navigate(from)` вместо `navigate("/")` — довнесено в рамках T2.3, как и предполагала пометка в решениях T2.2.** `location.state.from` читается через `useLocation()`, приводится к `{ from?: string } | null`, дефолт `"/"` при прямом заходе на `/login` (нет `state` — заход не через guard). Правка не выходит за пределы `LoginPage.tsx`, `LoginScreenView` не тронут.
- **`router.test.tsx` не потребовал правок.** Существующие тесты монтируют `AppRoutes` напрямую (не `App`), а `setAccessToken(...)` в каждом тесте выполняется до рендера — `RequireAuth` (нереактивный, читает токен синхронно) пропускает их так же, как раньше это делал плоский роут без guard'а. Бутстрап-гейт (`AppBootstrapGate`) живёт в `App.tsx`, выше `AppRoutes`, и в эти тесты не попадает вовсе — сьюта прошла без единой правки, включая уже отмеченный в плане риск («минимальная подгонка», если что-то сломается).
- **`Sidebar.tsx` не правился.** Логаут-путь (`logout().catch(() => {}); clearAccessToken(); window.location.reload()`) сверен построчно с описанием плана — совпадает буквально: перезагрузка страницы отдаёт бутстрапу управление заново, а он на отозванной refresh-cookie получает 401 и уходит по тихому пути анонима, `RequireAuth` на новой загрузке уводит на `/login`. Расхождений не найдено.

**T2.4:**

- **Реестр провайдеров и `getActiveProviders` вынесены в отдельный файл `provider-registry.ts`, не оставлены в `ProviderButtons.tsx`.** Первая попытка держать константу реестра и функцию-фильтр рядом с компонентом дала eslint-предупреждение `react-refresh/only-export-components` (файл с компонентом экспортировал ещё и функцию) — в проекте нет прецедента подавления этого правила. Разнесение на «данные» (`provider-registry.ts`: тип `ProviderEntry`, реестр, `getActiveProviders`) и «презентация» (`ProviderButtons.tsx`: только компонент) убрало предупреждение чисто структурно, без исключений линтера, и заодно чище легло на границу «список — вычисляется в контейнере (`LoginPage`), рендерится презентационным компонентом».
- **Фильтрация реестра — функция `getActiveProviders`, вызываемая в `LoginPage`, а не логика внутри `ProviderButtons`.** План описывает механизм («рендер итерирует локальный реестр и фильтрует его по серверному списку») как единый приём, не привязывая его к конкретному компоненту. Решено вынести наружу компонента: `LoginPage` получает готовый список `entries` и по его пустоте решает, передавать ли `providersSlot` вообще (`undefined` при пустом списке) — единая точка правды для трёх краевых состояний плана (загрузка, отказ запроса, `providers: []`), а не три отдельных `if` в разных местах.
- **Разделитель «или» в `LoginScreenView` стал условным (`{providersSlot && (...)}`), вместо безусловного рендера, заведённого в T2.2.** T2.2 сознательно оставила его безусловным (слот тогда всегда был `undefined`, вопрос не стоял); T2.4 explicitly требует «разделитель без кнопок не висит» для всех трёх краевых состояний. Правка точечная (одна условная обёртка), пропсы и структура `LoginScreenViewProps` не менялись — подмена компонента feat-013 после merge не усложняется.
- **Три краевых состояния (загрузка / отказ запроса / `providers: []`) закрыты одним и тем же путём данных, без отдельной ветки на каждое.** `useAuthProviders()` во всех трёх случаях либо ещё не отдал `data`, либо `data.providers` пуст — `providersData?.providers ?? []` даёт `[]`, `getActiveProviders([])` даёт `[]`, слот — `undefined`. Отдельного состояния загрузки/ошибки для блока провайдеров не заводилось: план явно требует лишь «парольная форма не блокируется», а не индикацию состояния запроса провайдеров.
- **Ошибки `?error=` читаются один раз при монтировании (`useState` с ленивым инициализатором), не через `useEffect`/`useSearchParams`.** Значение нужно ровно один раз — как начальное состояние того же `error`, что показывает и парольная форма; `useEffect` добавил бы лишний рендер-цикл и необходимость чистить URL, чего план не требует. `URLSearchParams(location.search)` — без добавления `useSearchParams` в импорты (план не called for новых паттернов чтения query).
- **Закрытый реестр кодов ошибок — литеральный union-тип `OAuthErrorCode` + `Record<OAuthErrorCode, string>`, не `Record<string, string>`.** Первая версия (`Record<string, string>`) не проходила `tsc` под `noUncheckedIndexedAccess`: индексный доступ по произвольной строке типизируется как `string | undefined` даже для собственного фоллбэка (`OAUTH_ERROR_MESSAGES.oauth_failed`). Литеральный union с type-guard'ом `isOAuthErrorCode` (сужение через `value in OAUTH_ERROR_MESSAGES`) убирает `undefined` из типа при обращении по известному ключу — типобезопасно отражает «закрытый реестр из пяти кодов» дословно, а не как открытую карту строк.
- **Переход на `/authorize` — `window.location.assign`, не `<a href>`.** План фиксирует именно этот вызов буквально («флоу редиректный, не fetch»); кнопки провайдеров и так используют `Button` (`type="button"`) как в остальной карточке, поэтому обработчик `onClick` с `assign()` — естественнее, чем подмена семантики кнопки на ссылку.
- **Стиль кнопок провайдера — `Button variant="outline" size="lg" className="w-full"`, без новых классов и без брендовых SVG-иконок.** Мокап `.prov-btn` (`border var(--border)`, `background var(--background)`, `hover: var(--muted)`) по палитре совпадает с существующим `variant="outline"` — совпадение не случайно, скорее заимствование мокапом токенов кнопки, чем наоборот. Иконки провайдеров в мокапе — брендовые инлайн-SVG (`#p-yandex`, `#p-google`, `#p-github`), но ни план, ни бриф не перечисляют их среди T2.4-изменений («каркас, не дизайн»); импорт брендовых SVG в `pages/login` — решение вне буквы плана, поэтому не взято. Текстовые подписи покрывают функциональность и Verification-критерии фазы полностью.

**Фикс-контекст (фаза GREEN, `[prod]`-находки ревью и ручных кейсов):**

- **R8 — accessible name полям формы и `role="alert"` блоку ошибки (`LoginScreenView.tsx`).** Первопричина: каркас T2.2 перенёс разметку полей из удалённого `AuthGate` как есть, а там подписи не было вовсе — единственным текстом поля оставался `placeholder`, который не даёт accessible name, поэтому кейсы вынуждены были ходить `getByPlaceholderText`, мимо приоритета запросов `getByRole(name)` → `getByLabelText` (`conventions/frontend.md`). Мокап feat-013 видимых `<label>` не рисует, поэтому взят `aria-label`, дублирующий текст placeholder'а, — имя появляется, визуальный каркас и DOM-порядок блоков не меняются; `placeholder` сохранён, существующие кейсы не ломаются. Блок ошибки получил `role="alert"`: он показывает и отказ входа, и коды `?error=` OAuth-callback'а, то есть ровно те сообщения, которые обязаны объявляться скринридером в момент появления. Классы не трогались — правка семантики, не дизайна, территория feat-013 не задета.
- **R9 — `BootstrapResult.authenticated` убрано, `bootstrapAuth` сведена к побочному эффекту (`useAuthBootstrap.ts`).** Первопричина: решение T2.3 «хук отдаёт только `ready`» было доведено до подписи хука, но не до `queryFn` — та продолжала возвращать статус, который никто не читает. Мёртвое возвращаемое значение размывает мутационный сигнал (подмена `false` на `true` в любой ветке ничего не меняет ни в одном кейсе). Единственный наблюдаемый результат функции — `setAccessToken` на успешном refresh, поэтому все ветки теперь возвращают `null`; `null`, а не `undefined`, — требование TanStack Query (`queryFn`, вернувшая `undefined`, считается ошибкой). Контракт `useAuthBootstrap(): { ready: boolean }` и тихое поведение на 401/сетевом сбое не изменились; описания решений T2.3 выше, упоминающие `{ authenticated: … }`, относятся к состоянию до этого фикса.
- **`{T2.2}` — кнопка смены режима переполняла карточку на мобильных ширинах (`LoginScreenView.tsx`).** Первопричина не в самой странице, а в базовом классе `Button` (`shared/ui/button.tsx:7`): `whitespace-nowrap` запрещает перенос, а `h-8` размера `default` фиксирует высоту. Подпись тумблера — самая длинная строка карточки (249 px при `text-sm`), поэтому кнопка держала эти 249 px на любом вьюпорте и с ~440 px вылезала за правый край карточки (на 390 px — на 34 px, на 320 px текст резался краем окна). Соседние элементы ужимались корректно: у них есть `w-full`, то есть проблема ровно в единственном месте, где ширину диктует контент. Починено на месте использования — `className="h-auto min-h-8 max-w-full whitespace-normal"`: перенос разрешён, высота растёт под число строк, ширина ограничена доступной. Общий примитив не тронут сознательно: `whitespace-nowrap` на кнопках — верный дефолт для всего остального приложения (кнопки тулбаров и модалок должны не переносить подпись), правка ради одного экрана аукнулась бы везде. `min-h-8` сохраняет прежний бокс однострочного состояния — на десктопе высота и ширина кнопки остались 32 × 249 px, то есть вертикальные отступы карточки не поехали. DOM-порядок и структура не менялись, подмена компонента feat-013 после merge не усложняется.

**Фиксы по code review (режим A — качество, режим B — контракт):**

- **Nit review-a (`app/model/useAuthBootstrap.ts:30`, `App.tsx:18-21`) — голый `fetch` бутстрапа получил таймаут.** Было: бутстрап гейтит монтирование всех маршрутов, а сам ходит `fetch` без `AbortSignal` — зависший (не отклонённый быстрым `catch`) бэкенд держал `isPending=true` неопределённо долго, и пользователь не мог попасть даже на `/login`. Добавлена локальная константа `BOOTSTRAP_TIMEOUT_MS = Number(import.meta.env.VITE_API_TIMEOUT_MS) || 30000` (тот же бюджет, что дефолт `apiClient` в `shared/api/client.ts`) и `signal: AbortSignal.timeout(BOOTSTRAP_TIMEOUT_MS)` на вызове `fetch`; таймаут реджектит `fetch` тем же путём, что и сетевой сбой, — существующий `catch` уже сводит его к тихому пути анонима (`return null`), новой ветки не потребовалось.
- **Nit review-a (`pages/login/ui/LoginPage.tsx:72-75`) — база URL кнопки провайдера больше не хардкодит `/api`.** Было: `handleProviderSelect` собирал `window.location.assign('/api/auth/oauth/...')` буквальной строкой, тогда как `shared/api/client.ts` и `useAuthBootstrap.ts` берут базу из `import.meta.env.VITE_API_URL ?? "/api"` — при заданном `VITE_API_URL` кнопка провайдера ушла бы на несуществующий путь origin'а SPA, разойдясь с остальным фронтендом. Добавлена локальная константа `API_BASE_URL` с тем же выражением (не импорт из `client.ts` — модуль заморожен для этого трека, а само выражение — не новый паттерн, три места теперь его буквально повторяют).
- **Nit review-b (докстринги `LoginScreenView.tsx:28`, `LoginPage.tsx:44`) — фазовые пометки убраны.** `providersSlot` больше не описан как «наполняется в T2.4»; докстринг `LoginPage` больше не говорит «блок кнопок провайдеров … обработка `?error=` — T2.4» — обе фазы трека давно слиты в один файл, докстринги теперь описывают текущее поведение без ссылок на подфазы (CLAUDE.md § Документация).
