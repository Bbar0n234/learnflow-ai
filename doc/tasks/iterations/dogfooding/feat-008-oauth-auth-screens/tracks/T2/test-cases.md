# Test Cases: feat-008 — OAuth + auth-экраны / трек T2 (Frontend: каркас `/login`, guard, бутстрап)

Трек меняет поведение, а не рефакторит его: блокирующая модалка `AuthGate` умерла, вход стал публичным маршрутом `/login` под роутером, «пускать или на логин» решает guard `RequireAuth`, а решение это принимается только после однократного app-уровневого бутстрапа аутентификации. Поэтому кейсы ниже страхуют новое поведение целиком, а не «ничего не сломалось».

Автотесты закрывают всё, что наблюдаемо в jsdom: страницу `/login` (два режима, валидация, копирайт, порядок блоков), состав и порядок кнопок провайдеров по ответу бэкенда вместе с тремя краевыми состояниями списка, закрытый реестр пяти кодов `?error=` с дословными текстами брифа, редирект анонима с сохранением исходного пути и публичность `/login`, а также бутстрап во всех трёх ветках (access есть · refresh 200 · refresh 401) с отдельной проверкой тишины в error-канале. Ручной хвост узкий: живой OAuth-редирект к провайдеру и обратно, гео-ветки на реальном `GET /providers`, визуальная приёмка каркаса и логаут с перезагрузкой страницы — всё это либо уходит за пределы процесса (полная навигация браузера), либо не наблюдаемо без глаз и реального бэкенда.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости (структура БД, логи, Langfuse); `[auto]` — кейс закрыт автотестом; `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe`, `make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты фронта: DevTools → Network (в т.ч. редиректы `/authorize` → провайдер → `/callback`, `Set-Cookie`), DevTools → Console (логи идут через `@/shared/lib/logger`), DevTools → Application → Local Storage (`learnflow-access-token`) и Cookies (`refresh_token`, `oauth_flow`); на бэкенде — structlog в stdout. Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer**.

**Скоуп по трекам.** Кейсы с префиксом `{T2.x}` гоняются на треке T2 + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST, когда собраны оба трека. Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура: `make docker-up-db`, `make migrate`, backend `make dev`, фронт `make dev-fe`. Для гео-веток — `GEOIP_FALLBACK_COUNTRY` в `.env.local` (RU и любая не-РФ страна), для OAuth — реальные креды Яндекса (ручные шаги архитектора, design-brief § Ручные шаги).
2. Акторы: **user-a** — обычный парольный пользователь (регистрация через `/login`); **oauth-user** — аккаунт, созданный первым входом через провайдера (отдельно регистрировать не нужно, find-or-create).
3. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.
4. После прогона — сводка (pass / failed / **deferred**). Deferred — кейсы 👤/заблокированные (нет кредов провайдера, нет гео-базы): отдельным счётчиком + причина по каждому.

### `LoginPage.test.tsx` — страница `/login` целиком

1. **Файл**: `frontend/src/pages/login/ui/LoginPage.test.tsx` — integration (компонент + его хуки + сеть), шов — MSW поверх `renderWithProviders` (свежий `QueryClient`, `retry: false`); маршрутизация наблюдается через `MemoryRouter`, у которого соседние маршруты `/` и `/projects/:id` работают маркерами «куда нас вернули». Поля формы запрашиваются по accessible name (`getByLabelText` поверх `aria-label`), кнопки — по роли и имени.
2. **Тестирует**: `pages/login/ui/LoginPage` вместе с `LoginScreenView`, `ProviderButtons` и `provider-registry` (внутренних соседей не подменяем — sociable).
3. **Суть**: суита фиксирует контракт страницы входа так, как его видит пользователь. Она проверяет, что каркас показывает оба режима с русским копирайтом мокапа и не пускает на сервер регистрацию с коротким или несовпадающим паролем; что успешный вход сохраняет access-токен и возвращает человека ровно на тот путь, который запомнил guard, а отказ сервера показывает его текст, не теряя страницу. Она же держит блок провайдеров: состав приходит с бэкенда, порядок — из локального реестра (Яндекс → Google → GitHub) независимо от порядка в ответе, незнакомый id не рендерится вовсе, а на пустом списке, отказе запроса и на время загрузки исчезает и разделитель «или», не ломая парольный вход. Наконец, она сторожит два стыка с бэкендом: клик по провайдеру уходит полной навигацией на `/authorize` с закодированным `next` (а не XHR — запрос на authorize зафиксировал бы отдельный хендлер-счётчик), и каждый из пяти кодов `?error=` показывает текст из таблицы брифа дословно, а неизвестный код деградирует в generic вместо белого экрана.
4. **Кейсы**:
   - каркас входа: заголовок «Вход», поля имени и пароля, кнопка «Войти», ссылка на регистрацию; повтора пароля нет
   - переключение в регистрацию: заголовок, повтор пароля, кнопка «Зарегистрироваться», обратная ссылка
   - кнопка отправки выключена, пока имя и пароль не заполнены
   - пока запрос входа в полёте: кнопка подписана «…» и выключена, повторный клик второго запроса не даёт
   - регистрация с паролем < 8 символов: сообщение, запроса на сервер нет, токен не сохранён
   - регистрация с несовпадающим повтором: сообщение, запроса на сервер нет
   - регистрация: имя уходит на сервер обрезанным по пробелам, токен сохранён
   - вход: токен сохранён, переход на `location.state.from`
   - вход при прямом заходе на `/login` (нет `from`): переход на `/`
   - после входа `/login` заменён в истории: шаг назад ведёт на страницу до входа, а не обратно к форме
   - отказ входа 401: показан `detail` сервера, остались на странице, токена нет
   - три провайдера в ответе → три кнопки + разделитель «или»
   - порядок кнопок Яндекс → Google → GitHub при обратном порядке в ответе сервера
   - РФ-гео (`["yandex"]`) → ровно одна кнопка, Google/GitHub отсутствуют
   - незнакомый id в ответе (`["telegram", …]`) не рендерится ни подписью, ни сырым идентификатором
   - порядок блоков карточки: форма → разделитель → провайдеры → смена режима (по мокапу feat-013)
   - `providers: []` → ни кнопок, ни разделителя; парольный вход доводится до успеха
   - отказ `GET /providers` (500) → ни кнопок, ни разделителя; парольный вход доводится до успеха
   - список в полёте → форма доступна, разделителя нет; после ответа появляются и кнопка, и разделитель
   - клик по провайдеру → `location.assign("/api/auth/oauth/yandex/authorize?next=%2Fprojects%2Fp1%3Ftab%3Dchats")`, XHR на authorize не уходит
   - клик при прямом заходе → `next=%2F`
   - пять кодов `?error=` (parametrized) → тексты из таблицы брифа дословно
   - неизвестный код → generic-текст `oauth_failed`, страница жива
   - без параметра `error` сообщений об ошибке нет

### `router.test.tsx` — guard входа и публичность `/login`

1. **Файл**: `frontend/src/app/router.test.tsx` (суита дополнена двумя кейсами, существующие не трогались) — integration на реальной таблице маршрутов; шов — MSW + `MemoryRouter`, рядом с `<AppRoutes />` смонтирован зонд, печатающий текущий путь, `location.state.from` и тип последней навигации (`useNavigationType`).
2. **Тестирует**: `app/router.tsx` (`AppRoutes`) вместе с `app/components/RequireAuth`.
3. **Суть**: суита проверяет, что защищённая группа маршрутов действительно закрыта guard'ом, а `/login` лежит снаружи него. Аноним, пришедший на глубокий защищённый URL, оказывается на `/login`, и исходный путь сохраняется **строкой** `pathname + search + hash` — той самой, которую потом получают и `navigate(from)`, и query-параметр `next`; зонд отличает строку от объекта `location`, который дал бы `next=[object Object]` и был бы отбракован backend-валидацией. Тем же зондом сторожится `replace` у редиректа: рендером push от replace не отличить (в обоих случаях на экране `/login`), а разница видна пользователю по кнопке «Назад» — с push она возвращает на защищённый URL, который тут же редиректит обратно, и Back перестаёт работать.
4. **Кейсы**:
   - аноним на `/projects/p1/artifacts?tab=all#top` → `/login`, `state.from` равен исходной строке целиком (со search и hash), навигация — `REPLACE`
   - `/login` открывается без токена, редиректа нет — маршрут публичный

### `App.test.tsx` — бутстрап аутентификации на app-уровне

1. **Файл**: `frontend/src/App.test.tsx` — integration; шов — MSW на `POST /api/auth/refresh` (200/401) плюс локальный `QueryClient` с `QueryCache({ onError })`. Хендлер refresh пишет в счётчик не факт обращения, а `request.credentials`: без `credentials: "include"` запрос уходит анонимным (`same-origin`), refresh-cookie не отправляется и возврат из OAuth-callback'а ломается молча. Отдельный файл нужен потому, что хук живёт **над** `AppRoutes`, в самом `App`, и через `router.test.tsx` недостижим. Через `renderWithProviders` эта суита не идёт сознательно: «тихо» означает «глобальный error-канал React Query не сработал», а в проде на этом канале висит `logger.error` — наблюдать тишину надо на том же шве; клиент создаётся заново на каждый кейс, потому что у бутстрап-запроса бесконечные `staleTime`/`gcTime` и общий кэш протёк бы между тестами.
2. **Тестирует**: `App` (гейт `AppBootstrapGate`) вместе с `app/model/useAuthBootstrap`.
3. **Суть**: суита закрывает главный риск перестройки входа — мигание `/login` при возврате из OAuth-callback'а. Она проверяет, что до завершения бутстрапа маршруты не смонтированы (сразу после рендера на экране паттерн загрузки, а не форма входа), что валидная refresh-cookie поднимает сессию (запрос уходит с `credentials: "include"`) и оставляет пользователя на запрошенном пути, а 401 без cookie ведёт тихим путём анонима на `/login` — без записи в error-канал Query и без `logger.error`, потому что ожидаемая анонимность ошибкой не является. Отдельно зафиксировано, что при наличии access-токена сети не возникает вовсе и что двойное монтирование эффектов под `StrictMode` не задваивает refresh-запрос. Редирект-луп отдельным ассертом суита не сторожит (см. «Осознанно не покрываем»).
4. **Кейсы**:
   - refresh 200 + пустой localStorage → сначала «Загрузка...» и никакой формы входа, затем защищённый экран; токен сохранён, запрос ушёл с `credentials: "include"`, путь остался `/`, error-канал и логгер молчат
   - refresh 401 на защищённом URL → `/login`, токена нет, error-канал и логгер молчат
   - access в localStorage → защищённый экран без единого запроса на `/auth/refresh`
   - `StrictMode` → ровно один запрос на `/auth/refresh`

**Осознанно не покрываем автотестом**:

- Визуальная сторона каркаса (токены, тень карточки, брендовая половина, адаптив `md:`, тёмная тема) — jsdom не считает стили и не имеет layout, ассерт на класс был бы проверкой реализации → ручные `{T2.1}`, `{T2.2}`.
- Реальный уход браузера на `/authorize` и возврат из callback'а — `window.location.assign` в jsdom не навигирует, а сам флоу выходит за пределы SPA (302 провайдера, cookie, редирект назад). Автотест сторожит только точную цель перехода → cross-cutting кейсы Layer 2.
- Гео-ветки на живом `GET /api/auth/providers` — состав ответа формирует backend по IP, фронт против MSW проверяет уже разобранные варианты состава → cross-cutting Layer 2.
- Логаут из сайдбара (`logout()` → `clearAccessToken()` → `window.location.reload()`) — путь не менялся в треке, а `reload()` в jsdom не перезапускает приложение, поэтому «после перезагрузки бутстрап получает 401 и уводит на `/login`» автотестом не наблюдаемо → ручной `{T2.3}`.
- Редирект-луп бутстрап ↔ guard отдельным ассертом: в jsdom он проявляется не лишней копией экрана входа, а исключением React «Maximum update depth exceeded», на котором прогон файла падает и подвисает. Наблюдаемого признака, который можно проверить `expect`'ом, среда не даёт — сторожем работает сам кейс «refresh 401 → `/login`»: доходит до конца, значит лупа нет.
- Поле `password` из ответа `/providers` — контракт v1 фиксирует его всегда `true`, ветки поведения за ним нет (задел на будущие политики); появится политика — появится и кейс.
- Смерть сессии mid-session (провал refresh в интерцепторе) и обратный редирект аутентифицированного пользователя с `/login` — сознательно вне scope брифа и трека (design-brief § Frontend; plan.md § Open Questions #5) → наблюдательный ручной `{T2.4}`.
- `shared/api/auth.ts::getAuthProviders` / `useAuthProviders` отдельной суитой — тонкий адаптер над `apiClient` без ветвлений (мягкий гейт glue); его поведение целиком проявляется в кейсах блока провайдеров.

**Замеченные прод-баги (для fixer'а, сам не чиню):** нет — реализация трека сошлась с контрактом брифа во всех проверенных точках, включая дословные тексты пяти кодов `?error=`, порядок блоков карточки и форму `from`.
