# Test Cases: feat-011 execution-runtime / трек T2 (frontend)

Трек переучил фронт на файловую модель: артефакт больше не строка в PostgreSQL с UUID, а файл, чья идентичность — путь. Отсюда всё остальное — REST и кэш адресуются путём, карточка артефакта рождается из части хода (`ArtifactPart`), перезапись видна бейджем «обновлён · +N −M», список стал деревом, вид вьюера выбирает словарь расширений. Вместе с этим приехал вход файлов от пользователя: вложения в композере, которые до отправки живут только в браузере.

Поведение меняется почти везде, поэтому кейсы страхуют не «ничего не сломалось», а сам новый контракт. Автотесты закрывают то, что видно в jsdom: словарь категорий, сборку дерева из плоских путей, точечные инвалидации кэша по SSE и довоз списка на терминальных ветках хода, перенос `ArtifactPart` в карточку с бейджем, тайминг вложений (✕ до отправки не ходит в сеть, upload идёт ровно в момент отправки, провалившаяся загрузка не отправляет сообщение и не стирает набранное) и различие «файла больше нет» против «сервер упал». Ручной хвост узкий: визуальная сверка с мокапом в обеих темах, настоящий drag&drop и системный диалог, реальное скачивание файла и ETag-ревалидация картинки — всё, чего среда тестов не исполняет. Сквозные сценарии приёмки (A3–A8, A11–A14) требуют живого бэкенда и уходят в INTEGRATION_TEST.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — проверка наблюдаемости; `🔴` — проверка реальных инъекций / security-событий; `[auto]` — кейс закрыт автотестом; `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe`, `make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Инструменты фронта: DevTools → Network (запросы, SSE-кадры, заголовки `Content-Disposition`/`ETag`), DevTools → Console (логи через `@/shared/lib/logger`), React Query Devtools для состояния кэша. Код читать только там, где поведение иначе не наблюдаемо (явно отмечать). Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer**, не сам тестировщик.

**Скоуп по трекам.** Кейсы с префиксом трека (`{T2.x}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST. Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура: `make docker-up-db`, `make migrate`, backend `make dev`, фронт `make dev-fe` (либо `make docker-up` целиком). Для сценариев с исполнением кода нужен поднятый executor трека T1.
2. Актор: обычный пользователь через UI register; проект с непустым workspace (хотя бы один артефакт в поддиректории — `lecture-1/…`).
3. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.
4. После прогона — сводка (pass / failed / **deferred**). Deferred — кейсы 👤/заблокированные, отдельным счётчиком с причиной по каждому.

### `src/test/blob-polyfill.ts`, `src/test/file-input.ts` — локальные тест-хелперы (не автотесты)

`jsdom` не реализует у `Blob` ни `arrayBuffer()`, ни `text()`, ни `stream()`, и перехватчик MSW под XHR не может прочитать тело с файлом: multipart-запрос **зависает до таймаута теста**, без ошибки, объясняющей причину. Хелпер ставит минимальные реализации поверх `FileReader` — по образцу уже живущих рядом `match-media-polyfill.ts` / `pointer-event-polyfill.ts` (локальные помощники, которые тест импортирует явно; замороженный `setup.ts` не тронут). Импортируется тремя суитами, где есть загрузка файла. Ограничение среды: `request.formData()` отдаёт часть-файл объектом чужого realm (`instanceof File` ложен), поэтому форма тела проверяется по сырому multipart-тексту — он приезжает целиком.

`file-input.ts` — вторая половина той же среды: выбор файла пользователь делает системным диалогом, которого в jsdom нет, поэтому отдать выбор можно только событием `change` на скрытом `<input type="file">`, а у скрытого input нет ни роли, ни доступного имени. Структурный селектор здесь неизбежен, но он ровно один на весь набор, спрятан за именем действия `attachFiles()` и не участвует ни в одном ассерте — кейсы читают результат по видимому чипу. Три суиты со вложениями (`ChatInput`, `ChatThread`, `ChatList`) берут хелпер отсюда, а не держат свою копию.
