# Design-brief: feat-013 — UI/UX polish

Пакет мелких UI/UX-правок одним заходом — предпоказная полировка продукта. Двенадцать пунктов из backlog § Frontend / UX сведены в один дизайн-заход: единый интерактивный HTML-мокап всех затрагиваемых экранов (ревью архитектора до реализации), затем реализация. Запись итерации — [tasklist-dogfooding.md § feat-013](../../../tasklist-dogfooding.md).

**Граница с feat-008 (идёт параллельно):** дизайн auth-экранов и 404 целиком здесь; feat-008 строит функциональный каркас `/login` (русский копирайт, FSD `pages/login`, кнопки провайдеров по гео: пароль + Яндекс ID для РФ; Яндекс ID, Google, GitHub вне РФ — VK ID снят решением архитектора: регистрация приложения VK требует подтверждённое бизнес-лицо). Контракт стыка: общие файлы — `router.tsx` (feat-008 владеет структурной перестройкой входа, мы добавляем только catch-all `path="*"`) и `shared/api/client.ts` (наш фикс исключений интерцептора, блок 10 — feat-008 классифицирует свои OAuth-эндпоинты по тому же правилу). Мокап auth-экрана — в общем пакете сейчас; реализация стилизации — после merge feat-008.

Ниже — решения по тематическим блокам. Инвентаризация текущего состояния (файлы, строки, вёрстка) собрана перед брифом и вплетена в решения; факты сверены с кодом worktree.

## 1. Дизайн-система

### 1.1 Токен `--success` (решение архитектора: вводим)

В продуктовой палитре токена успеха нет; ближайший зелёный `--mcp-connected` — узкоспециальный (точка статуса MCP). Утверждённый мокап `live-timeline-v3.html` уже содержит значения: **`--success: #3d7a45` (light) / `#6fbf78` (dark)** — берём их как каноничные, добавляем в `frontend/src/index.css` в обе темы + `@theme inline`-маппинг.

Первый потребитель — галочка успеха в ленте активности: `ActivityRow.tsx` `StatusMeta`, где `Check` сейчас наследует серый `text-muted-foreground` от мета-строки. Становится `text-success`. Доступность не деградирует: статус уже дублируется текстом (`sr-only` «успешно»), цвет — усиление, не единственный канал.

Прочие потребители: sonner-иконка success-тостов (`CircleCheckIcon`) красится токеном в этой же итерации — правка только цвета (доопределено по ревью брифа); подтверждение inline-сохранения имени проекта — блок 5.

### 1.2 Скроллбары под дизайн-систему

Кастомизации сейчас нет вообще — везде системный скроллбар. Единственное исключение — Base UI `ScrollArea` (`shared/ui/scroll-area.tsx`: полоса `w-2.5`, thumb `bg-border rounded-full`), используется в 4 местах (сфера, артефакт-вью, версии сферы); остальные ~18 контейнеров — нативный `overflow-auto`.

Решение: глобальная стилизация в `index.css` уровнем дизайн-системы, без точечных классов по контейнерам:

- `::-webkit-scrollbar` (**ширина 10px — утверждено на ревью мокапа**, прозрачный трек, thumb на токене границы, **hover-усиление к `--muted-foreground`-ослабленному — утверждено**) + `scrollbar-width: thin; scrollbar-color: … transparent` для Firefox;
- цвета — от `--border` (light: `#e2dcd0`, dark: `#322a44`), обе темы;
- **согласование с Base UI ScrollArea обязательно**: его thumb уже `bg-border` — глобальный стиль подгоняется под него (та же ширина/радиус/цвет), иначе на соседних экранах будут две разные полосы;
- заодно выставить `color-scheme` по теме на корне — мокап наглядно показал ярко-белую нативную полосу на тёмной теме у не-кастомизированных контейнеров;
- `scrollbar-gutter: stable` на основных скролл-контейнерах с центрированным `max-width`-контентом (чат: `--content-max-w`) — страховка от горизонтального дёргания при появлении/исчезновении classic-скроллбара (класс бага из SOFA TIL, см. § SOFA consulted);
- Firefox: `scrollbar-width: thin` + статичный `scrollbar-color` — точная ширина 10px и hover-акцент там недостижимы; расхождение принято как норма (доопределено по ревью брифа), обходов не изобретать.

## 2. Единый брендовый шаблон состояния (фундамент блоков 3, 4, 6, 7)

Инвентаризация показала: в продукте четыре несогласованных способа показать «не-контент» — голые `<p>Загрузка…</p>` в четырёх вёрстках и двух языках, две несовместимые формы ошибок (голый `text-destructive` против карточки `border-destructive/30 bg-destructive/10`), empty-state'ы с иллюстрацией то по ширине (`max-w-[280px]`), то по высоте (`h-48`), брендовый `ErrorBoundary` с сырым `<button>` и sans-заголовком при serif-заголовках во всём продукте.

Решение: **один shared-компонент `StateScreen`** (имя уточним на реализации) — композиция «иллюстрация (опционально) + заголовок + подпись + действие (опционально)», с вариантами размера (полноэкранный / встроенный в панель / компактный для списков). Потребители: 404, empty-state сферы и артефактов, error-состояния списков и страниц, `ErrorBoundary` (рефакторится на него же — унификация задним числом). Все тексты русские, многоточие — типографское `…`.

Это ядро мокапа: одна система состояний вместо дюжины ad-hoc вариантов. При рефакторинге `ErrorBoundary` на `StateScreen` сохраняется `componentDidCatch` → `logger.error` — унификация визуальная, логирование не трогаем (доопределено по ревью брифа).

### Заодно (найдено инвентаризацией, предлагается включить)

Дешёвые попутные правки того же класса, вкуса не требуют: англоязычные строки `Loading...` / `No projects yet` (`ProjectList`), `Loading chat...` (`ChatThread`), `Loading sphere...` / `Failed to load sphere.` (`SphereView`), `Loading...` в `ProjectLayout`, англ. `alt` у иллюстраций, англ. `title="Settings"` / `title="Logout"` в футере сайдбара — всё переводится при проходе по файлам.

## 3. Loading-состояния

Паттерн двухуровневый:

- **Списки** (ChatList, ArtifactList, ProjectList, SecurityEvents) — **скелетоны** по форме будущих строк (карточка чата, строка артефакта, пункт проекта): 2–3 мерцающих плейсхолдера на токенах `--muted`. Скелетон честнее спиннера для списков — сохраняет геометрию экрана.
- **Полноэкранные/панельные загрузки** (`router.tsx` Suspense-fallback, `SecurityRouteGuard`, `ChatThread`, `SphereView`, `ArtifactView`, `SkillContextSection`) — единый центрированный блок `StateScreen` в компактной форме: спиннер (lucide `Loader2` в `animate-spin`, как в sonner) + подпись. Без иллюстрации — загрузка мгновенно-переходное состояние, сцена тут лишняя.

Анимация скелетона — `animate-pulse` (штатный Tailwind), без кастомного шиммера — решение против лишней CSS-механики, вкус проверяется в мокапе.

## 4. Error-состояния per-query

Из двух существующих форм канонизируем **карточную**: `rounded-lg border border-destructive/30 bg-destructive/10 px-4 py-3 text-sm text-destructive` (уже живёт в стрим-ошибке чата и SIEM-экранах). Голые `text-destructive`-строки в `ProjectList`, `ChatThread`, `ChatList`, `ArtifactList` (+ англ. в `SphereView`) заменяются:

- **в списках** — компактная карточка с текстом «Не удалось загрузить …» и кнопкой-ссылкой «Повторить» (`refetch()` соответствующей квери — сейчас ни одно error-состояние не даёт пути восстановления кроме F5);
- **на страницах/панелях** (чат, сфера, артефакт) — `StateScreen` с иллюстрацией `error-state`, подписью и «Повторить».

Тосты не трогаем: канал мутаций (`MutationCache.onError → toast.error`) работает и остаётся; per-query ошибки — инлайн по месту, как и было спроектировано в feat-004.

## 5. Точечные компонентные правки

### 5.1 ModelSelector (два пункта, один компонент)

- **Локализация свёрнутого значения:** `selectedDisplayName` отдаёт `"Default"` / `"Inherit"` — меняем на «По умолчанию» / «Наследовать», зеркально уже локализованному раскрытому списку.
- **Resolved-модель в project scope:** `resolvedDisplayName` вычисляется всегда, но для `scope="project"` заменён статичной подсказкой — данные есть, регрессия чисто в рендере. Возвращаем строку «Активная модель: …» и для project; **подсказка про переопределение убирается совсем (решение ревью мокапа: избыточна)** — остаётся одна строка. Заодно уходит висящий пробел от `{" "}` + пустой строки.

### 5.2 Inline-edit имени проекта

Текущее: сырой `<input>` (не shared `Input`) + кнопка «Сохранить», без Enter, без blur, без подтверждения успеха.

Решение — **inline-edit с явным подтверждением (вариант А, утверждён на ревью мокапа)**: значение выглядит текстом с иконкой-карандашом, клик переводит в режим редактирования (shared `Input`), Enter/кнопка-галочка сохраняет, Esc/blur отменяет, после успеха — краткое подтверждение (галочка `--success`). Автосохранение по blur отвергнуто: молчаливая запись при уводе фокуса — сюрприз-поведение для «имени», которое пользователь может начать править случайно; явный commit дешевле недоразумений. Альтернатива-референс — модалка rename как в `ProjectActions`/`ChatActions` — отвергнута: поле уже стоит на экране настроек, прятать его в модалку — лишний хоп.

Доопределения по ревью брифа (чтобы реализация не разошлась с намерением):

- **Конкурентное обновление:** при входе в edit фиксируется снапшот; внешние обновления `project.name` (rename из модалки сайдбара, вторая вкладка, focus-refetch) применяются только в view-режиме и не клобберят открытое редактирование (сейчас `useEffect [project]` перетирает несохранённый ввод). Отмена возвращает в view-режим с актуальным серверным значением.
- **Blur vs кнопка-галочка:** клик по галочке не должен сорваться в blur-отмену — стандартное разрешение: `preventDefault` на `mousedown` кнопки (или blur внутри контейнера редактирования не считается отменой).

### 5.3 Владелец состояния стрима (ChatThread + useAgentStream)

Механика бага: `ChatThread` не перемонтируется при переключении чата, колбэки `useAgentStream` замыкают `cid` текущего рендера — терминальное событие, пришедшее после переключения, штампует состояние (`endNotice`, `streamError`) идентификатором **нового** чата. Окно узкое (класс закрыт скоупингом feat-001), но честный фикс определён в бэклоге: **владелец через контракт хука**.

Правка контракта `UseAgentStreamOptions`: каждый колбэк получает идентификатор чата-владельца потока — тот `chatId`, что был зафиксирован в момент `send()`. Форма зафиксирована: `onDone(info)` получает поле `chatId` в объекте; `onError`/`onSecurityBlock`/`onCancelled` — первый позиционный аргумент `ownerChatId`. Owner несут **все** ветки колбэков, включая не-SSE (сторож тишины «Превышено время ожидания», «Соединение прервано», catch «Ошибка соединения»). `ChatThread` перестаёт штамповать `cid` из замыкания — берёт владельца из колбэка; терминальные хендлеры чистят `localMessages` только своего чата. Вариант «ссылка на чат идущего потока» отвергнут ещё в бэклоге (течёт при отправке во второй чат во время стрима первого).

**Расширение по ревью брифа — owner-guard на store-пути.** Тот же класс бага живёт и в `stream-store`: стрим чата A не абортится при переключении (cleanup хука — только на unmount), и после `startStream(B)` события потока A продолжают писать в стор без сверки владельца (`applyEvent`), а его терминальный `endStream()` гасит живой стрим B. Окно не узкое — «молчаливый час работы агента» законен по дизайну сторожей. В scope фикса входит owner-guard на store-действия: события и терминал потока, чей `chatId` не равен `streamingChatId` стора, в стор не применяются (поток A дотекает в никуда — его результат всё равно приходит рефетчем по `done`).

Затрагиваются тесты `useAgentStream.test.ts`, `ChatThread.test.tsx`. UI-изменений нет — пункт не входит в мокап.

## 6. Empty-states

### 6.1 Сфера знаний

Сейчас: блок сидит вверху скролл-области (`py-8`, без центрирования), иллюстрация зажата `max-w-[280px]` при контентной ширине 1000+px — «мелкая и теряется». Решение: вертикальное центрирование в доступной высоте панели (`h-full` + flex-центр) и иллюстрация крупнее — порядок `max-w-[420–480px]` (точный размер — вкусовой, в мокапе слайдер/варианты), подпись и CTA «Редактировать» при ней. Существующая сцена `empty-sphere` остаётся.

### 6.2 Артефакты: «выберите артефакт из списка»

Причина нецентрированности найдена: инлайн-`div` в `router.tsx` — flex-item без `flex-1`/`w-full` внутри `ArtifactsPage`, схлопывается по контенту и прижимается влево. Решение: выносим из роутера в компонент на базе `StateScreen` (заодно уходит инлайн-вёрстка из роутера), центрирование фиксом ширины, добавляется **новая сцена «Электрик»** (см. блок 8).

## 7. Catch-all 404 (решение архитектора: полноценный брендовый сразу)

`path="*"` внутри layout-роута `AppLayout` (сайдбар остаётся видимым — пользователь не выпадает из приложения; это же закрывает `/security` при выключенном SIEM-флаге). Экран — `StateScreen` в полноэкранной форме: **новая сцена «Электрик»** (блок 8), заголовок «Страница не найдена», подпись, действие «На главную» (`Link` на `/`, кнопка primary — утверждено на финальном ревью мокапа). Не редирект — решение гейта chore-001 подтверждено. Несимметрия `/security` намеренная (зафиксировано на ревью брифа): флаг OFF → 404 (маршрута нет), флаг ON + не-админ → существующий redirect гарда на `/`; унификацию не делаем — поведение гарда вне scope.

Стык с feat-008: наша правка `router.tsx` — ровно одна строка catch-all; конфликт merge тривиален, разруливает мержащийся вторым.

## 8. Auth-экран: брендовый дизайн (мокап сейчас, реализация после merge feat-008)

Исходное состояние: `AuthGate` — generic shadcn-модалка с англ. копирайтом, без единого брендового элемента; feat-008 перестраивает вход на страницу `/login` (модель: пароль + провайдеры по гео).

Наш дизайн (в мокапе — два гео-варианта состава кнопок):

- полноэкранная страница на `--background` с брендовой композицией: wordmark, иллюстрация «Электрик» (кандидат — новая сцена или `welcome-hero`), карточка формы (`--card`, `--radius`);
- форма: имя + пароль, режимы вход/регистрация, русские тексты; кнопки провайдеров — **финальная гео-модель (решение архитектора): РФ — только Яндекс ID (149-ФЗ); вне РФ — Яндекс ID, Google, GitHub. VK ID снят полностью: регистрация приложения VK требует подтверждённое бизнес-лицо, которого у проекта нет**; разделитель «или»;
- иконки провайдеров — брендовые, не заглушки: разноцветный «G» Google, octocat GitHub, фирменная «Я» Яндекса (замечание ревью мокапа);
- обе темы, состояния ошибок валидации — карточный паттерн блока 4.

Файловая структура — каркас feat-008 (`pages/login`), мы красим, не переносим.

**Уточнение архитектора (при запуске конвейера).** Каркас `/login` к моменту реализации в `develop` не появился, а откладывать блок нельзя. Решение: весь брендовый auth-дизайн изготавливается **сейчас**, но вне файлов, которыми владеет feat-008, — как презентационный слой, который feat-008 подхватит при merge:

- брендовые примитивы — в `shared/ui` (`AuthLayout`: фон, wordmark, иллюстрация, слот под карточку; `ProviderButton` с фирменными иконками Google / GitHub / Яндекс);
- собранный из них **чисто презентационный** `LoginScreenView` — в `features/auth/ui` (место, названное самой feat-008 как целевое «при росте»; `pages/login` мы не трогаем). Никакой auth-логики: режим вход/регистрация, гео-состав провайдеров, текст ошибки и обработчики приходят через props;
- сцена `auth-hero` заезжает в `shared/assets/illustrations` вместе с остальными сценами блока 9.

feat-008 после merge собирает `pages/login` из этих частей, прокидывая свои обработчики. Контракт стыка (третий общий пункт после `router.tsx` и `client.ts`) архитектор доносит до агента feat-008.

## 9. Новые сцены иллюстраций «Электрик»

Нужны два, кандидат — три: **404**, **artifacts-select** («выберите артефакт»), опционально **auth-hero** (если `welcome-hero` не ляжет в композицию логина).

**Порядок работ утверждён архитектором на ревью мокапа — иллюстрации гейтят финал мокапа:** экраны с иллюстрациями (empty-states, 404, полноэкранный error, auth) утверждаются только с реальными сгенерированными сценами, не плейсхолдерами.

1. Согласование дизайн-идеи сцен с архитектором: персонажи, композиция, как сцена отражает смысл состояния.
2. Scene-блоки в стиле манифеста (паспорт стиля + эталоны feat-001 как binding reference) → генерация light-исходников, для обеих тем.
3. Dark-адаптация генеративным edit по режиму B (`dark-theme-adaptation.md`).
4. Вырез фона: managed BiRefNet General-HR @2048 через HF Space (`feat-002-cutout/tools/birefnet_cutout.py`, Gradio API).
5. Ручная доводка архитектором в Photoshop.
6. Вставка в мокап → повторное ревью гейтованных экранов → PNG в `frontend/src/shared/assets/illustrations/{light,dark}/`, ключи в `Scene` + карта `index.ts`.

## 10. Сайдбар не отображается при первом открытии (P2)

Статический анализ снял «плавающесть»: причина детерминированная. Пять ключевых файлов побайтово совпадают с `origin/main` — анализ применим к проду.

**Причина (H1).** Футер сайдбара (ник + тема + настройки — ровно перечисленное в баг-репорте) целиком гейтится `{user && …}`, где `user` — `useQuery(auth.me, staleTime: Infinity)` (`Sidebar.tsx:41-45,157`). Refresh-интерцептор (`client.ts:59`) исключает из refresh-flow всё по условию `!url.includes("/auth/")` — писалось против рекурсии на `/auth/refresh`, но случайно накрывает и **`GET /auth/me`**. Холодная сессия после перерыва >30 мин (access протух, refresh жив): при маунте параллельно летят `/auth/me`, `/projects`, `/chats/recent` со stale-токеном → все 401; projects/recent проходят single-flight refresh и ретраятся успешно, `/auth/me` отваливается сразу, react-query 4xx не ретраит (`QueryProvider.tsx:19-25`) → `user === undefined` → футер не рендерится. F5 чинит детерминированно: свежий токен уже в localStorage от refresh соседних запросов. Улика-асимметрия: кнопка «Безопасность» переживает падение `/me` (второй источник `getIsAdminFromAccessToken`), футер — нет.

**Фикс:** правило исключения формулируется семантически — из refresh-flow исключаются только эндпоинты, **не требующие access-токена** (анонимные: `/auth/refresh`, `/auth/login`, `/auth/register`); `/auth/me` и `/auth/logout` начинают проходить стандартный refresh-retry (уточнение по ревью брифа: logout с протухшим access без ретрая молча пропускал server-side revoke refresh-токена). Плюс тесты на 401-ветку интерцептора (сейчас `client.test.ts` покрывает только `ensureFreshToken`).

**Стык с feat-008 (по ревью брифа):** фикс правит `shared/api/client.ts` — ядро auth-flow, которое feat-008 расширяет OAuth-эндпоинтами. `client.ts` добавляется в контракт стыка вторым общим файлом; правило классификации для новых эндпоинтов feat-008 — то же семантическое: анонимные (OAuth callbacks до выдачи токена) в исключения, авторизованные — под refresh-retry. Донести до агента feat-008 через архитектора.

**Сопутствующие наблюдения** (второй ранг, решение по месту): H2 — транзиентные сетевые ошибки холодного старта роняют `getMe` в error без пути восстановления, кроме window-focus-refetch; смягчается тем же фиксом частично, отдельная механика recovery — вне scope, если репро не покажет обратного. Исключено анализом (не тратить время при репро): ui-store (`sidebarOpen: true` захардкожен, persist нет), гонка гидрации AuthGate (чтение синхронное), полное скрытие `<aside>` (рендерится безусловно).

**Верификация:** живое репро на стенде до и после фикса — временно укоротить `access_token_expire_minutes`, логин → пауза до протухания → reload: сигнатура «`/auth/me` 401 без повторов, рядом `/projects` 401 → `/auth/refresh` 200 → retry 200», футер отсутствует; второй reload — футер на месте. После фикса симптом не воспроизводится.

**Вердикт непересечения** (после ревью партиции свежим агентом — находки учтены). Пограничные места и почему они не конфликтуют:

- `pages/chat/` делят T1 (`ActivityRow.tsx` — галочка `--success`; `MessageList.tsx` — `scrollbar-gutter` на контейнере `--content-max-w`) и T2 (`ChatThread.tsx`, `useAgentStream.ts`, стор). Файлы разные. **T2 не трогает `MessageList.tsx`**: канонная карточка стрим-ошибки там уже соответствует блоку 4 и правок не требует.
- `app/components/` делят T4 (модалки, списки, `ErrorBoundary`) и T5 (`Sidebar.tsx`). Сайдбар прибит к T5, потому что тот владеет багом футера и верифицирует его; локализация `title="Settings"/"Logout"` едет тем же треком.
- `shared/ui/` делят T1 (`StateScreen`, `scroll-area`, `sonner`) и T6 (`AuthLayout`, `ProviderButton`) — файлы разные, барреля у `shared/ui` нет (импорт по путям), общего индекса под клоббер нет.
- `shared/assets/illustrations/index.ts` правит только T1 — он завозит все три сцены разом, включая `auth-hero` для T6; T6 ассеты только читает через `getIllustration()`.
- `index.css` правит только T1. Потребители токенов (`text-success` в T3) пишут классы, файл не трогают.
- `router.tsx` правит только T4 (catch-all + вынос инлайн-заглушки артефактов). Это же единственный файл стыка с feat-008.
- Слайсы, из которых импортирует роутер или другой слой, правятся вместе со своим `index.ts` (eslint-boundaries пускает `app` в `pages` только через публичный API) — поэтому скоупы T4 записаны директориями целиком, а экран 404 заводится отдельным слайсом `pages/not-found` со своим `index.ts`.
- Тест-файлы живут рядом с исходниками (co-located), поэтому тестовый скоуп трека = тест-файлы его же файлов; `{scope_id}` совпадает с файловым скоупом.

**Закрытый список.** Файл, не перечисленный в таблице, не правит никто. Соблазн «раз уж зашёл — переведу и здесь» ломает изоляцию: правка в чужом или ничейном файле поверх идущей волны обнаруживается только на merge. Нашёл работу вне своего скоупа — фиксируй в `## Follow-ups` своего трека и эскалируй оркестратору, не правь.

**Зависимости между волнами.** Волна 1 — T1 и T5 (фундамент и полностью независимый фикс интерцептора). Волна 2 — T2, T3, T4, T6 после коммита T1:

- T2 и T4 потребляют `StateScreen` и рецепты состояний, T6 — `AuthLayout`-фон и сцену `auth-hero`;
- T3 формально файлово независим, но подтверждение inline-сохранения красится токеном `--success`, которого до T1 не существует: стартовав раньше, агент увидит нерезолвящийся класс и полезет чинить `index.css` — то есть в чужой файл.

**DoD T1 как контракт волны 2.** T1 сдаёт `StateScreen` с зафиксированным публичным API и готовыми рецептами: компактная форма со спиннером для панельных загрузок, скелетон-форма для списков, карточка ошибки (`border-destructive/30 bg-destructive/10` + действие «Повторить»), полноэкранная форма с иллюстрацией. T2 и T4 берут контракт из кода T1 и его summary, а не согласуют между собой — иначе экран чата разъедется с остальным продуктом.

## SOFA consulted

Ресёрч проведён по темам итерации (design tokens / скроллбары, loading/error states, мокапы, background removal, auth refresh). Blueprint'ов по темам не нашлось; два релевантных TIL учтены:

- `e1bf02bb` «Centered SPA layout flickers … classic scrollbars vs overlay» — класс бага: classic-скроллбар исчезает на route-переходе → центрированный `max-width`-контент дёргается по горизонтали; CLS-метрики этот класс не ловят (шифт размазывается по границе view). **Взято:** `scrollbar-gutter: stable` добавлен в решение блока 1.2 как страховка.
- `29bce0b1` «Refresh short-lived session tokens at session start, not on first use» — паттерн: короткоживущий токен освежается на границе старта сессии, а не лениво на первом запросе; наличие токена в хранилище ≠ его валидность. **Взято частично:** главный фикс сайдбар-бага остаётся правкой исключения интерцептора (блок 10 — устраняет причину для всех запросов разом); паттерн подтверждает направление и слабое место «AuthGate верит `Boolean(getAccessToken())` без проверки срока» — если репро после фикса покажет остаточные кейсы, добавить проактивный `ensureFreshToken` на старте приложения.

Оба поста прочитаны целиком, отданы read-time голоса; verification отправим после реализации фикса (применение паттерна на живом коде).
