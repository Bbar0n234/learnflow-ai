# Test Cases: feat-013 — UI/UX polish / трек T2

Трек T2 чинит потерю владельца идущего потока: экран чата не перемонтируется при переключении `:cid`, поэтому и стор, и колбэки хука писали результат хода в тот чат, который открыт **сейчас**, а не в тот, где ход реально шёл. Фикс проводит владельца — `chatId`, зафиксированный в момент `send()` — через два пути разом: через owner-guard в `stream-store` (событие и терминал чужого потока не применяются) и через контракт `useAgentStream` (`onDone(info.chatId)`, `onError`/`onSecurityBlock`/`onCancelled` с `ownerChatId` первым аргументом), который `ChatThread` кладёт в транзиентное состояние вместо `cid` из замыкания. Третья фаза трека привела загрузку и ошибку экрана чата к общему для продукта шаблону состояний.

Автотесты страхуют именно поведение при **расхождении** владельца с открытым чатом — то, чего в наборе не было вовсе: до трека все кейсы хука жили на одном `CHAT_ID`, а значит не отличали «владелец» от «текущий чат» в принципе. Отсюда два новых шва: хук, который перерендеривается с другим `chatId` без перемонтирования, и два одновременно живых потока в двух чатах. Поведение при совпадении владельца (весь прежний набор) страхуется как регресс — фикс не имеет права ничего изменить в обычном одночатовом ходе. Ожидаемые изменения поведения ровно два: экран чата грузится русской подписью `LoadingState` вместо `Loading chat...` и показывает полную форму ошибки с «Повторить» вместо голой красной строки.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры** (применять, если итерация их касается): `📊` — проверка наблюдаемости (структура БД, метрики, Redis state, Langfuse); `🔴` — проверка реальных инъекций / атак / security-событий; `[auto]` — кейс закрыт автотестом (живёт рядом со слайсом); `*(регресс)*` — кейс страхует «поведение не сломалось» (отделяет регресс от проверки нового поведения).
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe`/`make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Наблюдаемость трека: DevTools → Network (два открытых SSE-соединения одновременно, кадры каждого), DevTools → Console (`@/shared/lib/logger`), экран (лента активности, композер, плашки). Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста), не сам тестировщик.

**Скоуп по трекам.** Кейсы с префиксом трека (`{T2.1}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST (`{track_id}=final`). Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура целиком: `make docker-up-db`, `make migrate`, backend `make dev`, фронт `make dev-fe`. Кейсы трека нужен **живой агент**: проверяется поведение двух одновременно идущих ходов, а не вёрстка.
2. Актор: один обычный пользователь, один проект и **два чата** в нём. Для двухчатового сценария нужен долгий ход — вопрос, на котором агент уйдёт в инструменты (поиск по вебу, несколько шагов), чтобы успеть переключиться.
3. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.
4. Визуальные кейсы (`{T2.2}`, `{T2.3}`) — в **обеих темах**.
5. После прогона — сводка (pass / failed / **deferred**). Deferred — кейсы 👤/заблокированные (нет живого агента, занят стенд): отдельным счётчиком + причина по каждому.

## Дизайн автотестов

**Покрываем автотестом** — по одной записи на суиту (тест-файл):

### `stream-store.test.ts` — стор как держатель инварианта «пишет только владелец»

1. **Файл**: `frontend/src/stores/stream-store.test.ts` — unit (чистые переходы состояния через публичные экшены, без дублей и сети; zustand-стор сбрасывается между тестами харнессом).
2. **Тестирует**: `stores/stream-store.ts :: useStreamStore` (`applyEvent` / `redact` / `setReviewing` / `endStream` / `reset`)
3. **Суть**: Новая половина суиты проверяет, что стор сам отбивает записи чужого потока, а не полагается на дисциплину вызывающего. Она страхует четыре охраняемых действия по отдельности: событие чужого хода не дописывается в ленту открытого чата, его терминал не гасит живой стрим (главный симптом, ради которого guard заведён), его редакция не схлопывает чужую ленту в заглушку, его индикатор проверки ответа не поднимается на чужом экране. Отдельно сторожится тонкое свойство, ради которого guard возвращает тот же объект состояния, а не пересобранный: подписчики стора при чужой записи не будятся вовсе — иначе лента открытого чата перерисовывалась бы на каждом кадре догорающего соседнего хода. Обратную сторону guard'а суита проверяет тем же приёмом: запись **своего** владельца обязана применяться как раньше, иначе стрим просто перестал бы показывать что-либо, и все кейсы остались бы зелёными. Прежние кейсы ленты (накопление текста, параллельные вызовы, редакция, полный сброс на `startStream`) остаются регрессом на совпадающем владельце.
4. **Кейсы**:
   - событие чужого потока не меняет ленту и не будит подписчиков
   - терминал чужого потока не гасит живой стрим и не трогает его ленту
   - редакция чужого потока не схлопывает ленту и не снимает стрим
   - `setReviewing` чужого потока не поднимает индикатор проверки ответа
   - запись своего владельца применяется как раньше *(обратная сторона guard'а)*
   - на погашенном сторе (владельца нет) любая охраняемая запись — no-op: `applyEvent`, `redact`, `setReviewing`, `endStream` (таблица через `it.each`)
   - `reset()` возвращает стор в idle независимо от владельца — неохраняемый путь ухода с экрана

### `useAgentStream.test.ts` — владелец в контракте хука и два живых хода разом

1. **Файл**: `frontend/src/pages/chat/model/useAgentStream.test.ts` — integration (хук целиком, сеть и SSE-поток через MSW; `renderHook` с перерендером под другим `chatId` — шов, которого в файле не было).
2. **Тестирует**: `pages/chat/model/useAgentStream.ts :: useAgentStream` (контракт колбэков и запись в стор)
3. **Суть**: Суита проверяет главное обещание контракта: колбэк узнаёт чат, в котором ход **шёл**, а не тот, что открыт в момент события. Проверяется это единственным честным способом — хук перерендеривается с другим `chatId` посреди хода, ровно как маршрут `chats/:cid` перерисовывает один и тот же экран, а терминальное событие приходит уже после. Каждая ветка получает свой кейс, включая четыре, где SSE-события не было вовсе: таймаут сторожа тишины, не-ok ответ на отправку, обрыв потока без терминального события и исключение транспорта — там владельца неоткуда взять «из потока», и потерять его проще всего. Отдельно сторожится единственный **неохраняемый** путь — уход с экрана: cleanup зовёт `reset()`, а не гашение по чату, и различает эти две реализации только сценарий с расхождением (ход начат в A, пользователь ушёл в B, экран размонтирован). Скоупленное гашение стало бы там no-op, и стор остался бы с `isStreaming: true` от чужого хода на весь остаток сессии. Вторая половина суиты — два одновременно живых хода: поток чата A при переключении не абортится по решению брифа, поэтому пока в чате B идёт свой ход, A продолжает слать события и рано или поздно пришлёт терминал; ни то, ни другое не имеет права коснуться ленты и стрима B, а сам колбэк обязан назвать владельцем A, хотя стором владеет B. Точка синхронизации здесь — терминал самого A: кадры одного потока разбираются по порядку, поэтому к моменту `onDone` всё, что A присылал раньше, уже прошло через стор, и ассерт «лента B цела» не может оказаться зелёным по случайности.
4. **Кейсы**:
   - `onDone` несёт владельца хода, а не чата, открытого к моменту события
   - `onError` на событии `error` после переключения несёт владельца
   - `onCancelled` после переключения несёт владельца
   - `onSecurityBlock` после переключения несёт владельца
   - владелец в таймауте сторожа тишины (сервер не ответил вовсе)
   - владелец в не-ok ответе на отправку (ответ придержан до переключения)
   - владелец в обрыве потока без терминального события
   - владелец в исключении транспорта
   - unmount после ухода в соседний чат сбрасывает стор целиком *(неохраняемый `reset()`, владелец на момент ухода — покинутый чат)*
   - события догорающего потока A не попадают в ленту чата B, а `onDone` называет владельцем A при живом стриме B
   - терминал догорающего потока A не гасит живой стрим чата B
   - *(регресс, прежние кейсы)* владелец в колбэках при совпадении чата, вся механика диспетчера, сторожа тишины, инвалидаций и патчей кэша

### `ChatThread.test.tsx` — транзиентное состояние экрана и его состояния загрузки/ошибки

1. **Файл**: `frontend/src/pages/chat/ui/ChatThread.test.tsx` — integration (экран целиком под `MemoryRouter`, переключение чатов настоящей навигацией без перемонтирования, сеть и SSE через MSW).
2. **Тестирует**: `pages/chat/ui/ChatThread.tsx :: ChatThread`
3. **Суть**: Суита проверяет, что исход хода достаётся тому чату, где ход шёл, даже если пользователь ушёл раньше, чем он закончился. Три терминальных исхода — отмена, ошибка и блокировка — проверяются одной таблицей: пользователь уходит в соседний чат посреди хода, ход заканчивается уже там, и результат обязан ждать его в чате-владельце и отсутствовать в открытом. Возврат в чат-владелец здесь не только ассерт, но и точка синхронизации: увиденное там уведомление — доказательство, что терминальное событие вообще обработано, поэтому проверка «в соседнем чате пусто» не вырождается в проверку неуспевшего рендера. Дождавшийся пользователя исход обязан ещё и **пережить работу в соседнем чате**: пара кейсов разводит две половины сброса при отправке — новый ход гасит ошибку и уведомление своего чата и не трогает чужие. Порядок «терминал в A, потом отправка в B» до находки R3 не покрывал никто: и таблица исходов, и ручной `{T2.1}` отправляют в соседний чат раньше, чем ход A закончится, поэтому гасить в слоте было нечего. Обратную половину приходится проверять после конца второго хода — живой регион прячет плашку сам (`streamError && !isStreaming`), и её отсутствие посреди хода не означало бы ничего. Отдельным кейсом закрыта оптимистичная копия: терминал чужого хода больше не стирает с экрана сообщение, отправленное в другой чат и ещё не подтверждённое сервером, — до фикса копия исчезала до всякого рефетча, и пользователь на секунду терял собственный текст. Состояния экрана из T2.3 закрыты одним кейсом (ошибка загрузки истории рисуется полной формой со сценой и даёт «Повторить», который действительно перезапрашивает историю — до фикса из этого состояния выводила только перезагрузка страницы) и одним ассертом внутри существующего кейса про отправку раньше истории (панельная загрузка подписана общей для продукта русской строкой). Три прежних кейса скоупинга (`не переносит … в соседний чат`) остаются регрессом на фильтрах рендера — второй половине того же фикса.
4. **Кейсы**:
   - исход хода (`cancelled` / `error` / `security_block`) остаётся в чате-владельце и не появляется в открытом чате (таблица через `it.each`)
   - отправка сообщения в соседнем чате не гасит исход чужого хода
   - отправка в своём чате гасит собственную плашку как раньше *(обратная половина сброса)*
   - `done` чужого хода не стирает оптимистичную копию, отправленную в соседний чат
   - упавшая история показывает сцену ошибки и «Повторить», клик перезапрашивает историю
   - панельная загрузка чата подписана «Загрузка…» — ассерт внутри кейса `does not wait for the chat history to load before sending`, своего кейса не имеет *(отменяет `Loading chat...`)*
   - *(регресс)* три прежних кейса скоупинга и весь контракт первой отправки из router state

**Мутационная проверка сторожей** (§ Целостность тестов). Двенадцать точечных мутаций прод-кода, каждая откачена точечной правкой (файл трека восстанавливался из снятой до мутации копии, не `git checkout` — worktree общий с параллельными T3/T4/T6); после отката все три прод-файла побайтово совпали с исходными, дерево чистое. Базовый прогон скоупа — 138 зелёных.

- `stream-store.ts`: снят guard у `endStream` → покраснели ровно 3 кейса: «не гасит живой стрим терминалом чужого потока» (стор) и обе половины двухпоточного сценария в хуке. Второй из хуковых («не пишет события догорающего потока в ленту нового чата») краснеет здесь закономерно — незащищённый `endStream` стирает ленту B целиком.
- `stream-store.ts`: снят guard у `applyEvent` → покраснели ровно 2 кейса стора («не применяет событие чужого потока…», «оставляет погашенный стор нетронутым: applyEvent») и 1 кейс хука («не пишет события догорающего потока в ленту нового чата»).
- `stream-store.ts`: снят guard у `redact` → покраснели ровно 2 кейса, и это «не схлопывает ленту в заглушку по редакции чужого потока» и «оставляет погашенный стор нетронутым: redact».
- `stream-store.ts`: снят guard у `setReviewing` → покраснели ровно 2 кейса, и это «не поднимает индикатор проверки ответа по чужому потоку» и «оставляет погашенный стор нетронутым: setReviewing».
- `ChatThread.tsx`: `handleDone` снова снимает копию безусловно (`setLocalMessages(null)`) → покраснел ровно 1 кейс, и это «не стирает оптимистичную копию соседнего чата терминалом чужого хода».
- `ChatThread.tsx`: инлайновый `onError` снова штампует `cid!` вместо владельца из аргумента → покраснел ровно 1 кейс, и это строка `error` таблицы исходов. Строки `cancelled` и `security_block` остались зелёными — половины признака разведены.
- **Обратная мутация той же половины** — `ChatThread.tsx`: `handleCancelled` и `handleSecurityBlock` снова штампуют `cid!` (с `cid` в зависимостях, дофиксовая форма) → покраснели ровно 2 кейса, и это строки `cancelled` и `security_block`; строка `error` осталась зелёной.
- `useAgentStream.ts`: владелец во **всех** колбэках берётся из текущего рендера (`chatIdRef.current`), а не из замыкания `send()` — ровно та потеря владельца, которую чинит трек (исходный баг) → покраснели ровно 12 кейсов: все восемь кейсов группы «владелец хода при переключении чата» и все четыре кейса `ChatThread`, зависящих от владельца. Ни один прежний одночатовый кейс не покраснел — подтверждение, что старый набор эту регрессию не ловил в принципе.
- **Отдельная мутация на отвергнутый брифом вариант** — `useAgentStream.ts`: владелец в колбэках берётся из общей на все ходы ссылки, зафиксированной в момент `send()` (`ownerRef.current = chatId` в начале `send`, все восемь вызовов колбэков читают `ownerRef.current`). Мутация выживает одночатовые кейсы и все кейсы группы «владелец при переключении чата» — течёт она только при **второй** отправке во время живого первого хода → покраснели ровно 2 кейса: «не пишет события догорающего потока в ленту нового чата» (на ассерте владельца в `onDone`: `chatId: "c2"` вместо `"c1"`) и `ChatThread` «не стирает оптимистичную копию соседнего чата терминалом чужого хода». Записи в стор мутация не трогает, поэтому store-путь двухпоточных кейсов здесь ни при чём — красит именно аргумент колбэка.
- `useAgentStream.ts`: cleanup на unmount гасит поток скоуплено по текущему чату (`endStream(chatIdRef.current)`) вместо неохраняемого `reset()` → покраснел ровно 1 кейс, и это «сбрасывает стор на unmount после ухода в соседний чат». Прежний одночатовый кейс «aborts the in-flight stream and resets the store on unmount» остался зелёным — владелец там совпадает, и различить две реализации он не может (находка R2).
- `ChatThread.tsx`: `handleSend` снова гасит `streamError`/`endNotice` безусловно (`setStreamError(null)`, `setEndNotice(null)`, дофиксовая форма) → покраснел ровно 1 кейс, и это «не гасит исход чужого хода отправкой сообщения в соседнем чате». Обратная половина («гасит собственную плашку следующей отправкой в том же чате») осталась зелёной.
- **Обратная мутация той же половины** — `ChatThread.tsx`: `handleSend` не гасит ничего (`setStreamError((prev) => prev)`, то же для `endNotice`) → покраснел ровно 1 кейс, и это «гасит собственную плашку следующей отправкой в том же чате»; кейс про чужой исход остался зелёным. Половины признака разведены. Первая редакция обратного кейса проверяла плашку **посреди** второго хода и оставалась зелёной под обеими мутациями — живой регион прячет её сам (`streamError && !isStreaming`); кейс переписан на признак после `done` и только тогда стал сторожем.

**Осознанно не покрываем автотестом** (что — почему — куда уехало):

- **Два реальных одновременных SSE-соединения к живому бэкенду** — jsdom-кейсы гоняют потоки на MSW: транспорт, реальные задержки, поведение сервера при втором открытом стриме и рефетч по `done` живого хода в них не участвуют → `{T2.1}`.

### Layer 1: Трек T2 — владелец состояния стрима и состояния экрана чата

- [ ] `{T2.1}` 👤 **Двухчатовый сценарий на живом стенде** (главный кейс трека). Проект с двумя чатами. В чате A задать вопрос, требующий долгой работы агента (поиск по вебу в несколько шагов) → не дожидаясь ответа, переключиться в чат B → отправить сообщение в B → дождаться, пока ход A закончится (в Network видно два открытых `messages`-стрима, терминальный кадр A приходит первым).
