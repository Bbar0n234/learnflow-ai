# Test Cases: feat-013 — UI/UX polish / трек T5 (Refresh-интерцептор + футер сайдбара)

Трек T5 чинит P2-баг «сайдбар не отображается при первом открытии». Правило исключений в
refresh-интерцепторе axios переформулировано семантически: из 401-ретрая выпадают только
эндпоинты, которые выдают или обновляют учётные данные и вызываются без валидного
access-токена (`/auth/refresh`, `/auth/login`, `/auth/register`); всё остальное — включая
`GET /auth/me` и `POST /auth/logout` — проходит стандартный single-flight refresh с повтором
запроса. Заодно локализованы англоязычные подписи `title="Settings"` / `title="Logout"` в
футере сайдбара (блок 2 брифа «Заодно»).

Кейсы страхуют **изменение поведения**, а не рефактор: до фикса 401 на `/auth/me` отдавался
наверх без повтора, react-query 4xx не ретраит, `user` оставался `undefined` и футер сайдбара
не рендерился. Ожидаемые изменения, которые кейсы фиксируют: `/auth/me` и `/auth/logout`
теперь ретраятся; `/auth/refresh` по-прежнему не ретраится (рекурсии нет); `/auth/login` и
`/auth/register` по-прежнему отдают 401 наверх; поведение соседей (`/projects`,
`/chats/recent`), single-flight и ветка провала refresh (очистка токена + перезагрузка) не
менялись. Автотесты — компонентная и клиентская интеграция через MSW; ручной хвост — живая
Network-сигнатура на стенде с укороченным TTL access-токена, которую jsdom не воспроизводит.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры**: `📊` — наблюдаемость (DevTools Network, structlog); `[auto]` — кейс закрыт автотестом (живёт колокацией рядом со слайсом); `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов): `runs: r1 ✅ → r2 ❌ (причина) → r3 ✅`. Один прогон — run-log не нужен.

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe` / `make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация. Инструменты: DevTools → Network (последовательность и статусы запросов, заголовок `Authorization` на повторе), DevTools → Console (`@/shared/lib/logger`), `localStorage["learnflow-access-token"]`, structlog бэкенда. Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста).

**Скоуп по трекам.** Кейсы с префиксом `{T5.x}` гоняются на треке T5 + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST против живого стека. Неприменимый кейс помечать причиной, не пропускать молча.

### Процесс (тестировщик поднимает стенд сам)

1. Инфраструктура: `make docker-up-db` + `make migrate`, backend `make dev`, фронт `make dev-fe` — либо `make docker-up` целиком.
2. Актор: обычный пользователь через UI register / `POST /api/auth/register`. Для репро протухания — временно укоротить `access_token_expire_minutes` (напр. до 1 минуты) в настройках backend и перезапустить его; после прогона вернуть значение.
3. Прогон сверху вниз; каждый failed-кейс — повторная попытка, затем фиксация в run-log + `## Решения и обоснования` summary трека.
4. После прогона — сводка (pass / failed / **deferred**). Deferred — кейсы 👤/заблокированные, отдельным счётчиком с причиной.

## Дизайн автотестов

**Покрываем автотестом** — по одной записи на суиту:

### `client.test.ts` — 401-ветка refresh-интерцептора API-клиента

1. **Файл**: `frontend/src/shared/api/client.test.ts` — интеграция клиентского слоя (реальный экземпляр axios со своими интерцепторами), шов: **MSW** (`server.use(...)`) на сетевом уровне + `vi.stubGlobal("location", …)` там, где ветка провала refresh перезагружает страницу. Изоляция состояния — **пересоздание модуля на каждый кейс**: `beforeEach` делает `vi.resetModules()` и заново импортирует `./client`, поэтому single-flight-состояние интерцептора (module-level флаг «refresh в полёте» и очередь ожидающих) не переносится между кейсами. Прод ради этого ничего не экспортирует: тест берёт весь публичный API из свежего инстанса модуля (`client.apiClient`, `client.setAccessToken`, …).
2. **Тестирует**: `shared/api/client :: apiClient` (response-интерцептор 401 → refresh → retry, вместе с классификатором эндпоинтов и single-flight-очередью) и `ensureFreshToken` — обе его ветки. Существующие кейсы файла (хранение токена, happy-path `ensureFreshToken`) оставлены как были, к ним добавлена негативная ветка.
3. **Суть**: Суита проверяет, что 401 от запроса, сделанного от имени уже авторизованного пользователя, поднимает single-flight refresh и повторяет исходный запрос с новым токеном, — и делает это для `/auth/me` и `/auth/logout` наравне с `/projects`, то есть закрывает ровно ту дыру, из-за которой сайдбар терял пользователя на холодной сессии. Она страхует обратную сторону правила: 401 от `/auth/login` и `/auth/register` уходит наверх нетронутым (неверный пароль — не протухшая сессия), а 401 от самого `/auth/refresh` не порождает второй refresh, иначе интерцептор рекурсировал бы через себя. Отдельно закреплена **строгость** правила: маршрут, который лишь содержит имя учётного эндпоинта внутри своего пути, — обычный авторизованный маршрут и свой ретрай сохраняет, потому что правило сформулировано по эндпоинтам, а не по подстрокам. Она гарантирует, что повтор делается ровно один раз (сервер, который отвечает 401 и на свежий токен, не вводит клиент в бесконечный цикл), что два параллельных 401 обслуживаются одним refresh, а провал refresh чистит токен, перезагружает приложение и отклоняет в том числе запросы, вставшие в очередь за ним, — причём отклоняет **именно провалом refresh**, а не любой посторонней ошибкой. Наблюдение всюду внешнее — счётчик обращений к `/auth/refresh`, число обращений к защищённому эндпоинту, заголовок `Authorization` на повторе, содержимое `localStorage`; ни одна внутренняя переменная интерцептора не ассертится.
4. **Кейсы**:
   - 401 на `/auth/me` → refresh → повтор с новым токеном → 200 (ядро фикса);
   - 401 на `/auth/logout` → то же (эндпоинт вызывается от имени авторизованного пользователя);
   - 401 на `/projects` → то же *(регресс: соседи фикса не задеты)*;
   - 401 на `/projects/auth/login-notes`, `/auth/login-notes`, `/oauth/auth/refresh` → то же: путь, лишь содержащий учётный эндпоинт подстрокой, остаётся под refresh-retry (сторож строгости классификатора; при подстрочном сопоставлении такой маршрут молча выпал бы из ретрая);
   - запрос без URL в конфиге → трактуется как требующий токена, идёт под refresh (консервативный дефолт классификатора);
   - два параллельных 401 (`/projects` + `/chats/recent`) → ровно один `POST /auth/refresh`, оба запроса завершаются успешно (single-flight);
   - 401 на `/auth/login` → отклоняется без единого обращения к refresh, токен не тронут, перезагрузки нет;
   - 401 на `/auth/register` → то же;
   - 401 от самого `/auth/refresh` → наверх без второго refresh (защита от рекурсии);
   - ошибка 500 → проходит мимо refresh-ветки нетронутой;
   - повторный 401 уже после ретрая → запрос отклоняется, защищённый эндпоинт получил **ровно два** обращения (исходное + один повтор), refresh был один. Эндпоинт перестаёт отвечать 401 с третьего обращения — петля без guard'а становится конечной и падает ассертами, а не зависанием раннера;
   - провал refresh → запрос отклонён **с 401 самого refresh**, токен очищен, приложение перезагружено;
   - провал refresh при двух параллельных 401 → отклоняются оба (включая вставший в очередь) и оба — тем же 401 от refresh;
   - `ensureFreshToken` на почти протухшем токене, когда refresh отвечает 401 → возвращает `null`, токен очищен, `reload` вызван (негативная половина проактивного пути SSE/fetch).

- Возврат предиката к исходному `!originalRequest.url?.includes("/auth/")` красит **ровно 4 кейса, и это они**: «refreshes and retries a 401 from `/auth/me`», «… from `/auth/logout`», «gives up after one retry instead of looping on a repeated 401», «Sidebar — shows the user footer on a session whose access token has expired». Остальные остаются зелёными.
- Возврат сопоставления путей к подстрочному (`CREDENTIAL_ENDPOINTS.some((e) => url.includes(e))` вместо равенства нормализованных путей) красит **ровно 3 кейса, и это они** — все три пути-двойника: `/projects/auth/login-notes`, `/auth/login-notes`, `/oauth/auth/refresh`; остальные 18 зелёные. Прогон завершается за 4 с: маршрут выпадает из refresh-ретрая, 401 приходит наверх, кейс падает ассертом на данные ответа.
- Обратная мутация (убрать `/auth/refresh` из списка исключений) красит **ровно 4 кейса, и это они** — все, кто реально проходит веткой провала refresh: «does not refresh a 401 that came from `/auth/refresh` itself» (целевой), «clears the token and reloads the app when the refresh is rejected», «rejects the requests queued behind a failed refresh as well» и `ensureFreshToken` «clears the token and reloads the app when the near-expiry refresh fails». Отказ — по пер-тестовому таймауту (интерцептор уходит в самоблокировку: refresh ждёт сам себя из очереди), прогон под `--testTimeout=4000` завершается за 19 с. Сторож двусторонний. **Побочных покраснений больше нет**: раньше залипший флаг топил три последующих кейса файла, теперь соседи каждого зависшего кейса (например «passes a non-401 error through untouched» сразу за целевым) зелёные — это и есть наблюдаемое доказательство изоляции модульного состояния.
- Мутация `if (!url) return true` → `return false` красит ровно 1 кейс — «treats a request with no reported URL as needing a token».
- Возврат `title="Settings"` / `title="Logout"` красит ровно 1 кейс — «labels the footer actions in Russian».
- Снятие guard'а `!originalRequest._retry` красит **ровно 1 кейс, и это он** — «gives up after one retry instead of looping on a repeated 401», отчётом и со счётом: `promise resolved "{ data: { looped: true } }" instead of rejecting`. Прогон завершается за 3 с (раньше та же мутация вешала раннер: неограниченный цикл 401 → refresh → повтор вычерпывал event loop, пер-тестовый таймаут его не останавливал, прогон приходилось убивать внешним). Конечность обеспечена в самом MSW-хендлере кейса — эндпоинт отвечает 401 только на первые два обращения.
- Все мутации откачены точечными правками (не `git checkout` — в общем worktree параллельно идут другие треки); прод-файлы совпадают с версией fixer'а.

**Осознанно не покрываем автотестом** — триадой *что — почему — куда уехало*:

- Живая Network-сигнатура фикса (укороченный `access_token_expire_minutes`, логин → пауза до протухания → reload, наблюдение порядка `/auth/me` 401 → `/auth/refresh` 200 → повтор 200 и наличия футера) — *почему*: воспроизводится только на живом стеке с реальным TTL JWT и реальной refresh-cookie; jsdom не даёт ни настоящей перезагрузки страницы, ни браузерного Network-таймлайна, а подделка TTL в MSW проверяла бы уже покрытое → ручной кейс `{T5.1}` 👤.
- Настоящая перезагрузка страницы в ветке провала refresh — *почему*: `window.location.reload()` в jsdom не исполняется, тест наблюдает только факт вызова через подменённый `location`; что после перезагрузки пользователь оказывается на экране логина — свойство приложения целиком, не интерцептора → ручной кейс `{T5.2}` 👤.
- Внутреннее состояние интерцептора (`isRefreshing`, `pendingRequests`, флаг `_retry` на конфиге) — *почему*: это реализация, а не контракт; single-flight и анти-петля наблюдаются снаружи числом обращений к `/auth/refresh` и к защищённому эндпоинту → покрыто кейсами «serves concurrent 401s with a single refresh» и «gives up after one retry» той же суиты. Изоляция этого состояния между кейсами обеспечена не ассертом, а пересозданием модуля в `beforeEach`.
- Визуальная приёмка футера (иконки, обе темы, тултип на hover, расположение блока) — *почему*: в jsdom нет layout и CSS-каскада, а запросы по `className`/токенам запрещены конвенцией → ручной кейс `{T5.3}` 👤.
- Локализация остальных англоязычных строк блока 2 брифа (`ProjectList`, `ChatThread`, `SphereView`, `ProjectLayout`, `alt` иллюстраций) — *почему*: вне файлового скоупа T5, эти файлы принадлежат другим трекам → покрытие соответствующих треков.
- Поведение `getMe` при транзиентной сетевой ошибке холодного старта (наблюдение H2 брифа) — *почему*: механика восстановления в scope трека не вводилась, тест закреплял бы отсутствующее поведение → follow-up трека (`summary.md`), при подтверждении на репро — отдельная итерация.

**Замеченные прод-баги (для fixer'а, сам не чиню):** не найдено. Фикс соответствует контракту брифа блока 10 и плана T5.1; все новые кейсы зелёные, существующие ассерты не правились. Наблюдения:

- Нестрогость классификатора (сопоставление URL подстрокой) вынесена ревьюером в R2 и **починена fixer'ом** — сравнивается нормализованный путь на равенство. Соответствующий кейс из «намеренно не покрываем» переехал в покрытие: три пути-двойника теперь сторожат строгость.
- Ветка провала refresh отклоняет исходный запрос и одновременно перезагружает страницу — из-за этого в консоли остаётся `[API Error] 401` от уже мёртвой сессии. Поведение прежнее, треком не менялось; шума добавляет ровно столько же, сколько до фикса.

## Ручные кейсы + статусы

> Узкий ручной хвост: живая Network-сигнатура репро, реальная перезагрузка страницы и
> визуальная приёмка футера — то, чего jsdom не исполняет.

### Layer 1: T5 — Refresh-интерцептор и футер сайдбара

> **Решение оркестратора: ручной хвост трека гоняется на финальном прогоне (INTEGRATION_TEST), не на треке.**
> Все четыре кейса требуют живого стека с укороченным TTL access-токена и браузера, то есть одного и того же
> подъёма стенда. Волна 2 (треки T2, T3, T4, T6) добавит в тот же стенд свои экраны, поэтому шесть отдельных
> подъёмов вместо одного — чистая трата, а автотесты фикса уже подтверждены мутацией (§ Дизайн автотестов).
> Кейсы не «пропущены»: тестировщик финального прогона обязан отработать их наравне с cross-cutting и
> посчитать в сводке pass / failed / deferred.
