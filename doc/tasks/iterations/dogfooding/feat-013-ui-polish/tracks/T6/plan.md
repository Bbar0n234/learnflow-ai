# Implementation Plan: feat-013 / трек T6 — Брендовый auth-дизайн

## Контекст

Трек делает первый экран продукта брендовым: вместо generic shadcn-модалки с англоязычным копирайтом (`app/components/AuthGate.tsx`) появляется полноэкранная композиция «wordmark + тэглайн + сцена «Электрик» + карточка формы + кнопки провайдеров».

Особенность трека — **работа делается сейчас, но вне файлов feat-008**. Каркас `/login`, который строит параллельная итерация, в `develop` ещё не появился, поэтому по уточнению архитектора (design-brief, блок 8) весь дизайн изготавливается как **презентационный слой**: брендовые примитивы в `shared/ui` (`AuthLayout`, `ProviderButton`) и собранный из них чисто презентационный `LoginScreenView` в `features/auth/ui`. Никакой auth-логики внутри: режим вход/регистрация, значения полей, гео-состав провайдеров, текст ошибки, состояние отправки и все обработчики приходят через props. feat-008 после merge собирает свой `pages/login` из этих частей, прокидывая логику.

Главный продукт трека — не пиксели, а **контракт props `LoginScreenView`**: по нему feat-008 подключает свою логику, и он же не должен утащить в презентационный слой ни запросов, ни роутинга, ни чтения гео.

### Проверенные факты по коду и инструментам

- **Брендовых иконок в `lucide-react` нет.** В установленной `lucide-react@0.577.0` (`frontend/package.json:27`) есть только `Github`, и он помечен `@deprecated`: «Brand icons have been deprecated and are due to be removed… will be removed in v1.0» (`node_modules/lucide-react/dist/lucide-react.d.ts:9661`). `Google`, `Yandex`, `Vk` отсутствуют вовсе (проверено грепом по d.ts). Вывод: иконки провайдеров — inline-SVG в нашем компоненте; внешних зависимостей (`simple-icons`, `react-icons`) трек не вводит.
- **Сцена `auth-hero` уже в продукте** — T1 закоммичен (`a46c804`): PNG в `shared/assets/illustrations/{light,dark}/`, ключ в типе `Scene` и в карте `index.ts`. Доступ — через `Illustration` (`{ scene, alt, className }`), тема резолвится сама.
- **Контракт T1 доступен**: `shared/ui/StateScreen.tsx` экспортирует `StateScreen`, `LoadingState`, `ErrorCard`. `ErrorCard({ message, onRetry?, retryLabel?, className? })` рисует ровно карточку блока 4 (`rounded-lg border border-destructive/30 bg-destructive/10 px-4 py-3 text-sm text-destructive`), без `onRetry` — без кнопки. Это и есть форма ошибки auth-экрана.
- **Токены геометрии сходятся с мокапом без арифметики:** `--radius: 0.7rem`, и в `@theme inline` заведён `--radius-xl: calc(var(--radius) * 1.4)` (`index.css:192`) — это ровно радиус `.auth-card`/`.auth-frame` из мокапа, то есть утилита `rounded-xl`. Тень карточки — `--shadow-input` (`index.css:64`), в проекте уже применяется инлайновым `style={{ boxShadow: "var(--shadow-input)" }}` (`pages/project-chats/ui/ChatList.tsx:55`, `pages/chat/ui/ChatInput.tsx:65`) — берём тот же паттерн (это токен, не хардкод).
- **Примитивы сходятся с мокапом:** `.input` мокапа (32px, `rounded var(--radius)`, `border --input`, `dark: bg input/30`) — это shared `Input` как есть (`h-8 rounded-lg border-input … dark:bg-input/30`). `.prov-btn` (36px, бордер `--border`, hover `--muted`, в тёмной — `--input`-варианты) — это `Button variant="outline" size="lg"` **дословно**: `outline` несёт `border-border bg-background hover:bg-muted dark:border-input dark:bg-input/30 dark:hover:bg-input/50`, `lg` — `h-9` (=36px). `.btn.btn-lg.btn-primary` сабмита — `Button size="lg"` дефолтного варианта.
- **Иконка в `Button` по умолчанию `size-4`** (`[&_svg:not([class*='size-'])]:size-4`), а мокап требует 20px — значит на SVG провайдера явный `size-5`, иначе базовый класс победит.
- **FSD-границы проверяются линтером:** `eslint.config.mjs` (`boundaries/dependencies`) разрешает `features → shared|stores` и запрещает cross-slice; `pages`/`features` видны наружу только через `index.{ts,tsx}`. Новый слайс обязан иметь `features/auth/index.ts`. Для `src/shared/ui/**/*.tsx` правило `react-refresh/only-export-components` выключено — экспорт нескольких сущностей из одного файла `shared/ui` легален.
- **Vitest** (`frontend/vitest.config.ts`): jsdom, `globals: false`, include `src/**/*.{test,spec}.{ts,tsx}` — тест-файлы co-located, их пишет `test-author`.
- **`tsconfig.app.json`** включает весь `src` со `strict`, `noUnusedLocals`, `noUncheckedIndexedAccess` — временные файлы внутри `src` тоже проходят `tsc` (важно для фазы T6.4).

## Фазы

### T6.1: Брендовые иконки провайдеров и `ProviderButton`

**Цель:** отдать кнопку входа через провайдера с настоящим фирменным знаком (не заглушкой lucide), в обеих темах, на существующем `Button variant="outline"`.

**Изменения:**

- `frontend/src/shared/ui/ProviderButton.tsx` (новый) — один компонент + три приватные иконки-компонента в этом же файле (отдельных файлов под иконки не заводим: закрытый список файлов трека, и знаки нужны ровно одному потребителю).
  - Публичный API:

    ```ts
    export type AuthProvider = "yandex" | "google" | "github";

    export interface ProviderButtonProps {
      provider: AuthProvider;
      /** Переопределение подписи. Дефолт — фирменная формулировка провайдера. */
      label?: string;
      onClick?: () => void;
      disabled?: boolean;
      className?: string;
    }
    export function ProviderButton(props: ProviderButtonProps): JSX.Element;
    ```

  - Подписи по умолчанию — буквально из мокапа (строки 927, 932–933): «Войти с Яндекс ID», «Войти через Google», «Войти через GitHub». Неразрывный пробел в «Яндекс ID» (`&nbsp;` мокапа) переносится как ` ` — визуальный разрыв бренда недопустим.
  - Вёрстка: `Button` с `variant="outline"`, `size="lg"`, `type="button"`, классы `w-full justify-center gap-2.5` (мокап: `gap: 10px`, `justify-content: center`, `width: 100%`). Радиус, бордеры, hover и тёмная тема достаются от варианта `outline` — своих цветовых классов не добавлять.
  - Иконки — inline-SVG, пути берутся **дословно из мокапа** (строки 442–454), каждой ставится `className="size-5"` и `aria-hidden="true"` (подпись рядом уже несёт смысл):
    - Google — четырёхцветный «G», официальные фирменные цвета в `fill` внутри `<path>`;
    - GitHub — octocat одной `<path fill="currentColor" fill-rule="evenodd">`; цвет знака берётся от текста кнопки (мокап красит его почти-чёрным в light и почти-белым в dark — у нас это `text-foreground` через наследование `currentColor`, отдельного класса не нужно);
    - Яндекс — белый круг с тонкой обводкой и фирменная красная «Я» текстом, как в мокапе; `font-family` оставить списком с финальным `sans-serif`, чтобы знак не поехал при отсутствии Instrument Sans.
  - **Хардкод цветов в этом файле — единственное место трека, где он появляется** (фирменные палитры провайдеров задаются их гайдлайнами и не являются токенами темы). Над блоком иконок обязателен комментарий, объясняющий это исключение из `design-system.md` § Границы, чтобы grep-гейт не читался как «правило протухло». См. `## Open Questions` — если архитектор исключение не санкционирует, знаки переезжают в `shared/assets/` файлами, а компонент остаётся тем же.
  - Логика провайдера (URL авторизации, редиректы) в компонент **не заходит** — только `onClick`.

**Verification:**

- `make check-fe` проходит.
- Сверка с мокапом по значениям (не «на глаз»): высота 36px, gap 10px, иконка 20×20, шрифт 14/500, радиус `var(--radius)`, бордер `--border` в light и `--input` в dark, hover — `--muted` / `color-mix(--input 50%)`. Источник — `.prov-btn` (мокап 399–405); фактические классы приходят от `Button variant="outline" size="lg"`, задача — убедиться, что они дают ровно это.

### T6.3: `LoginScreenView` и публичный API слайса `features/auth`

**Цель:** собрать из `AuthLayout`, `ProviderButton`, shared `Input`/`Button` и `ErrorCard` полный экран входа/регистрации — и зафиксировать контракт props, по которому feat-008 подключит логику.

**Изменения:**

- `frontend/src/features/auth/ui/LoginScreenView.tsx` (новый) — компонент и его типы.
- `frontend/src/features/auth/index.ts` (новый) — публичный API слайса: `LoginScreenView` + все типы контракта (`export type`). Внутренние файлы наружу не видны (eslint-boundaries).

**Контракт props (главный продукт трека).** Экран **полностью контролируемый**: всё, что относится к логике, — снаружи.

```ts
export type AuthMode = "login" | "register";
export type { AuthProvider } from "@/shared/ui/ProviderButton"; // re-export, чтобы потребитель не тянул shared напрямую

export interface AuthFormValues {
  name: string;
  password: string;
  /** Используется только в mode="register". */
  confirmPassword: string;
}

export interface LoginScreenViewProps {
  mode: AuthMode;
  onModeChange: (mode: AuthMode) => void;

  values: AuthFormValues;
  onFieldChange: (field: keyof AuthFormValues, value: string) => void;

  /** Сабмит формы. View сам делает preventDefault и ничего не валидирует. */
  onSubmit: () => void;

  /** Гео-состав решает потребитель. Пустой массив — блок провайдеров и разделитель «или» не рисуются. */
  providers: readonly AuthProvider[];
  onProviderSelect: (provider: AuthProvider) => void;

  /** Текст ошибки для карточки блока 4. Пусто/undefined — карточки нет. */
  error?: string | null;
  /** Идёт отправка: сабмит и провайдеры заблокированы. */
  submitting?: boolean;

  className?: string;
}
```

Почему так:

- **Ни `useQuery`, ни `useNavigate`, ни чтения гео, ни `login()`/`register()` из `shared/api`** — иначе презентационный слой станет вторым владельцем auth-логики и feat-008 придётся его разбирать. Импорты компонента ограничены `shared/ui/*` и `shared/lib/utils`.
- **Валидация — за потребителем.** View не проверяет «пароль ≥ 8», «пароли совпадают», «поля непусты»; он рисует готовый `error`. Тексты валидации из мокапа («Введите имя и пароль.», «Пароль должен содержать не менее 8 символов.», «Пароли не совпадают.») перечислить в JSDoc как ожидаемые сообщения — feat-008 и `test-author` берут их оттуда, а не выдумывают. Кнопка сабмита блокируется только по `submitting` (пустые поля не блокируют — иначе экран молча не отвечает на клик, вместо того чтобы объяснить).
- **`values` + `onFieldChange` вместо шести плоских props** — одна точка расширения (появится e-mail — вырастет `AuthFormValues`, а не сигнатура). Поле `confirmPassword` живёт в типе всегда, рендерится только в `mode="register"`.
- **Гео приходит массивом `providers`**, а не флагом «РФ/не-РФ»: чтение гео — работа feat-008, и утверждённая модель (РФ — `["yandex"]`; вне РФ — `["yandex", "google", "github"]`, VK снят полностью) фиксируется в JSDoc как справка о составе, а не в коде как логика. Порядок кнопок — тот, что пришёл в массиве; мокап задаёт эталонный порядок Яндекс → Google → GitHub.

Вёрстка карточки — значения из мокапа (строки 392–408, 914–938):

- карточка: `w-full rounded-xl border border-border bg-card p-7 text-card-foreground` + `style={{ boxShadow: "var(--shadow-input)" }}` (28px паддинг, радиус `--radius-xl` = мокапный `calc(var(--radius)*1.4)`);
- заголовок «Вход» / «Регистрация» — `font-serif text-[22px] font-semibold tracking-[-0.01em]`; подзаголовок — `mt-[3px] text-[13px] text-muted-foreground` с текстами мокапа;
- поля — `flex-col gap-2.5 mt-[18px]`, shared `Input` с `placeholder` и `autoComplete` из мокапа (`username`, `current-password`, `new-password`), автофокус на имени;
- ошибка — `ErrorCard` из `shared/ui/StateScreen` без `onRetry`, с уплотнением до мокапных значений через `className` (`px-3.5 py-2.5 text-[13px]`);
- сабмит — `Button size="lg" type="submit" className="w-full"`, подпись «Войти» / «Создать аккаунт»; при `submitting` — `disabled` и подпись «…» (типографское многоточие, как в мокапе);
- разделитель «или» — строка с двумя `h-px flex-1 bg-border` и `text-xs text-muted-foreground`, `my-4`, `gap-3`;
- провайдеры — `flex-col gap-2` из `ProviderButton`, `disabled={submitting}`;
- переключатель режима — `Button variant="link"` (у него уже `text-primary` + hover-подчёркивание) на всю ширину, `mt-3.5`, тексты «Нет аккаунта? Зарегистрироваться» / «Уже есть аккаунт? Войти».

Семантика и доступность: корень карточки — `<form onSubmit>`, чтобы Enter в поле отправлял форму; кнопка переключения режима — `type="button"` (иначе она сабмитит форму); поля получают `id` + связанный `<label className="sr-only">` либо `aria-label` — плейсхолдер не является доступным именем.

## Open Questions

1. **Хардкод фирменных цветов провайдеров против запрета hex в `.tsx`.** `design-system.md` § Границы формулирует правило абсолютным («Хардкод hex/rgba в `.tsx` запрещён, статический греп — часть quality-gate»), а брендовые знаки Google и Яндекса по определению не выражаются токенами темы: их палитра задана гайдлайнами провайдеров и одинакова в обеих темах. План по умолчанию делает inline-SVG в `ProviderButton.tsx` с комментарием-обоснованием (GitHub при этом идёт на `currentColor`, без своих цветов). Альтернатива — вынести знаки в `shared/assets/` файлами и импортировать как ассеты: правило остаётся буквально ненарушенным, но появляется третье место хранения бренд-графики (после `Wordmark`-кодом и иллюстраций-картой). Нужно решение архитектора: санкционировать исключение в коде (и, вероятно, дописать его в § Границы фазой DOC_UPDATE) или уводить знаки в ассеты.
2. **Копирайт экрана помечен в мокапе как черновой** («Копирайт черновой — финал согласуется при реализации», мокап, строка 898). План берёт все тексты буквально из мокапа — заголовки «Вход»/«Регистрация», подзаголовки, «Войти»/«Создать аккаунт», подписи провайдеров, тэглайн «Учитесь со своим ИИ-наставником…», тексты валидации в JSDoc. Если у архитектора есть финальные формулировки — момент их дать сейчас, до реализации; иначе мокапный текст становится продуктовым.
3. **Поведение ниже `lg` мокапом не определено.** Мокап показывает только широкую композицию (1fr + 440px). Дефолт плана — скрывать брендовую колонку и оставлять карточку с уменьшенным wordmark над ней. Это дизайнерское решение вне утверждённого мокапа: прошу подтвердить либо назначить другое (например, оставлять сцену над карточкой в уменьшенном размере).
4. **Временная обвязка для живой сверки (фаза T6.4).** Чтобы увидеть экран сегодня, нужен временный dev-вход вне закрытого списка файлов (html + мини-`tsx` в `frontend/`), удаляемый до коммита. Формально это файлы вне партиции — по духу правила («не править чужое/ничейное») нарушения нет, так как файлы новые, никем не владеемые и не доживают до коммита. Прошу подтвердить; при отказе фаза T6.4 сводится к статической сверке значений, а живой визуальный контроль экрана переходит к архитектору на pre-commit gate.

## Резолюции оркестратора

Все четыре вопроса закрыты без эскалации: каждый имеет ровно одну интерпретацию, не противоречащую конвенциям и утверждённому мокапу. Пункт 1 дополнительно выносится архитектору на pre-commit gate — как уточнение границы правила, а не как блокер.

1. **Брендовые hex провайдеров разрешены внутри inline-SVG знаков, с комментарием.** Запрет хардкода цветов (`conventions/frontend.md` § Дизайн-токены, `design-system.md` § Границы) защищает **палитру продукта**: цвет продукта обязан темизироваться и жить в одном месте. Фирменный знак чужого бренда — не палитра продукта: он одинаков в обеих темах, задан владельцем бренда и не имеет права меняться вместе с нашей темой. Заводить под него токены значило бы притворяться, что мы можем его перекрасить. Условие: цвета живут только внутри SVG-знака провайдера, рядом стоит комментарий «фирменные цвета бренда, не палитра продукта, темизации не подлежат»; ни одна другая часть auth-экрана hex не получает. Кандидат в конвенцию (явное исключение по образцу `sonner.tsx`) уходит в harvest — решение о правке `design-system.md` за архитектором.
2. **Тексты берутся из мокапа буквально.** Мокап утверждён архитектором целиком (коммит `6b2b577`), пометка «черновой копирайт» относится к процессу его сборки, а не к статусу утверждённого файла. Финальных формулировок сверх мокапа нет — выдумывать свои нельзя; расхождение с мокапом было бы отступлением от утверждённого дизайна.
3. **Поведение ниже `lg` — по дефолту плана**: брендовая колонка скрывается, wordmark уменьшённым уезжает над карточкой. Мокап этот брейкпоинт не покрывает, но решение единственное, не противоречащее ему: карточка формы остаётся носителем функции, иллюстрация — украшением, которое на узком экране уступает место. Зафиксировать в summary как решение сверх мокапа, чтобы архитектор увидел его на гейте.
4. **Временная dev-обвязка для живой сверки разрешена** — с теми же условиями, на которых её уже применял трек T1 в фазе T1.2: файлы создаются вне закрытого списка, не индексируются, удаляются до сдачи фазы, а в отчёте приводится, что именно замерено. Визуальную сверку в обеих темах провести обязательно: у компонента сегодня нет потребителя, и без неё трек сдаётся вообще без визуального контроля.

## Правки по plan-review (внесены оркестратором, обязательны к исполнению)

Ревью плана свежим агентом: blocker — 0, nit — 4, question — 1. Покрытие блока 8 и раскладка под merge feat-008 подтверждены; ниже — уточнения. **При расхождении с телом фаз приоритет у этой секции.**

1. **`providers` различает «провайдеров нет» и «гео ещё не известно».** Это единственный шов, на котором feat-008 могла бы упереться в необходимость переписать компонент — а вся форма трека выбрана ради того, чтобы ей этого не пришлось. Состав приходит из запроса, значит на первом рендере он неизвестен; при нынешнем контракте (`providers: readonly AuthProvider[]`, пустой массив → блок не рисуется) карточка отрисуется без кнопок и разделителя, а затем они выпрыгнут. Итог: тип становится `providers?: readonly AuthProvider[]`, где `undefined` — «ещё загружается» (место под блок зарезервировано, чтобы не прыгало), а **пустой массив** — «провайдеров нет, блок и разделитель „или“ не рисуются». Семантику обоих значений записать в JSDoc — его читает feat-008.

2. **Поле пароля отдаёт `autoComplete` по режиму, а не буквально из мокапа.** Мокап статичен и потому всегда несёт `current-password`; буквальный перенос дал бы в режиме регистрации неверную подсказку менеджеру паролей — он предложил бы подставить существующий пароль вместо генерации нового. Это тот случай, где «буквально из мокапа» тиражирует ограничение мокапа, а не решение дизайна. В `mode="register"` — `new-password` (и у поля подтверждения тоже), в `mode="login"` — `current-password`. Отступление от буквы мокапа отметить строкой в summary.

3. **Знак GitHub красится брендовыми значениями мокапа, а не наследует цвет текста.** Мокап задаёт ему собственное правило (`#24292f` в светлой теме, `#f0f0f0` в тёмной); план заменял это на `currentColor`, из-за чего знак получил бы тёплый `--card-foreground` вместо холодного фирменного — и подавал подмену как эквивалентность. Резолюция 1 брендовые цвета внутри знака уже разрешает, так что бери значения мокапа для обеих тем. (Заодно: внутри карточки цвет наследуется от `text-card-foreground`, а не `text-foreground` — план тут неточен.)

4. **Два отступления от буквы брифа признать в summary, не пряча их.** Первое: геометрия карточки ошибки уплотняется под auth-экран (`px-3.5 py-2.5 text-[13px]`) — мокап это поддерживает инлайновым стилем, но это единственное место в итерации, где карточка отличается от канона блока 4; архитектор должен увидеть отступление на гейте и решить, канон это или исключение auth-экрана. Второе: радиус карточки — `--radius-xl` (×1.4) по мокапу, тогда как бриф обобщённо писал `--radius`. Обе строки — в `## Решения и обоснования`, чтобы на гейте они не читались как самодеятельность.
