# Test Cases: feat-013 — UI/UX polish / трек T6

Трек T6 делает первый экран продукта брендовым: вместо generic shadcn-модалки появляется полноэкранная композиция «wordmark + тэглайн + сцена «Электрик» + карточка формы + кнопки провайдеров». Особенность трека в том, что **у экрана сегодня нет потребителя**: страницу `/login` строит параллельная итерация feat-008, а `pages/login` этот трек не трогает. Поэтому главный продукт трека — не пиксели, а **контракт props `LoginScreenView`**, по которому feat-008 подключит свою логику после merge. Автотесты страхуют ровно его: если feat-008 передаст пропы по документированной семантике, экран обязан вести себя предсказуемо — в этом вся ценность набора, и другой страховки у контракта нет, пока потребитель не появился.

Компонент чисто презентационный: ни запросов, ни роутинга, ни чтения гео, ни валидации — всё приходит через props. Сети в скоупе нет, MSW не нужен. Граница авто/ручное здесь проходит резко: **jsdom не исполняет CSS** — он не считает раскладку, не резолвит токены, не применяет `dark:`- и `lg:`-варианты Tailwind. Живую сверку экрана с мокапом по числам (`getComputedStyle`/`getBoundingClientRect`, обе темы, оба режима, оба гео-состава, оба граничных состояния `providers`, узкий вьюпорт) трек уже провёл в фазе T6.4 — расхождений не найдено; её значения перечислены в `summary.md`. Изображать это покрытие ассертами на классы бессмысленно, поэтому весь визуальный слой ушёл в ручные кейсы `{T6.1}`–`{T6.8}` честно, а не декорацией. Поведенческих изменений на существующих экранах трек не вносит: `AuthGate.tsx`, `router.tsx`, `pages/**` не тронуты ни строкой.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры** (применять, если итерация их касается): `📊` — проверка наблюдаемости; `🔴` — проверка реальных инъекций / атак; `[auto]` — кейс закрыт автотестом (живёт рядом со слайсом); `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия инвалидации) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода обязателен (см. ре-верификацию).

**Ре-верификация.** Правка кода аннулирует прошлый зелёный статус затронутого. После фиксов: детерминированный гейт (`make check-fe`/`make test-fe`) — перепрогон всегда; ручные/UI-кейсы — перепрогон только затронутой области. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Наблюдаемость этого трека — DevTools: `Computed` (вычисленные стили и цвета), панель Elements, переключатель темы приложения, изменение ширины окна. Код тестировщик не правит: прод-баги, вскрытые кейсом, чинит **fixer** (A6: fixer ≠ автор теста).

**Скоуп по трекам.** Кейсы с префиксом трека (`{T6.1}`) гоняются на своём треке + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST (`{track_id}=final`). Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс (тестировщик поднимает стенд сам)

1. Фронт: `make dev-fe`. Backend для кейсов трека не нужен — экран не ходит в сеть.
2. **Стенда у экрана нет, и владелец ручного хвоста назначен явно (резолюция оркестратора по находке R3).** `pages/login` принадлежит feat-008 и в `develop` пока не появился, `AuthGate` трек не трогает — значит `LoginScreenView` не смонтирован ни на одном маршруте. Поэтому **`{T6.1}`–`{T6.8}` гоняет тестировщик на фазе INTEGRATION_TEST через временную dev-обвязку** — это не «по возможности», а назначенный путь прохождения: html + мини-`tsx` в корне `frontend/`, монтирующие компонент с локальным `useState` под контракт props, начальное состояние (`mode`, `providers`, `error`, `submitting`, `dark`) читается из query-строки, так что каждый сценарий открывается прямым URL. Рецепт, включая грабли с HMR-ремаунтом, — `summary.md` § T6.4; обвязка лежит вне закрытого списка файлов трека и удаляется сразу после прогона, `git status` проверяется на чистоту.
3. **Живая сверка T6.4 приёмкой не считается.** Её делал имплементер трека, а по A6 автор кода не принимает собственную работу: её замеры (`summary.md`, § T6.4) — вход для тестировщика (что именно смотреть и какие числа ожидать), а не готовый зелёный статус кейсов. Ставить `{T6.1}`–`{T6.8}` в `[x]` со ссылкой на неё нельзя.
4. Прогон сверху вниз в **обеих темах** (класс `.dark` на `<html>`) — все кейсы трека темозависимы.
5. После прогона — сводка (pass / failed / **deferred**). Deferred — отдельным счётчиком с причиной по каждому кейсу, чтобы архитектор видел хвост на ручную добивку.

## Дизайн автотестов

**Покрываем автотестом** — по одной записи на суиту (тест-файл):

### `LoginScreenView.test.tsx` — контракт стыка с feat-008

1. **Файл**: `frontend/src/features/auth/ui/LoginScreenView.test.tsx` — integration (экран целиком под RTL вместе с `AuthLayout`, `ProviderButton` и shared-примитивами; без сети и провайдеров — компонент в квери не ходит, шва для MSW здесь нет).
2. **Тестирует**: `features/auth :: LoginScreenView` — импорт идёт **через публичный API слайса** (`@/features/auth`), а не через файл компонента: feat-008 увидит ровно то, что отдаёт `index.ts`, и суита краснеет, если из барреля пропадёт компонент или тип контракта.
3. **Суть**: Суита проверяет каждый проп контракта по его документированной семантике — то есть страхует ровно тот интерфейс, по которому параллельная итерация будет подключать логику к экрану, которого она не видела. Она фиксирует, чем различаются режимы входа и регистрации (заголовки, подзаголовки, третье поле, подпись сабмита, текст переключателя) и что переключатель зовёт `onModeChange` с противоположным режимом, не отправляя при этом форму. Она сторожит подсказки менеджеру паролей: в регистрации оба поля пароля просят `new-password`, во входе — `current-password`; это осознанное отступление от статичного мокапа (plan-review п.2), и молча вернуться к букве мокапа оно не должно. Она проверяет, что экран полностью контролируемый: значения приходят из `values`, каждый ввод уходит наружу через `onFieldChange` с именем поля, а `onSubmit` вызывается даже на пустой форме — экран сам ничего не валидирует и кнопку по пустым полям не блокирует. Отдельно закрыт `submitting`: поля, сабмит и кнопки провайдеров блокируются, подпись сабмита сменяется на многоточие, повторный клик до потребителя не доходит. Ядро суиты — **гео-состав провайдеров**: три состояния `providers` различаются наблюдаемо (`undefined` — разделитель «или» и плашка-резерв без кнопок; `[]` — ни разделителя, ни блока; непустой массив — кнопки строго в порядке состава), утверждённая гео-модель проверяется обоими составами (РФ — только Яндекс ID, вне РФ — Яндекс ID, Google, GitHub), а **отсутствие VK ID** сторожится во всех четырёх состояниях сразу: это требование 149-ФЗ и решение архитектора, и его молчаливая отмена — главный риск этого блока. Замыкают набор клавиатурные обещания: автофокус в поле имени, отправка по Enter, обход табом в порядке чтения. Отдельный кейс сторожит **брендовую половину экрана**: `LoginScreenView` обязан быть собран из `AuthLayout`, а не быть одной карточкой формы, — иначе wordmark, тэглайн и сцену `auth-hero` можно молча вынести (или подменить форком с теми же подписями формы), и суита, смотрящая только внутрь `<form>`, промолчит; брендовость же и есть предмет трека. Наблюдаются DOM-факты, которые jsdom исполняет, — сцена по доступному имени и текст дефолтного тэглайна, — геометрия остаётся ручной. Отсутствие карточки ошибки проверяется **переходом**, а не чистым рендером: у `ErrorCard` нет ни роли, ни `data-slot`, поэтому «карточки нет» в первом рендере неотличимо от «карточка есть, но пустая»; кейс берёт узел карточки с текстом, снимает `error` через `rerender` и требует, чтобы узел ушёл из документа.
4. **Кейсы**:
   - режим `login`: заголовок «Вход», подзаголовок, два поля, подпись сабмита «Войти», поля подтверждения нет
   - режим `register`: заголовок «Регистрация», подзаголовок, поле «Повторите пароль», подпись «Создать аккаунт»
   - переключатель зовёт `onModeChange` с противоположным режимом (таблица через `it.each` — обе стороны)
   - переключение режима не отправляет форму (кнопка внутри `<form>`)
   - `login`: имя — `username`, пароль — `current-password`
   - `register`: пароль и подтверждение — `new-password`
   - ввод в каждое из трёх полей зовёт `onFieldChange(<поле>, <значение>)`
   - поля показывают значения из `values`, а не собственное состояние
   - автофокус стоит в поле имени
   - клик по сабмиту на пустой форме зовёт `onSubmit` один раз; кнопка при этом активна, своей ошибки экран не рисует
   - Enter в поле отправляет форму
   - `submitting`: поля, сабмит и провайдеры заблокированы, подпись сабмита — «…», клик не доходит до `onSubmit`
   - `error` рисуется карточкой; после снятия `error` (`undefined` / `null` / пустая строка) узел карточки уходит из документа — проверка переходом через `rerender` (таблица через `it.each`)
   - РФ (`["yandex"]`) — ровно одна кнопка, Яндекс ID; разделитель «или» на месте
   - вне РФ — три кнопки в порядке Яндекс → Google → GitHub (проверяется и состав, и порядок)
   - **VK ID не предлагается ни в одном из четырёх состояний `providers`** — ни кнопкой, ни текстом (таблица через `it.each`)
   - клик по кнопке провайдера зовёт `onProviderSelect(<провайдер>)` и не отправляет форму
   - `providers === undefined`: разделитель есть, кнопок нет, место занято плашкой-резервом
   - `providers === []`: ни разделителя, ни блока, ни плашки
   - экран собран из брендовой рамки: сцена `auth-hero` (по доступному имени) и дефолтный тэглайн на месте
   - обход табом: имя → пароль → сабмит → провайдеры → переключатель режима
   - `className` доезжает до корня экрана *(класс — контракт, см. ниже)*

   **Состав кнопок провайдеров считается исключением, а не белым списком.** Хелпер `providerButtonNames()` берёт все кнопки экрана и вычитает собственные кнопки формы (сабмит в трёх подписях — обе режимные и «…» на время отправки — плюс переключатель режима). Отбор по списку известных подписей молча прятал бы лишнюю кнопку с незнакомым текстом, и «состав» читался бы как «эти в таком порядке среди известных» вместо «ровно эти».

### `ProviderButton.test.tsx` — кнопка входа через провайдера

1. **Файл**: `frontend/src/shared/ui/ProviderButton.test.tsx` — integration (компонент целиком под RTL, без сети).
2. **Тестирует**: `shared/ui/ProviderButton.tsx :: ProviderButton, AuthProvider`
3. **Суть**: Суита закрепляет доступное имя кнопки для каждого из трёх провайдеров — фирменные формулировки мокапа «Войти с Яндекс ID» / «Войти через Google» / «Войти через GitHub», которые потребитель не задаёт и не видит, пока они не разъедутся. Она же проверяет, что знак провайдера присутствует в разметке и скрыт от скринридера: подпись рядом уже называет провайдера, и дублировать его безымянной графикой нечем — это DOM-факт, который jsdom как раз исполняет, в отличие от цвета знака. Дальше идут обещания кнопки потребителю: переданный `label` вытесняет фирменную подпись, `className` доезжает до корня (потребитель сажает кнопку в свою геометрию, не форкая её), клик зовёт `onClick` ровно один раз, `disabled` гасит и вид, и клик, а внутри `<form>` кнопка форму не отправляет — иначе на auth-экране клик по «Войти через GitHub» отправил бы форму логина. Состав союза `AuthProvider` сторожит не рантайм-ассерт, а `tsc`: таблица подписей объявлена как `Record<AuthProvider, string>`, поэтому четвёртый провайдер (в том числе возвращённый VK ID) не проедет `make check-fe`, а исчезнувший третий — тоже.
4. **Кейсы**:
   - три провайдера объявляют свои фирменные подписи (таблица через `it.each`)
   - у каждого провайдера знак есть в разметке и несёт `aria-hidden="true"` (таблица через `it.each`)
   - переданный `label` вытесняет фирменную подпись
   - клик зовёт `onClick` ровно один раз
   - `disabled`: кнопка неактивна, клик до `onClick` не доходит
   - кнопка не отправляет форму, в которой стоит
   - `className` доезжает до корня кнопки *(класс — контракт, см. ниже)*

### `AuthLayout.test.tsx` — брендовая рамка auth-страницы

1. **Файл**: `frontend/src/shared/ui/AuthLayout.test.tsx` — integration (компонент целиком под RTL).
2. **Тестирует**: `shared/ui/AuthLayout.tsx :: AuthLayout`
3. **Суть**: Суита проверяет контракт обёртки, которую feat-008 может взять и напрямую, минуя `LoginScreenView`: слот `children` доходит до DOM нетронутым (карточка формы остаётся формой со своими кнопками), тэглайн имеет утверждённый мокапом дефолт и перекрывается своим, сцена `auth-hero` рисуется с подписью для скринридера и резолвится в собственный ассет, а `className` доезжает до корня — потребитель сажает рамку в свою геометрию, не форкая компонент. Раскладку двух колонок и поведение ниже брейкпоинта суита не трогает: этого jsdom не исполняет.
4. **Кейсы**:
   - слот `children` доходит до DOM как есть
   - без своего тэглайна показывается дефолтный текст мокапа
   - переданный тэглайн вытесняет дефолт
   - сцена `auth-hero` рисуется с `alt` и резолвится в путь своей сцены
   - `className` доезжает до корня *(класс — контракт)*

**Про ассерты на класс.** Конвенция запрещает ассертить `className` там, где проверяется поведение, — и в этих трёх суитах поведение везде проверяется запросами по роли, ярлыку и тексту. Ассертов на класс ровно три, по одному на каждый компонент скоупа (`className` → корень `LoginScreenView`, корень `AuthLayout`, корень `ProviderButton`), и в них класс **и есть** наблюдаемый контракт: проп существует затем, чтобы потребитель (`pages/login` из feat-008) задал компоненту свою геометрию, а иначе проброс не наблюдаем вовсе. Плашка-резерв при `providers === undefined` ищется по `data-slot="skeleton"` — маркеру примитива, а не по классу оформления. Ни один из этих ассертов не подменяет визуальную проверку: реальные цвета, отступы, радиусы и высоты живут в ручных кейсах ниже.

**Мутационная проверка сторожей** (§ Целостность тестов). Прогон точечный (`npx vitest run src/features/auth src/shared/ui`), каждая мутация откатывалась **точечной правкой**, не `git checkout` (ветка общая с параллельными треками T2/T3/T4); прод-код после прогона побайтово исходный, `prettier --check` на трёх файлах трека чист. Записи про `{true && …}`, вынос `AuthLayout` и лишнюю кнопку провайдера — перепрогон после правок по находкам ревью R1, R2 и R6; счёт VK-мутанта после R6 пересчитан там же.

- `LoginScreenView.tsx:112`, `autoComplete` по режиму → жёстко `"current-password"` → покраснел ровно 1 кейс, и это «в режиме регистрации просит менеджер паролей сгенерировать новый».
- **Обратная мутация того же признака**: → жёстко `"new-password"` → покраснел ровно 1 кейс, «в режиме входа подсказывает менеджеру паролей существующий пароль». Обе половины режимного признака сторожатся симметрично.
- `LoginScreenView.tsx:197`, тристейт `providers`: `(providers === undefined || providers.length > 0)` → `providers !== undefined && providers.length > 0` (загрузка гео перестаёт резервировать место) → покраснел ровно 1 кейс, «пока гео грузится, держит место под блок провайдеров».
- **Обратная мутация тристейта**: `providers.length > 0` → `providers.length >= 0` (пустой состав начинает рисовать разделитель) → покраснел ровно 1 кейс, «при пустом составе не рисует ни разделитель, ни блок провайдеров». Оба граничных значения различаются наблюдаемо, а не на словах.
