# Post-implementation summary: feat-009 / трек T1

## T1.1: Автосписок файлов скилла в ответе `load_skill` без `file`

Реализовано в `backend/app/agent/tools/skills.py`:

- Хелпер `_list_skill_files(skill_dir: Path) -> list[str]` — рекурсивный обход директории скилла (`Path.rglob("*")`), фильтрует только файлы, исключает `SKILL.md` (сравнением относительного пути с `Path("SKILL.md")`, то есть только сам корневой файл скилла) и dotfiles (любой сегмент относительного пути, начинающийся с `.`). Возвращает отсортированный список путей в POSIX-нотации (`as_posix()`) относительно директории скилла.
- В теле `load_skill` (ветка без `file` — параметр `file` ещё не существует, он добавится в T1.2) после чтения `SKILL.md` вызывается `_list_skill_files(skill_path.parent)`. Если список пуст — возвращается исходное содержимое без изменений. Если не пуст — дописывается футер по формату design-brief: `\n\n---\nSkill files (load with load_skill(skill_name, file)):\n- <path>` (по одной строке на файл).

Проверено вручную (скрипт с временными директориями, не автотест — автотесты вне scope фазы): многофайловый скилл с вложенной поддиректорией и dotfile-файлом даёт корректный отсортированный список без `SKILL.md`/`.hidden`; однофайловый скилл (`structure`-подобный) — ответ не меняется, футер не появляется.

## T1.2: Параметр `file` — загрузка модуля скилла с защитой от path traversal

Реализовано в `backend/app/agent/tools/skills.py`:

- Сигнатура `load_skill` расширена до `load_skill(skill_name: str, file: str | None = None) -> str`. Докстринг переписан под обе формы вызова (`load_skill(skill_name)` / `load_skill(skill_name, file)`), включая когда использовать вторую форму (после получения футера из первой) — по нему LLM строит вызовы.
- Существующая ветка валидации `skill_name` и чтения `SKILL.md` не изменена по поведению; из неё вынесен `skill_dir = skill_path.parent`, переиспользуемый в обеих ветках (`file is None` / `file` задан).
- Ветка без `file` (было в T1.1) перенесена как есть под `if file is None:`, без изменения логики.
- Ветка с `file`:
  - Первый слой валидации — новый модульный хелпер `_is_safe_relative_path(file: str) -> bool` и константа `_SAFE_PATH_SEGMENT_RE = re.compile(r"^[A-Za-z0-9_.-]+$")`. Путь режется по `/`, каждый сегмент проверяется на непустоту, не равен `"."`/`".."`, и соответствует safe-паттерну; пустая строка и путь, начинающийся с `/` (абсолютный), отклоняются до цикла по сегментам.
  - Второй слой — `(skill_dir / file).resolve()` + `is_relative_to(skill_dir)` (симметрично существующей проверке `skill_path` относительно `skills_dir.resolve()`).
  - Файл не найден → `_list_skill_files(skill_dir)` переиспользован, ошибка в формате «file '<file>' not found in skill '<skill_name>'. Available files: <list>» (пустой список → `(none)`), по образцу существующей «skill not found → available skills».
  - Бинарный файл — `file_path.read_text(encoding="utf-8")` в `try/except UnicodeDecodeError`, ошибка «file '<file>' is a binary file, cannot load as text.».

Проверено вручную (временная директория со скиллом, вложенной поддиректорией, `.py`-модулем, бинарным файлом и dotfile'ом — не автотест, автотесты вне scope фазы): happy path верхнего уровня и поддиректории; `../escape`, `/etc/passwd`, `sub/../../outside` — все три формы traversal отклонены на первом слое (`_is_safe_relative_path`); несуществующий файл — ошибка со списком реальных файлов скилла; бинарный файл — ошибка про binary; вызов без `file` — поведение T1.1 не изменилось (автосписок, dotfile исключён).

## Решения и обоснования

- **Критерий исключения `SKILL.md`.** Design-brief говорит «исключается сам SKILL.md» — реализовано как сравнение относительного пути с `Path("SKILL.md")`, то есть исключается только корневой файл скилла, а не любой файл с таким именем на любом уровне вложенности. Скилл принципиально имеет ровно один `SKILL.md` в своём корне (по контракту загрузки — `skills_dir / skill_name / "SKILL.md"`), так что различие между «только корневой» и «любой уровень» здесь не наблюдаемо на практике, но более узкая трактовка точнее соответствует формулировке брифа и не удаляет случайно файл с тем же именем во вложенной поддиректории, если такой появится.
- **Критерий dotfiles.** Реализовано как проверка «любой сегмент относительного пути начинается с `.`», а не только имя файла. Это исключает не только dotfiles на верхнем уровне, но и файлы внутри dot-директорий (например, гипотетический `.git/config` внутри скилла) — консервативнее буквальной формулировки брифа («dotfiles»), но не противоречит ей: явных модулей скилла с dot-директориями в контракте нет, а дополнительная защита от кейса, который бриф не рассматривал явно, не меняет наблюдаемое поведение для реальных скиллов проекта.
- **Формат путей — `as_posix()`.** Список файлов относительный и должен быть стабилен и переносим (загружается через `load_skill(skill_name, file)` в T1.2, где путь снова станет строкой). POSIX-разделитель `/` соответствует примеру из брифа (`sub/a.py`-подобные пути) и не зависит от ОС выполнения — хотя рантайм всегда Linux, `as_posix()` явно фиксирует формат вместо неявной зависимости от `os.sep`.
- **Место хелпера в файле.** `_list_skill_files` размещён между `load_skill`/`make_load_skill_tool` и `_list_available`, рядом с существующими module-level хелперами (`_list_available`, `scan_skills_index`, `_parse_frontmatter`) — по указанию плана «добавить хелпер... рядом с существующими». Функция module-level (не замыкание внутри `make_load_skill_tool`), так как не держит состояния и не нуждается в `skills_dir` из closure — принимает директорию конкретного скилла параметром, симметрично `_list_available`.
- **Не добавлен параметр `file`.** Явно вне scope T1.1 (это T1.2) — сигнатура `load_skill(skill_name: str)` не менялась, докстринг не менялся (актуализация докстринга под обе формы вызова — тоже T1.2 по плану).
- **Отвергнутый вариант:** использовать `Path.walk()` (Python 3.12+) вместо `rglob("*")`. `rglob("*")` проще (одна строка обхода + фильтр `is_file()`), не требует дополнительной сортировки директорий на каждом уровне (сортировка всё равно применяется к финальному плоскому списку через `sorted()`), и не вводит по-новому используемый в файле API — в остальном коде модуля обходов директорий уже используется `iterdir()`/`sorted(...)` (в `_list_available`, `scan_skills_index`), `rglob` — минимальный шаг в сторону от уже принятого стиля.
- **Safe-паттерн сегментов пути — allowlist символов, не blocklist подстрок.** `_SAFE_PATH_SEGMENT_RE = re.compile(r"^[A-Za-z0-9_.-]+$")` разрешает только буквы, цифры, `_`, `-`, `.` в каждом сегменте (после разбиения по `/`), плюс отдельная проверка `segment not in ("", ".", "..")`. Design-brief требует «safe-паттерн по сегментам пути отклоняет абсолютные пути и `..`» — allowlist-паттерн (симметричный `_SKILL_NAME_RE`, уже принятому в модуле стилю для `skill_name`) закрывает это перечислением допустимого, а не попыткой перечислить все опасные конструкции (`..`, `%2e%2e`, null-байты и т.п.) блок-листом. Абсолютный путь отклоняется отдельной проверкой `file.startswith("/")` до разбиения на сегменты, так как ведущий `/` даёт первый сегмент `""`, который и так отклонён бы проверкой на пустоту — но явная проверка делает намерение читаемым и не зависит от порядка проверок.
- **Разбиение по `/`, не `Path(file).parts`.** Первый слой работает со строкой `file` до создания `Path`, разбивая её `str.split("/")`, а не через `PurePath(file).parts`. Так `Path`-конструирование остаётся исключительно за вторым слоем (`(skill_dir / file).resolve()`), где `resolve()` обязателен по контракту, — первый слой не тянет pathlib-семантику там, где хватает строковой операции. Побочный эффект того же разбиения: двойной слэш (`a//b` → `['a', '', 'b']`) и ведущий/замыкающий слэш дают пустой сегмент, который отклоняется той же проверкой `segment not in ("", ".", "..")`, без отдельного случая.
- **`skill_dir = skill_path.parent` вместо повторного `(skills_dir / skill_name).resolve()`.** Design-brief формулирует второй слой как `resolve()` + `is_relative_to(skills_dir/skill_name)`. `skill_path` уже `.resolve()`-нут строкой выше (`(skills_dir / skill_name / "SKILL.md").resolve()`), а `skill_name` прошёл `_SKILL_NAME_RE` (только `[a-z0-9_-]`, без `/` и `..`) — поэтому `skill_path.parent` эквивалентен `(skills_dir / skill_name).resolve()` без второго вызова `resolve()`. Переиспользование убирает дублирование между веткой `file is None` (уже читала `skill_path.parent` в T1.1) и новой веткой с `file`.
- **Формат ошибки «file not found» — симметрия с «skill not found», а не идентичный текст.** Существующий паттерн: `f"Error: skill '{skill_name}' not found. Available skills: {available}"`, где `available` — уже готовая строка через `_list_available` (join с `", "`, `"(none)"` при пустом списке). Для файла применена та же форма: `f"Error: file '{file}' not found in skill '{skill_name}'. Available files: {available_files}"`, где `available_files` строится инлайн (`", ".join(skill_files) if skill_files else "(none)"`) без отдельного хелпера, поскольку `_list_skill_files` уже возвращает готовый `list[str]` (в отличие от `_list_available`, которая инкапсулирует и сбор, и форматирование в одну строку-хелпер) — заводить симметричный `_list_skill_files_display()` ради одной строки избыточно.
- **`UnicodeDecodeError`, не проверка сигнатуры/MIME-типа файла.** Design-brief: «канал tool-результата текстовый, поэтому не декодируемое как UTF-8 содержимое → ошибка». Контракт явно завязан на декодируемость UTF-8, а не на эвристику «похоже на бинарник» (null-байты, магические числа и т.п.) — `try: file_path.read_text(encoding="utf-8") except UnicodeDecodeError` реализует ровно это: файл читается один раз, ошибка декодирования перехватывается точечно (не широкий `except Exception`, чтобы не маскировать `OSError`/`PermissionError` и другие реальные проблемы файловой системы, для которых внятной обработки не требовалось по контракту).
- **Дока: детали алгоритма — да, устройство ошибок — нет.** В `agent-runtime.md` вынесены критерии, которые формируют наблюдаемое поведение агента при работе со скиллом (что исключается из автосписка, что делает автосписок робастным для progressive disclosure, из каких двух слоёв состоит защита `file`, что означает каждая ошибка) — это то, что нужно понимать, читая архитектуру рантайма, не заглядывая в код. Оставлено деталью реализации в `skills.py` (не упомянуто в доке): регэкспы дословно (`_SKILL_NAME_RE`, `_SAFE_PATH_SEGMENT_RE`), устройство `_list_skill_files`/`_is_safe_relative_path` как отдельных хелперов, точный текст сообщений об ошибках, выбор `rglob` vs `Path.walk()` — это меняется при рефакторинге без изменения архитектурного факта и без документационного долга, если останется только в коде.
- **Затронута секция Context Engineering, не только Tools/Skills System.** План называл явно только строку таблицы Tools и § Skills System, но таблица уровней контекста (§ Context Engineering) и её mermaid-диаграмма содержали ту же устаревшую формулировку («Полный SKILL.md» / `load_skill(skill_name)` без `file`) — тот же факт, что уже правился в двух других местах. Оставить её как есть значило бы создать несогласованность внутри одного документа сразу после правки. Расценено как дрейф, исправление которого «в рамках своего изменения» покрыто CLAUDE.md § Документация, а не расширение скоупа фазы: строка таблицы и подпись узла диаграммы переписаны в одном стиле с остальными правками, без новых структурных решений.
- **Docs-updater: фикс по review-b, nit 2 (`skills.py:104-118`, `_list_skill_files`).** Ревью отметило, что формулировка «исключает сам `SKILL.md` и dotfiles» в `agent-runtime.md` п. 3 (Loading) — надмножество факта: код исключает не только dotfiles-имена, но и любой файл внутри dot-сегмента пути (`any(part.startswith(".") for part in relative.parts)`), т.е. надмножество формулировки «dotfiles» (например, гипотетический `.git/config` внутри скилла). Расхождения контракта нет (всё, что бриф называет исключаемым, исключено), это была не ошибка, а менее точная формулировка — nit помечен как опциональный («точность ради точности, не долг»), но правка дешёвая (одна вставка в скобках) и убирает потенциальную будущую путаницу при чтении доки без кода. Применено: п. 3 дополнен уточнением «скрытым считается любой сегмент относительного пути, начинающийся с `.`, не только имя файла».
- **Фикс по review-a, nit A3 (`skills.py:68`).** Ветки отказа валидации пути `file` — невалидный путь по safe-паттерну первого слоя (`_is_safe_relative_path`) и выход за пределы директории скилла по второму слою (`is_relative_to`) — возвращали обобщённое `Error: invalid file path '<file>'.` без списка доступных файлов, в отличие от ветки «файл не найден», которая уже отдаёт `Available files: <list>`. Для LLM-агента это менее наводящая диагностика: столкнувшись с опечаткой в пути или случайным `../`, агент получал ошибку без подсказки, что грузить вместо этого. Исправлено симметрично с веткой not-found — обе отказные ветки теперь тоже вызывают `_list_skill_files(skill_dir)` и приклеивают `Available files: <list>` к тому же тексту `Error: invalid file path '<file>'.`. Секретность не нарушена: список — те же относительные имена файлов скилла, что и в футере `load_skill(skill_name)` и в ветке not-found; резолвнутые пути и внутренности `is_relative_to`-отказа по-прежнему не раскрываются. Синхронизирован `doc/tech/agent-runtime.md` (п. 4 Module loading): формулировка «Файл не найден → ошибка со списком» расширена до «Файл не найден, либо `file` отклонён валидацией пути → ошибка со списком... — единообразная наводящая диагностика для всех отказных веток», чтобы дока отражала новую механику, а не только ветку not-found.
