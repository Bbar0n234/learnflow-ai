# Test Cases: feat-009 — Многофайловые скиллы + перенос tech-article-writing / трек T2

Трек T2 переносит обкатанный discovery-скилл `tech-article-writing` из личной библиотеки
агента-разработчика (`~/.claude/skills/tech-article-writing/`) в продуктовую директорию
`skills/tech-article-writing/` — как первый многофайловый актив рантайм-библиотеки. Прод-кода
трек не содержит: это перенос контента (SKILL.md + 5 модулей) плюс сверка доменной конвенции
`description`. Механику загрузки (параметр `file`, автосписок) реализует T1 — тут она не проверяется
изолированно, только на стыке с перенесённым контентом (cross-cutting).

Кейсы страхуют **пять инвариантов переноса** из design-brief § «Перенос скилла» (правила 1–5):
методология переносится as-is (дифф против источника чистый, кроме обвязки из 7 нейтрализованных
мест); `author-voice/` не переносится; внутренние ссылки скилла живые; нет ссылок на `~/.claude/`
и абсолютных путей; frontmatter `description` соответствует конвенции. Плюс cross-cutting-приёмка
итоговых критериев приёмки итерации: скилл виден в Skills Index, `load_skill` отдаёт SKILL.md +
автосписок ровно 5 модулей, модули читаются по `file`, скилл проходим агентом в режиме B.

Проверяемый контракт трека берётся из design-brief, **не** из «как сделано»: кейсы сформулированы
против правил переноса, а не под фактическое состояние директории. Кейсы, уже доказанные при
реализации (см. `tracks/T2/summary.md`), сформулированы всё равно — tester прогоняет их независимо.

## Конвенции прохождения (инлайн — это рамка тестировщика)

**Статус и run-log.** У каждого кейса — текущий статус плюс опциональный run-log, если кейс прогонялся не раз:

- `- [x]` + лаконичный результат: что проверялось, что получилось, значимые нюансы. По заполненному чек-листу должно быть видно, что всё работает, без перепрохождения.
- `- [ ] ⚠️` + причина, если кейс не пройден или требует отдельного внимания.
- Кейсы с 👤 — требуют ручного действия / решения архитектора (UI, браузер); тестировщик помечает и эскалирует.
- **Доменные маркеры** (применять, если итерация их касается): `📊` — проверка наблюдаемости; `🔴` — проверка реальных инъекций / атак; `[auto]` — кейс закрыт автотестом (живёт в `tests/<scope>/`); `*(регресс)*` — кейс страхует «поведение не сломалось».
- **run-log** (только у перепрогнанных кейсов) — строка-история флипов с причиной:
  `runs: r1 ✅ → r2 ❌ (после фикса review #3) → r3 ✅`.
  Один прогон — run-log не нужен. Перепрогон после правки кода/контента обязателен (см. ре-верификацию).

**Ре-верификация.** Правка контента скилла или кода T1 аннулирует прошлый зелёный статус
затронутого. После фиксов: детерминированные grep/diff-кейсы — перепрогон всегда; агентский прогон
(режим B) — перепрогон при изменении SKILL.md/модулей. Каждый перепрогон → запись в run-log.

**Диагностика — через наблюдаемость, не догадки.** Один кейс — одна попытка диагностики: не сошлось — повтори (мог быть транзиент); не сошлось второй раз — fail + эскалация, без долгой отладки. Код тестировщик не правит: дефекты переноса, вскрытые кейсом, чинит **fixer** (не сам тестировщик).

**Скоуп по трекам.** Кейсы с префиксом трека (`{T2.1}`) гоняются на треке T2 + Layer 0; cross-cutting (Layer 2/3 без префикса) — в INTEGRATION_TEST (`{track_id}=final`), когда контент T2 и код T1 сойдутся за барьером. Не пропускать кейсы молча — неприменимый помечать причиной.

### Процесс

1. Для детерминированных кейсов трека (Layer 1) стенд не нужен — только рабочая копия
   репозитория: проверки — это `grep`/`diff`/`ls`/чтение файлов в `skills/tech-article-writing/`.
2. Кейс `{T2.5}` (дифф против источника) требует доступа к источнику переноса
   `~/.claude/skills/tech-article-writing/` на машине прогона. Источник доступен локально; в
   облачной сессии его может не быть — тогда кейс помечается deferred с причиной «источник
   недоступен» и добивается архитектором локально.
3. Cross-cutting-кейсы (Layer 2) прогоняются кодом T1 против контента T2. Repro — питон-сниппет из
   пакета `backend/` (функции `scan_skills_index` / `make_load_skill_tool` из
   `app.agent.tools.skills`), либо полный стенд `make docker-up` + реальный агентский чат.
4. Кейс режима B (Layer 3) — реальный агентский прогон через UI/чат: требует живого стенда и
   ручной оценки архитектора (👤).

## Дизайн автотестов

**У трека T2 автотестов нет — и это осознанно, по партиции треков.** T2 не содержит прод-кода:
его продукт — контент в `skills/tech-article-writing/**` и сверка доменной конвенции в
`doc/tech/conventions/agent.md`. По модели тестов (`testing.md` § Граница авто/ручное) автотесты
страхуют **поведение кода**; контент скилла — это данные, а не код с ветвлениями, I/O или
бизнес-логикой, поэтому unit/integration-тест на него ложится неестественно. Design-brief
(§ «Партиция треков», «Тесты») прямо фиксирует: автотесты пишет только T1 (в
`backend/tests/personalization/test_skills.py`), T2 автотестов не заводит.

Что вместо автотестов покрывает контракт T2:

- **Детерминированные команды** (`grep`/`diff`/`ls`) — инварианты переноса (правила 1–5
  design-brief): отсутствие `author-voice/`, отсутствие ссылок на `~/.claude/` и абсолютных путей,
  живость внутренних ссылок, чистота диффа против источника. Эти команды воспроизводимы и
  бинарны — не уступают автотесту в оракульности, просто не живут в `tests/`.
- **Cross-cutting-проверки на стыке с T1** — детерминированный вызов `scan_skills_index` и
  `load_skill` против реального контента (Skills Index, автосписок 5 модулей, чтение модуля по
  `file`). Сам код `load_skill` покрыт solitary-unit-тестами трека T1; здесь проверяется, что
  **перенесённый контент** правильно подхватывается этим кодом — это интеграция контента с кодом,
  а не второй набор unit-тестов загрузчика (дублировать тесты T1 в T2 запрещено партицией).
- **Агентский прогон в режиме B** — UX-приёмка проходимости скилла живым агентом. Это по природе
  ручной сквозной сценарий с оценкой качества (`testing.md`: «приёмка UX» — узкий ручной хвост),
  автотестом не покрывается принципиально.

**Осознанно НЕ покрываем автотестом:** ничего в скоупе T2 — автотестов у трека нет вовсе (см.
выше). Автопокрытие механики `load_skill` (happy path `file`, path traversal, бинарный файл,
автосписок без SKILL.md/dotfiles, no-footer для однофайловых скиллов) — целиком в скоупе T1;
кейсы ниже его не дублируют, а лишь проверяют стык кода T1 с контентом T2.

**Замеченные дефекты переноса (для fixer'а):** не обнаружено. Дифф против источника содержит
ровно 7 нейтрализованных мест обвязки (`author-voice/` → «профиль голоса пользователя»), 3 файла
из 6 байт-в-байт идентичны источнику, внутренние ссылки все живые, ссылок на `~/.claude/` и
абсолютных путей нет, `author-voice/` отсутствует. Состояние директории соответствует контракту
design-brief.
