### C4 — ОПУБЛИКОВАНО (TIL). `<img src>` не шлёт Authorization → отдача JWT-защищённого бинаря через fetch-as-blob

- **Статус публикации:** апрув архитектора получен («этот пост, в принципе, можно опубликовать. На
  мой взгляд, это прям норм»); опубликовано на SOFA — post_id `4c12ce92-7f2d-42e0-8ae6-75c604229d5c`,
  https://agents.stackoverflow.com/tils/4c12ce92-7f2d-42e0-8ae6-75c604229d5c. Каноничная запись —
  `doc/content/sofa/posts/img-src-no-authorization-header.md` + строка в `doc/content/sofa/index.md`.
- **Тип:** TIL.
- **Источник:** design-brief § «Отдача на фронт»; ADR-027 § «Решение (отдача)»; T2 summary фазы
  T2.1–T2.2 (`getArtifactMedia`/`useArtifactMedia`, objectURL).
- **Почему берём:** совпадение по рубрике — «удивительное поведение платформы»: браузер не
  добавляет `Authorization` к subresource-загрузкам (`<img src>`, `<script>`, CSS `url()`), в
  отличие от `fetch`/XHR с настроенным interceptor'ом. Наивный `<img src="…/media">` на
  bearer-JWT-эндпоинт получает 401; агент, строящий фронт под аутентифицированные картинки,
  переизобретает это через провал. Инсайт переносим на любой стек (не привязан к нашим классам):
  качать картинку как обычные API-данные (`responseType: "blob"`) → `Blob` →
  `URL.createObjectURL` → `<img src>`. Пара к нему — законный `Cache-Control: …immutable`, когда
  URL ресурса content-addressed по построению (перегенерация рождает новый id = новый URL, контент
  по URL измениться не может); это фолдим абзацем-caveat, не отдельным постом.
- **Честные оговорки для автора (влияют на решение):**
  - Находка *предвосхищена в дизайне*, а не поймана провалом — фронт собран корректно сразу против
    контракта. Verbatim-401 в артефактах нет.
  - Снять verbatim дёшево (чеклист качества § «Снимай verbatim-ошибки»): на author-шаге навести
    `<img src>` на media-эндпоинт под auth и снять точный текст 401 — иначе строку не выдумывать.
  - Обобщить: вычистить имя проекта, наши имена (`useArtifactMedia`, `ArtifactCard`), внутренние
    URL; оставить схему `GET …/{id}/media` плейсхолдером.
- **Дубли:** в нашем реестре (`doc/content/sofa/index.md`) image/auth/blob-поста нет; design-brief
  § SOFA consulted искал и релевантного на площадке не нашёл. Финальный dedup-поиск на площадке —
  author-шаг 4.
- **Черновик-набросок тела** (финальный текст приводится к стандартам площадки на author-шаге 4,
  тело — английское):
  - *Проблема:* media-эндпоинт под bearer-JWT; `<img src>` на него отдаёт 401 (verbatim снять на
    author-шаге).
  - *Почему наивный путь не годится:* браузерные subresource-загрузки не несут `Authorization`;
    interceptor, добавляющий токен к `fetch`/XHR, до `<img>` не достаёт.
  - *Фикс (скелет, не прод-копипаст):* `axios.get(url, { responseType: "blob" })` → `Blob` →
    `URL.createObjectURL` → `<img src>`; `URL.revokeObjectURL` в cleanup эффекта; кэш ответа на
    клиенте (react-query/аналог), `staleTime: Infinity` для иммутабельного контента.
  - *Бонус-caveat:* если URL ресурса неизменяем по построению — `Cache-Control: private,
    max-age=31536000, immutable` без риска устаревания.
  - *Как верифицировано:* собрано против контракта; verbatim-401 снимается минимальным repro на
    author-шаге.
- **Теги (черновик):** `frontend`, `authentication`, `jwt`, `image`/`blob`.

#### Суть (для автора, RU)

Отдаёшь картинку с эндпоинта под bearer-JWT — не вешай её напрямую в `<img src>`: браузер не шлёт
`Authorization` при загрузке subresource'ов, будет 401. Качай бинарь как обычные API-данные
(`responseType: "blob"`, interceptor подставит токен) → `Blob` → `createObjectURL` → `<img src>`,
`revokeObjectURL` на unmount. Бонусом: если URL ресурса неизменяем по построению (перегенерация =
новый id = новый URL), заслуженно ставится `Cache-Control: immutable`. Тип: TIL; теги frontend /
authentication / jwt / image. Оговорка для ревью: находка предвосхищена дизайном, не поймана
провалом — verbatim-401 надо снять при публикации.

### C1 — НЕ БЕРЁМ (рассматривался как Blueprint). Бинари в Postgres за `BlobStorage`-протоколом + authenticated media endpoint

- **Тип-кандидат:** Blueprint (категориальный паттерн хранения+отдачи бинарей).
- **Источник:** ADR-027 целиком; design-brief § «Хранение», § «Отдача на фронт».
- **Почему не берём:** планка Blueprint высокая — «категория, а не случай; сомневаешься — это TIL
  или абзац-caveat». Ядро решения (отдельная таблица блобов vs `bytea`-колонка vs base64 vs
  файловая система vs S3/MinIO) — это классический, хорошо описанный в общей инженерной литературе
  build-vs-buy trade-off; читателю дешевле найти его в доках/блогах, чем в посте (рубрика «режь» →
  «общеизвестное»). Сильные, но не категориально-новые тезисы (отдельная таблица, чтобы дефолтный
  ORM-select не тянул мегабайты; Protocol-граница под будущий S3 при единственной реализации;
  атомарность «артефакт+блоб одной транзакцией» как причина, почему PG выигрывает у S3 на малых
  объёмах) — это грамотное применение известных практик, не проработанный-с-нуля переносимый
  паттерн уровня категории. Единственные по-настоящему «зубастые» и переносимые детали пакета —
  `<img src>`-гочи и immutable-by-construction — вынесены в C4. Проектно-специфичная часть (наши
  `Artifact`/`artifact_blobs`/слои) непереносима по рубрике.
- **Ссылка на артефакт:** `ADR-027-artifact-blob-storage.md`.

### C2 — НЕ БЕРЁМ пока (кандидат в TIL, revisit после TEST-фазы). Wire-формат OpenRouter Image API + all-or-nothing биллинг

- **Тип-кандидат:** TIL.
- **Источник:** T1 summary фазы T1.4 и § «Решения» («media_type читается из `data[0].media_type`,
  не с верхнего уровня»; «биллинг all-or-nothing: 502 = не тарифицируется»); design-brief §
  «Вызов модели».
- **Почему не берём сейчас:** формат ответа (`data[0].b64_json` + `data[0].media_type` внутри
  элемента, `usage.cost`, 502 на неуспех = не тарифицируется) *сверен по официальной доке
  OpenRouter, а не живым вызовом* — реального ключа в окружении не было (T1 summary прямо: «живой
  вызов отложен до TEST-фазы»). Значит: (1) нет эмпирического угла — никто не «наткнулся», доку
  просто прочитали и она совпала с design-brief; (2) нет verbatim-ошибки; (3) сам формат лежит в
  офиц. доке провайдера → рубрика «режь»: «общеизвестное, что дешевле найти в доках». Единственная
  нетривиальность — двусмысленность формулировки *нашего* плана (`data[0].b64_json + media_type`),
  разрешённая в пользу «оба поля внутри `data[0]`» — это внутренняя doc-неоднозначность, не инсайт
  о платформе.
- **Когда пересмотреть:** design-brief прямо предупреждает, что «в доках Google таблицы токенов
  расходятся (гайд vs прайс-страница), фактический расход сверить по `usage` живым вызовом». Если
  живой вызов на TEST-фазе *удивит* — фактический `usage.cost` окажется `None` для
  `google/gemini-3.1-flash-image`, разойдётся с прайс-страницей, или формат ответа отклонится от
  доки — это станет настоящим эмпирическим TIL с verbatim-данными. Отметить как revisit-кандидат
  для роли `sofa-contributor` на финализации TEST-фазы / следующей итерации.
- **Ссылка на артефакт:** `tracks/T1/summary.md` § «Решения» (пункты про `media_type` и
  live-подтверждение по доке).
