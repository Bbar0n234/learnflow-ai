# Test Cases: feat-012 — Skill-scoped user context / трек T2 (Frontend)

Трек T2 добавляет на `/settings` секцию «Контекст скиллов»: пользователь видит свои
per-user документы, сгруппированные по скиллу, раскрывает документ в отрендеренный
Markdown-предпросмотр, правит сырой Markdown и сохраняет, удаляет документ. Создание из
UI не предусмотрено (документы рождает агент). Скилл, которого больше нет в библиотеке,
помечается бейджем, но данные и действия сохраняются.

Кейсы страхуют **новую фичу** и её контракт из design-brief (§ REST API — формы тел; § UI —
поведение секции) и мокапа. Автотесты — компонентная интеграция (компонент + хуки +
замоканная MSW сеть) против замороженного фундамента (`renderWithProviders`, `server`).
Ручной хвост — визуальное соответствие мокапу на обеих темах и прогон против живого backend
(появляется в INTEGRATION_TEST после барьера T1).

## Дизайн автотестов

**Покрываем автотестом** — по одной записи на суиту:

### `SkillContextSection.test.tsx` — секция «Контекст скиллов» на `/settings`

1. **Файл**: `frontend/src/pages/user-settings/ui/SkillContextSection.test.tsx` — компонентная интеграция (компонент + хуки TanStack Query + сеть через MSW), шов: `renderWithProviders` (свежий `QueryClient`, `retry:false`) + `server.use(...)`.
2. **Тестирует**: `pages/user-settings/ui/SkillContextSection :: SkillContextSection` (и через него — API-слой `shared/api/skill-context`: `useSkillContexts` / `useUpdateSkillContext` / `useDeleteSkillContext`).
3. **Суть**: Суита проверяет, что секция читает per-user листинг с `/users/me/skill-contexts`, группирует документы по скиллу и показывает счётчик, а пустой листинг (в том числе группа без документов) отдаёт как пустое состояние. Она гарантирует, что содержимое документа не попадает в DOM, пока строку не раскрыли, а при раскрытии рендерится именно Markdown, а не сырой текст. Она страхует контракт правки: редактор держит сырой Markdown, «Сохранить» шлёт PUT на пару `(skill, key)` с телом `{description, content}`, где `description` документа переносится неизменным, а меняется только `content`; «Отмена» откатывает без единого запроса; ответ 422 от security-checkpoint показывает то же сообщение, что «Свои инструкции», и оставляет пользователя в редакторе. Она проверяет, что «Удалить» шлёт DELETE на ту же пару и обновляет листинг, и что документы скилла, которого нет в библиотеке, помечены бейджем, но остаются полностью действующими (открываются, правятся, сохраняются).
4. **Кейсы**:
   - хинт загрузки, пока листинг в полёте;
   - пустой листинг → текст пустого состояния;
   - группа с пустым `documents` → пустое состояние, имя скилла не рендерится (страхует фильтр);
   - группировка по скиллу: имена скиллов, `key` + `description` документов, счётчик «N скилл(ов) · M документ(ов)»;
   - бейдж «скилла нет в библиотеке» при `in_library=false` и его отсутствие при `in_library=true` (ровно один бейдж на смешанном листинге);
   - прогрессивное раскрытие: контент отсутствует в DOM до клика, `aria-expanded` флипается `false→true`, Markdown отрендерен (заголовок без `#`), сырой `# …` не показан;
   - правка → «Сохранить»: редактор держит сырой Markdown; PUT-тело `{description: <исходное>, content: <изменённое>}`; путь `(skillName, key)`; по успеху редактор закрывается, обновлённый превью подхватывает свежий контент;
   - «Отмена»: возврат в превью с исходным контентом, PUT не отправлен;
   - 422 security-violation → `SECURITY_VIOLATION_MESSAGE`, пользователь остаётся в редакторе для правки и повтора;
   - «Удалить» → DELETE на `(skillName, key)` + рефетч листинга убирает группу (пустое состояние);
   - документ скилла с `in_library=false` открывается, правится и сохраняется наравне с остальными (данные переживают удаление скилла — фронтовая половина).

**Осознанно не покрываем автотестом** — триадой *что — почему — куда уехало*:

- Отдельная суита API-слоя `shared/api/skill-context.ts` — *почему*: функции и хуки уже прогоняются через компонентную интеграцию сквозь MSW (URL, path-params, тело PUT/DELETE, инвалидация листинга проверены на уровне поведения секции); отдельная solitary-суита дублировала бы то же без нового сигнала → покрыто суитой `SkillContextSection.test.tsx`.
- `encodeURIComponent` на сегментах пути `(skillName, key)` — *почему*: контракт design-brief не выделяет спецсимволы в именах скиллов/ключей как поведение секции (имена — kebab-case идентификаторы), а изолированная проверка кодирования была бы тестом реализации API-функции → мягкий гейт glue (адаптерная склейка URL), при появлении реального кейса со спецсимволами — отдельный кейс.
- Пиксельное соответствие мокапу и обе темы (светлая/тёмная), скролл длинного превью, поведение `focus-visible`/`hover`, моноширинный шрифт имён — *почему*: визуальная приёмка и темизация не наблюдаемы через jsdom (нет layout/CSS-каскада), запросы по `className`/токенам запрещены конвенцией → ручной хвост `{T2.1}`/`{T2.2}` 👤 + Layer 3.
- Русская плюрализация счётчика на всех числовых формах (11/21/111 …) — *почему*: `pluralizeRu` — локальная чистая функция форматирования без бизнес-ветвления, счётчик проверен на формах 2/3 в суите; полный перебор форм — solitary-unit на хелпер, ценность низкая (нет второго потребителя) → мягкий гейт glue.

**Замеченные прод-баги (для fixer'а, сам не чиню):** нет. Прод-код (`SkillContextSection.tsx`, `shared/api/skill-context.ts`) соответствует контракту design-brief и мокапу; все 11 автотестов зелёные с первого прогона.
