# ADR-001: General Agent (ReAct)

## Статус

Принято

## Контекст

AI-инструмент для подготовки материалов: разные задачи (структурирование, research, генерация), разные сценарии использования. Агент должен адаптироваться под задачу, а не следовать фиксированному пайплайну.

В v1 проекта использовался hardcoded agentic workflow — жёсткая последовательность шагов с переходами. Это показало свои ограничения: каждый новый сценарий требовал переписывания графа, гибкость отсутствовала.

## Решение

General Agent с ReAct loop (Reason → Action → Observe → Adjust).

**Формула:**

```
General Agent = Based Prompt + ReAct Loop + Context Engineering + Memory + Tool Use
```

- **Based Prompt** — "законы физики" для агента: как думать, реагировать на ошибки, взаимодействовать с пользователем, границы поведения.
- **ReAct Loop** — цикл до достижения цели или явной остановки. Агент сам решает какие шаги предпринять, исходя из контекста.
- **Tool Use** — вызов tools через единый интерфейс (search, generate, export).
- **Memory** — short-term (текущий диалог) + long-term (Knowledge Sphere).
- **Context Engineering** — управление тем, что попадает в контекст агента и когда.

## Альтернативы

### Hardcoded Agentic Workflow (отклонено)

Чёткая последовательность шагов с фиксированными переходами. Использовался в v1 проекта.

**Причина отклонения:** негибкий. Каждый новый сценарий = переписывание графа. Не масштабируется при росте количества задач и сценариев. Реальный опыт v1 подтвердил ограничения.

### Мультиагентная архитектура с первого дня (отклонено)

Несколько специализированных агентов (research, generation, review) с оркестратором.

**Причина отклонения:** преждевременная сложность, overhead на коммуникацию между агентами. Вводится позже, когда основной агент перегружен контекстом. Критерии выноса в sub-agent зафиксированы в [vision.md](../../vision.md).

## Следствия

- Единая точка входа для пользователя
- Поведение определяется контекстом, а не жёстким графом
- Расширение — через skills и tools (см. [ADR-002](ADR-002-skills-system.md))
- **Централизованная архитектура:** единая точка входа для общения с пользователем, интерпретируемость (состояние читается из main agent). Децентрализованная не подходит: нет единого view состояния, сложно координировать общение с пользователем.

### Эволюция мультиагентности

Мультиагентность откладывается до реальной необходимости. Эволюционный путь:

```
v1: Single Agent + Tools + Knowledge Sphere Agent
              ↓ (при перегрузке контекста)
v2: Orchestrator + Sub-agents
              ↓ (при росте количества sub-agents)
v3: Hierarchical (если понадобится)
```

**Потенциальные sub-agents** (когда понадобятся): Research Agent (глубокий поиск, верификация), Generation Agent (генерация контента по структуре), Review Agent (проверка качества, consistency).
