# ADR-005: Механика обновления Knowledge Sphere

## Статус

Отложено (MVP-решение принято, оптимизация — при реальных проблемах)

## Контекст

Knowledge Sphere ([ADR-003](ADR-003-knowledge-sphere.md)) нуждается в механизме обновления: когда и как новые факты из диалога интегрируются в шар знаний проекта.

Исходная идея (из ранних проработок): отдельный Classifier (лёгкий LLM) на каждое сообщение решает, нужно ли обновление → если да, KS Agent (sub-agent) извлекает факты и интегрирует в картину.

## MVP-решение

**Main Agent сам обновляет шар через tool `update_sphere`.**

Обоснование:
- Принцип "простота > сложность" — один агент, без дополнительных компонентов
- Main Agent имеет полный контекст диалога → качественное решение о том, что и когда обновлять
- Classifier на одном сообщении — bottleneck: мысль может быть расплескана по нескольким сообщениям
- Отдельный Classifier / KS Agent — преждевременная оптимизация на этапе MVP

## Отложенные варианты

Прорабатываются при реальных проблемах (перегрузка контекста, стоимость токенов).

### Вариант A: Classifier (лёгкий LLM) + KS Agent

```
User message → Classifier (нужно ли обновление?)
  → нет: продолжить
  → да:  KS Agent извлекает факты, интегрирует
```

**Проблемы:**
- Classifier видит одно сообщение — не ловит контекст, размазанный по нескольким
- Classifier с полным контекстом ≈ дублирование Main Agent (зачем тогда отдельный?)
- Classifier на лёгкой модели = преждевременная оптимизация

### Вариант B: Main Agent как триггер + KS Agent (sub-agent)

Main Agent решает "пора обновить" → вызывает KS Agent как tool с нужным контекстом.

**Плюсы:** изоляция работы по обновлению, не засоряет контекст Main Agent.
**Минусы:** KS Agent получает ограниченный контекст (только то, что передаст Main Agent).

### Вариант C: Main Agent обновляет сам + context cleanup

Main Agent сам идёт и актуализирует шар. После завершения промежуточные шаги очищаются из контекста, подставляется summary: "шар обновлён, добавлено X".

**Плюсы:** максимальное качество (полный контекст), простота.
**Открытые вопросы:** ждёт ли пользователь во время обновления? Прозрачность vs скорость.

## Критерии перехода к оптимизации

- Стоимость токенов становится проблемой
- Main Agent перегружен контекстом (основная задача + обновление шара)
- Обновление шара заметно замедляет ответ пользователю

## Следствия

- MVP: один агент, tool `update_sphere`, без Classifier
- Эволюция совпадает с ADR-001: v1 Single Agent → v2 Orchestrator + Sub-agents
- Решение можно пересмотреть без переделки архитектуры
