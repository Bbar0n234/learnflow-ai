# ADR-009: Logging Strategy

## Статус

Принято

## Контекст

Текущее состояние: дефолтный вывод uvicorn, 4 разрозненных логгера через `logging.getLogger(__name__)` без централизованной конфигурации, нет управления уровнями, нет корреляции запросов. На фронтенде — 3 вызова `console.error` в error-хендлерах, нет Error Boundary, нет уровней.

Нужно: управляемое логирование с единой конфигурацией, контроль шума библиотек, фундамент для будущей observability (feat-003: Langfuse, в перспективе — агрегация логов).

## Решения

### Backend: structlog поверх stdlib logging

structlog интегрируется поверх stdlib logging через процессорный пайплайн. Все библиотеки Python-экосистемы (uvicorn, sqlalchemy, httpx) используют stdlib — structlog управляет ими через единый пайплайн, а не конфликтует.

Ключевые возможности, определившие выбор:
- Контекстные переменные через `structlog.contextvars` — нативное решение для request_id
- Двойной рендеринг: human-readable с цветами (dev) / JSON (prod) — переключение через конфиг
- Типизирован, зрелый проект

**Отклонено:**
- **loguru** — несовместим со stdlib напрямую: требует `InterceptHandler`-хак для перенаправления stdlib → loguru. Глобальный синглтон без иерархии логгеров — нет per-module уровней через конфиг. Хорош для скриптов, не для web-приложения с множеством библиотек.
- **stdlib alone** — нет structured logging без дополнительных форматтеров, нет контекстных переменных из коробки (только через `logging.Filter` или `contextvars` вручную), verbose конфигурация.

### Конфигурация: YAML-файл + переменная окружения

Два уровня управления:
- **`LOG_LEVEL`** (переменная окружения) — единственный динамический параметр. Дефолтный уровень — info по конвенции, в YAML не дублируется (single source of truth).
- **`configs/logging.yaml`** — формат вывода (`human-readable` | `json`), per-library overrides для шумных библиотек.

YAML вместо кода: чтобы не пересобирать Docker-образ для изменения уровня конкретной библиотеки. Изменил файл → `docker compose restart app`.

### Вывод: stdout-only

Приложение пишет в stdout/stderr. Docker перехватывает через log driver. Никаких файлов внутри контейнера — это стандартный подход для контейнеризированных приложений (12-factor app).

### Docker: log rotation

`json-file` driver с ограничением размера и количества файлов. Решает проблему бесконечного роста логов — без этого `docker compose logs` становится непригодным для использования.

### Frontend: обёртка над console + Error Boundary

Обёртка с уровнями логирования, переключение через `import.meta.env.DEV` (Vite). В dev — всё видно, в prod — только warn/error.

Отдельная `VITE_LOG_LEVEL` не нужна: `VITE_*` переменные вшиваются в бандл при сборке (compile-time), `DEV`/`PROD` из Vite достаточно для текущих потребностей.

Error Boundary — обязательный компонент: без него непойманная ошибка рендера = белый экран без информации.

### Request ID (correlation)

FastAPI middleware генерирует UUID, кладёт в `contextvars`. structlog автоматически добавляет request_id ко всем логам в контексте запроса. Особенно ценно для LangGraph agent stream, где один запрос порождает множество лог-событий.

## Следствия

- structlog — новая зависимость, одноразовая кривая обучения (процессоры, bound loggers, интеграция со stdlib)
- Фундамент для feat-003 (Langfuse): structured logging + request_id готовы к интеграции с tracing
- JSON-формат заложен, но не активирован по умолчанию — включается при появлении агрегатора (Loki, ELK)
- Remote error reporting на фронтенде (Sentry) — не в scope, но точка расширения заложена в logger-обёртке
