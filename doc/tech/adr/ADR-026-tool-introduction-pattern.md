# ADR-026: Паттерн ввода инструментов — spike → validate → integrate

## Статус

Принято

## Контекст

По мере догфудинга (Фаза 5 роадмапа) у агента всплывают новые потребности в инструментах: генерация слайдов, аудио-обзоры, работа с файлами, память. Возникает вопрос — как вводить новый инструмент / фичу в продукт, чтобы не встраивать сырое и не платить интеграцией за то, что в итоге не нужно.

Две ловушки. Первая — встроить фичу сразу в код по интуиции «вроде нужна», потратить интеграцию и обнаружить, что в реальном воркфлоу она не та или не нужна; откат стоит дороже спайка. Вторая, специфичная для нашего стека: прототип, обкатанный на топовой модели (Claude Code / Opus), «работает», а на реальной prod-модели (GLM / cost-optimal через OpenRouter) разваливается — качество структурирования и чувствительность к промптам зависят от модели жёстко (см. roadmap, Фаза 5a, разделение сигналов).

## Решение

Любой новый инструмент / фича проходит три шага: **прототип → валидация → интеграция**.

1. **Прототип (spike).** Щупаем возможность вне продукта — на внешнем пайплайне (Claude Code) или изолированно, без интеграции в рантайм. Цель — понять, нужна ли она и в какой форме.
2. **Валидация.** Решаем по факту работы прототипа: нужна / не нужна / нужна иначе. Не нужна — закрываем спайк, в код не лезем.
3. **Интеграция.** Встраиваем в LearnFlow AI.

**Гейт.** Статус Done в интеграции ставится только после **ре-валидации на реальном рантайме и реальной (prod) модели** продукта, а не на стеке прототипа. Прототип на Opus подтверждает «возможность ценна»; он **не** подтверждает «работает на нашей модели». Без ре-валидации фича считается недоделанной.

## Альтернативы

### Встраивать сразу в код (отклонено)

Реализовать фичу по интуиции и проверять уже в продукте. Платим полной интеграцией за непроверенную гипотезу; откат дороже спайка. Сырые и ненужные инструменты раздувают агентную обвязку.

### Прототип = достаточное доказательство (отклонено)

Считать обкатку на Claude Code / Opus финальной валидацией. Игнорирует модельную неконсистентность: лучшая модель маскирует требования к качеству, которые на prod-модели критичны. «Работало в прототипе» — не «работает в проде».

## Следствия

- Ввод инструментов трассируется: спайк → требование в backlog (`[spike]`) → интеграция → ре-валидация на prod-модели.
- Паттерн переиспользуемый и постоянный — не разовое решение под Фазу 5.
- Дополнительная стоимость: каждая фича валидируется дважды (стек прототипа + prod-рантайм). Осознанная плата за защиту от модельной неконсистентности.
- Связан с Фазой 5a роадмапа (discovery spike — источник требований) и backlog P1 «Cost-optimal модель» (целевая prod-модель для ре-валидации).
