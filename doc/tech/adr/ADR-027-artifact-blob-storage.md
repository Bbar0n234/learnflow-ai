# ADR-027: Хранение и отдача бинарных данных артефактов

## Статус

Принято

## Контекст

feat-010 вводит генерацию изображений агентом — первые бинарные данные в системе. До этого артефакт по всему стеку текстовый (`artifacts.content: Text`), механизмов хранения и отдачи бинарей нет.

Нужно решить два связанных вопроса: где физически хранить байты изображения и как отдавать их на фронт. Оба решения приняты в одном заходе, потому что выбор хранилища напрямую определяет допустимые способы отдачи (presigned URL требует объектного хранилища, прямая отдача через backend — не требует).

Объёмы на обозримом горизонте — некритичны (изображения, не видео); инфраструктурных мощностей под object storage в проекте пока нет.

## Рассмотренные варианты (хранение)

### A: `bytea`-колонка на `artifacts`

Добавить колонку с данными прямо в существующую таблицу.

- **За:** одна таблица, без JOIN.
- **Против:** блоб в основной таблице — обычный ORM-select рискует тянуть мегабайты; листинг артефактов нужно ограждать deferred-загрузкой во всех местах, где `Artifact` читается целиком.

### B: base64 в `content: Text`

Кодировать байты и класть в уже существующее текстовое поле.

- **За:** ноль новых таблиц/типов.
- **Против:** мегабайтные JSON-ответы; ломает текстовый контракт `content` (markdown-рендер, download в md/pdf ожидают текст); нет HTTP-кэширования бинарных данных.

### C: Файловая система + `StaticFiles`

Писать файлы на диск, отдавать через FastAPI `StaticFiles`.

- **За:** просто, нативная поддержка FastAPI.
- **Против:** авторизация статики — не из коробки (нужен кастомный guard перед раздачей); volumes; бэкап и консистентность с БД (какой файл соответствует какой записи) — вручную, вне транзакционных гарантий Postgres.

### D: S3/MinIO

Объектное хранилище, presigned URL для загрузки/отдачи.

- **За:** правильное решение на масштабе — presigned URL разгружает backend от проксирования байтов, прямая отдача клиенту.
- **Против:** новая инфраструктура (деплой, credentials, бэкап); двухфазность записи (запись артефакта в PG + запись блоба в S3 — не одна транзакция, нужна компенсация при частичном отказе). На текущих объёмах цена этой инфраструктуры не окупается.

### E (выбрано): таблица `artifact_blobs` в PostgreSQL

Отдельная таблица (`FK` на `artifacts`, 1:1, `bytea`), за протоколом `BlobStorage`.

- **За:** нулевая новая инфраструктура; артефакт и блоб пишутся одной транзакцией (никакой компенсирующей логики на частичный отказ); блоб не в основной таблице — обычный select артефактов не тянет мегабайты.
- **Против:** не масштабируется так же хорошо, как объектное хранилище на больших объёмах бинарных данных; backend проксирует байты вместо разгрузки на CDN/presigned URL.

## Решение (хранение)

Вариант E. Таблица `artifact_blobs`: собственный PK (не FK-as-PK — таблица заявлена будущим общим хранилищем бинарей для разных потребителей, где natural key не единственный), `artifact_id` (FK CASCADE, `unique` — 1:1), `mime_type`, `data: bytea`.

Доступ — за протоколом `BlobStorage` (`typing.Protocol`: `put`/`get`/`delete`) с единственной реализацией `PgBlobStorage`. Протокол существует уже сейчас, при единственной реализации, ради двух вещей: изолирует прикладной код (tool, endpoint) от знания о Postgres как бэкенде блобов, и фиксирует форму будущего перехода на S3 — заменить реализацию протокола, не вызывающий код. `PgBlobStorage` конструируется вокруг `session` (как репозитории), не принимает `session` параметром метода — иначе PG-деталь (транзакция) протекала бы в сигнатуру протокола, которую future S3-реализация не смогла бы честно удовлетворить.

`artifact_blobs` — переиспользуемая таблица, не специфичная для изображений: следующие потребители — file attachments, референсные изображения для image-to-image.

## Рассмотренные варианты (отдача на фронт)

### Presigned URL

Backend генерирует короткоживущую подписанную ссылку, фронт качает напрямую с объектного хранилища.

- **Против:** требует объектного хранилища (см. выше — отклонено); новая security-поверхность (подпись, TTL, отзыв).

### Cookie-based auth на статику

Отдавать блоб как обычный статический ресурс, авторизация — через cookie.

- **Против:** меняет модель авторизации приложения (сейчас — Bearer JWT в заголовке); двойная модель auth ради одного endpoint'а.

### Base64 в JSON деталей артефакта

Отдавать байты прямо в ответе `GET /artifacts/{id}`.

- **Против:** тяжёлый ответ на каждый fetch метаданных; нет HTTP-кэша (кэшируется весь JSON целиком или ничего).

### Выбрано: authenticated media endpoint + client-side blob fetch

`GET /projects/{project_id}/artifacts/{artifact_id}/media` — отдаёт bytes под существующим JWT-слоем, `Content-Type` из `mime_type`. `<img src>` не отправляет `Authorization`, поэтому фронт качает блоб как обычные API-данные (`axios`, `responseType: "blob"` — паттерн уже существующего `downloadArtifact`) → `Blob` → `URL.createObjectURL` → `<img>`.

## Решение (отдача)

Media endpoint с агрессивным client-side кэшем: `Cache-Control: private, max-age=31536000, immutable`. Право на `immutable` даёт иммутабельность блоба **по построению** — путей редактирования изображения нет, «перегенерация» создаёт новый артефакт с новым `id` (= новым URL), поэтому контент по данному URL измениться не может. `private` — контент под авторизацией, кэш только в браузере пользователя, не в промежуточных прокси.

## Следствия

- Первая бинарная сущность в системе задаёт паттерн для будущих (file attachments, референсные изображения): таблица блобов + `BlobStorage`-протокол + authenticated media endpoint — не переизобретаются заново.
- Переход на S3/MinIO при росте объёмов — замена реализации `BlobStorage` + endpoint переключается на presigned-редирект; протокол уже изолирует эту границу. Не запланирован, но путь не закрыт.
- Backend остаётся на пути проксирования байтов (не CDN/presigned) до перехода — приемлемо на текущих объёмах, неприемлемо при кратном росте объёма/трафика бинарных артефактов.
- Детали реализации (форма протокола, миграция, docstring tool'а) — [design-brief feat-010](../../tasks/iterations/post-mvp/feat-010-image-generation/design-brief.md).
