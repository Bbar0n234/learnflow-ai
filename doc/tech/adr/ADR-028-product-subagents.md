# ADR-028: Продуктовые субагенты — subagent-as-tool

## Статус

Принято

## Контекст

Backlog P2 «Продуктовые субагенты» долго был заблокирован формулировкой «после инструментов (web search, sandbox)» — к моменту итерации блокировка устарела дважды: discovery-спайк (Фаза 5a) обнаружил потребителя, которому инструменты не нужны вовсе.

Первый потребитель — judge-проходы скилла `tech-article-writing` (анти-слоп-скан, cold-reader): им нужен независимый ревьюер со «свежими глазами», не отравленными историей сессии основного диалога, получающий текст + инструкцию и возвращающий вердикт. Второй потребитель — web-research: built-in firecrawl MCP (`firecrawl_search`/`firecrawl_scrape`/`firecrawl_extract`) уже работает в проде, нужна только изоляция контекста — страницы жгут контекст, наружу должна уходить выжимка с источниками.

Общий вопрос: как основной ReAct-агент делегирует подзадачу изолированному исполнителю — с гарантией, что история сессии не утекает в его контекст, — и как эта механика задаётся конфигурацией, а не кодом на каждую новую роль.

## Решение

### Паттерн: subagent-as-tool

Субагент — отдельный скомпилированный `StateGraph` со своим state, вызываемый `ainvoke` изнутри обычного tool основного графа; наружу возвращается только результат. Чистота контекста не требует отдельного механизма фильтрации — она гарантирована конструкцией: вход субагента собирает tool из аргументов вызова, история сессии туда физически не передаётся, потому что канал в субагента — это аргументы tool-вызова, а не разделяемый state.

Слоистость разделяет декларацию, исполнение и точку вызова:

- **`SubagentSpec`** — декларация типа субагента: имя, description (видна модели в выборе инструмента), имя промпта, опциональный override модели, список tools, режим persistence. Реестр специй — секция `subagents` в `configs/agent.yaml`.
- **`SubagentRunner`** — принимает spec + task (+ документы), резолвит модель/промпт, компилирует граф per-invoke (та же цена, что per-request компиляция `GraphFactory` — единицы миллисекунд, кэш не оправдан на этом объёме), вызывает `ainvoke`, возвращает результат. Инвариант: `run_subagent` никогда не резолвится в собственный toolset субагента — рекурсия исключена на уровне Runner'а независимо от содержимого конфига.
- **tool `run_subagent(agent_type, task, input_artifact_ids?)`** — тонкая обёртка над Runner'ом: единственная точка, которую видит основной граф.

Такая слоистость — не декоративное разделение: она прямое условие того, что async v2 (см. «Extension points») ложится поверх того же Runner'а как вторая обёртка вокруг ядра, не переделывая его.

### Отклонённые альтернативы паттерна

| Вариант | Почему нет |
|---|---|
| `langgraph-supervisor` | Официально не поддерживается; собственный миграционный гайд библиотеки ведёт ровно к ручному subagent-as-tool |
| `langgraph-swarm` | Исчезла из актуальной документации LangGraph — нет оснований строить архитектуру на снятой с поддержки библиотеке |
| `deepagents` | Чужой runtime поверх графа — дополнительный слой абстракции и точка отказа, которую не контролируем, ради того, что решается штатным `StateGraph` + tool |

### Отклонённые альтернативы задания субагентов

| Вариант | Почему нет |
|---|---|
| Tool на каждую роль (`review_text(...)`, `research_web(...)`) | Код и растущий список tools на каждую новую роль; скилл не может завести роль без релиза бэкенда |
| Один generic `run_subagent(instruction, input)` без реестра | Нет контроля capabilities — произвольная инструкция управляет поведением исполнителя, качество зависит от умения основной модели формулировать роль на лету |
| **Реестр типов + один tool `run_subagent(agent_type, ...)` (выбрано)** | Роли декларативны (prompt/tools/model зафиксированы за типом в конфиге), новая роль — правка конфига, а не код; ментальная модель ближе к Agent-tool паттерну Claude Code |

### Формат реестра: секция `agent.yaml`, не директория

Реестр специй — плоская секция `subagents` (`llm`-дефолт + `registry: list[SubagentSpec]`) внутри `configs/agent.yaml`, а не отдельная директория по образцу `skills/` (там — файл на скилл с собственным содержимым, автономным жизненным циклом). Для трёх типов v1 (judge, web-research, general-purpose), каждый из которых — несколько строк конфига (имя промпта, tools, persistence), директория добавила бы косвенность без выигрыша: нет собственного содержимого сверх ссылки на промпт, читать/резолвить по имени проще из единого списка. Решение переоценивается при реальном росте числа типов — сейчас это преждевременная генерализация.

### Вход субагента: task + референс на артефакт

Судье нужен точный текст (вердикт цитирует нарушения — цитаты обязаны биться с черновиком байт в байт) и только текст (cold-reader читает статью без посторонних материалов — иначе проверка нечистая). Единственный канал в чистый контекст субагента — аргументы tool-вызова, а всё, что идёт через аргументы, основная модель воспроизводит токен за токеном: копия статьи в `task` — это output-токены на каждый judge-проход, guard-проверка args по всему тексту и риск парафраза при копировании, ломающий цитаты.

Решение — референсы, инжектируемые кодом, а не моделью: tool принимает опциональный `input_artifact_ids`, сам достаёт содержимое через `ArtifactRepository` (скоуп по `project_id` из контекста вызова), а Runner собирает `HumanMessage` из `task` + документов, каждый в XML-обёртке с атрибуцией (`id`, `title`) — вердикт адресует цитаты к конкретному документу. Модель никогда не видит и не воспроизводит содержимое документа как токены собственного ответа — только его id.

Семантика ошибок разрешения — **всё или ничего**: любой чужой (`project_id` не совпал) или несуществующий id обрывает вызов целиком, возвращая error-строку с перечнем именно проблемных id; частичный вход не собирается никогда. Причина: частичный вход молча портил бы валидность проверки — модель получила бы результат, не подозревая, что часть документов выпала.

Отклонено: read-only tool «прочитай артефакт» в toolset субагента-судьи — недетерминированный вход (субагент может «гулять» по артефактам проекта) прямо противоречит требованию чистоты judge-контекста.

### Sync v1 vs async v2

Judge — блокер по природе: основному агенту нечего делать до вердикта, синхронный вызов внутри tool — прямое отражение семантики задачи. Async вводит два обязательства, не окупающихся для v1: job-паттерн (`start → task_id → check/get`, отдельный канал уведомлений) и обход подводного камня OSS LangGraph — два конкурентных рана на один `thread_id` не координируются (double-texting — фича платной платформы, не open-source runtime). Фоновый субагент, чтобы работать корректно, требует собственного `thread_id`, отдельного от основной сессии, и механизма уведомления родителя о готовности — вся эта инфраструктура не нужна блокирующему judge и не была бы использована.

### Persistence: `none | inherit`

Checkpointer не участвует в исполнении графа — он нужен для resume после падения процесса, HITL (`interrupt`) и истории thread. Judge не требует ничего из этого: упал субагент — родитель получает ошибку tool и решает сам (перезапуск, деградация); памяти между вызовами быть не должно по конструкции — «свежие глаза» противоречат состоянию, унаследованному от предыдущего рана.

- `persistence: none` (все типы v1) — `compile(checkpointer=False)`: ноль записей в PG, субагент полностью stateless между вызовами.
- `persistence: inherit` — `checkpointer=None`: субграф наследует PG checkpointer родителя, чекпойнты попадают в тот же `thread_id` под отдельным `checkpoint_ns`. Свойство архитектуры, доступное сменой одного поля спеки — становится актуальным первому потребителю с HITL внутри субагента.

Наблюдаемость не зависит от режима persistence: callbacks пробрасываются во вложенный граф автоматически через contextvars — запуски субагентов видны в Langfuse вложенными span'ами с токенами и стоимостью независимо от `persistence`.

### Security-политика: переиспользование границы + inline-проверки внутри цикла

Субагент — тот же trust-контур, что основной агент; отдельный периметр не строится.

- **На границе вызова** — переиспользуются существующие checkpoint'ы основного графа: `task` + `input_artifact_ids` — аргументы tool-вызова, проверяемые `TOOL_CALL_ARG` после ответа модели; результат субагента становится `ToolMessage`, проверяемым `TOOL_RESULT` до следующего вызова LLM. Содержимое инжектируемого артефакта — производная уже проверенных входов (артефакт создан агентом через `create_artifact` внутри той же сессии).
- **Внутри субагента с tools** (web-research) — те же inline-проверки, что в основном agent node, с той же fail-safe-семантикой redact, не блокировкой: инъекция в результате инструмента (заражённая страница) заменяется заглушкой, цикл продолжает работу; инъекция в аргументах вызова инструмента срезает `tool_calls` из ответа модели, не обрывая граф. Guard-код переиспользуется буквально (общий модуль-коллаборатор для основного и субагентского графа), а не переизобретается — единая политика, единое место правки.
- **Toolless-субагенты** (judge, general-purpose) внутренних проверок не получают — untrusted-источников внутри цикла нет, единственный вход уже проверен на границе.
- `recursion_limit` ограничивает ReAct-цикл субагента с tools, не позволяя ему крутиться бесконечно — тот же механизм LangGraph, что защищает основной граф.

Инъекция страницей внутрь субагентского ReAct-цикла — новая поверхность атаки, ранее не существовавшая (основной граф работает с MCP на верхнем уровне, субагент — первый случай вложенного tool-цикла с untrusted-контентом).

### Extension points

Слоистость Runner/Spec/tool оставляет три точки расширения как свойства архитектуры, не как обязательства предстоящих итераций:

- **`output_schema` в спеке** — v1 возвращает финальный текст графа; структурированный вывод не введён, потому что потребитель вердикта — LLM и человек, а не код, и формат конкретного judge-прохода диктует `task`. Поле принимается слоистостью Runner'а без переделки ядра, когда появится программный потребитель.
- **`persistence: inherit`** — уже часть контракта `SubagentSpec` (см. выше), не требует изменений Runner'а или графа для активации, только смены значения поля спеки.
- **Async v2 как вторая обёртка над Runner'ом** — job-паттерн (start/check/get, отдельный `thread_id`, канал уведомлений) оборачивает тот же `SubagentRunner.run`, не меняя декларацию специй и не трогая toolless/ReAct графы субагента.

## Обоснование

- **Subagent-as-tool, а не supervisor/swarm-библиотека:** канонический паттерн актуальной документации LangGraph для делегирования подзадачи изолированному исполнителю без разделяемого state; все рассмотренные библиотеки либо сняты с поддержки, либо добавляют чужой runtime поверх штатного `StateGraph` без выигрыша для этого кейса.
- **Реестр вместо кода на роль:** декларативное задание типов через конфиг соответствует AIDD-модели проекта — новая роль субагента добавляется правкой `agent.yaml` + промпт-файла, не релизом бэкенда; одновременно сохраняет контроль capabilities, недоступный generic-инструменту без реестра.
- **Референс вместо инлайна документа:** единственный канал в чистый контекст — аргументы tool-вызова, воспроизводимые основной моделью токен за токеном; инжект кодом по id устраняет и издержку токенов, и риск парафраза, ломающего цитаты в вердикте.
- **Sync, не async, для v1:** блокирующая природа judge делает синхронный вызов прямым отражением задачи; асинхронность добавила бы job-инфраструктуру и обход известного ограничения OSS LangGraph (некоординируемые конкурентные раны на `thread_id`) без потребителя, которому это нужно сейчас.
- **Переиспользование, не новый периметр безопасности:** субагент работает в том же trust-контуре, что и основной агент; граница входа уже закрыта существующими checkpoint'ами, а внутренний guard-код для ReAct-цикла — тот же модуль, что использует основной граф, что исключает рассинхронизацию политик между двумя графами.

## Следствия

- Новый тип субагента = запись в `registry` + seed-файл промпта + (если нужны tools) резолв имён из built-in пула; фейл резолва — ошибка старта приложения, а не тихая деградация в рантайме.
- User-installed MCP не резолвятся в toolset субагента ни при каких обстоятельствах — пул субагентов строится только из internal tools + built-in MCP, что сохраняет trust-границу между продуктовыми и пользовательскими интеграциями.
- Инъекция через инструмент внутри субагентского цикла (web-research) — новая поверхность атаки, требующая отдельного red-team покрытия сверх существующего сканера основного графа.
- `persistence: none` в v1 означает, что упавший субагент не восстанавливается — родительский tool получает ошибку и решает сам; это осознанный trade-off ради простоты, а не забытый случай.
- Structured-output вердикта, `persistence: inherit`, async-обёртка над Runner'ом не реализуются, пока нет конкретного потребителя — расширение контракта без потребителя было бы преждевременной генерализацией.
