# ADR-029: Операционные kill-switch'и для исследовательских подсистем

## Статус

Принято

## Контекст

LearnFlowAI выходит в прод после длительной фазы исследовательской разработки (>300 коммитов без релиза, chore-001 «Prod-closing»). Две подсистемы, выросшие как исследовательские артефакты, не годятся для дефолтного продакшна:

- **Inline LLM-защита** (`SecurityGuard`: детекторы + LLM classifier, hardening-преамбула, обёртки границы доверия) — построена для учебного red-team/blue-team формата ([ADR-017](ADR-017-prompt-injection-defense.md)). В продукте для доверенного круга техспикеров она добавляет latency и cost без продуктовой ценности, а hardening-преамбула портит поведение агента (запрет называть инструменты, требование говорить только о возможностях функционально).
- **SIEM-сервис** ([ADR-018](ADR-018-siem-service-topology.md)–[021](ADR-021-siem-correlation-engine.md)) — построен под учебную цель (дисциплина по ИБ, фундамент диплома) и её закрывает; для прод-нагрузки не готов (невалидируемый JSONB `config` правил корреляции, RBAC-guard admin-only, но без более тонкой модели доступа).

Обе подсистемы должны быть выключаемы в проде без удаления кода, тестов и данных — обратимость нужна для будущих red-team прогонов, дообучения классификатора, возврата SIEM при реальной потребности (диплом, прод-нагрузка). Одновременно у обеих уже существует гранулярная настройка для исследовательских прогонов: per-checkpoint `classifier_enabled` в `configs/security.yaml`, `enabled` на уровне отдельного правила корреляции в БД SIEM.

## Решение

**Env-переменная — операционный тумблер «включено в этом окружении или нет», один булев флаг на подсистему целиком.** Гранулярность для исследовательских прогонов остаётся там, где уже жила, — в `configs/security.yaml` и в БД правил корреляции; кто-то один флаг «на минимум» под конкретный чекпоинт заводить не пытается.

Отсюда прямо следуют остальные свойства обоих тумблеров ([design-brief chore-001 § Принцип разделения конфигурации](../../tasks/iterations/dogfooding/chore-001-prod-closing/design-brief.md)):

- `LLM_DEFENSE_ENABLED` и `SIEM_ENABLED` — bool, дефолт `true` (dev/CI ведут себя как раньше, прод переключает явно).
- Флаг читается один раз в lifespan (composition root не строит guard / не создаёт транспорт событий); переключение требует рестарта контейнера, а для SIEM ещё и синхронной правки `COMPOSE_PROFILES` (контейнеры) и пересборки фронта (`VITE_SIEM_ENABLED`, build-time) — тумблер один по смыслу, механизмов применения по числу изолированных слоёв столько, сколько у подсистемы точек присутствия.
- Выключенное состояние обязано быть наблюдаемым: ровно одна INFO-строка на старт («security guard disabled by flag», «siem event emission disabled by flag»), иначе «выключено флагом» и «зависимость недоступна» (Redis лежит, guard LLM не отвечает) схлопываются в одинаковый молчаливый результат — не различить по логам.
- Граница проводится по назначению подсистемы, не по цене конкретного компонента. Для LLM-защиты это означает, что под тумблер уходит и разметка происхождения (`<user_message>`, `<tool_output>`), которая не делает LLM-вызовов и почти ничего не стоит: «выключено» обязано означать «выключено полностью», а не оставлять систему в непротестированном промежуточном состоянии.

## Альтернативы

### Per-checkpoint / per-rule env-переменные (отклонено)

Env-флаг на каждый checkpoint guard'а или на каждое правило SIEM (`LLM_DEFENSE_INPUT_ENABLED`, `LLM_DEFENSE_FINAL_OUTPUT_ENABLED`, ...). Даёт эксплуатации точечный контроль без редеплоя ценой того, что: (а) env-поверхность разрастается пропорционально числу чекпоинтов/правил и требует от оператора знания внутренней таксономии подсистемы; (б) дублирует уже существующий гранулярный механизм (`configs/security.yaml`, БД правил) вторым, конкурирующим — два источника правды для одного и того же «включено ли конкретно это». Отклонено: у гранулярности уже есть дом, здесь нужен только переключатель верхнего уровня.

### Дефолт `false` (отключено по умолчанию) (отклонено)

Симметричный вариант: подсистемы выключены везде, кроме явного `=true`. Отклонено по характеру отказа: забытая правка `.env` в dev/CI незаметно выключила бы существующее поведение (регресс без сигнала), тогда как забытая правка в проде (дефолт `true`) — расход на неиспользуемые исследовательские подсистемы, наблюдаемый и не создающий дыру в базовой app-security (auth, rate limiting, RBAC тумблерами не затрагиваются).

## Следствия

- Будущие исследовательские подсистемы с тем же профилем («нужна для догфудинга/диплома/red-team, не нужна в проде по умолчанию») получают готовый паттерн: один env-флаг, дефолт `true`, INFO-лог на выключение, гранулярность — в существующих конфигах предметной области, не в новых env-переменных.
- Точечное включение одной проверки для целевого исследовательского прогона в проде недоступно через операционный слой — только через `configs/security.yaml`/БД правил при включённом тумблере целиком. Это осознанный trade-off: тумблер отвечает на вопрос «жива ли подсистема здесь», не «насколько тонко она настроена».
- Треды, уже заблокированные `SecurityGuard`, остаются заблокированными и после выключения тумблера — блокировка исторический факт рантайма, не текущее состояние конфигурации.
- Полное устройство обоих тумблеров (точки врезки, слои SIEM, env-гигиена, ручные шаги на прод-VM) — [design-brief chore-001](../../tasks/iterations/dogfooding/chore-001-prod-closing/design-brief.md); эксплуатационный контур — [setup/production.md](../setup/production.md).
