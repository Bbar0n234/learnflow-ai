# ADR-029: Результат инструмента — проверка и отчёт повызовно, внутри узла `tools`

## Статус

Принято

## Контекст

Событие завершения tool-вызова несёт пользователю содержимое результата: лента активности показывает, что вернул инструмент, а не только факт «вызов закончился». Как только результат стал видимым, у выхода узла `tools` появилось два независимых потребителя — провод (SSE) и чекпоинтер, — и место проверки перестало быть безразличным.

Две силы столкнулись в одной точке.

**Безопасность.** Чекпоинт `TOOL_RESULT` — inbound-граница: результат инструмента (веб-страница, ответ MCP-сервера, вывод субагента) — untrusted-источник, из которого приезжает инъекция. Проверка, стоящая шагом позже — на входе в следующий узел, — редактирует результат только для модели: пользователь к этому моменту уже прочитал отравленный текст в ленте, а корректирующего события в контракте нет и заводить его бессмысленно (прочитанное не отзывается).

**Правдивость ленты.** `ToolNode` исполняет все вызовы хода одним `ainvoke` и возвращается, когда закончился самый долгий из них. Отчёт, снятый с апдейта узла, приходит в один и тот же момент для всех вызовов хода: поиск, отработавший за десять секунд рядом с трёхминутным `run_subagent`, стоит в ленте идущим все три минуты и получает чужую длительность. Единица работы для пользователя — отдельный вызов (свой `call_id`, своя строка, своя длительность), а единицей отчёта был батч.

## Решение

Узел `tools` обоих графов (основного и субагентского) — не голый `ToolNode`, а обёртка `execute_tools_guarded`, для которой **единица исполнения, проверки и отчёта — один вызов инструмента**:

- батч из нескольких вызовов режется на по одному входу узла на вызов; вызовы по-прежнему идут параллельно, но guard и отчёт живут внутри каждой ветки;
- результат проверяется чекпоинтом `TOOL_RESULT` до отчёта и до возврата из узла — то есть до обеих дорог наружу; отредактированное сообщение **заменяет** сырое, и отравленный текст не попадает ни на провод, ни в чекпоинт;
- о результате отчитывается сам узел, через custom-канал, в момент завершения своего вызова; ответ узла собирается обратно в порядке, в котором вызовы просила модель, поэтому разговор в чекпоинте читается как при батче.

Из-за этого же порядка отчётность субагента разнесена по границе «что уже проверено»: прокси вокруг его инструментов анонсирует вызов (`tool_call_started` / `tool_call_args`), а результат эмитит узел `tools` субагентского графа — прокси сидит внутри `ToolNode` и внутри чекпоинта, поэтому не видит ни санированную ошибку, ни редакцию инъекции.

**Принятая цена:** классификатор зовётся по разу на результат вместо раза на батч — больше токенов и денег на ходах с параллельными вызовами, и результат появляется в ленте позже на время работы классификатора. Размен сознательный: платим за ленту, которая не врёт о завершённости и не показывает непроверенный текст. Обратно в батч не оптимизировать.

## Альтернативы

**Проверять на входе в следующий узел (как было до появления содержимого в событии).** Отклонено: редакция достаётся только модели, пользователь уже прочитал инъекцию. Пока событие завершения не несло содержимого, разницы не было — с появлением содержимого место проверки стало определять, кто увидит сырой текст.

**Оставить батчевое исполнение, а момент отчёта чинить чтением апдейта узла раньше.** Отклонено как физически невозможное: апдейт узла не может прийти раньше, чем узел вернётся, а он возвращается по самому долгому вызову. Никакая правка потребителя апдейтов этого не лечит.

**Один вызов классификатора на батч результатов (склейка текстов).** Отклонено: дешевле, но вердикт становится общим для нескольких источников — редакция по одному отравленному результату либо глушит соседние (ложная блокировка чистых данных), либо требует разбирать, к какому из них относится находка, то есть возвращает поштучную проверку окольным путём. Плюс склейка сама по себе — конкатенация untrusted-текстов, где инъекция может ссылаться на соседний фрагмент.

**Отчитываться из прокси инструмента у субагента (как анонс).** Отклонено: прокси стоит до guard'а и до санитайзера ошибок `ToolNode` — на провод уходил бы сырой `str(exc)` с путями и параметрами транспорта MCP и непроверенный результат.

## Последствия

- Один источник правды на событие результата: `tool_result` / `artifact_created` эмитит только узел `tools`, updates-канал за ним остаётся исключительно реестром анонсированных вызовов.
- Стоимость guard'а растёт линейно по числу параллельных вызовов в ходе — это первый кандидат в наблюдение, если ходы станут вызывать инструменты десятками.
- Обёртка узла — место, где fail-open теперь возможен структурно (нечитаемое состояние, форма ответа `ToolNode` без батча `ToolMessage`), поэтому обе такие дороги обязаны быть громкими: `agent.guard.degraded`, как и деградация самого классификатора.
- Контракт провода не изменился: типы событий, payload'ы и их порядок те же, что при батчевом отчёте, — изменились момент и внутренний источник.
