# ADR-031: Изоляция execution runtime — executor-сервис под gVisor

## Статус

Принято (feat-011, dogfooding).

## Контекст

Агент получает способность исполнять код (Python/bash) — фундамент выходных форматов (PDF, слайды, ГОСТ-docx как скиллы со скриптами) и произвольных вычислений. Код пишет LLM — он недоверенный by design. Деплой проекта — одна VM, docker-compose, сборка на сервере (ADR-012); LLM-защита в проде выключена kill-switch'ем (ADR-029), guard-обвязка не наращивается. Единственное жёсткое требование безопасности: недоверенный код не исполняется на хосте и не достаёт до основного стека (секреты, БД, Store).

## Рассмотренные варианты

1. **Исполнение в процессе/контейнере backend с фильтрацией кода** (AST-whitelist импортов и т.п.). Отклонено: фильтры Python-кода дырявы принципиально; индустрия (smolagents: «no local python sandbox can ever be completely secure») выносит исполнение из процесса приложения без исключений. Код рядом с секретами и БД — неприемлемо.
2. **Отдельный контейнер в compose, обычный runtime (runc).** Настоящая изоляция namespaces/cgroups; слабое место — общее ядро хоста: побег возможен через ядерную уязвимость (редкое, дорогое событие).
3. **Вариант 2 + gVisor (`runtime: runsc`).** Между контейнером и ядром хоста встаёт user-space «ядро-посредник» (Sentry): syscalls перехватываются, до хост-ядра доходит узкий фильтрованный набор. Побег требует пробить два слоя. Интеграция тривиальна: установка runsc на хост + одна строка в compose; KVM не нужен. Цена — оверхед 10–30% на I/O-тяжёлых нагрузках (для рендера/расчётов некритично).
4. **bwrap/nsjail per job внутри контейнера.** Изолирует джобы друг от друга, но от хоста защищает не сильнее варианта 2 (то же ядро). Не альтернатива, а возможное дополнение.
5. **Firecracker microVM.** Сильнейшая изоляция, но требует KVM — на облачных VM среднего класса обычно недоступен. Не для нашей инфраструктуры.
6. **Managed-сервисы (E2B, Modal, Cloudflare, Daytona).** Отклонены: vendor lock-in и/или не self-hostable на одной VM (E2B self-host требует кластер; Modal/Cloudflare закрыты; Daytona заморожена с июня 2026).
7. **Pyodide/WASM.** Отклонён: нет threading/multiprocessing, нативные зависимости рендер-тулчейна (Cairo/Pango) без WASM-портов; оба индустриальных Pyodide-executor'а (langchain-sandbox, smolagents) похоронены авторами.

## Решение

Вариант 3: **отдельный сервис `executor` в docker-compose под gVisor**.

- Свой образ с запечённым тулчейном (Python + научный стек + рендер-инструменты; состав финализируют спайки feat-005/006 по ADR-026), non-root, потолки CPU/RAM на контейнер (`cpus`/`mem_limit`), deadline per job.
- **Сетевая сегментация.** Executor живёт в выделенной сети `exec` (app ↔ executor) с `internal: true` и исключён из стековой сети compose: db/redis/siem для него недостижимы (ни DNS-имени, ни маршрута), **выхода в интернет из executor нет вообще** (internal-сеть без NAT). App подключён к обеим сетям (stack — для БД, exec — для джоб). Порт executor наружу не публикуется. Отсутствие egress закрывает заодно network-exfiltration из скомпрометированной джобы. Executor не знает о пользователях и не принимает решений о доступе — авторизация целиком в backend (модель доверия как у PostgreSQL: backend думает, executor исполняет).
- **Интернета и pip в рантайме нет** — пересмотр первоначального наброска «сеть + живой pip». Причина: executor — один общий контейнер, runtime-`pip install` писал бы в общий site-packages всех джоб — интерференция версий между пользователями (A ставит `numpy==2.x`, джобы B молча получают её) и плацдарм для вредоносных пакетов. Вместо этого — **толстый образ**: весь тулчейн запечён при сборке (состав финализируют спайки feat-005/006), недостающий пакет добавляется релизом образа. Включение egress обратно — одна строка в compose, рассматривать только вместе с per-job изоляцией окружений (bwrap + свой venv на джобу).
- Fallback: если runsc не встаёт на прод-VM — временно вариант 2 (runc) с теми же остальными границами; gVisor догоняет. Реализовано как `runtime: ${EXECUTOR_RUNTIME:-runsc}` в compose (интерполяция на уровне compose, не app-настройка — переменная не заводится ни в `Settings` backend'а, ни в `Settings` executor'а): дефолт остаётся `runsc`, прод-гарантия «прод всегда под gVisor» не ослабляется тем, что переменная в принципе существует. Нужна она была не для прод-фолбэка, а для dev: хосты без зарегистрированного в docker-демоне `runsc` (обычная dev-машина) выставляют `EXECUTOR_RUNTIME=runc` в своём `.env` — без override `docker compose up` на такой машине падает `unknown or invalid runtime name: runsc` ещё до старта контейнера.

## Следствия

- Файловые операции backend'а НЕ ходят через executor: volume workspaces смонтирован в оба контейнера, изоляции подлежит исполнение кода, а не доступ к данным (см. ADR-032). Executor не является критическим путём продукта — его отказ не ломает просмотр артефактов.
- Изоляция **между проектами внутри executor** — **bwrap per job** (вариант 4 как дополнение), в этой же итерации, а не по триггеру. Резолв путей (файловый слой backend) защищает только аргументы файловых инструментов; код внутри джобы путей-аргументов не имеет — `open()`/`rm -rf` абсолютным путём резолв не видит принципиально (парсинг кода на «плохие пути» дыряв — обфускация обходит любой blacklist). Поэтому границей для исполняемого кода служит видимость ФС: mount-namespace джобы содержит только её workspace (rw), тулчейн образа (ro), `/skills` (ro) — чужие workspace недостижимы ни на чтение, ни на запись/удаление. Без этого слоя джоба может снести `/workspaces` целиком (rw-volume смонтирован полностью). **Спайк подтвердил выполнимость под gVisor** (release-20260803.0; историческая проблема mount-ns gvisor#221 не воспроизводится; изоляция чужих директорий честная — ENOENT, не «нельзя прочитать»; non-root через userns без setuid-bwrap): отчёт `doc/tasks/iterations/dogfooding/feat-011-execution-runtime/spikes/spike-bwrap-gvisor.md`. Два следствия спайка в реализацию: (1) родной `--unshare-net` bwrap под gVisor фатален (в netns нет `lo`) — пустой netns джобы создаётся внешней обёрткой `unshare -U --map-current-user -n` перед bwrap (сокеты не создаются вовсе — `app:8000` и egress закрыты); (2) каталог workspace обязан принадлежать uid джобы, иначе запись под gVisor падает `EINVAL` даже при mode 777 — принят **единый uid app = executor = джоба**: все mkdir делает backend, владелец совпадает автоматически (альтернатива «совместимый umask» мертва — EINVAL вызывается владельцем, не правами; изоляцию единый uid не ослабляет: граница между проектами проходит по mount-ns, не по POSIX-правам). Прод-топология (docker+runsc, Ubuntu) отличается от тестового `runsc --rootless` — при развёртывании перепроверить `bwrap --unshare-user` от non-root под seccomp docker и AppArmor Ubuntu (unprivileged userns). Fallback при прод-регрессе — setuid-per-project (POSIX-права: детерминированный uid на проект, `0770`, `setuid()` джобы — гарантированно работает под gVisor, ценой CAP_SETUID у executor); в этой схеме uid'ы разъединяются, и mkdir workspace переезжает из backend в executor.
- **Остаточный риск сети.** Compose-сети привязаны к network namespace контейнера, не процесса: job-subprocess наследует сети executor'а и видит `app:8000` по exec-сети — отрезать джобу от app на уровне compose невозможно в принципе. Это та же JWT-защищённая поверхность API, что публикуется в интернет для браузера. Закрывается пустым netns джобы (обёртка `unshare -n` вокруг bwrap — родной `--unshare-net` bwrap под gVisor фатален, спайк) — в v1 вместе с изоляцией проектов. Сильные пароли БД/Redis в проде — defense in depth поверх сегментации, не замена ей.
- Установка runsc на хост — новый шаг подготовки VM (документируется в setup/production).
- **Именованный volume `workspaces` запекается с `chown` в оба образа.** Единый uid (см. выше) требует, чтобы владельцем каталога был uid 10001 — но точка монтирования свежего именованного volume наследует владение того пути, который уже существует в образе на момент первого использования (docker copy-on-first-use); ни один из образов изначально не создавал `/workspaces` внутри себя, поэтому Docker создавал точку монтирования `root:root` — под non-root uid 10001 первый же `mkdir` внутри неё падал `Permission denied`, независимо от единого uid. Обнаружено при живой сборке топологии (оба контейнера впервые подключены к общему volume), не на бумаге: единый uid необходим, но недостаточен без этого шага. Решение — `RUN mkdir -p /workspaces && chown 10001:10001 /workspaces` запечено в **оба** Dockerfile (backend и executor) до `USER 10001`: какой бы контейнер ни стартовал первым, владелец точки монтирования уже корректен. Альтернатива — отдельный init-контейнер в compose, поднимающийся первым и делающий `chown -R` от root, — отклонена: новый элемент топологии ради проблемы, которая решается двумя идентичными строками в уже существующих образах.
- **`security_opt` контейнера executor — `[seccomp=unconfined, apparmor=unconfined, systempaths=unconfined]`, не `--privileged`.** Дефолтные seccomp/AppArmor-профили docker блокируют непривилегированное создание user-namespace и часть mount-операций, на которых стоит bwrap per job (слой 3) — без снятия этих профилей у контейнера executor джоба не может запуститься вообще, независимо от `runtime: runsc`. Это снятие профилей **самого контейнера executor**, отдельное от gVisor: граница изоляции недоверенного кода — `runtime: runsc` (прод) и bwrap на джобу (везде), а не seccomp/AppArmor-профиль контейнера executor сам по себе. `--privileged` для этого не используется сознательно: он расширил бы привилегии контейнера сверх необходимого и создал бы ложное впечатление, что контейнерный seccomp — часть периметра безопасности джобы, тогда как периметр проходит по видимости ФС (bwrap) и по Sentry (gVisor), а не по syscall-фильтру самого контейнера.
- **`tini` как `ENTRYPOINT` образа executor — не `init: true` в compose.** Каждая джоба оставляла в контейнере зомби-процесс `bwrap`: `--die-with-parent`/`--unshare-pid` (кill-контракт, выше) корректно убивают саму джобу, но обвязка (`unshare`+`bwrap`) при выходе реперентится на PID 1 контейнера — а PID 1 (`uvicorn` из `CMD`) не является init-процессом и не жнёт сирот, так что запись в таблице процессов оставалась навсегда, медленно вычерпывая `pids_limit` compose. Из двух мест, где это можно починить, выбран образ (`ENTRYPOINT ["tini", "--"]` + пакет `tini`), не compose-флаг `init: true` для сервиса: гарантия должна держаться везде, где запускается этот образ (смоук-прогон, ручной `docker run` вне compose, будущий прод), а не только там, где кто-то не забыл выставить флаг у конкретного сервиса. `tini` пробрасывает сигналы (включая `SIGTERM` на `stop_grace_period`) в `CMD`-процесс без изменений — kill-контракт джобы и graceful shutdown сервиса не затронуты.
- Оркестрация инструментов кодом (code-mode) при необходимости строится на этом же канале (workspace + internal HTTP) — отдельной инфраструктуры не потребует.
