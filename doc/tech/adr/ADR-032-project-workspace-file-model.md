# ADR-032: Файловый workspace проекта и переезд артефактов из PostgreSQL

## Статус

Принято (feat-011, dogfooding). Уточняет ADR-027 (blob-хранилище артефактов): модель хранения артефактов меняется с PG-таблиц на файлы workspace.

## Контекст

Execution runtime (ADR-031) вводит файловое рабочее пространство: код исполняется над файлами, результаты — файлы. Индустриальный паттерн (Anthropic code execution with MCP, Manus) — файловая система как рабочая память агента: промежуточные результаты живут в файлах, не в контексте модели. Одновременно у проекта уже есть модель артефактов в PG (`artifacts` + `artifact_blobs`, ADR-027) с четырьмя read-endpoint'ами; редактирования пользователем нет, данных прод-масштаба нет (личный догфудинг).

Вопросы решения: скоуп workspace (thread/user/project), где живут артефакты (PG vs файлы), судьба Store-механик (Knowledge Sphere, user memory, custom instructions, skill-context).

## Рассмотренные варианты

**Скоуп workspace:**
1. Per thread — файлы умирают с чатом, ломается «продолжи вчерашнюю работу». Отклонено.
2. Per user — свалка всех проектов, конфликт с доменной моделью (артефакты/KS/настройки живут в проекте), удаление проекта не чистит файлы. Отклонено.
3. **Per project** — совпадает с доменной моделью один в один; ownership уже решён существующей dependency; удаление проекта = удаление директории. Принято.

**Хранение артефактов:**
1. PG остаётся источником правды, workspace эфемерный per job — файловая память агента не реализуется, «продолжи работу» требует пересборки из БД.
2. **Артефакты — файлы в workspace, PG-таблицы упраздняются** — один источник правды, файловая память агента, инструменты сводятся к файловым операциям.
3. Гибрид (workspace рабочий + публикация копией в PG) — два места хранения, нужна дисциплина синхронизации; выгода только в неизменности REST-реализации.

## Решение

**Workspace per project** на именованном volume, смонтированном в app и executor:

```
/workspaces/{project_id}/
├── artifacts/      ← зона публикаций: выход агента (видна UI)
├── uploads/        ← вложения пользователя: вход (file attachments)
└── …               ← рабочие файлы агента
/skills/            ← отдельный ro-mount из репозитория (не в workspace)
```

**Артефакты — вариант 2**: файл в `artifacts/`; таблицы `artifacts`/`artifact_blobs` упраздняются. **Идентификатор артефакта = путь относительно зоны `artifacts/`** (`lecture-1/slides.md`, без префикса `artifacts/`) — искусственный UUID убирается совсем, идентичность несёт сама файловая система, PG-индекса нет. Метаданные — имя файла (`title`), расширение (`type`), mtime (`updated_at`; после перезаписи файла агентом дата обновляется — это `updated_at`, не `created_at`). Вложенность (поддиректории в `artifacts/`) поддерживается по умолчанию.

**Адресация REST — путь в query-параметре**, не в сегменте URL: `GET …/artifacts?path=lecture-1/slides.md` (detail), `…/artifacts/media?path=…`, `…/artifacts/download?path=…`, `…/artifacts` без `path` (list = дерево). Причина: путь-как-сегмент конфликтует со слэшами URL — ASGI разворачивает `%2F` до роутинга, суффиксы `/media`/`/download` становятся неоднозначны, React-роут не матчит слэши. Query-параметр кодирует слэши штатно, вложенность любой глубины работает без спецхаков, суффиксы остаются фиксированными сегментами. Маршруты list/get/media/download сохраняют семантику, меняется сигнатура (path-query вместо `{artifact_id}`).

**Связь «артефакт ↝ чат» в истории** несёт **typed part нового типа `ArtifactPart` {path, title, type, kind, diff?}** (`kind: created | updated` различает создание и перезапись; `diff {added, removed}` — счётчики строк для текстовых обновлений, `null` для бинарных и создания), выводимый из `ToolMessage.artifact` при реплее чекпоинта — не PG-колонка `message_id` (её механизм упраздняется вместе с таблицей). Путь становится сквозной идентичностью: запись (diff-снапшот джобы / `write_file` → `ArtifactPart` в чекпоинте) и чтение (реплей чекпоинта → карточка по пути → файл по пути) обходятся без PG-маппинга. Фронт переучивается рендерить артефакты на уровне part, не из `message.artifacts`. Джоба с N новыми файлами даёт N `ArtifactPart` (конверт `content_and_artifact` расширяется до списка). Из detail-контракта уходят `thread_id`/`message_id`.

SSE `artifact_created` эмитится файловым слоем backend: при прямой записи агентом — сразу, после джобы — по diff-снапшоту зоны `artifacts/`, который backend снимает до и после джобы сам (executor файлы не отчитывает — та же модель доверия ADR-031; снимает и вопрос валидации путей из песочницы). Тот же снапшот отличает новый путь от изменившегося: перезапись существующего эмитит **`artifact_updated`** (новый SSE-тип рядом с `artifact_created`) с компактной дельтой строк `{added, removed}` — счётчики, не полный дифф (для полного нужна старая версия, а версий модель не хранит; полный дифф-просмотр — backlog «Версии артефактов»). Wire-имя типа файла в обоих событиях — `artifact_type`: конверт SSE плоский, ключ `type` из payload затёр бы тип события; `type` — только в `ArtifactPart` истории. Эмиссия остаётся в reporter'е узла за guard-проверкой; `content_and_artifact` несёт список артефактов (N файлов джобы → N событий, каждое created или updated).

**Границы путей** — единая точка в файловом слое backend, два разрешённых корня: workspace `/workspaces/{project_id}` (rw) и `/skills` (ro). Резолв против подходящего корня по канонизированному пути (`resolve()` + `is_relative_to()`); `write_file` — только workspace, `/skills` read-only. `project_id` только из `AgentContext` (не параметр инструмента). Отказ резолва — доменное исключение + security-лог (`agent.runtime.path_denied`).

**Store-механики остаются**: Knowledge Sphere (per project), user memory, custom instructions, skill-context (per user) — специализированное хранилище с семантическим поиском; per-user данным в per-project workspace структурно не место.

**Скиллы**: хранение — репозиторий (git, деплой релизом), доступ — ro-mount в оба контейнера по пути `/skills`. Копии в workspace нет — нет задачи сверки. Вход в скилл — `load_skill` (SKILL.md + skill-context), отдельные файлы — `read_file`. Модель хранения пользовательских скиллов — открытый вопрос feat-007, текущая модель двери не закрывает.

## Следствия

- Инструменты агента: `create_artifact` упраздняется (покрыт `write_file` и diff-снапшотом джобы); `load_skill` **остаётся** — семантический вход в скилл, читает `SKILL.md` через файловый слой (`/skills`) и докидывает per-user индекс skill-context из Store (механика персонализации сохраняется); `generate_image` пишет файл в `artifacts/` вместо PG-блоба (имя = слаг `title` + расширение из mime ответа, запись `tmp + rename` вместо PG-транзакции; промпт лишается колонки `content` — виден в аргументах вызова в ленте и в Langfuse; вызов image-модели и качество не меняются). Появляются `read_file`, `write_file`, `list_files`, `execute_code`, `run_command`.
- Фронт: `id` артефакта становится путём-строкой в query-параметре; артефакты в истории рендерятся из `ArtifactPart` (не `message.artifacts`); обвязка подписей инструментов и фикстура имён обновляются.
- Удаление проекта чистит workspace (директорию) вместо каскада `artifact_blobs`.
- Файловая модель поглощает file attachments (бывшая feat-004): вложение пользователя = файл в `uploads/`, загрузка — multipart через файловый слой в момент отправки сообщения; backend дописывает пометку с путями в user-сообщение (модель) и список вложений в metadata (UI-чип). Ingestion-пайплайна нет: извлечение текста из бинарных форматов агент делает через executor. Контракт — в design-brief feat-011 § Вложения пользователя.
- Конкурентный доступ (два чата одного проекта) — норма рабочей директории; атомарность записи `tmp + rename`; переименование файла агентом делает старые ссылки истории битыми — принято.
- **Существующие данные не мигрируются**: артефактов/чатов прод-масштаба нет (личный догфудинг) — старые артефакты и, при необходимости, чаты сносятся. Миграция сводится к drop-миграции таблиц `artifacts`/`artifact_blobs` (autogenerate против запущенной БД по conventions/db.md); выгрузки PG→файлы и маппинга UUID→путь нет. Обратная совместимость истории до миграции не проектируется.
- Бэкап прода расширяется с «дамп PG» до «дамп PG + volume workspaces» — контур продумывается ближе к реальному проду.
- Зафиксированное направление: Knowledge Sphere — кандидат на файловую модель в workspace (масштабирование на десятки разделов, менеджмент файловыми операциями агента) — отдельной итерацией вместе с версионированием сферы; фундамент делает переезд дешёвым (новая зона workspace).
- ADR-027 остаётся историей решения для PG-эпохи. Кэш media **меняется**: immutable-кэш (был корректен для неизменного UUID-блоба) заменяется на **ETag/Last-Modified из (mtime + size) + `Cache-Control: no-cache` (ревалидация)** — путь-id перезаписываем, immutable отдавал бы вечно старую версию. Браузер шлёт условный запрос, сервер отвечает 304 (не менялось) или 200; фронт дополнительно инвалидирует media-ключ по событиям `artifact_created`/`artifact_updated`, а список артефактов — по завершении каждого хода (событий удаления/переименования нет — без этого список копил бы карточки-призраки).
