# ADR-033: OAuth Identity Model

## Статус

Принято

## Контекст

Вход через внешних провайдеров (Яндекс ID, Google, GitHub) добавляется к существующему парольному входу (JWT + refresh, [ADR-011](ADR-011-auth-architecture.md)). Пользователь при этом может иметь несколько провайдеров, ни одного пароля, или и то и другое — auth-схема токенов не меняется, но модель идентичности пользователя требует решения: как связать `User` с внешним аккаунтом, что делать с паролем при OAuth-регистрации, нужен ли `email` как способ сматчить OAuth-вход с уже существующим парольным аккаунтом.

Ресёрч сверил четыре эталона: Auth.js/NextAuth (`accounts`), Django allauth (`SocialAccount`), better-auth (`account`), Rails omniauth (`identities`). Все четыре независимо сходятся на одной форме.

## Решения

### Идентичность — отдельная таблица `oauth_accounts`, ключ `(provider, provider_account_id)`

Не поля `oauth_provider`/`oauth_uid` в `users`. Единогласный эталон всех четырёх систем: связка 1:N от `User` к внешним аккаунтам, `UNIQUE(provider, provider_account_id)`. Гонка при параллельном создании закрывается самим constraint'ом (`INSERT` + обработка unique violation через `SAVEPOINT`-retry), не `SELECT`-then-`INSERT` — согласуется с правилом «бизнес-инварианты в БД» (db.md).

**Отклонено:** поля прямо в `users` — ограничивает одного провайдера на пользователя, требует NULL-пар для парольных пользователей, кривой unique по nullable-паре. Ни один эталон так не делает.

### `password_hash` → nullable, честный NULL без sentinel

OAuth-пользователь не заводит пароль. `NULL` — прямая семантика «пароля нет»; парольный вход при `password_hash IS NULL` отклоняется тем же 401, что и неверный пароль (способ входа аккаунта не раскрывается наружу).

**Отклонено:** sentinel-значение (невалидный хеш à la Django `!`-префикс) — магическое значение вместо явного NULL, семантика «пароля нет» перестаёт быть видна из схемы. Django к этому привязан историческим ограничением NOT NULL, у проекта такого долга нет.

### Авто-линковка по email запрещена; `users.email` не вводится

OAuth-аккаунт находится или создаётся исключительно по `(provider, provider_account_id)`. Совпадение email с существующим парольным пользователем не триггерит автоматическую связку.

Причина — pre-account-takeover: неверифицированный (или скрытый — GitHub может не отдавать email) email как ключ линковки позволяет атакующему завести аккаунт у стороннего провайдера с чужим email и получить доступ к существующему пользователю платформы. `users.email` как колонка не заводится вообще: в v1 email не участвует ни в логине, ни в линковке, а unique + не-verified email на `users` был бы ровно той же дырой. Email от провайдера хранится нейтрально — как nullable-колонка `oauth_accounts.email`, факт «что сообщил провайдер на момент входа», без права участвовать в поиске пользователя.

Ручная линковка (пользователь осознанно привязывает второй провайдер к своему аккаунту в настройках) схемой не заблокирована — просто не реализована в v1.

**Отклонено:** `users.email` NOT NULL/unique уже сейчас — GitHub скрывает email по построению (NULL), а уникальный неверифицированный email — сама по себе заготовка pre-account-takeover.

### Токены провайдера и сырой профиль не хранятся

`oauth_accounts` несёт только то, что нужно для идентификации при повторном входе: `provider`, `provider_account_id`, `email`. Access/refresh/id_token провайдера, scope, raw JSON-профиль — не персистятся.

OAuth в системе используется одноразово, на входе: обмен `code` → `token` → `userinfo` происходит один раз за флоу, дальше работает собственная сессионная машина (`refresh_tokens`, не зависящая от способа входа). Хранение токенов провайдера оправдано только при последующих вызовах его API от имени пользователя (кейс Auth.js) — у проекта такого потребителя нет. Подтверждено эталоном: allauth по умолчанию токены не хранит (`SOCIALACCOUNT_STORE_TOKENS=False`) именно по этой причине.

**Отклонено:** отдельная таблица токенов провайдера (allauth `SocialToken`) — нет потребителя. Сырой профиль в JSONB — балласт PII без потребителя; единственное нужное поле (`email`) уже вынесено явной колонкой.

### Провайдеры — `Text` + `CHECK`, не `pg-ENUM`

`provider` — enum-подобная строка, зашитая в код (`OAUTH_PROVIDERS` в `app/models/oauth_account.py`), constraint генерируется из неё же (`CHECK (provider IN (...))`). `pg-ENUM` запрещён общей конвенцией проекта (дорог в эволюции, требует `ALTER TYPE` вне транзакции); новый провайдер стоит код + одну tривиальную миграцию — цена, уже принятая для остальных enum-подобных колонок проекта (db.md).

## Следствия

- Новая таблица `oauth_accounts` (миграция `e7fac2fe3bdf`): PK UUID, FK на `users.id` (`ondelete=CASCADE`, индексирован), `UNIQUE(provider, provider_account_id)`, `CHECK` по составу провайдеров.
- `users.password_hash` — nullable; `AuthService.login` проверяет `NULL` явной веткой до `verify_password`.
- Инвариант «пароль ИЛИ oauth-связка» не выражается CHECK-constraint'ом (кросс-табличный) — контролируется сервисным слоем: создание OAuth-пользователя и его первой `oauth_accounts`-записи происходит одной транзакцией.
- Точка расширения: ручная линковка/отвязка провайдера, смена пароля OAuth-пользователем — не реализованы, схема этому не мешает. Возврат ранее исключённого провайдера (VK ID) — код + расширение `CHECK`, без структурных изменений.
- Полная механика флоу (endpoints, cookie `oauth_flow`, гео-gate, реестр кодов ошибок) — [auth.md](../auth.md#oauth-вход). Ресёрч и сверка с эталонами — `research-data-model.md` (`doc/tasks/iterations/dogfooding/feat-008-oauth-auth-screens/`).
