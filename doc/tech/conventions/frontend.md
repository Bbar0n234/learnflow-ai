# Конвенции: Frontend

Проектные решения по структуре frontend, состоянию и мутациям. Ядро — [conventions.md](../conventions.md).

## Frontend

Теория FSD и паттернов состояния — в skill `feature-sliced-design` и skill-map. Здесь — только решения проекта: выбранные развилки и осознанные отступления на нашем коде (`frontend/src`).

### Раскладка по слоям (FSD-адаптация)

Слои: `app/` (shell — providers, router, layouts, Sidebar и его project-компоненты), `pages/` (композиция уровня маршрута), `features/` (переиспользуемые interactions), `shared/` (инфраструктура). Слой `widgets/` и `entities/` **не вводим** — нет материала (нет UI-блоков, переиспользуемых между несколькими страницами; доменные модели не переиспользуются между страницами). Появится — заведём тогда, не «на вырост».

Осознанные отступления от каноничного FSD (документируем, т.к. скилл требует фиксировать причину):

- **`features/` = только реально переиспользуемое.** Слайс в `features/` заводится, когда interaction используется в 2+ страницах. Сейчас это `model-selector` и `mcp-servers` (оба тянут чат + user-settings + project-settings). Одиночные экраны — это `pages/`, а не `features/`.
- **`stores/` живёт на верхнем уровне `src/`, а не в `model/`-сегментах слайсов.** Причина: `stream-store` — cross-feature (пишет `pages/chat`, читают компоненты чата), привязка к одному слайсу неверна. `ui-store` — глобальный UI-флаг сессии.
- **`shared/` импортируется по доменным файлам, без barrel-индексов.** У `shared/` нет слайсов (правило публичного API FSD — про слайсы), поэтому `@/shared/api/projects`, `@/shared/ui/button` легальны и предпочтительны 13-экспортному баррелу (хуже tree-shaking, лишняя возня).

### Публичные API слайсов

Каждый слайс `pages/` и `features/` экспортирует наружу только через `index.ts`; внешние потребители (роутер, layouts, другие страницы) импортируют из него, не из внутренних файлов. Внутри слайса — сегменты `ui/` (компоненты), `model/` (оркестрация/состояние, напр. `pages/chat/model/useAgentStream.ts`). Это даёт свободу рефакторинга внутренностей слайса за стабильным контрактом.

### Ось состояния: серверное в Query, клиентское в Zustand

- **Серверные данные — только TanStack Query.** Data-хуки (`useProjects`, `useChat`, `useSecurityAPI`, …) живут в `shared/api/<domain>.ts` рядом с API-функциями и DTO-типами (CRUD — инфраструктура, по FSD место в `shared/api`). Компоненты вызывают хуки, не API-функции напрямую. **Исключение — императивный некэшируемый write-вызов**: когда эндпоинт только пишет и кэшировать нечего (загрузка файла, скачивание), компонент дёргает API-функцию напрямую, без хука-обёртки — так устроены `uploadFile` и `downloadArtifact`. Хук ради буквы правила создал бы ложное ожидание кэш-инвалидации там, где инвалидировать нечего.
- **Клиентское UI-состояние — Zustand** (`stores/`). Серверные данные в стор **не дублируем**; производное (активный таб, текущий проект/чат) вычисляем из URL (`useParams`), не храним.
- **Подписки на стор — через селекторы** (`useUIStore((s) => s.sidebarOpen)`), не деструктуризацией всего стора: иначе компонент перерисовывается на любое изменение стора.

### Состояние стрима: модель ленты чистая, стор — её держатель

Лента активности агента (что видно во время хода и что переживает перезагрузку) описана чистой моделью `shared/lib/agent-feed.ts`: редьюсер событий `applyStreamEvent(state, event)`, адаптер истории `fromMessageParts(parts)`, редакция `redactFeed(stub)`, группировка блоков `groupFeedBlocks(feed)`. `stores/stream-store.ts` эту модель только держит и отдаёт подписчикам (`StreamState extends AgentFeedState`); единственная точка мутации ленты — экшен `applyEvent(event)`, отдающий событие целиком редьюсеру.

Нормализация контракта в ленту — знание одного места. Набор мелких экшенов («дописать текст», «отметить активный инструмент») размазал бы решение «какое событие во что превращается» по диспетчеру `pages/chat/model/useAgentStream.ts`, чья работа — транспорт: читать поток, отдавать события модели, обрабатывать терминальные и инвалидировать кэши. Побочный эффект единственной точки мутации: событие, ленты не касающееся (`heartbeat`, `done`, `artifact_created`, `artifact_updated`), возвращает тот же объект состояния, и zustand не будит подписчиков вовсе.

**Между чтениями тела потока диспетчер уступает событийному циклу** (`yieldToEventLoop` в `pages/chat/model/useAgentStream.ts`). Кадры одного чтения разбираются синхронно и сводятся в одну перерисовку, но когда сервер отдаёт накопленное разом, `reader.read()` резолвится уже готовыми данными — микрозадачей, а не задачей ввода-вывода, — и чтения идут вплотную. Каждое обновляет стор по sync-lane (`useSyncExternalStore`), поэтому у React после каждого коммита остаётся незакрытая работа, и его сторож вложенных обновлений (`NESTED_UPDATE_LIMIT = 50`) на пятом десятке чтений подряд бросает исключение: диспетчер принимает его за обрыв соединения, и ход теряется целиком вместе с ответом. Уступка размыкает цепочку — React успевает закоммитить кадр до следующего чтения. Носитель уступки — `MessageChannel`, а не `setTimeout`: фейковые таймеры её не подменяют, и транспорт остаётся независим от того, чем тест двигает время. Замер границы: без уступки ход из 55 кадров до `done` уже не доходит, с ней проходит и 400.

Скаляров «текущий текст» / «текущий инструмент» в сторе нет: строки адресуются по `call_id` внутри самой ленты, параллельные вызовы живут и закрываются независимо. Второй индекс рядом с лентой (карта активных вызовов, список ожидающих карточек) не заводится — узлы ленты иммутабельны и пересоздаются на каждой мутации, поэтому такой индекс немедленно становится вторым источником правды. Производное от ленты (карточка генерации изображения, активная строка, сигнал автопрокрутки) вычисляется из неё на рендере.

Тикающее время в сторе не хранится: модель фиксирует момент старта вызова и итоговую длительность, а «сколько уже идёт» — локальное состояние строки. Секундный тик в сторе будил бы всех подписчиков ради одной подписи.

Один и тот же компонент ленты рисует live и историю — структура у них общая по построению: адаптер истории даёт ту же форму, что редьюсер live. Расхождение между тем, что показал стрим, и тем, что видно после перезагрузки, — баг модели, а не разных экранов.

### Живость строки: статус из модели, тишина по времени

Живость строки — основание для всего, что показывает работу агента: бегущих точек, счётчика времени, подписи процессом («Рассуждаю» против «Рассуждал») и строки-паузы, которая обязана закрывать любой промежуток хода без движения на экране. Берётся она из двух источников, разных по природе.

У строки вызова живость лежит в модели: `status: "running"` до парного `tool_result`. Ищется рекурсивно по всей ленте — шаг субагента живёт в `children` строки его вызова, и работающий субагент делает живым и себя, и своего родителя.

У рассуждения и текста статуса в контракте нет вовсе, и **из положения элемента в списке он не выводится**: хвост остаётся хвостом и после того, как в него перестали дописывать — от последнего фрагмента до следующего события ленты проходит сколько угодно времени, и всё это время «последний элемент» врал бы, что поток пишет в него. Поэтому живость хвоста измеряется фактом прихода данных: `useFeedSilence` (`pages/chat/ui/MessageList.tsx`) отвечает, молчит ли лента дольше порога. Носитель факта — идентичность самой ленты: редьюсер иммутабелен и пересоздаёт массив ровно тогда, когда событие в ней что-то изменило, а событие, ленты не касающееся, возвращает прежнее состояние и подписчиков не будит. Отдельного счётчика рядом с лентой не заводится — он разошёлся бы с ней на первой правке модели.

Состояние такого признака пишется **только таймером**, после коммита, а на рендере лишь сравнивается с текущей лентой. Правка состояния на фазе рендера здесь запрещена, хотя и выглядит короче: она превращает каждое обновление стора в лишний проход. Сравнение же на рендере даёт нужное свойство построением — кадра, в котором новые данные уже на экране, а пауза ещё висит, не существует, потому что новой ленте отметка тишины не равна никогда.

Порог тишины — **2 с**, и он зажат между двумя величинами протокола, а не выбран на глаз. Сверху — интервал биений (`heartbeat`, 5 с): окно, которое сервер сам считает достаточно долгим, чтобы напомнить о себе, экран не должен проживать немым. Снизу — темп фрагментов живого потока (десятки миллисекунд): порог на два порядка выше, поэтому нормальная генерация паузу не зажигает, а мигающая пауза хуже её отсутствия. Меняется любая из этих двух величин — порог пересчитывается.

Признаки строки разведены: `active` — эта строка хвост, то есть **куда** придёт следующий фрагмент; `live` — данные идут **прямо сейчас**. Подпись, точки и цвет строки живут по обоим (`active && live`), а авторазворот рассуждения — только по `active`: пауза в потоке гасит подпись, но схлопывать при этом уже показанный текст значит прятать от пользователя то, что он читает, и раскрывать обратно на следующем фрагменте. Отсчёт тишины — локальное состояние компонента, как и тикающий счётчик строки, и это один таймер ровно на момент истечения порога: между фрагментами перерисовывать нечего.

### Добавляешь инструмент агенту

Фронтовая половина чек-листа; бэкендовая — в [agent.md § «Добавляешь инструмент агенту»](agent.md#добавляешь-инструмент-агенту). Здесь — что делать после того, как инструмент заведён в реестре бэкенда и фикстур имён перегенерирован.

1. **Завести запись в реестре подписей.** Реестр — `shared/config/agent-tools.ts` (`AGENT_TOOL_SIGNATURES`), ключ — имя инструмента с провода. В записи: `label` — действие по-русски от лица агента в настоящем времени («Ищу в интернете», «Обновляю память проекта»); `pastLabels` — прошедшие формы для завершённой строки: `done` — совершенный вид для success («Обновил память проекта»), `interrupted` — несовершенный для error/pending/cancelled («Обновлял память проекта»); запись без `pastLabels` держит `label` на всех статусах — так работают подписи-имена (`run_subagent`) и MCP fallback; `icon` — компонент `lucide-react` (файл остаётся `.ts` — хранит ссылку на компонент, не JSX); `argTemplate(args)` — осмысленное дополнение подписи из разобранных аргументов (поисковый запрос в кавычках, идентификатор раздела памяти, ключ записи); `labelTemplate(args)` — когда сама подпись зависит от аргументов (единственный носитель — `run_subagent`: `agent_type` даёт «Проверяющий субагент»). Оба шаблона возвращают `null`, когда нужного аргумента нет, — тогда остаётся базовый `label` либо подпись без дополнения. Дополнение возвращается **без разделителя**: «·» ставит рендер строки, зашитый в записи он стал бы второй точкой правды при смене грамматики.
2. **Пропуск красит CI, а не оставляет тихий пробел в UI.** Фикстур имён `backend/contracts/agent-tool-names.json` генерирует бэкенд (команда — в чек-листе `agent.md`), а `shared/config/agent-tools.test.ts` требует запись в реестре для каждого имени фикстура и падает с именем инструмента в сообщении. Своего списка имён у фронта нет намеренно: он сторожил бы сам себя и на забытую подпись не покраснел бы. Реестр держится полной ширины — read-only инструменты порождают такие же `tool_call_*` и видны в ленте, объявленный, но выключенный сервер может включиться на бэкенде без правок фронта.
3. **Имя вне реестра UI не ломает — дописывать ветку не надо.** `resolveToolSignature(name)` для незнакомого имени (пользовательский MCP) отдаёт сырое имя как `label`, нейтральную пометку «инструмент MCP» в слот дополнения и `known: false` — та же грамматика «подпись · дополнение», что у знакомого инструмента. Имя сервера в пометку не подставляется: его нет ни в SSE-событиях, ни в `ToolCallPart`, ни в фикстуре — искать это поле бесполезно.
4. **Аргументы разбираются только целые.** `parseToolArgs(args, truncated)` — единственная точка разбора: `args` приезжает JSON-строкой, при усечении она обрезана посреди JSON и невалидна, поэтому усечённая не парсится вовсе, а целая — под `try/catch`. Неудача разбора означает подпись без дополнения, а не пустую строку и не исключение. Оборванный JSON на экран не идёт и в развороте: там вместо аргументов стоит явное «Аргументы оборваны сервером — не разобраны».
5. **Флагов усечения два, и они независимы.** `argsTruncated` — про аргументы, `resultTruncated` — про результат; live даёт их раздельно (`tool_call_args.truncated` / `tool_result.truncated`), история — полями `args_truncated` / `result_truncated` у `tool_call`-part. Схлопывать их в один флаг нельзя: длинный результат (обычное дело для поиска) пометил бы усечёнными и аргументы, разбор бы не состоялся, и строка поиска потеряла бы дополнение подписи — сам запрос, ради которого оно и заведено.
6. **Содержимое результата — raw-разворот, честный про усечение.** Результат показывается сырым текстом: большие значения свёрнуты в три строки с кнопкой раскрытия; факт серверного усечения несёт формулировка кнопки («Показать всё, что пришло» вместо «Показать полностью») — отдельного бейджа у зоны нет. Типизированный rich-рендер по видам результата этим чек-листом не вводится: новый инструмент своей карточки в UI не получает.

### Фабрика query keys

Единственный источник ключей — `shared/api/query-keys.ts` (объект `queryKeys`). Инлайн-литералов `["projects", id, …]` в хуках/компонентах нет. Иерархия ключей намеренная: префиксная инвалидация (`invalidateQueries({ queryKey: queryKeys.projects.detail(id) })`) задевает всех потомков. Новый ресурс → сначала ключ в фабрику, потом хук.

### Optimistic vs пессимистичные мутации

Дефолт — **пессимистичный**: дождаться ответа сервера, затем `invalidateQueries` (и/или `setQueryData` вернувшимся значением). Так сделаны все мутации, включая security ack/resolve — для admin-панели корректность важнее мгновенности. **Optimistic update с откатом** (`onMutate` снимает снапшот → `onError` восстанавливает) держим в резерве для частых низкорисковых взаимодействий. Оптимистичные патчи в текущем UI: `security_block` в `useAgentStream` (терминальный, отката не требует) и feedback-кнопки `FeedbackButtons` — с откатом при ошибке (`setFeedback(prevFeedback)`).

### Граница shadcn в `shared/ui`

`shared/ui/` — UI-kit: примитивы shadcn (генерируются CLI по `components.json`, **руками не правим** — перегенерация затрёт) и наши общие UI-композиции поверх них (напр. `MarkdownRenderer`, `Wordmark`, `SphereOrb`, `Illustration`). Отдельной папки под «наше» не заводим (одна композиция — оверинжиниринг); граница «сгенерированное / наше» — по этому соглашению, не по дереву каталогов.

### Дизайн-токены и темизация

Цвета, тени, радиусы, типографика — только через CSS-переменные токенов («Чернила / Электрик», `frontend/src/index.css`) и Tailwind-утилиты; хардкод hex/rgba в `.tsx` запрещён. Фиолетовый в UI всегда плоский — радиальный градиент живёт только в `SphereOrb` (токены `--orb-*`). Полный контракт системы (палитра, шрифты, переключатель темы, бренд-примитивы, иллюстрации, error UX) — [design-system.md](../design-system.md).

### Гейтинг незрелых фич (stub-gating)

Фичи, у которых ещё нет бэкенд-контракта и которые реализованы на mock-данных, **не должны рендериться в проде** — иначе обычный пользователь увидит fake-контент. Гейтятся за единым флагом `shared/config/feature-flags.ts`, привязанным к `import.meta.env.DEV`: в dev-сборке (`make dev-fe`) фичи видны для догфудинга, в прод-сборке (`vite build`) флаг статически `false` → ветки мертвы, Rollup DCE убирает и сам мок (строки выпадают из бандла). Гейт ставится в точке рендера (`FLAG && <Feature/>`), мок-данные при этом остаются референсимы внутри ветки (lint не ругается на «unused»). Раз-гейтить индивидуально по фиче, когда появляется её бэкенд. Проверка после правок: распознаваемые мок-строки отсутствуют в `dist/` (grep собранного бандла).

### Логирование

`import { logger } from "@/shared/lib/logger"` вместо `console.*` (обёртка фильтрует по `DEV`/`PROD`). Прямых `console.*` в коде нет.
