# Конвенции: Тестирование

Проектные решения по тому, что и чем мы тестируем, как раскладываем и пишем тесты, и что считаем зелёным. Ядро — [conventions.md](../conventions.md). Доменные нормы, на которые тесты опираются, живут в своих местах и **не дублируются здесь**: миграции, сессии и транзакции — [db.md](db.md); REST-контракты, problem+json, статус-коды, аутентификация на эндпоинтах — [api.md](api.md); устройство agent runtime — [agent.md](agent.md); FSD-раскладка и состояние фронта — [frontend.md](frontend.md).

Базовый раннер бэкенда — **pytest** (async через pytest-asyncio); фронта — **Vitest**. Запуск всегда через Makefile (`make test`, `make test-fe`), а не сырой `pytest`/`vitest`: цели уводят прогон в нужную директорию пакета и поднимают сеть вне sandbox.

## Модель: что и чем тестируем

Мы **не следуем ни одной тестовой пирамиде на 100%**. Берём лучшее из подходящих моделей: trophy/diamond-скелет для бэкенда и фронта (центр тяжести — sociable-unit и integration), honeycomb-идею контракта для одной границы (main app ↔ siem-service через `packages/siem-contracts`), статический анализ (`make check` / `make check-fe`) как самый широкий и дешёвый фундамент. Первичен не силуэт распределения, а **стиль**: выразительные тесты, проверяющие поведение, быстрые и детерминированные, падающие только по полезной причине.

**Sociable-unit по умолчанию, solitary — точечно.** Тестируя сервис с коллабораторами, настоящих ин-процесс соседей (чистые функции, форматтеры, другие компоненты того же процесса) **не подменяем** — дублируем только болезненные границы: внешний мир, недетерминизм, медленное I/O (Redis, сеть, LLM). Solitary-стиль (все соседи — дубли) применяем только там, где он естественен: чистая функция без зависимостей. На таких чистых функциях (нормализация, парсинг, сериализация) уместен property-based (Hypothesis) — вместо набора примеров проверяем инварианты на сгенерированных входах. Причина выбора solitary именно здесь — solitary на каждый сервис заставляет мокать всех соседей, тест узнаёт слишком много про внутреннее устройство и ломается от любого рефакторинга (см. § Дубли и § Антипаттерны).

**Реальная инфраструктура — только под тот слой, ради которого она существует.** Тяжёлую инфру (Postgres через testcontainers) поднимаем не под каждый тест, а под repository-integration, где проверяется сам SQL (JOIN, eager-загрузка, пагинация, constraints) — там фейк бессмысленен (мокать SQLAlchemy = тестировать заглушку). Логику сервисов с коллабораторами гоняем на фейках в памяти, без БД. Логику графа и guard — на фейковой модели, без сети и ключа.

Соответствие «слой → тип теста»:

| Слой / участок | Тип теста | Дубли / инфра |
|----------------|-----------|---------------|
| Чистые функции (нормализация, парсинг, сериализация) | solitary-unit | без дублей — зависимостей нет |
| Service / бизнес-логика | sociable-unit | fake-коллабораторы в памяти (репозитории, runner, store) |
| Repository | integration | реальный Postgres (testcontainers) + транзакционный откат |
| HTTP-handler / REST-контракт | integration | ASGI-клиент + аутентифицированная фикстура; БД реальная или fake-сервис — по тому, что под handler'ом (поверх repository → реальная БД на транзакционном откате; поверх сервиса с фейками → fake) |
| Rate-limit / скользящее окно | solitary-unit (near-pure) | инъекция монотонных часов (`time.monotonic`), без Redis |
| Agent-node / граф / роутинг | unit | `GenericFakeChatModel`, `InMemorySaver` |
| Security guard / ветвление по вердикту | unit | guard-стаб, возвращающий `GuardResult` с нужным `verdict` |
| SIEM event parsing / ingest | sociable-unit + integration | фейки для sociable-логики; реальный Postgres под ingest (как repository) |
| SSE-маппер событий | unit | фейк-модель, сбор событий в список |
| SSE-эндпоинт (поток целиком) | integration | async ASGI-клиент, `.stream()` |
| Контракт main ↔ siem | contract | словарь `packages/siem-contracts/siem_contracts/`; тесты-стражи в `packages/siem-contracts/tests` |
| Frontend: компонент + хук + сеть | integration (основной объём) | MSW, свежий `QueryClient` |
| Frontend: чистая логика, store, хук | unit | сброс Zustand-сторов |
| Сквозной journey | smoke / e2e | `create_app()` обоих сервисов (smoke); Playwright (e2e — узко) |

Глубина покрытия дифференцирована (см. § Coverage и DoD): широкое покрытие поведения везде, дополнительная глубина (edge/negative) — на критпутях: auth, security guard, agent runtime, chat/SSE.

**Rate-limit — near-pure unit.** Скользящее окно (`infra/rate_limit.py`) — in-memory структура на `time.monotonic()`, не Redis, поэтому framing «Redis — болезненная граница» к нему не применим: дублируем только часы. Инъекция монотонных часов делает тест детерминированным — проверяем N+1 запросов → 429 + `Retry-After` и истечение окна.

**Контракт vocabulary — обе стороны границы.** Контракт-тест проверяет не только внутреннюю целостность словаря (`packages/siem-contracts/siem_contracts/vocabulary.py`), но и что эмиттер (main app) и консьюмер (siem-service) ходят в один `vocabulary` — ловит cross-side drift, когда одна сторона разъезжается с другой.

## Структура и нейминг

**Расположение.** Тесты бэкенда живут в своём пакете рядом с его `pyproject.toml`: `<package>/tests/<scope>/...` (например `backend/tests/`, `services/siem-service/tests/`). Внутри пакета режем по подсистемам (`tests/auth/`, `tests/agent/`, ...) — директории скоупов не пересекаются, что позволяет писать тесты параллельно без конфликтов по коду. Общие тест-утилиты (фикстуры, фабрики, билдеры, фейки, SSE-хелперы) — в выделенном пакете `packages/testing`, который сервисы подключают dev-зависимостью; дублировать фейки по пакетам запрещено. Контрактные тесты библиотеки живут в самой библиотеке (`packages/siem-contracts/tests`). Фронтенд — колокация теста рядом со слайсом/сегментом (`Button.tsx` ↔ `Button.test.tsx`), e2e — отдельным top-level каталогом (кросс-слайсовые сценарии).

**Имена.** Файлы — `test_<unit>.py`. Функции — `test_<unit>_<condition>_<expected>` (что тестируем, при каком условии, какой исход). Таблицы «вход → ожидание» — через `parametrize`, а не копипаста тестов.

**Структура теста — AAA** (Arrange / Act / Assert): подготовка данных и дублей → одно целевое действие → проверка. Один тест проверяет **одно поведение**; ассерты группируются в один логический assert-блок про этот исход, а не россыпь несвязанных проверок.

**Тест проверяет поведение, не реализацию.** Проверяем наблюдаемый контракт — вход → выход / побочный эффект через публичный интерфейс. Не лезем в приватные методы, внутренние вызовы, структуру состояния. Диагностический признак нарушения: тест краснеет при рефакторинге, который **не менял поведения** (переписали цикл на регулярку с тем же результатом, заменили N вызовов на батч). Такой тест прибит к реализации — он тормозит рефакторинг и врёт о регрессии.

**Маркеры** `@pytest.mark.unit` / `integration` (опц. `slow`) — для селективного прогона: быстрый unit-гейт отдельно от полного набора с БД.

## Async и pytest

Async-движок — **pytest-asyncio 1.x в режиме `asyncio_mode = "auto"`**: любой `async def`-тест подхватывается без явного `@pytest.mark.asyncio`. (anyio-маршрут не берём — его единственная выгода, trio-совместимость, нам не нужна.)

- Фикстура `event_loop` в 1.x **упразднена** — scope событийного цикла задаётся аргументом `loop_scope` у маркера и фикстуры (`@pytest_asyncio.fixture(loop_scope="session")`), не переопределением `event_loop`.
- **Согласование loop scope обязательно.** При session-scoped engine (asyncpg) и function-scoped event loop соединение, созданное в одном loop, нельзя использовать в другом → `RuntimeError: Future attached to a different loop`. Лечение — держать весь async-стек (engine, соединение, клиент) на согласованном loop scope.
- **Scope фикстур — баланс скорости и изоляции.** Дорогое и неизменяемое (контейнер БД, engine, прогон миграций) → `session`. Состояние, которое тест меняет (соединение/транзакция/сессия, HTTP-клиент) → `function`. Session-scoped мутабельное состояние — антипаттерн (протечки между тестами).
- **conftest-иерархия — это фича.** Корневой `conftest.py` держит кросс-проектные фикстуры; conftest рядом с пакетом — специфику пакета; pytest собирает фикстуры вверх по дереву, переопределение работает по близости.
- **Проверка логирования** — `structlog.testing.capture_logs` (контекст-менеджер, перехватывает события без вывода), а не `caplog`.

## HTTP-тесты

HTTP-слой тестируем через **`httpx.AsyncClient` поверх `ASGITransport`** — приложение вызывается в памяти, без сокета. Синхронный `TestClient` для async-кода не дефолт (в частности, он буферизует SSE-стрим — для честной проверки потока нужен async-клиент с `.stream()`).

```python
from httpx import ASGITransport, AsyncClient

async with AsyncClient(transport=ASGITransport(app=app), base_url="http://test") as client:
    resp = await client.get("/api/...")
```

- **lifespan не запускается** `AsyncClient`'ом сам по себе. Ресурсы (engine, сессия, agent/guard) подменяются фикстурами через `app.dependency_overrides` (предпочтительно — так подменяем БД-сессию на тестовую транзакцию и модель на фейк), либо при необходимости реального lifespan — через `LifespanManager` из `asgi-lifespan`. Каждый `create_app()` изолирован, `app.state` не протекает между тестами.
- **Аутентифицированный клиент.** Защита стоит на каждом приватном endpoint, поэтому дефолтная фикстура ходит «как залогиненный пользователь» через **override `Depends`-провайдера текущего пользователя** (`app.dependency_overrides` на тест-юзера) — быстро, без минта реальных JWT, обходит крипто. Эта фикстура — для тестов, которые проверяют **не** auth, а защищённую функциональность за ним. Сам auth-флоу (логин, refresh-ротация, отзыв токена) тестируется **отдельной узкой группой** через реальный логин-флоу (`/auth/login` → токены → хождение с ними).
- **Одна сессия на тест — конкурентные запросы не поддерживаются.** Клиент и тело теста делят одну транзакционную `AsyncSession` (хендлер видит данные фикстур без коммита). Цена — у `AsyncSession` одно соединение: два запроса разом в одном тесте (`asyncio.gather(client...)`, открытый SSE + второй вызов) падают «another operation is in progress». Это следствие транзакционного отката (§ Тестовая БД), не дефект харнесса; тесты с конкурентностью либо последовательны, либо коммитят данные и чистят `TRUNCATE` (узко).
- Контракты ответов (форма problem+json, статус-коды, list-envelope, ownership) — нормы из [api.md](api.md); тест ассертит соответствие им, сами нормы здесь не повторяем.

## Тестовая БД

Repository-integration гоняется против **реального Postgres через testcontainers** (session-scoped контейнер — самодостаточно, чистый старт/гашение, работает и в облаке, где Docker доступен). SQLite-замена — **антипаттерн**: расходится с Postgres по типам и семантике (нет JSONB/массивов, иные constraints) и даёт ложную уверенность, а мы используем Postgres-специфику.

- **Схему поднимаем миграциями** — `alembic upgrade head`, тем же путём, что прод (консистентность с продакшеном; ловит факт применимости миграций). `Base.metadata.create_all()` не используем — он тестирует модель, а не реальную БД, и прячет дрейф миграций. Канон миграций и hard-rule на autogenerate — [db.md](db.md).
- **Изоляция на тест — транзакционный откат.** Внешняя транзакция на `AsyncConnection`, к ней биндится `Session` с `join_transaction_mode="create_savepoint"`; в teardown — `rollback()` внешней транзакции. Тестируемый код свободно зовёт `session.commit()` — всё живёт внутри savepoint и откатывается. Семантика commit'ов продакшн-кода — [db.md](db.md#db-сессии-и-commit).
- **Параллельный прогон (xdist) — отдельная БД на воркер.** При `pytest -n` воркеры топчут данные друг друга, поэтому каждый воркер поднимает/мигрирует **свою** БД (имя воркера — `PYTEST_XDIST_WORKER`). Шарить одну БД только на транзакционном откате — хрупко.
- **Страж дрейфа модель ↔ миграции.** Отдельный быстрый тест проверяет, что `alembic revision --autogenerate` против поднятой тестовой БД пуст (нет несинхронизированных изменений модели). Заводится **на каждую из двух независимых alembic-цепочек** (backend и siem-service) против своей схемы — смешивать их в одном прогоне нельзя.
- **Downgrade критичных ревизий** проверяется циклом `upgrade → downgrade → upgrade`: upgrade-only тесты не ловят необратимые миграции, а сломанный откат вскрывается в проде ровно тогда, когда он нужен.

## Фейки LLM и guard

Логику вокруг модели тестируем детерминированно, **подставляя фейковую модель в шов** — без сети, ключа и недетерминизма. Код программируется против `BaseChatModel`/`Runnable`, а не против конкретного `ReasoningChatOpenAI`, поэтому в шов встаёт любой fake-наследник.

- **Шов для модели.** `build_graph(model=...)` и `LLMClassifier(llm=...)` инъектируемы — принимают модель параметром, логику графа и guard пишем фейком без правок прода. `GraphFactory.build()` создаёт модель инлайн (`create_llm_from_config`); норма тестового шва здесь — **инъектируемая model-factory (callable), которую переопределяют тесты** (прод подставляет фабрику поверх `create_llm_from_config`). Через эту фабрику тесты подменяют модель, не вводя глобального состояния — в духе hard-rule «никаких module-level синглтонов». Устройство runtime — [agent.md](agent.md).
- **Agent-LLM — `GenericFakeChatModel`** (`langchain_core.language_models.fake_chat_models`): принимает итератор ответов, поддерживает streaming и `tool_calls`. Через программируемые `AIMessage(content="", tool_calls=[ToolCall(...)])` детерминированно прогоняется ReAct-петля «модель → tool → модель → ответ». Старые `FakeListChatModel`/`FakeMessagesListChatModel` беднее (нет нормального tool-calling) — для агента не берём.
- **Guard — стаб на плоском тексте.** Guard читает плоский текст ответа модели, **не** structured output (без tool_calls и JSON): классификатор парсит content и сверяет с `{CLEAN, SUSPICIOUS, INJECTION}`. Фейк нужного вердикта = `AIMessage(content="INJECTION")`. Деградацию в `CLEAN` воспроизводят **два разных фейка**: бросающий исключение (сбой модели) и **возвращающий невалидную строку** (`AIMessage(content="GARBAGE")`) — это отдельная ветка ретрай-петли: классификатор парсит content, на невалидном ответе ретраит `max_retries` раз, затем деградирует в CLEAN (`degraded=True`).
- **Два разных слоя поверх вердикта — не смешивать.** (1) **Слой действий** гейтится строго по `INJECTION`: блок/редакция срабатывают только на `INJECTION`; `SUSPICIOUS` и `CLEAN` проходят дальше без редакции. (2) **`VERDICT_TO_LEVEL`** (`INJECTION→ERROR / SUSPICIOUS→WARNING / CLEAN→DEFAULT`, `agent/security/types.py`) — это уровень Langfuse-обсервации, **не** block/redact. Один слой решает судьбу хода, другой — уровень наблюдаемости; ветвление каждого тестируется отдельно от самого вердикта.
- **Что именно проверяем.** Тест guard проверяет, что **наш код реагирует на вердикт**, а **не качество вердикта** LLM: `INJECTION` → блок/редакция; `SUSPICIOUS` → только наблюдаемость (лог-warning, Langfuse WARNING-уровень), проходит дальше **без** редакции; `CLEAN` → пропуск. Точность классификации на реальных атаках — это eval, не unit (см. § Граница unit / eval).
- **Checkpointer.** По умолчанию `InMemorySaver` для всей логики (быстро, без БД). Реальный `AsyncPostgresSaver` — узким integration-контуром ради сериализации состояния и поведения store; всю логику против PG не гоняем (медленно, без дополнительного сигнала).
- **Граф — официальные паттерны LangGraph:** свежий checkpointer в каждом тесте; прямой вызов ноды `compiled_graph.nodes["name"].invoke(state)` (минует checkpointer); частичный прогон через `update_state(..., as_node="prev")` + `interrupt_after`; стриминг событий `astream_events(..., version="v3")`.

## Дубли (test doubles)

Дубль — управляемый заменитель настоящего коллаборатора на время теста (не «копия»). Таксономия от простого к умному:

| Дубль | Что делает |
|-------|------------|
| **Dummy** | Заполняет обязательный параметр, не используется (обычно `None` / голый объект) |
| **Stub** | Отдаёт заранее заданный ответ на вызов |
| **Spy** | Stub + записывает, как его вызвали |
| **Mock** | Запрограммирован ожиданиями вызовов, сам их проверяет |
| **Fake** | Рабочая упрощённая реализация (in-memory-репозиторий на `dict`) |

**Предпочитаем fake и stub. Mock — только когда сам факт/форма вызова и есть проверяемое поведение.** Эталон уместного mock'а — отправка score в Langfuse (`langfuse.create_score(...)`): смысл фичи — «мы вызвали внешнюю систему с правильным payload», проверять больше нечего, вызов **и есть** контракт. Сервис с коллабораторами, наоборот, тестируем fake'ами и проверяем **результат** (возвращённый объект, ветку 404, graceful-деградацию), а не «какие методы дёрнулись внутри».

**Мокаем только внешние эффекты** (Langfuse score, сеть, недетерминизм), **не внутренних коллабораторов**. Внутренних подменяем fake-реализацией там, где они лезут в инфру, и оставляем настоящими там, где они ин-процесс (sociable).

**Формы в Python.** Дубль не обязан наследовать реальный класс — благодаря duck-typing и `Protocol`-интерфейсам достаточно объекта с теми же методами. Stub/fake — маленький свой класс с тем же интерфейсом; mock/spy — `unittest.mock.AsyncMock`/`MagicMock` (сам записывает вызовы, умеет `assert_called_once_with`); dummy — `None` или голый объект под сигнатуру.

## Граница unit / eval

Это **разные инструменты с разной природой и частотой**, их нельзя смешивать.

**Детерминированные тесты** (CI-гейт, на каждый PR, без ключа) покрывают **код вокруг модели**: логику графа (рёбра, роутинг, аккумуляция состояния, HITL), парсинг ответов, ветвление guard на фиксированных вердиктах, слой действий, трансформацию SSE, контракт checkpointer/store. Ответ модели здесь — фиксированный *вход* теста; проверяем код. Ассерт строгий, бинарный, дешёвый. Вопрос теста: «не сломал ли я код».

**Eval-наборы** (Langfuse datasets + LLM-as-judge, по расписанию или перед релизом промпта, с живым ключом) покрывают **качество ответов живой модели**: качество ответов агента, точность guard на реальных атаках, качество fuzzy-patch. Ответ модели здесь — *то, что оцениваем*; он недетерминирован, `assert ==` не работает. Вопрос: «стала ли система отвечать лучше или хуже».

Eval-контур (датасеты + метрики + judge на Langfuse) — **отдельный пайплайн вне CI-гейта, в backlog**, не в этих тестах: недетерминированный eval в гейте даёт флак и заблокированные мержи. Точечный **VCR record/replay** (`pytest-recording`, с обязательной фильтрацией `Authorization`/api-key из кассет) допустим узко — на 2–3 сквозных пути, где важен реальный wire-формат reasoning-модели; основа же — ручные фейки (быстро, читаемо, не ломается от смены версии модели).

## Фабрики данных

Тестовые данные — через **factory_boy** (много полей и связей: `SubFactory`, `Faker`, `Sequence`, `post_generation` убирают шум). factory_boy без нативного async, поэтому для async-сессий SQLAlchemy — обёртка **`async-factory-boy`** либо синхронная фабрика со стратегией `build` + явный `session.add` в async-фикстуре. Базовые фабрики живут в `packages/testing`. Для нескольких вариаций в одном тесте — **fixture-factory** (фикстура, возвращающая функцию-конструктор). На маленькой модели данных ручной билдер проще и прозрачнее фабрики — выбираем по объёму.

## Coverage и DoD

**Покрытие — диагностика, не цель.** Процент как KPI вреден (закон Гудхарта: 100% добиваются тестом без ассертов → false-green). Мерим **branch coverage** (`--cov-branch`: строковое покрытие переоценивает — ветка `if` без `else` считается покрытой при заходе в одну сторону), **per-package** (общий котёл маскирует дыры одного пакета хорошим покрытием другого), репортим тренд, `term-missing` для поиска непокрытых веток. Действует правило **ratchet — «не понижать»**; жёсткого числового floor не ставим. Mutation testing (mutmut) — не в обычном CI, а разовым/периодическим аудитом силы тестов на ядре (auth, guard, парсинг).

**DoD — через поведение, не процент.** «Каждый функционал имеет тесты» читается как «**каждое поведение/контракт покрыто на адекватном уровне**», не «каждая строка имеет unit». Минимум новой фичи: unit на нетривиальную логику сервиса + integration на критпуть + проходит статанализ. Гейт **жёсткий для services и repositories**; мягкий, с явной пометкой-исключением, — для glue/конфига/прототипов/UI-полировки.

Операциональный признак glue под мягким гейтом: **нет бизнес-ветвлений, нет I/O, чистая адаптерная склейка** — DI-проводка в `lifespan`, перекладка DTO ↔ доменной модели, регистрация роутеров, тонкий passthrough-провайдер `Depends`. Сервис с бизнес-логикой (ветвление по доменному состоянию, расчёт, оркестрация коллабораторов, graceful-деградация) — под жёстким гейтом, даже если код короткий.

**Глубина дифференцирована.** Широкое покрытие поведения везде (happy + основные ошибки/авторизация) **плюс глубина на критпутях**: auth, security guard, agent runtime, chat/SSE дополнительно получают edge- и negative-кейсы.

**Граница авто / ручное.** Основная масса проверок — автотесты. Ручные тест-кейсы (`test-cases.md` с run-log) остаются **узко** — длинный хвост: многошаговые сквозные сценарии, тяжело автоматизируемое, exploratory, приёмка UX. Регламент ручных кейсов и ре-верификации — в ядре [conventions.md](../conventions.md#тестирование).

## Frontend

Стек — **Vitest + jsdom + React Testing Library + MSW**; центр тяжести по Testing Trophy — **integration** (компонент вместе со своими хуками и замоканной через MSW сетью), не unit и не e2e. Static-слой (`tsc` + ESLint) уже закрыт `make check-fe`.

- **Поведение, видимое пользователю, а не внутренности.** Запросы по приоритету `getByRole(name=...)` → `getByLabelText` → `getByText`; `getByTestId` — последнее средство. Взаимодействия — `@testing-library/user-event` (реалистичная цепочка событий), асинхронность — `findBy*`/`waitFor`. Не лезем в `container.querySelector`/`className`, не shallow-рендерим, не проверяем «вызвалась ли функция / поменялся ли внутренний стейт».
- **TanStack Query — свежий `QueryClient` на каждый тест** + `retry: false` в `defaultOptions.queries` (общий кэш и дефолтные ретраи — главный источник флака). Тонкая утилита `renderWithProviders` оборачивает рендер в свежий клиент + провайдеры.
- **Zustand-сторы сбрасываем между тестами** (`__mocks__/zustand.ts` копит reset-функции, `afterEach` откатывает к `getInitialState()`): сторы — module-level, без сброса состояние протекает и даёт флак.
- **Сеть — MSW** (`setupServer` в node): перехват на сетевом уровне, код приложения не знает, что отвечает мок. Ручные моки `fetch` — антипаттерн (хрупки, привязаны к реализации клиента). **SSE-стрим агента** мокается нативным MSW SSE API.
- **Раскладка** — колокация рядом со слайсом; e2e (Playwright, тонкий слой 3–7 journey) — отдельным top-level каталогом. Реальный browser-e2e и visual-regression — в backlog (в облаке headless-браузер к HTTPS не работает). FSD-границы и состояние — [frontend.md](frontend.md).

## Антипаттерны

- **False-green** — зелёный тест нулевой ценности: тест без ассертов ради процента покрытия; тест, проверяющий поведение моков, которое сам же и запрограммировал.
- **Флак** — недетерминированный тест: общий кэш/состояние между тестами, гонки на event loop, недетерминированный вывод LLM под строгим `assert ==`, реальная сеть.
- **Тестирование приватного** — проверка приватных методов, внутренних вызовов, структуры состояния в обход публичного контракта.
- **Mock-heavy / тест-зеркало реализации** — каждый mock с ожиданием фиксирует, *как* код работает внутри; невинный рефакторинг (три вызова в цикле → один батч) красит тест, хотя поведение то же. Тест превращается в налог на рефакторинг.
- **Проверка вызовов вместо результата** — ассертим «дёрнулся метод X», когда надо ассертить возвращённое значение / побочный эффект. Допустимо только когда вызов **и есть** контракт (внешний эффект, § Дубли).
- **SQLite вместо Postgres**, `Base.metadata.create_all()` вместо миграций, синхронный `TestClient` на SSE-стрим, крупные хрупкие снапшоты на фронте.
- **Удаление/правка падающего теста под реализацию** — делает набор зелёным, меняя спецификацию, а не код (см. § Целостность тестов).

## Целостность тестов

Оракульное свойство теста (объективный pass/fail, на который можно замкнуть автономную итерацию) даёт **не порядок** (тест раньше кода), а **независимость теста от реализации**. Из этого — правила, обязательные для автономных и параллельных прогонов:

- **Автор тестов независим от автора кода.** Если один агент пишет и код, и тесты — тесты тавтологичны (валидируют то, что реализовано, а не то, что требует контракт). **Обязательно:** тесты пишет не тот, кто писал код (отдельный агент/архитектор) — это и есть оракульное свойство. **Желательно:** автор тестов идёт из другого контекста (свежая сессия), чтобы не унаследовать допущения реализации.
- **Имплементер кода не трогает тест-файлы** своего скоупа — не правит и не удаляет ассерты под себя. Это против «удалил/переписал падающий тест, чтобы стало зелёно». Дифф на тронутые тест-файлы — предмет ревью.
- **Test-first не обязателен.** Можно писать код → потом тесты → вешать оракул-loop; оракул сохраняется, **если тесты пишет не тот, кто писал код**. От порядка отказываемся свободно; критична независимость автора.
- **Adversarial-ревью свежим агентом** диффа против контракта: реализовано ли требование, есть ли тесты на краевые случаи, не тронуто ли лишнее. Автор ревью независим от автора тестов.
- **Тест считается сторожем только после проверки мутацией.** Заявка «этот кейс сторожит фикс» не принимается по чтению кода: прод-механизм возвращается к сломанному виду одной точечной правкой, набор прогоняется, и считается, **сколько** кейсов покраснело и **те ли** («мутация красит ровно N кейсов, и это они»); мутация откатывается, дерево остаётся чистым. Для составного признака мутируется и вторая половина — обратная мутация обязана красить свой кейс, иначе набор сторожит только одну сторону. Свойство, которое тестовая среда не исполняет (напр. CSS-анимации в jsdom), сторожа не получает вовсе — это фиксируется явно, а не кейсом-декорацией. Откат мутации — точечной правкой, не `git checkout` файла (сметает параллельные изменения).

## Чек-лист автора тестов

Перед сдачей тестов проверь:

- [ ] Тест проверяет **поведение** (вход → выход / побочный эффект через публичный интерфейс), а не приватные методы и внутренние вызовы.
- [ ] Падает по полезной причине: ломается при изменении поведения, **не** при рефакторинге, сохраняющем поведение.
- [ ] Есть осмысленный ассерт на результат; нет «зелено без проверки» (false-green).
- [ ] Дубли минимальны: fake/stub для внутренних коллабораторов, mock **только** на внешний эффект (Langfuse/сеть). Внутренних коллабораторов не мокаем.
- [ ] Sociable по умолчанию: настоящие ин-процесс соседи не подменены без причины.
- [ ] Реальный Postgres — только в repository-integration; логика сервисов — на фейках; граф/guard — на фейк-модели.
- [ ] Детерминизм: нет общего состояния/кэша между тестами, loop scope согласован, нет реальной сети, нет `assert ==` на недетерминированный вывод LLM.
- [ ] AAA-структура, одно поведение на тест, таблицы через `parametrize`.
- [ ] Нейминг `test_<unit>_<condition>_<expected>`, файл в правильном `tests/<scope>/`, общие утилиты взяты из `packages/testing`, не продублированы.
- [ ] Покрыты happy + основные ошибки/авторизация; на критпути (auth/guard/runtime/SSE) добавлены edge/negative-кейсы.
- [ ] guard/agent: проверяется реакция кода на вердикт/tool_call, **не** качество ответа модели (это eval).
- [ ] Frontend: свежий `QueryClient` + `retry:false`, сброс Zustand, сеть через MSW, запросы по роли/тексту, не по `className`.
- [ ] Закрывающий кейс прод-фикса сдан с результатом мутации: «убери механизм — краснеет ровно N кейсов, и это они» (§ Целостность тестов).

## Чек-лист ревьюера

- [ ] **Поведение, не реализация:** тест не прибит к внутренней структуре; пережил бы рефакторинг без смены поведения.
- [ ] **Нет false-green:** ассерты содержательны; тест не проверяет поведение собственных моков; покрытие не накручено пустыми прогонами.
- [ ] **Нет флака:** изоляция состояния между тестами, согласованный loop scope, отсутствие реальной сети и недетерминированных ассертов на LLM.
- [ ] **Дубли по правилу:** mock только на внешнем эффекте; внутренние коллабораторы — fake/sociable, не mock-heavy; нет проверки вызовов там, где надо проверять результат.
- [ ] **Инфра по слою:** Postgres только под repository-integration; схема — миграциями; транзакционный откат на тест.
- [ ] **Фикстуры и нейминг:** корректный scope (мутабельное — `function`), `test_<unit>_<condition>_<expected>`, правильная директория скоупа, переиспользование `packages/testing`.
- [ ] **Критпути покрыты:** auth, guard, agent runtime, chat/SSE имеют edge/negative сверх happy-path; новый функционал services/repositories имеет тесты (жёсткий гейт DoD).
- [ ] **Граница unit/eval соблюдена:** качество ответов LLM не затащено в CI-гейт строгими ассертами.
- [ ] **Целостность (§ Целостность тестов):** автор тестов независим от автора кода; в диффе не правились/не удалялись чужие тест-файлы под реализацию.
- [ ] **Сторож подтверждён мутацией:** заявка «кейс сторожит фикс» проверена мутацией прод-кода со счётом покрасневших кейсов, не чтением.
