# Skill Map

Карта скиллов проекта: какие приняты и в какой роли, какие отклонены и почему, по каким
принципам набор пополняется. Единственный источник правды по скилл-политике — операционный
триггер «когда использовать» живёт в таблице скиллов `CLAUDE.md` и ссылается сюда.
История дискавери (как пришли к этим решениям) — в артефакте итерации
`doc/tasks/iterations/codebase-maturity/feat-001-foundation/skill-discovery-draft.md` (заморожен).

## Принципы

1. **Объём набора не страшен при дисциплине скоупа.** Много скиллов — не проблема, если каждый
   узко ограничен своим доменом и грузится лениво, только в релевантном контексте (progressive
   disclosure: SKILL.md + максимум один conditional reference). Не боимся 4–5 тестовых скиллов,
   если каждый по делу и подгружается по месту.

2. **Скилл вокруг быстроменяющегося инструмента — слабый скилл.** Упакованная документация
   незрелого/быстро меняющегося слоя (LangGraph) устаревает быстрее, чем приносит пользу.
   Для таких доменов скилл — концептуальная карта, конкретные сигнатуры сверяются по живым
   источникам (MCP `docs-langchain`, firecrawl по официальным докам, inspect установленных
   пакетов). Это причина отклонения `langchain-architecture` и режима использования
   `langgraph-patterns`.

3. **Воевать с training prior модели стоит только за семантику, не за стиль.** Правила скилла
   делятся на три корзины: *семантика/безопасность* (старый паттерн из training data — баг или
   бомба: блокирующий код в `async def`, утечка полей без `response_model`), *anti-rot* (запреты
   deprecated API) и *косметика* (синтаксические предпочтения). Скилл оправдан корзиной
   семантики; косметика едет паровозом и отдельной цены не имеет. На чистой кодовой базе скилл
   работает **стабилизатором против регрессии**: без него новые правки тянут старый стиль и
   получается микс, который хуже обоих чистых вариантов. Правила в файле — ещё и **артефакт для
   ревью** (чек-лист reviewer'у), не только инструкция генератору.

4. **Глубина разбора скилла = глубина решения, а не объём содержимого.** Архитектор ныряет
   туда, где решается политика проекта, и проходит по верхам там, где внутри детали реализации,
   исполняемые агентом со скиллом и линтерами. Критерий понимания — способность оценить
   результат и объяснить решение, не знание каждого правила.

5. **Голос скилла: description — третье лицо, тело — императив.** `description` пишется в третьем
   лице (инжектится в системный промпт; несогласованная точка зрения ломает discovery) — без «I
   can…»/«You can…». Тело SKILL.md — команды агенту («Сделай», «Проверь», «Не давай»), не персона
   «ты — X» и не повествование «скилл делает / агент извлекает». Персона и идентичность живут в
   промпте саб-агента (`aidd-orchestrator/prompts/<role>.md`), не в скилле: скилл — host-agnostic
   знание, грузится в любого агента, и «ты — X» конфликтует с идентичностью хоста. Это канон
   Anthropic по авторингу Agent Skills.

Операционные правила:

- **Принятые скиллы живут в репозитории** (`.claude/skills/`) и версионируются с проектом;
  пользовательский уровень (`~/.claude/skills/`) — не источник правды. Отклонённые в репо
  не держим.
- **Отложенные внешние кандидаты ставим при заходе в их slice**, не заранее — каталог не
  засоряется скиллами, решение по которым ещё не подтверждено.
- Новый скилл проходит тот же цикл: разбор с архитектором → решение → фиксация здесь.

Политики по скиллам — только там, где есть решение проекта, не пересказ содержимого:

- **`api-design-principles`** — resource-oriented дизайн принят как **дефолт, не догма**:
  на честных действиях (auth-флоу, запуск/стриминг агента, security/admin-операции) идём
  action-эндпоинтами в стиле Google AIP custom methods. Формат ошибок скилла самодельный —
  заменяется нашей конвенцией RFC 9457 (см. «Пробелы»). Эталон зрелого REST внутри проекта —
  API siem-service.
- **`postgresql`** — работает только на физическом уровне; **логическое проектирование и
  доменная модель — за архитектором**, скилл их не решает. ORM-специфика (SQLAlchemy 2.x
  async, Alembic) не покрыта — кандидат `sqlalchemy-alembic-expert` (см. «Отложенные»).
- **`fastapi`** — ядро — **предохранители, не оптимизации**: async vs sync (блокирующий вызов
  в `async def` останавливает event loop — при SSE-ядре проекта это вешает стримы всех
  пользователей), `response_model` как фильтр утечки internal-полей, `yield`+`scope` в Depends.
  Кодовая база уже на новом каноне — скилл держим как стабилизатор против регрессии (принцип 3).
  Не покрывает инфраслой (`lifespan`, `app.state`, `Settings`, middleware) — см. «Пробелы».
- **Авторские (`langgraph-patterns`, `schema-guided-reasoning`, `prompt-engineering`)** —
  берутся как есть, не ревьюятся и не правятся. `langgraph-patterns` используется
  концептуально, сигнатуры API сверяются по живым источникам (принцип 2).
- **`feature-sliced-design`** — сильнейшая часть — decision framework («куда класть код»,
  золотое правило: сомневаешься — оставь в pages) и анти-оверинжиниринговая тональность
  (запрет пустых слоёв «на вырост», консерватизм по entities). Официальный линтер **Steiger** —
  кандидат на enforcement в feat-008. Findings прогона текущего `frontend/src` — входной
  материал feat-006 (зафиксированы в артефакте дискавери).
- **`frontend-design`** — не справочник, а промпт-надстройка на творческое поведение модели
  при вёрстке; двухрежимный (ищет дизайн-систему проекта: нашёл → constrained mode, не нашёл →
  creative mode). **Трёхфазная политика:** (1) пока дизайн-системы нет — применять только по
  явному запросу на визуал, результат проверять на нативность (creative mode для рабочего
  инструмента опасен: «непохожесть» воюет с нативным UX); (2) при создании дизайн-системы —
  опционально один заход в creative mode как генератор 2–3 эстетических направлений-кандидатов
  под выбор архитектора; (3) после — постоянный constrained mode, ценность = качество
  исполнения деталей. Требование: дизайн-систему положить туда, где скилл её ищет
  (ui-conventions / design tokens / гайдлайн в CLAUDE.md).

- **`sofa` / `sofa-contributor`** — пара «механика + обвязка». `sofa` — vendored-копия апстрим-скилла
  Stack Overflow (механика API площадки); держим в репо ради портативности (cloud-сессии, другие
  участники), периодически сверять с апстримом на дрейф. `sofa-contributor` — авторская надстройка:
  рубрика отбора кандидатов, чеклист качества под стандарты площадки, грабли публикации, реестр в
  `doc/content/sofa/`, режим опроса статистики. Progressive disclosure — три режима отдельными
  reference-доками (плановая работа / blueprint-свип / опрос статистики). Находки оседают **прямо в скилл**, без
  промежуточного `learnings.md`. Публикация — всегда author-gated; автономная роль в оркестраторе
  только генерирует кандидатов. Реализовано в Треке C (early-adoption SOFA).

- **`operational-audit`** — компенсирует структурную слепую зону конвейера: все роли
  оркестратора входят через дифф итерации, свойства работающей системы (рестарты, воркеры,
  shutdown, деградации зависимостей) не видит никто. Три политики: запускается архитектором
  вручную (не роль оркестратора и не фаза FSM); находка без верификации чтением кода в отчёт
  не выходит; скилл ничего не пишет в `doc/` и код — только отчёт и кандидаты записей в
  backlog, фиксация за архитектором. Оси проверки в скилле — примеры, не граница (laundry
  list запрещён как ограничитель). Единственный источник инструкций аудита — сам скилл;
  conventions содержат лишь смежную ось в чек-листе бриф-ревью (другой гейт: новая фича до
  реализации, а не периодика по существующей системе).

## Отклонённые

Фиксируются, чтобы не «находить» их заново при будущих охотах.

- **`langchain-architecture`** — центр скилла — LangChain-обёртки (`create_agent`,
  AgentMiddleware), которые проект не использует (raw LangGraph). По принципу 2 — упакованная
  документация быстроменяющегося слоя. Удалён, в том числе с пользовательского уровня.
- **`react-state-management`** (wshobson/agents) — ~40% мёртвого веса (Redux Toolkit, Jotai,
  миграция с легаси-Redux при нашем зафиксированном стеке Zustand 5 + TanStack Query 5), жанр
  «выбери инструмент» при уже сделанном выборе, небрежное качество примеров. Ценное ядро
  переиспользуется конвенцией в feat-006 (см. «Пробелы»).

## Пробелы — закрываем конвенциями в slice'ах

Готовых внешних скиллов нет; кодифицируем сами внутри соответствующего slice (отдельные
задачи в backlog не заводятся — решение архитектора):

- **RFC 9457 Problem Details** (формат ошибок REST) → feat-002, результат в `conventions.md`.
- **FastAPI-инфраслой** (`lifespan` + `app.state` + `Settings(BaseSettings)` + middleware +
  exception handlers) → feat-004; согласовано с Hard Rules (state в `app.state`, не в
  module-globals).
- **Ось состояния фронта** (Zustand + TanStack Query) → feat-006: таксономия категорий
  состояния (серверное — только в Query, клиентское UI — в Zustand, производное вычисляется),
  Don'ts (не дублировать серверное состояние в сторе, подписки через селекторы), Query-паттерны
  (фабрика query keys, optimistic update с откатом) — ядро отклонённого
  `react-state-management`; плюс наши темы: стриминговое состояние (`stream-store`/SSE),
  инвалидация между сущностями.
- **Тесты SSE-стриминга + моки LLM/LangGraph** → feat-009.
