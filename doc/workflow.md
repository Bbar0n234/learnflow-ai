# Рабочий процесс

## Подход

**AI-Driven Development (AIDD):** разработчик = архитектор, LLM-агент = исполнитель. Реализация делегируется агенту на основе подготовленного контекста.

**Context First:** качество результата определяется качеством входного контекста. Документация — основной инструмент передачи контекста. Согласуй архитектуру и подходы до начала генерации кода.

**Outline-first:** для каждого нового документа: outline → ревью архитектора → апрув → полный документ. Агент не принимает архитектурных решений самостоятельно.

## Двухуровневое планирование

### Roadmap ([product/roadmap.md](product/roadmap.md))

Продуктово-стратегический уровень: **фазы** (последовательные этапы с целью и условием завершения) и **треки** (направления работ внутри фаз и сквозные). Определяет **что** делаем и в каком порядке.

Фазы — это эпики: они **ссылаются** на пункты backlog, а не дублируют их детали. Деталь живёт в backlog; при активации фазы её пункты триажатся в tasklist по общему механизму. Сквозные и параллельные треки (контент, maintenance, meta/workflow) идут вне фаз — это режимы без условия завершения.

### Backlog ([backlog.md](backlog.md))

Входящий поток: фичи, баги, UX-проблемы, tech debt. Пополняется из опытной эксплуатации и Langfuse. Элементы из backlog тянутся в tasklist при триаже. После переноса в tasklist элемент удаляется из backlog — tasklist становится его новым домом (секция "Из backlog" в записи итерации хранит историю).

**Пункт — единица переноса (атомарность).** Переносится пункт целиком или не переносится. Если в итерацию уходит только часть пункта — сперва раздели его в backlog на два самостоятельных пункта (каждый — чистый scope), затем перенеси готовый целиком (удали из backlog), второй остаётся. Так инвариант «после переноса — удалён» остаётся буквальным, и каждый scope живёт ровно в одном месте.

**Backlog не содержит указателей переноса.** Провенанс перенесённого пункта живёт только в tasklist (секция "Из backlog"), никогда обратной ссылкой в backlog. Фраза вида «перенесено в feat-X» внутри backlog запрещена — это и есть второй источник правды. Отличай от relational/провенанс-ссылок («выявлено в feat-X», «связано с feat-X», «предусловие Фазы N») — они переноса не заявляют и допустимы: сам пункт при этом живёт в backlog.

### Tasklist (tasks/tasklist-\<scope\>.md)

Технический уровень: итерации по областям ответственности (backend, frontend, devops...). Определяет **как** реализуем. Итерации закрывают пункты из roadmap или backlog.

Деление на scope гибкое — выделяем отдельный tasklist, когда текущий становится слишком большим.

## Итерация

Единица работы разработчика. Формат: `<type>-<number>` (нумерация отдельная для каждого scope).

Типы (аналогично Conventional Commits):

| Тип | Назначение |
|-----|-----------|
| `feat` | Новая функциональность |
| `fix` | Исправление |
| `refactor` | Рефакторинг |
| `docs` | Документация |
| `test` | Тесты |
| `chore` | Инфраструктура, зависимости |

### Жизненный цикл

**1. Планирование** (архитектор)

- Выбрать задачи из roadmap или backlog для реализации
- Создать запись итерации в `tasklist-<scope>.md`
- ADR — если есть архитектурные решения
- Design brief — при развитии существующей системы, когда есть зазор между архитектурной документацией и тем, что агенту нужно для реализации. Должен включать архитектурные диаграммы (Mermaid), по которым можно рассказать суть фичи без погружения в код

**2. Реализация** (агент)

- Implementation plan: верификация решений, пошаговый план
  - При работе с новыми или быстро меняющимися библиотеками — верифицировать актуальное API доступными средствами: inspect установленных пакетов, MCP-серверы документации, веб-поиск, специализированные скиллы. Какие источники доступны и уместны — такие и использовать
  - План может быть отдельным файлом или в Plan Mode агента (история сообщений)
  - Если план не оформлен как файл — индексировать его не нужно
- Код: реализация по плану, итеративное улучшение до достижения результата

**3. Верификация** (агент + архитектор)

- Верификация проводится всегда, когда есть что протестировать
- **test-cases.md** — опциональный отдельный документ с детальными тестовыми кейсами (чек-лист с prerequisites, слои: automated → API → E2E). Создаётся после plan.md **копированием шаблона** `doc/tasks/iterations/_templates/test-cases-template.md`. Шаблон несёт формат прохождения, run-log и тест-конвенции **инлайн** — тестировщик читает кейс-документ, а не `conventions.md`, поэтому конвенции должны быть у него перед глазами. Для простых итераций достаточно верификации по критериям приёмки из tasklist
- Процесс прохождения:
  - Агент поднимает инфраструктуру (`make` targets), проходит кейсы последовательно
  - Каждый кейс отмечается сразу: текущий статус (`- [x]` + лаконичный результат — что проверялось, что получилось, значимые нюансы) плюс **run-log**, если кейс прогонялся не раз: строка-история флипов с причиной (`runs: r1 ✅ → r2 ❌ (после фикса review #3: регрессия) → r3 ✅`). Один прогон — run-log не нужен; история копится только у перепрогнанных. По заполненному чек-листу должно быть наглядно видно, что всё работает, без повторного прохождения
  - Кейс требует ручного действия или агент не может пройти — эскалация архитектору с описанием, что нужно проверить. Архитектор проверяет → агент записывает результат
  - Непройденные кейсы — явно помечены с причиной
- **Ре-верификация после правок.** Правка кода (по фидбэку ревьюеров или тестировщика) аннулирует прошлый зелёный статус затронутого — тривиальность правки гарантий не даёт. После фиксов: детерминированный гейт (`make check`/`make check-fe`, а с тестовой инфраструктурой — `make test`) перепрогоняется **всегда** (цена ≈ ноль); ручные/UI-кейсы перепрогоняются **только в затронутой области** (полный прогон дорог и неоправдан). Перепрогон фиксируется в run-log кейса
- Результаты верификации фиксируются в summary.md (общий итог + ссылка на test-cases.md, если есть)

**4. Завершение**

- Post-implementation summary (`summary.md`): отклонения от плана, принятые решения, нюансы
- Актуализация документации:
  1. Обновить затронутые существующие документы
  2. Появился новый концепт, не покрытый отдельным документом? → создать (критерии: кросс-сервисность, самодостаточность, объём, собственный жизненный цикл, ключевая доменная абстракция)
  3. Были архитектурные решения без ADR? → создать ADR
  4. Добавлены новые документы? → обновить навигацию (index.md)
  - Обязательно отсмотреть вручную все изменения
- Если design brief содержит temporary conventions — мигрировать их в `conventions.md`
- Индексация всей документации в записи итерации
- Обновление статуса в roadmap
- **Распространение знаний (опционально, author-gated).** Если итерация дала переносимую находку
  (удивительное поведение tool/API, нетривиальный фикс, verbatim-ошибка) — роль `sofa-contributor`
  читает артефакты и предлагает кандидатов в посты Stack Overflow for Agents, складывая их в
  `sofa-proposals.md` директории итерации. Это **только генерация кандидатов**; сама публикация —
  внешнее действие под явным апрувом архитектора, вне автономного конвейера. Процесс, рубрика
  отбора и реестр публикаций — в скилле `sofa-contributor` и `doc/content/sofa/`.
- **Сбор хвостов (harvest, author-gated).** Хвост в summary — могила: при планировании туда не
  заходят, его никто не возьмёт. Чтобы ценное доходило до очереди, незакрытые долги собираются в
  канонической секции `## Follow-ups` summary (ссылка + приоритет + тип) и оттуда — роль `harvester`
  читает артефакты, отбирает по рубрике достойных и складывает кандидатов (в backlog / в конвенции /
  known-trivial) в `harvest-proposals.md`, отсеивая шум. Любой агент по ходу итерации может дописать
  anytime-кандидата в тот же файл. Перед заведением — проверка «не закрыто ли уже» (grep + git log),
  чтобы в backlog не попал фантом, закрытый под другим именем в смежной итерации. Это **только
  предложения**; перенос в `backlog.md`/`conventions.md` — под апрувом архитектора на pre-commit gate.
  Рубрика и процесс — в роли `harvester` (`.claude/skills/aidd-orchestrator/prompts/harvester.md`).

### Делегирование агентам

Жизненный цикл может выполняться вручную (архитектор последовательно дёргает агентов) или через автономный конвейер — skill `aidd-orchestrator`. Конвейер оркестрирует роли последовательно: одна роль за раз, общий worktree, общая ветка.

Соответствие ролей этапам:

| Роль | Этапы | Артефакты |
|------|-------|-----------|
| architect | Планирование, pre-commit gate, разрешение тупиков | design-brief.md, test-cases.md, запись в tasklist |
| planner | Implementation plan | plan.md |
| implementer | Реализация фазы плана, фиксы по review/test | код, summary.md |
| tester | Прохождение test-cases | обновлённый test-cases.md |
| reviewer-a | Code review — режим A (качество кода: баги, сложность, читаемость) | `review-a.md`, severity blocker / nit / pre-existing |
| reviewer-b | Code review — режим B (соответствие контракту: конвенции, doc-first, архитектура) | `review-b.md`, severity blocker / nit / pre-existing |
| docs-updater | Актуализация документации | обновлённые/новые doc-файлы, ADR, index.md |
| sofa-contributor | Распространение знаний (опц., author-gated) | `sofa-proposals.md` — кандидаты в посты Stack Overflow for Agents |
| harvester | Сбор хвостов → backlog / конвенции (author-gated) | `harvest-proposals.md` — кандидаты на апрув архитектора |

**Обязательные гейты архитектора:**

- **Pre-commit gate** — финальный ревью diff'а, summary.md и списка затронутых документов перед коммитом
- **Тупик** — любой агент при невозможности продолжить эскалирует через оркестратор архитектору со структурированным отчётом (фаза, что пытался, что мешает, какие варианты рассмотрел, что нужно от архитектора)

Прочие шаги (ревью плана, ревью отчётов ревьюеров A/B) — не обязательные гейты. Архитектор может ревьюить любой артефакт в любой момент, но конвейер не блокируется на этом.

Ручной запуск любой роли вне конвейера возможен в любой момент: архитектор может вызвать planner'а на отдельную итерацию, прогнать tester'а на отдельный test-case, дёрнуть docs-updater'а после ручной правки кода. Skill `aidd-orchestrator` — автоматизация типового сценария, не замена ручному управлению.

Детали (state machine конвейера, политика эскалации, модельные тиры, шаблоны промптов) — в `.claude/skills/aidd-orchestrator/`.

### Research-артефакты

Технологические ресёрчи, deep-dives, анализ подходов — хранятся в `doc/research/`. Рождаются до или во время планирования фичи, когда нужно изучить незнакомую область перед принятием архитектурных решений.

В отличие от iteration-артефактов (design-brief, plan, summary), research-документы живут отдельно — один ресёрч может информировать несколько итераций.

### Связность документации

Каждый нетемпорарный документ должен быть достижим через ссылки из контекста, который его использует. Без обратной ссылки документ становится "сиротой" — формально существует, но на практике невидим при планировании.

Типичные связи:

| Документ | Ссылается из |
|----------|-------------|
| Research | Backlog-запись, design-brief |
| ADR | Design-brief, tech-документ |
| Design-brief | Запись итерации в tasklist |
| Tech-документ | index.md, CLAUDE.md |

При создании нового документа — добавить ссылку из контекста, который его потребляет. При планировании фичи — проверить, есть ли релевантный ресёрч в `doc/research/`.

### Структура в файловой системе

```
tasks/iterations/<scope>/<type>-<number>-<desc>/
├── design-brief.md      # Контекст реализации (опционально)
├── reference-*.md        # Опорный материал (опционально)
├── plan.md               # Implementation plan
├── test-cases.md         # Детальные тестовые кейсы (из шаблона, опционально)
├── review-a.md           # Отчёт code-review режим A (качество кода)
├── review-b.md           # Отчёт code-review режим B (соответствие контракту)
├── sofa-proposals.md     # Кандидаты в посты SOFA (опционально, author-gated)
├── harvest-proposals.md  # Кандидаты в backlog / конвенции (author-gated)
└── summary.md            # Post-implementation summary
```

Шаблоны артефактов живут в `tasks/iterations/_templates/` (напр. `test-cases-template.md`).

## Формат tasklist

### Легенда статусов

- 📋 Planned
- 🚧 In Progress
- ✅ Done
- ⏸️ Paused
- ❌ Cancelled

### Overview

Таблица в начале файла для быстрого понимания прогресса:

| Итерация | Статус | Закрывает |
|----------|--------|-----------|
| feat-001 | ✅ Done | v1: пункт X |
| feat-002 | 🚧 In Progress | v1: пункт Y |

### Запись итерации

Каждая итерация содержит:
- **Цель** — краткое описание желаемого результата
- **Статус** — текущее состояние
- **Связь с roadmap** — какие пункты закрывает
- **Из backlog** — тезисные пункты, перенесённые из backlog
- **Definition of Done** — конкретные критерии приёмки. Дописываются после design brief, когда scope проработан архитектурно. До design brief — отсутствуют
- **Документация** — ссылки на design-brief.md, plan.md, summary.md, ADR, технические документы
