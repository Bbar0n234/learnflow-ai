# External Sources Service - Архитектурное решение

**Дата:** 2025-11-10
**Статус:** В разработке (M2 - AI-Enhanced Generation)

---

## Контекст

Задача: обогащение генерируемых образовательных материалов информацией из внешних источников (не только из весов модели).

**Рассматриваемые источники:**
- **Web search** (Tavily, Perplexity) - базовая тема, MVP-уровень
- **Telegram RAG** - индексация LLM-тематических чатов (за рамками MVP, production-ready)
- **Документы пользователя** - поддержка агностично от реализации

---

## Архитектурная дилемма

Изначально рассматривались 4 варианта:

1. **Узел в LangGraph** (`ExternalSourcesNode`)
2. **Сервис-класс** в `learnflow/services/` (как `PromptConfigClient`)
3. **Отдельный микросервис** (как `prompt-config-service`)
4. **LangGraph sub-agent** (автономный агент для поиска)

**Вывод:** Делать сразу отдельный сервис = антипаттерн (как "сразу микросервисы"). Это инжиниринг ради инжиниринга.

---

## Решение: MVP подход

### Выбор: Узел в LangGraph с research функционалом

**Обоснование:**
- ✅ Не оверкилл для MVP
- ✅ Утоляет инженерные амбиции (делать что-то интересное)
- ✅ Определенно не "в стол" - закроет поинт на каком-то уровне
- ✅ Гибкость для будущего масштабирования

**Почему НЕ линейный поиск:**

Простой вариант (тема → генерация 3-7 вопросов → поиск по каждому → сбор → контекст):
- Понятно и будет работать
- НО не очень круто для нетривиальных сценариев

**Вместо этого:** Агент с итеративным research
- Копит контекст
- Интеллектуально собирает информацию
- Более интересная реализация

---

## Путь масштабирования

```
MVP (сейчас)          →  Production (после ревизии)
─────────────────────────────────────────────────────
Узел в LangGraph     →  Подграф в основном графе
                     →  Сабэйджент
                     →  Отдельный сервис
```

**Решение о масштабировании** будет приниматься после:
1. Завершения текущего функционала (через неделю)
2. Большого пересмотра проекта:
   - Системное видение
   - Планы развития
   - Продуктовый момент
   - Сценарии использования
   - Типовые пользователи

---

## Зависимость от продуктового видения

### Сценарий A: Фокус на документах пользователя
**Если** основная фишка = генерация по пользовательским документам:
- Глубокий функционал
- Супер-агент
- Фреймворки и продвинутая логика
- Возможно: Google Drive интеграция, MCP протокол

### Сценарий B: Максимальная простота
**Если** продукт требует простоты:
- Минимальная логика
- Возможно, даже не выносить в отдельный сервис
- Базовая интеграция

---

## MVP Scope

**Сейчас реализуем:**
- Узел `ExternalSourcesNode` в LangGraph
- Research функционал (итеративный, не линейный)
- Web search интеграция (Tavily/Perplexity)

**Откладываем:**
- Telegram RAG (требует Qdrant/Chroma, индексацию)
- Сложная RAG инфраструктура
- Отдельный микросервис

**Место в workflow:**
```
input_processing → recognition_handwritten → external_sources (NEW)
  → planning_structure → generate_section → document_assembly → ...
```

---

## Ключевые принципы

1. **Не делать инжиниринг ради инжиниринга**
2. **MVP = минимально, но интересно**
3. **Гибкость для будущего** - узел легко выносится в подграф/агент/сервис
4. **Продуктовое видение определяет архитектуру**, не наоборот
