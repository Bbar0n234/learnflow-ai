# Wizard: подключение титульника нового вуза

Инструкция для агента: как из .docx-титульника пользователя сделать подключаемый шаблон `templates/title_pages/<name>.docx`. Выполняется **один раз** при настройке (setup-time); при обычной сборке отчётов шаблоны не меняются.

## Границы

- **Вход — только .docx.** PDF не конвертируем и не воссоздаём вёрстку по картинке — честно попросить у пользователя исходный .docx (вузы обычно раздают бланки в docx).
- Подписные бланки (задание, календарный план, отзывы, рецензии), ЕСКД-рамки, печати — вне скоупа.
- Wizard настраивает только титульник. Стили тела фиксированы (ГОСТ 7.32) и от титульника не зависят.

## Главный принцип

**Вёрстку исходника сохранять, менять только значения.** Бланк пользователя — эталон: «странные» отступы, спейсинг, пустые параграфы могут быть осознанной подгонкой под страницу. «Наведение порядка» = интерпретация = запрещено. Единственное согласованное исключение — форм-строки с линиями (шаг 4).

## Шаг 0 — вход и значения

Определи тип входа:

- **Заполненный пример** (лучший вход): работа сводится к замене конкретных значений на плейсхолдеры, ноль интерпретации. Бонус — эталонный тест: «собери с теми же значениями → рендер должен совпасть с оригиналом».
- **Чистый бланк**: рабочий, но требует интерпретации (пустые линии, подсказки «(Ф.И.О. полностью)»). Эталона «как должно быть» нет — порог эскалации к пользователю ниже. Если у вуза есть официальный заполненный пример — найди/запроси его.
- **Пример + бланк вместе**: вёрстку бери с примера, формулировки шапки сверь с бланком (в примерах встречаются устаревшие шапки, например «высшего профессионального образования» вместо актуального «высшего образования»). Специально бланк не запрашивать.

Запроси у пользователя **реальные значения полей** (вуз, кафедра, группа, ФИО и т.д.) — они всё равно нужны для YAML, а здесь станут базой тест-матрицы.

## Шаг 1 — заготовка

Скопируй исходник в `templates/title_pages/<vuz>_<tip>.docx` (латиницей: `spbgeu_course`, `guap_lab`). Если в файле несколько страниц (пример + бланк) — оставь одну титульную страницу, лишние параграфы удали.

Работа дальше идёт на уровне XML внутри docx (zipfile → `word/document.xml`, `word/styles.xml` → записать обратно). Средство — небольшие python-скрипты; python-docx для правки не использовать (он ресериализует весь XML), только точечные замены строк/регэкспы.

## Шаг 2 — плейсхолдеры

Замени значения на плейсхолдеры `{{FIELD}}`. Механика подстановки генерическая: любой YAML-ключ отчёта доступен шаблону как `{{KEY}}` и `{{KEY_UPPER}}` (капсом). **Регистр решает шаблон**: если на титуле значение капсом — ставь `{{KEY_UPPER}}`, код ничего не капсит сам.

Правила:

- Используй существующие имена полей, где подходят: `discipline`, `lab_number`, `lab_title`, `topic`, `group`, `student_name`, `teacher_name`, `teacher_title`, `department`, `faculty`, `programme`, `specialization`, `year`. Новые поля — только если сущности действительно нет.
- **Плейсхолдер — одним run'ом.** Не допускай разрыва `{{FIELD}}` на несколько runs.
- Замена — **по спану runs**: найди runs, целиком покрывающие значение, замени их одним run'ом с форматированием первого; соседние runs (label, двоеточия, линии) не трогай.
- Значение может быть разбито по runs неочевидно (например, `20__` как `20` + `__`) — ищи по склеенному тексту параграфа, а замену делай по спану.
- В таблицах (титульники с полями в ячейках) — тот же механизм, плейсхолдеры внутри `<w:tc>` работают.

## Шаг 3 — XML-линтер (обязателен всегда)

Детерминированная проверка на известные анти-паттерны — **до всякого рендера**. Прогони по document.xml и styles.xml:

| Анти-паттерн | Как выглядит в XML | Рецепт |
|---|---|---|
| Белые филлеры | run с `<w:color w:val="FFFFFF"/>` | Часть механизма форм-строк → шаг 4 |
| Форм-строки на подогнанных пробелах | подчёркнутые runs из пробелов (`w:u` + текст из пробелов) | Пересобрать на подчёркнутые табы → шаг 4 |
| Псевдоцентрирование | ведущие пробелы в начале текста параграфа | Статичный текст — оставить как есть. Строку с плейсхолдером — проверить в тест-матрице; если длинные значения ломают центрирование — заменить настоящим `jc="center"` (сохранение замысла) |
| Страница добита пустыми абзацами | пачка пустых параграфов перед нижним блоком (город/год) | При длинных значениях (тема/должность в 2 строки) нижний блок выталкивается на вторую страницу. Рецепт: нижний блок — во frame (`framePr`), прижатый к нижнему полю; наполнители удалить; в конце титула явный page break |
| Нет page break в конце | нет `<w:br w:type="page"/>` в последнем параграфе | Добавить, **если** титул короче страницы. Если вёрстка заполняет страницу целиком (спейсингом) — break не нужен и вреден (даст пустую страницу) |
| Конфликт имён стилей | `w:name` стиля совпадает с именем стиля тела (`Normal`, `Heading 1`, …) | Всем именам стилей шаблона — префикс `Title ` (`Normal` → `Title Normal`). Ссылки в документе идут по styleId — не ломаются. В русском Word styleId краткие (`a`, `a0`), человекочитаемо только name |
| Конфликт styleId с reference.docx | styleId шаблона совпадает с id стиля из `templates/reference.docx` (сверять динамически, не по списку) | Переименовать id (префикс `T`: `1` → `T1`) и обновить **все** ссылки: `w:styleId`, `basedOn`, `next`, `link` в styles.xml; `pStyle`, `rStyle`, `tblStyle` в document.xml. Иначе transplant при сборке заменит определение по id и сломает титульник |
| outlineLvl в стилях/параграфах | `<w:outlineLvl>` | Вычистить — иначе текст титульника (тема на heading-стиле бланка) попадёт в автособираемое СОДЕРЖАНИЕ |
| Параграфы на ГОСТ-стилях | pStyle титульных параграфов = стили тела | Титульные параграфы живут на своих родных стилях. Сажать на `Normal`/ГОСТ-стили нельзя: ГОСТ-Normal с полуторным интервалом растянет титул на две страницы |

Логотипы-картинки не трогать — переносятся как есть.

## Шаг 4 — форм-строки с линиями

Типовой хак исходников: линия «label ________» сделана подчёркнутыми пробелами, подогнанными под длину конкретного значения, плюс **белый символ-филлер** в конце (белая буква нужна, чтобы Word рисовал подчёркивание хвостовых пробелов). С другими значениями это ломается: строка переполняется (перенос → фантомная пустая строка с одиноким филлером) или линия не дотягивает до края.

Заменяй на схему **«ведущие пробелы + правый таб»**:

- label без подчёркивания → позиция значения задаётся **ведущими подчёркнутыми пробелами из оригинала** (в одном run'е с плейсхолдером) → подчёркнутое значение (`{{FIELD}}` с `w:u`) → подчёркнутый таб до **единственного right tab stop** у правого края контента (позицию снять с оригинала);
- **левый tab stop для позиции значения не ставить**: если значение переносится на вторую строку, хвостовой таб продолжения застревает на левом стопе и линия не дотягивает до края (проверено эмпирически);
- многоколоночные строки без переносов («Группа … Подпись») — можно на полной схеме табов с несколькими стопами;
- **центрированную форм-строку** (например «Тема:» по центру с подчёркиванием) на табы не пересобирать — сохранить вёрстку оригинала, удалить только белый филлер;
- подчёркивание таба Word растягивает сам при любой длине значения; белые филлеры удалить.

Это сохранение **замысла** вёрстки (линия от label до края, значение на линии), а не байтов — единственное разрешённое отступление от главного принципа.

## Шаг 5 — тест-матрица

Собери тестовые отчёты через `scripts/build.py` (минимальный md с YAML `title_page: <имя шаблона>`):

1. **База** — реальные значения пользователя (для заполненного примера — значения из него: рендер обязан совпасть с оригиналом).
2. **Стресс-длины** — только по полям, где перенос реалистичен: должность/степень/звание, тема, кафедра/факультет, направленность — да; ФИО — длинное, но однострочное; группа/номер/год — только короткие. Нереальные значения не выдумывать.

## Шаг 6 — визуальная приёмка

Каждую сборку отрендери и осмотри сам (если умеешь смотреть изображения):

```bash
soffice --headless --convert-to pdf <file>.docx
pdftoppm -png -r 100 <file>.pdf page
```

Чек-лист осмотра:
- титульник ровно одна страница, тело начинается со следующей;
- нет фантомных строк-обмылков (пустая строка с коротким подчёркиванием);
- линии форм доходят до правого края, значения стоят на линиях;
- значения на своих позициях, ничего не съехало и не переносится там, где не должно;
- тело merged-документа не потеряло ГОСТ-стили (шрифт, отступы, заголовки);
- для заполненного примера — сравнение с рендером оригинала бок о бок: расхождения только намеренные.

Если осматривать изображения нечем — шаг пропусти; тогда человеческая приёмка (шаг 7) обязательна с расширенным чек-листом.

## Шаг 7 — приёмка пользователем (обязательна всегда)

LibreOffice-рендер ≠ Word-рендер; финальная правда — Word пользователя. Отдай пользователю docx-файлы тест-матрицы и явный чек-лист «что смотреть» (из шага 6). После «ок» шаблон заморожен: на runtime отдельной проверки вёрстки нет, только обычная вычитка каждого собранного отчёта.

## Шаг 8 — регистрация

Добавь запись о шаблоне в реестр `templates/title_pages/registry.yaml`: id, вуз, тип работы, используемые поля, шаблонная специфика (формат — по существующим записям). Специфика конкретного вуза (кегли, формы) живёт **в реестре**, а не в общих правилах движка. Тело скилла (SKILL.md/PROFILES.md/WIZARD.md) при регистрации не меняется.
